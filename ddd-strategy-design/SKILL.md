# DDD 战略设计 — 业务需求技术方案

## 适用场景

- 启动新业务/新模块,需要做技术方案设计
- 收到 PRD/需求文档,要把"业务语言"翻译成"系统结构"
- 现有系统要微服务拆分或平台化重构,需要识别限界上下文
- 团队对业务概念有分歧,需要用统一语言对齐
- 评审已有技术方案,做 DDD 战略视角的差距分析(把已有方案当"需求"输入)

## 工作原则

1. **战略先行,战术次之** — 优先做边界划分(上下文/聚合),再谈实现细节
2. **语言驱动建模** — 代码和文档用同一套词;词不达意,边界一定划错
3. **关键决策点必须确认** — 限界上下文和上下文映射影响团队分工与部署单元,不能由模型自己拍板
4. **承认不确定** — 不确定的地方写进"开放问题",不要为了完整硬猜
5. **不发明新概念** — 严格用 DDD 通用术语(限界上下文/聚合/上下文映射),不混用其他方法论的词

## 流程总览

```
阶段 0 需求澄清
   ↓
阶段 1 统一语言表
   ↓
阶段 2 事件风暴
   ↓
阶段 3 子域分类
   ↓
阶段 4 限界上下文       ← 🛑 强制暂停确认
   ↓
阶段 5 上下文映射       ← 🛑 强制暂停确认
   ↓
阶段 6 聚合根草图
   ↓
阶段 7 输出技术方案文档
```

---

## 阶段 0 — 需求澄清

**目标**:确认需求文本够用,识别 3 件事 — 业务目标 / 关键参与者 / 范围边界。

**做法**:
1. 阅读用户给的需求(PRD/口头描述/已有方案)
2. 检查是否明显缺项;缺项时向用户提问,**一次最多 3 个问题,每个问题只问 1 个关键缺失**
3. 缺项举例:
   - "第一期上线的范围是什么?哪些明确不做?"
   - "有没有现有系统需要兼容/替换/数据迁移?"
   - "上下游依赖方是谁,集成方式有约束吗(REST/事件/文件)?"

不要在阶段 0 追求完美 — 70% 清晰就推进,剩余的不确定项写入"开放问题",在后续阶段补。

---

## 阶段 1 — 统一语言表(Ubiquitous Language)

**目标**:从需求中抽取业务概念,建立术语表。这是后续所有建模的基石 — 词不齐,后面全跑偏。

**做法**:
1. 找出所有**名词**(实体/角色/对象)和**关键动词**(行为/事件)
2. 排除技术词汇(数据库/接口/字段名/中间件)
3. 对每个术语给定义;识别同义词(领域方言)、反义词
4. 标记**歧义词**(同名不同义) — 后续可能要在歧义处切上下文
5. 标注每个术语的**作用范围**(还不知道上下文归属时,标"待定")

**输出格式** — 表格:
| 中文术语 | 英文术语 | 定义 | 作用范围 | 同义词/反义词 |

**暂停判断**:术语表 > 30 行 或 出现 ≥ 3 个明显歧义词 → 先给出当前术语表和歧义点,再停下与用户对齐。

---

## 阶段 2 — 事件风暴(Event Storming)

**目标**:把业务流程梳理成"事件 + 命令 + 参与者"的因果链。

**做法**:
1. 列**领域事件**(过去式,已成事实):`订单已创建` `支付已完成` `库存已扣减`
2. 为每个事件倒推**命令**(触发它的动作):`创建订单` `发起支付`
3. 为每个命令标出**触发方(Actor)**:用户/管理员/系统/外部服务/定时任务
4. 标出**反应式策略**:某事件触发另一命令 — `支付已完成 → [策略] → 通知商家发货`
5. 标出**关键时间窗口**:超时取消/有效期/审批时限
6. 标出**外部依赖**:第三方支付/物流查询/短信网关

**输出格式** — 时间线:
```
用户 ─创建订单─▶ 订单已创建 ─[策略]─▶ 库存预扣 ─▶ 库存已预扣
                                          │
                                          ▼
                                    用户 ─发起支付─▶ 支付已完成
```

或用表格(复杂时优先用表格):
| 序号 | 触发方 | 命令 | 领域事件 | 后续策略/事件 | 时间约束 |

**暂停判断**:事件链 > 20 步 或 出现明显分叉/合并 → 先给出当前主干流程和分叉点,再停下确认流程理解是否到位。

---

## 阶段 3 — 子域分类(Subdomain Classification)

**目标**:把第 2 步的事件按业务聚类,识别核心竞争力 vs 支撑/通用。

**做法**:
1. 把事件按"业务主题"聚类(订单/支付/库存/会员/营销/...)
2. 每个聚类判定子域类型:
   - **Core(核心域)** — 差异化竞争力,必须自研,投入最优秀的人
   - **Supporting(支撑域)** — 业务必需但非差异化,可自研或半自研
   - **Generic(通用域)** — 通用能力(发短信/支付通道/文件存储),优先用现成服务/三方
3. 给实现建议:自研 / 内部框架 / 三方 SaaS

**输出格式**:
| 子域 | 类型 | 关键事件 | 实现建议 | 备注 |

---

## 阶段 4 — 限界上下文(Bounded Context) 🛑 **强制确认**

**目标**:把上一步的子域拆成可独立部署/协作的上下文。**这是影响最大的决策**,必须人工拍板。

**做法 — 4 个切分信号**:
1. **语言断层** — 同一词在不同子域含义不同 → 在断层处切
   例:"订单"在销售上下文是"销售订单",在库存上下文是"待出库订单"
2. **团队边界** — 不同负责人/团队,即使语言没断层,也可能要拆
3. **变化频率差异** — 修改原因/节奏差异大的部分拆开
4. **事务边界参考** — 强一致性约束部分尽量同上下文

**不要这样切**:
- ❌ 按技术层切(Controller 层一个上下文、Service 层一个) — 这是分层,不是上下文
- ❌ 按数据表切(每张表一个上下文) — 表是实现细节
- ❌ 一切就拆 — 一个新人能 hold 住的业务不要硬拆

**输出格式**:
| 上下文 | 职责 | 包含的子域 | 关键事件 | 候选模块/服务名 |

**🛑 暂停**:向用户确认以下问题:
- "以上边界划分是否准确?有需要合并/拆分的地方吗?"
- 给出 2-4 个候选边界方案时,让用户选

---

## 阶段 5 — 上下文映射(Context Map) 🛑 **强制确认**

**目标**:为每对有交互的上下文定义**关系类型**,这是后续接口设计、防腐层、领域事件的总纲。

**关系类型速查**:

| 类型 | 含义 | 典型场景 |
| --- | --- | --- |
| **Partnership** | 两个上下文协同演进,接口同步改 | 两个团队紧耦合迭代 |
| **Shared Kernel** | 共用一小部分模型 | 双方都认的公共枚举/常量 |
| **Customer-Supplier** | 上游决定接口,下游被动接受 | 上游有 SLA,下游只能适应 |
| **Conformist** | 下游被迫接受上游模型 | 对接老系统/外部 API |
| **Anti-Corruption Layer(ACL)** | 下游用翻译层隔离上游脏数据 | 对接外部/遗留系统**首选** |
| **Open Host Service(OHS)** | 上游提供稳定 API 供多下游消费 | 平台型服务 |
| **Published Language** | 上下游共用一个标准格式 | JSON Schema / Protobuf / 事件 schema |
| **Separate Ways** | 没有实质集成,各自独立 | 几乎不需要对方 |

**输出格式** — ASCII 图 + 关系矩阵:
```
┌──────────────┐  ACL   ┌──────────────┐
│  老 ERP 系统  │ ◀────▶ │  新订单上下文  │
└──────────────┘        └──────────────┘
                             │ OHS + 事件
                             ▼
                      ┌──────────────┐
                      │  新支付上下文  │
                      └──────────────┘
```

| 上游 | 下游 | 关系类型 | 集成方式 | 备注 |

**🛑 暂停**:向用户确认:
- "以上关系类型是否符合实际?有没有需要从 Conformist 升级到 ACL 的?"
- "上游接口稳定性如何?是否需要 OHS?"

**典型反模式提醒**:
- ❌ 对接外部系统不做 ACL — 外部字段变更直接击穿到核心域
- ❌ 内部核心上下文长期裸用 Conformist — 自己可控的核心模型应该有翻译层或清晰的发布语言
- ❌ 滥用 Shared Kernel — 范围扩大就变成大泥球

---

## 阶段 6 — 聚合根草图(Aggregate Sketch)

**目标**:在每个上下文内识别聚合根,确定**事务边界**。此阶段是"草图"级别,不需要到字段/方法。

**做法**:
1. 在每个上下文内,把事件归到候选聚合(`订单已创建/已支付/已取消` → `Order` 聚合)
2. 检查**不变式(invariant)** — 哪些业务规则要跨实体保持一致?这些实体必须同聚合
   例:`Order.totalAmount = sum(OrderItem.amount)` → Order 和 OrderItem 同聚合
3. 找**聚合根** — 通常是生命周期最长、拥有其他实体的那个
4. 列**关键值对象**(无 ID 的对象):`Money` / `Address` / `DateRange`
5. 识别**跨聚合的领域事件** — 跨聚合用**最终一致性**,不要分布式事务

**输出格式**:
| 上下文 | 聚合根 | 包含的实体 | 关键值对象 | 关键不变式 | 跨聚合事件 |

**判断提示**:
- 聚合过大(超过 7-8 个实体)→ 考虑再切
- 一个用例要改 2 个聚合 → 通常用领域事件 + 幂等接收
- 跨聚合一致性诉求强 → 退一步看是不是该合并聚合

---

## 阶段 7 — 输出技术方案文档

把前 6 阶段产物组装成一份完整 markdown 文档。**模板**:

```markdown
# [需求名称] — 技术方案

> 基于 DDD 战略设计 · 生成时间 YYYY-MM-DD

## 1. 背景与目标
[2-3 句话:解决什么问题、为什么做、成功标准]

## 2. 业务参与者(Actors)
| 角色 | 描述 | 主要诉求 |

## 3. 统一语言表
[阶段 1 的表]

## 4. 领域事件流
[阶段 2 的时间线/表格]

## 5. 子域分类
[阶段 3 的表]

## 6. 限界上下文
[阶段 4 的表]

## 7. 上下文映射
[阶段 5 的 ASCII + 关系矩阵]

## 8. 聚合根草图
[阶段 6 的表]

## 9. 集成策略摘要
- 上下文间通信方式(同步 RPC / 异步事件)
- 防腐层(ACL)位置 — 列具体上下文
- 领域事件总线方案
- 跨聚合一致性方案(本地事务 / Saga / 事件 + 幂等)
- 数据所有权 — 每个聚合的数据归谁

## 10. 落地映射
- 候选模块/服务划分
- API 契约归属
- 数据表归属原则
- 需要新增/改造的接口、事件、定时任务
- 第一阶段 MVP 范围

## 11. 开放问题与风险
- [ ] 阶段暂停时未决的问题
- [ ] 假设与约束
- [ ] 后续要验证的边界情况
- [ ] 团队/排期风险

## 12. 下一步行动
- [ ] 拆分到任务/工单的建议
- [ ] 评审/对齐会议建议
- [ ] 第一个迭代的 MVP 范围

## 13. 附录:关键决策确认记录
- 阶段 4 限界上下文确认: [用户意见]
- 阶段 5 上下文映射确认: [用户意见]
```

## 输出物存放

**默认**:把方案文档以 markdown 块直接输出到对话,供用户复制/审阅。

**可选**:用户要求保存文件时,写到用户指定路径;未指定路径时先问,不要自行猜路径。

---

## 异常处理

- **需求过于模糊** — 阶段 0 问 1-3 个问题,不要超过 3 个;反复模糊时建议用户先补 PRD
- **需求明显是单模块小功能** — 保留 3-5 个核心事件即可,阶段 3-5 可合并,直接给"语言表 + 事件小表 + 上下文 + 1-2 个聚合",不强行展开完整事件风暴
- **需求是已有系统的差距分析** — 把现有方案文本作为"需求"输入,阶段 1 把"现状"也写进语言表,阶段 4 标"现状边界 vs 建议边界"
- **领域跨度过大** — 主动建议拆成多次设计(本次只做核心子域);不要一次做完
- **用户对 DDD 术语不熟** — 用业务语言解释关键概念,术语表里加一栏"通俗解释"
- **用户在阶段 4/5 想跳过确认** — 提醒一句"这两个决策改起来代价大,建议至少口头对一下"

---

## 项目适配

默认保持通用 DDD 输出,不要绑定特定代码库。若用户要求落到当前项目或某个仓库,在阶段 7 的"落地映射"中增加项目约束:

- 模块命名与依赖规则
- API / 实现模块的职责边界
- 跨模块调用方式
- 数据所有权与跨模块外键约束
- 需要同步更新的配置、权限、菜单、租户忽略项或消息订阅

---

## 风格提示(给执行者)

- 用中文输出(用户语言)
- 表格优先,少用大段文字
- ASCII 图用于上下文映射,简洁清晰即可
- 每个阶段结束给一句话总结,方便用户追上下文
- 阶段暂停时,先给方案再说"这里要不要确认一下",不要纯问
- 开放问题不要回避,直接写出来
