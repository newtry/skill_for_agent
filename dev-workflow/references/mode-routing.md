# 模式与门禁

## 1. 识别用户意图

优先看最新一句话，再看当前会话中尚未完成的阶段。不要用历史中的旧目标覆盖新指令。

| 信号 | 进入模式 | 默认输出 |
| --- | --- | --- |
| “分析/梳理/出方案/技术方案/报告/评审” | 方案 | 证据、决策、开放问题和落地步骤 |
| “实现/执行/改代码/开始做/修复” | 实现 | 修改代码并进入验证 |
| “测试/验证/再跑/手动触发/能用吗” | 验证 | 命令、结果、失败原因和残余风险 |
| “继续/接着做” | 继续 | 读取现场后继续最近未完成阶段 |
| “提交/推送/发布” | 交付 | 只执行明确指定的动作 |

“先给方案”“做完先不要推送”属于硬门禁，覆盖默认自动执行倾向。

## 2. 风险分级

### 低风险：可在一次授权中完成

- 单模块、局部业务逻辑或文案调整
- 有现成模式可复用的 DTO、Controller、Mapper、校验和测试
- 不改变数据结构、事务边界、权限、租户或外部契约

### 高风险：先方案，再确认关键决策

- 跨 `erp-*-biz` 模块或跨限界上下文
- 数据库迁移、批量导入、库存/金额、事务和并发
- 权限、租户隔离、认证、敏感配置或数据删除
- 外部 API、消息协议、定时任务和生产部署

高风险任务至少列出影响面、失败/回滚策略、幂等性和回归范围。用户明确要求执行后仍须遵守被调用专业 Skill 的强制确认点。

## 3. 阶段状态

在心里维护以下状态，不必每轮重复打印完整清单：

`context → requirements → design → test-plan → implementation → verification → handoff`

每次“继续”先判断当前状态和已有证据，再只推进一个合理阶段。遇到阻塞时保留上下文并说明下一步需要什么。
