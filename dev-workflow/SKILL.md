# 研发交付工作流

把用户的短指令转成可追踪的研发闭环：理解范围，设计方案，明确测试，修改代码，验证结果，最后按授权交付。保持现有工作区改动，不把“建议”误当成“执行”，不把“验证通过”误写成“业务完成”。

## 意图路由

根据用户最新一句话和当前会话状态选择最小模式；最新指令优先于历史计划。

| 模式 | 常见表达 | 行为 |
| --- | --- | --- |
| 方案 | 分析、方案、报告、梳理、评审、怎么设计 | 读取证据并输出方案，不修改代码 |
| 实现 | 实现、执行、开始做、按这个改、修复 | 先完成必要的设计和测试条件，再修改代码 |
| 验证 | 测试、验证、再跑、手动触发、现在能用吗 | 针对当前改动运行检查，报告实际结果 |
| 继续 | 继续、接着做、未完成的继续 | 从现有工作区和上一阶段结果恢复，不重新发明范围 |
| 交付 | 提交、推送、发布 | 仅在明确授权后执行对应 Git/发布动作 |

当一句话同时包含多个意图时按“方案 → 实现 → 验证”执行；没有明确写“提交/推送/发布”时，停在交付前检查。

## 阶段 0：建立上下文

1. 定位当前工作目录和最近的用户目标。若目录不清楚，先询问或根据当前 IDE 路径判断，不要扫描无关的大目录。
2. 从当前目录向上查找适用的 `AGENTS.md`。若它是指向 `CLAUDE.md` 的软链接，只读取一次。工作区根部存在 `AI-DEV-WORKFLOW.md` 时也读取它，了解会话恢复和共享记忆边界。
3. 检查 `git status --short`、相关 diff、模块 `pom.xml`、附近实现和附近测试。把用户已有的未提交改动视为输入，绝不覆盖或回滚。
4. 对异常先搜索调用链、配置、数据模型和测试，再下根因结论。优先使用 `rg`，只读取与需求有关的文件。

## 阶段 1：需求与方案

### 新功能或跨模块变更

- 将需求拆成业务目标、角色与场景、功能规则、状态/异常流程、非功能约束和验收条件。
- 需要业务边界、模块拆分、上下文映射或聚合边界时，使用 `$ddd-strategy-design`；遵守其在限界上下文和上下文映射阶段的确认点。
- 需要测试设计时，使用 `$derive-test-cases`，让每条用例追溯到需求、设计、风险或回归原因。
- 把不确定内容列为开放问题，不用猜测填满方案。需求缺项时最多一次询问 3 个关键问题；可推进的部分先标注假设。
- 小型单模块改动可采用轻量方案；不要为了形式强行展开完整事件风暴。

### Bug、日志或数据问题

- 先还原触发条件、调用链、状态变化和数据影响，再区分根因、诱因与环境噪声。
- 方案至少说明复现方式、修复策略、幂等/事务/并发影响和回归范围。
- 批量导入、事务、库存、金额、权限、租户隔离、数据库迁移和跨模块一致性属于高风险变更，先给方案并保留明确确认点。

按需读取：

- [方案检查表](references/solution-checklist.md)
- [模式和门禁细则](references/mode-routing.md)

## 阶段 2：实现

只有进入“实现”模式后才编辑文件。遵循以下顺序：

1. 复用当前项目的包结构、命名、DTO/DO、Mapper、转换器、异常码、权限和事务模式；先找同类实现，不凭空创建抽象。
2. 遵守项目的 API/Biz 分层、Admin/App 入口和模块依赖边界；跨模块调用通过对应 `*-api`，不要直接引用兄弟模块的 Biz Service 或 Controller。
3. 将验证条件落实为测试或可执行检查；关键规则先补测试，无法补测试时说明替代验证方法。
4. 使用 `apply_patch` 做手工编辑，保持 diff 聚焦；不要顺手重排无关代码、修改凭据或清理用户文件。
5. 修改配置、SQL、迁移或接口时，检查租户、权限、逻辑删除、兼容性、数据所有权和回滚路径。

按需读取 [实现检查表](references/implementation-checklist.md)。

## 阶段 3：验证

按风险从窄到宽执行，并记录实际命令与输出：

1. 先运行受影响模块的单元测试或指定测试类。
2. 再运行模块构建/编译；跨模块变更使用 `-pl <module> -am`。
3. 对接口、数据库、消息、权限或租户变更，增加相应集成/回归检查。
4. 检查测试是否真的执行、是否被跳过、是否因外部服务或环境失败；环境失败不能标记为代码通过。
5. 最后复查 `git diff`、敏感文件、生成文件和工作区边界。

可用脚本执行聚焦 Maven 验证：

```bash
scripts/verify_maven_change.sh --project /path/to/maven-root --module erp-server
scripts/verify_maven_change.sh --project /path/to/maven-root --module erp-wms-order/erp-wms-order-biz --test StockTakingOrderServiceTest
```

脚本默认只测试，不提交、不推送；详见 [验证矩阵](references/verification-matrix.md)。

## 阶段 4：交付

交付前用简洁结果说明：

- 完成了什么，涉及哪些文件或模块
- 方案、代码和测试分别处于什么状态
- 执行了哪些验证，结果是什么
- 哪些问题仍未验证、被环境阻塞或属于开放决策
- 工作区是否还有用户原有改动

只有用户明确要求时才执行 `git add/commit/push`、远程拉取、发布、删除或清理。提交前检查敏感配置未被纳入；除非用户明确指定，不修改历史提交者信息或强制让本地与远程一致。

需要保存独立文档时，使用 [技术方案模板](assets/technical-solution-template.md)；需要保存交付记录时，使用 [交付摘要模板](assets/delivery-summary-template.md)。用户未要求保存时，优先在对话中输出关键结果。

## 连续会话规则

- “继续”表示继续当前未完成阶段；先读取现有 diff、最近测试结果和上一轮遗留项。
- 新需求覆盖旧需求时，以新需求为准，并说明被放弃或保留的旧工作。
- 不重复输出已经确认的背景；只报告新增决策、改动、验证和阻塞点。
- 短指令缺少对象时，从当前会话唯一未完成目标推断；存在多个候选时先列出候选并询问，不要盲改。

## 完成标准

将任务标记为完成前，确认：需求范围已明确，代码改动符合项目边界，关键验收条件有测试或明确替代验证，测试结果真实可复现，diff 没有越界，交付动作没有超出授权。任一项不满足时，明确标记为“未完成/待确认/环境阻塞”。
