# AI 自动完成任务后，为什么仍然需要“待评审”状态

> 系列导航：[完整目录](00-series-titles.md)

如果 AI 能读任务、改代码、跑测试，最容易产生的想法是：测试通过就把任务直接关掉。我的实践恰好证明，“待评审”不能省略。

AI 可以验证代码是否符合它理解的规则，却不能独立确认业务口径、风险接受、改动范围和发布时机。任务完成和任务可交付，是两个不同状态。

## 核心判断：待评审是责任移交门禁，不是重复检查

AI 完成实现后，交付的是一组代码、验证结果和未决风险；评审人决定这些证据是否足以承担业务和发布责任。待评审状态把“执行已经结束”和“结果已经被接受”明确分开，避免系统把自动化成功误写成团队已经验收。

## 一次“测试通过”的任务为什么被退回

一个查询任务完成后，AI 回写了代码和通过的单元测试。评审时把验收条件与测试数据对照，发现样本只有一个账套，无法证明跨账套隔离；继续检查缓存键，又发现账套维度没有进入缓存。接口在当前样本中返回正确，换一组数据就可能串账。

任务因此从待评审退回处理中，补充跨账套对照样本、缓存断言和接口级权限验证后才再次提交。待评审不是重新写代码，而是用业务风险检查 AI 提供的证据是否足够。

这次退回也说明，评审对象不是 AI 的表达质量，而是需求、实现和证据之间是否闭合。AI 的总结即使没有事实错误，只要关键验收条件没有可复核证据，就不能进入可交付状态。

## 自动完成报告不等于验收

AI 回写的完成报告应包含改动文件、实现摘要、测试命令、实际结果、未验证项和风险。评审人要检查这些证据是否覆盖验收条件，不能只看状态从处理中变成完成。

例如测试覆盖了正常扣分，却没有覆盖积分释放；编译通过了，却新增了不允许的跨模块依赖；接口返回正确，却漏了账套过滤。状态自动关闭会把这些问题变成后置事故。

一份可评审的证据包至少包括：

| 内容 | 需要回答的问题 |
| --- | --- |
| 任务与验收 | 本次承诺了什么，哪些不在范围内 |
| 变更摘要 | 修改了哪些模块、契约和数据路径 |
| 实际 diff | 是否混入无关改动或覆盖用户现场 |
| 验证记录 | 执行了什么命令，结果对应哪个代码版本 |
| 风险与未验证项 | 哪些场景尚未证明，原因是什么 |
| 外部副作用 | 是否访问共享数据库、对象存储或外部服务 |
| 回退与接管 | 评审退回后从哪里继续，谁负责下一步 |

“所有测试通过”仍然不够。评审人要知道跑了哪些测试、哪些没有跑、样本是否具备辨识力，以及测试发生后代码是否又被修改。

## 待评审是风险边界

在待评审状态，AI 可以继续提供证据和回答问题，但不应自行发布、合并高风险变更或关闭任务。评审人确认范围、业务结果、测试和敏感信息后，任务才能进入可交付状态。

```text
处理中 -> AI 完成实现与验证 -> 待评审
                              | 通过 -> 可交付/关闭
                              | 退回 -> 补充实现或测试
                              | 阻塞 -> 人工处理
```

状态转换也需要结构化原因。通过要记录接受人和证据版本；退回要指出缺失的验收或风险证据；阻塞要说明外部条件和接管人。不能只把状态改回“处理中”，否则下一轮 AI 不知道应该修代码、补测试还是等待业务决策。

对于低风险任务，可以由规则预审并简化人工操作；但生产写入、支付、权限、迁移和数据清理等高影响任务仍需明确授权。自动化程度可以按风险变化，责任记录不能消失。

## 评审不应重新做一遍所有工作

有了结构化报告，评审人重点看高风险项：业务规则、数据边界、权限、事务、兼容性和未验证内容。AI 负责提供导航，工程师负责做最后判断。

评审可以采用风险驱动抽样：先核对验收追溯和高风险 diff，再复跑关键测试，最后检查未验证项和外部副作用。若证据链完整，不必逐行重演 AI 的分析；若任务报告与实际 diff 不一致，则应立即退回，因为后续结论已经失去基线。

## 我使用三类评审结论

| 结论 | 适用条件 | 后续状态 |
| --- | --- | --- |
| 接受 | 验收有证据，风险在授权范围内，版本一致 | 可交付或进入发布流程 |
| 退回 | 实现、测试、范围或报告存在可修复缺口 | 回到处理中并指定补充项 |
| 接管 | 需要业务决策、生产权限或重大方案调整 | 转人工处理，AI 保留只读支持 |

评审意见需要指向验收条目或风险，不写“再完善一下”这种无法执行的结论。例如“AC-3 缺少跨账套碰撞样本，缓存键未证明包含 `ledgerId`”，下一轮执行器就能直接补齐证据。

## 评审本身也要可度量

我会记录任务被退回的原因：需求理解偏差、实现缺口、测试不足、范围扩张、环境副作用或报告不实。重复出现的原因应反向更新任务模板、项目规则、测试基线或自动检查。

AI 可以整理证据包、建立验收追溯并回答评审问题；评审人负责业务口径、风险接受和最终授权。待评审完成的证据，是某个明确版本被接受或带着具体原因退回，而不是评论区出现一句“看过了”。

```text
请评审【任务运行】的交付证据：

1. 对照目标、范围和每条验收条件检查实现与测试；
2. 核对报告、实际 diff、代码版本和测试版本是否一致；
3. 重点检查业务边界、权限、事务、兼容和外部副作用；
4. 列出未验证项及其影响，不把环境阻塞标为通过；
5. 输出“接受、退回或接管”，并为每项结论提供依据和下一步。
```

保留待评审状态并不是不信任 AI，而是承认交付结果包含业务责任。自动化可以缩短实现时间，但不能消除审查和授权。

任务完成评审后，单次自动化闭环已经成立。但长任务经常跨越上下文限制、工作日和模型切换。下一篇将处理同一任务怎样在新会话中恢复到正确现场，而不是依赖聊天记忆重新开始。
