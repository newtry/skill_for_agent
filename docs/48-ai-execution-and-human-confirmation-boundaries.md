# 如何划分 AI 的自动执行边界与人工确认边界

> 系列导航：[完整目录](00-series-titles.md)

“哪些事情可以让 AI 自动做”没有一个适用于所有团队的固定答案。真正的边界要看动作是否可逆、影响是否局部、数据是否敏感、业务责任是否明确，以及失败后能否恢复。

## 核心判断：自动化边界是运行时策略，不是一张静态名单

同一个动作会因目标资源、数据范围、任务阶段和授权状态而改变风险。边界必须在每次执行前根据动作、环境、影响和恢复能力重新计算，并由工具和工作流强制执行。提示词里的“谨慎操作”既不能证明获得授权，也不能阻止越权调用。

## 我用四个问题判断风险

第一，动作能否撤销，回滚是否真实可用？第二，影响是一个文件、一个测试环境，还是多个租户和生产数据？第三，是否涉及金额、权限、隐私或外部承诺？第四，执行后是否能立即观察和校验？

只读扫描、日志整理、测试运行和文档生成通常可以自动化；代码局部修改需要 diff 检查；数据库写入、支付退款、权限变更、发布和删除则需要人工确认。

四个问题最终要落成动作矩阵，而不是一句“高风险需谨慎”：

| 动作 | 默认权限 | 升级条件 |
| --- | --- | --- |
| 搜索代码、读取日志和元数据 | 自动执行 | 触达敏感数据时脱敏 |
| 修改局部代码和测试 | 允许执行，必须复查 diff | 跨模块或改变契约时先确认方案 |
| 生成 DDL、修复 SQL 和发布计划 | 只生成，不执行 | 明确环境、备份、窗口和授权 |
| 支付、退款、权限、生产数据和发布 | 默认禁止 | 指定执行人、范围及回滚后受控执行 |

我还会增加两个维度：动作是否会产生外部承诺，以及授权是否可以绑定到不可变参数。发送客户消息、创建正式订单或触发第三方接口，即使本地数据容易回滚，也已经产生外部影响；一句“可以执行”如果没有绑定环境、对象和有效期，也可能被错误复用。

## 从风险分类到能力令牌

确认不应只存在于聊天文本。高风险动作获得批准后，系统可以签发一次性能力令牌，绑定：

```text
操作者与审批人
允许动作和目标环境
业务对象与数据范围
参数摘要或预览哈希
有效时间和最大执行次数
幂等键与审计编号
```

工具执行前校验令牌，参数或环境变化后令牌失效。这样用户批准“在测试库创建索引”，不能被解释为允许在生产库执行；批准一笔退款预览，也不能被模型改写金额后继续使用。

## 边界要写成状态和动作

不要只写“高风险操作要谨慎”，而要明确：分析可以自动做，脚本可以生成，执行需要谁确认，确认后在哪个环境做，执行后检查什么，失败怎样回滚。

```text
自动分析 -> 生成计划 -> 人工确认 -> 受控执行 -> 结果验证 -> 评审/回滚
```

更完整的状态机还需要拒绝、过期和接管：

```text
ANALYZING -> PREPARED -> WAITING_CONFIRMATION -> AUTHORIZED
-> EXECUTING -> VERIFYING -> ACCEPTED
       |              |          |
       v              v          v
    REJECTED       EXPIRED     FAILED -> ROLLBACK/HANDOFF
```

每次状态转换都有前置条件。生成脚本不等于允许执行，工具返回成功不等于业务结果被接受，验证失败也不能自动重复高风险动作。

## 共享开发环境也不是默认沙箱

一次数据约束改造中，AI 可以正确生成唯一索引和历史数据清理脚本，但目标是多人共用的开发数据库。若立即执行，尚未升级的其他分支会因为旧写入方式失败，所谓“开发环境操作”同样会影响团队。

因此环境名称不能代替影响判断。AI 可以在共享库执行只读扫描、生成重复数据报告和幂等修复 SQL；添加强约束、清理数据和回滚仍要确认使用方、执行窗口与恢复路径。只有独立、可重建且没有其他使用者的测试资源，才适合扩大自动执行范围。

同样的边界也适用于测试：如果测试继承真实对象存储或消息配置，即使运行在本机，也已经越过了本地范围。判断权限时要看动作实际触达的资源，而不是命令从哪台机器发出。

## 一次共享库约束为什么不能直接执行

在数据约束改造中，AI 已经发现重复数据并生成唯一索引。技术方案本身正确，但共享开发库中仍有旧分支按原方式写入。如果立即加约束，其他成员的开发会突然失败；如果先清理重复数据，又可能破坏他们正在使用的样本。

正确流程是先只读统计影响、识别生产与消费方、生成幂等迁移和回滚脚本，再由负责人确定升级顺序和窗口。执行后检查约束、旧写入、数据差异和团队阻塞。风险不是 SQL 语法，而是共享资源上的时序和责任。

## 自动确认也要有边界

低风险、规则明确的动作可以使用策略自动批准，例如隔离工作树内的格式化和局部测试。但自动批准策略本身要版本化，并设置范围、频率和异常停止条件。模型不能自己声明当前任务“风险较低”后获得更高权限。

人工确认也不是万能防线。若预览不展示实际参数、影响范围和回滚方式，人只能盲目点击。因此 AI 的重要职责是把确认前材料准备到可判断，而不是只弹出一个“是否继续”。

## 边界也可以逐步调整

低风险动作积累了稳定证据后，可以扩大自动化；一旦出现越权、数据错误或不可回滚事故，就应缩小权限并补门禁。自动化边界不是一次配置，而是根据失败记录持续校准的工程策略。

最成熟的做法不是让 AI 什么都能做，而是让它在清楚知道不能做什么的情况下，把能做的部分做到足够完整。

调整边界时，我会同时看成功率、阻断命中、错误逃逸、恢复时长和人工确认质量。稳定自动化可以扩大范围，但任何未授权副作用都应触发收缩和事故复盘。模型升级本身不是扩大权限的证据。

AI 可以评估动作影响、生成预览、准备脚本和执行授权后的受控步骤；策略服务负责运行时校验；人负责业务规则、风险接受与高影响授权。执行边界完成的证据，是一次动作能够说明为什么被允许、使用了什么授权、改变了什么状态、怎样验证和恢复。

```text
请为【动作】设计自动执行与人工确认边界：

1. 评估可逆性、影响范围、敏感性、外部承诺、可观察性和恢复能力；
2. 按分析、准备、确认、执行、验证和接受拆分权限；
3. 定义授权令牌绑定的环境、对象、参数、有效期和幂等键；
4. 设计拒绝、过期、失败、回滚和人工接管状态；
5. 用真实失败与运行指标说明边界怎样扩大或收缩。
```
