# 批量导入为什么最能检验 AI 的工程能力

> 系列导航：[完整目录](00-series-titles.md)

“把 Excel 里的商品批量导入系统”，第一版实现通常很快：读取一行，校验字段，转换对象，然后保存。

真正的问题会在失败时出现。一次导入中，部分行校验失败，代码捕获异常后继续处理，最终报告显示其余记录成功；但外层事务早已被标记为只能回滚，方法结束后整个批次没有任何数据提交。另一种实现把每行独立提交，主表写入成功，关联库存和业务流水却在后续异常中缺失。用户再次上传同一文件后，系统又产生重复数据。

这些问题都不在“读取 Excel”的循环里，而在事务、幂等、状态、资源和结果报告之间的关系里。

批量导入因此特别能检验 AI 是否具备工程能力：它能否从正常路径继续推演失败、重试、中断和恢复，并最终说明系统里到底留下了什么。

## Excel 文件只是输入载体，导入协议才是系统边界

开始编码前，首先要定义一批数据在业务上的含义。商品、客户、库存和组合资料的导入，即使都使用 Excel，事务和重复处理策略也可能完全不同。

一份完整导入协议至少包含：

| 协议部分 | 需要确认的问题 |
| --- | --- |
| 行粒度 | 一行代表一个实体、一个变体还是一组关系 |
| 身份与范围 | 数据属于哪个租户、账套、门店和操作人 |
| 字段规则 | 必填、格式、单位、枚举和默认值怎样解释 |
| 业务键 | 什么字段识别同一对象，是否允许更新 |
| 关联规则 | 依赖对象不存在、多条匹配或无权限时怎样处理 |
| 批次语义 | 整批原子成功，还是允许部分成功 |
| 重复语义 | 同一文件或业务键再次提交时拒绝、跳过还是更新 |
| 结果契约 | 用户怎样获得成功、失败、警告和可重试信息 |

如果这些问题没有在任务阶段确定，AI 只能从相似代码推测。它可能写出技术上完整的导入器，却选择了错误的业务语义。

## 导入不是循环，而是一条分阶段工作流

我现在会把批量导入拆成七个阶段：

```text
接收文件 -> 解析与标准化 -> 结构校验 -> 业务校验
-> 制定写入计划 -> 执行与记录 -> 汇总与对账
```

接收阶段确认文件、模板版本、租户和操作者；解析阶段只负责把外部格式转换成内部标准值；结构校验检查必填、类型和长度；业务校验再查询唯一键、权限和关联对象。

只有校验策略明确后，系统才制定写入计划：哪些新增、哪些更新、哪些跳过、哪些失败。执行阶段按照事务策略写入主表、关联表和流水，最后通过汇总与对账证明报告数字与数据库状态一致。

分阶段设计有两个价值。第一，错误能够定位到输入、规则还是写入阶段；第二，验证和恢复可以围绕明确状态进行，而不是只能重新运行整个循环。

## 事务策略必须与批次语义一致

批量导入最先需要确认的是原子性，也就是失败时保留多少成功结果。

| 事务策略 | 适用条件 | 必须承担的代价 |
| --- | --- | --- |
| 整批事务 | 财务、库存等要求整批一致 | 任一错误导致全部回滚，大文件事务时间长 |
| 行级事务 | 各行完全独立且允许部分成功 | 提交次数多，跨行一致性较难维护 |
| 分块事务 | 大文件允许按批次提交 | 需要检查点、分块结果和恢复策略 |
| 校验后统一写入 | 可先完整发现错误再决定提交 | 校验与写入间的数据变化需要处理 |

最危险的实现，是业务上想要部分成功，代码上却使用一个外层大事务，并在内部捕获异常继续执行。某些数据库异常发生后，事务已经进入只能回滚状态；成功计数继续增加，不代表数据最终能够提交。

因此，AI 不能只标注 `@Transactional` 在哪里，还要画出事务边界、异常传播和最终提交点，回答三件事：哪一组数据必须共同成功，失败由谁捕获，用户看到的成功数量何时才算确定。

## 幂等要覆盖请求、业务对象和副作用

批量导入天然会重复：用户双击上传、网络超时后重试、后台任务补偿、服务重启后恢复，都可能让同一批数据再次进入系统。前端禁用按钮不能提供幂等保证。

我会把幂等拆成三个层次：

| 幂等层次 | 识别方式 | 要防止的问题 |
| --- | --- | --- |
| 批次级 | 批次号、文件摘要、租户和模板版本 | 同一文件被完整重复处理 |
| 业务对象级 | 租户范围内的业务唯一键 | 同一商品或客户被重复创建 |
| 副作用级 | 业务流水号、事件号或操作记录 | 库存、积分、消息等效果重复发生 |

仅在导入前查询“是否存在”不够可靠。并发请求可能同时通过检查，仍然需要数据库唯一约束、原子写入或冲突处理。对于更新型导入，还要定义同一内容重复执行是否无变化，以及不同内容使用同一业务键时是覆盖、拒绝还是生成版本。

幂等验证也不能只看主表行数。主数据不重复，但库存被加了两次、流水多了一条，系统仍然不是幂等的。

## 部分成功需要显式状态和恢复点

当文件很大、任务异步执行或采用分块事务时，导入就不再是一次接口调用，而是一个有生命周期的任务。至少需要区分：

```text
已接收 -> 校验中 -> 待执行 -> 执行中
-> 全部成功 / 部分成功 / 失败 / 已取消
```

状态变化要与实际数据提交保持一致。任务显示成功之前，必须确认对应事务已经提交；任务失败后，要知道哪些分块完成、哪些尚未开始、哪些结果需要补偿。

检查点用于恢复，不应只是一个“处理到第几行”的数字。它还需要关联模板版本、排序方式、批次状态和已经产生的业务效果。否则文件内容或处理规则变化后，从旧行号继续可能写出另一组数据。

## 错误报告是导入协议的一部分

一份只返回“第 38 行失败”的报告，通常不足以让用户修复数据。专业的错误项至少应包括：原始行号、业务键、字段、错误代码、可理解原因，以及是否可以修改后重试。

错误还应区分层次：

- 文件级：模板错误、文件损坏、版本不支持；
- 行级：必填缺失、格式错误、枚举非法；
- 业务级：唯一键冲突、关联不存在、状态不允许；
- 权限级：跨租户、跨账套或无权操作；
- 系统级：数据库、缓存、外部服务或资源失败。

错误代码比自由文本更适合统计和重试策略，自由文本则负责让用户理解。对于部分成功，报告中的成功数、失败数和跳过数必须能与批次记录及数据库最终状态对账。

## 大文件还会暴露资源边界

小样本测试通过，不代表导入可以上线。把整个工作簿、所有校验结果和全部实体一次放进内存，可能在大文件下导致内存溢出；单个长事务可能占用连接、扩大锁范围并超过网关超时；逐行查询关联对象又会形成大量重复 SQL。

AI 在设计时还应分析：

- 是否需要流式读取和分块处理；
- 批大小如何影响内存、事务和数据库负载；
- 关联数据能否批量预取并在租户范围内缓存；
- 异步任务如何汇报进度、取消和超时；
- 原始文件、错误文件和日志保留多久，谁可以访问；
- 多实例同时处理时如何避免同一批次被重复领取。

性能不是导入完成后的优化项。处理方式一旦从整批改为分块，事务、幂等和恢复模型都会随之变化。

## 测试必须验证最终数据状态

接口返回“导入成功”只能证明响应路径结束，不能证明导入契约成立。我会先让 AI 生成一张覆盖矩阵：

| 测试类别 | 关键场景 | 核心断言 |
| --- | --- | --- |
| 正常路径 | 新增、更新、关联数据 | 主表、关联表、流水和汇总一致 |
| 输入错误 | 空值、格式、重复、非法模板 | 精确错误项，无意外写入 |
| 事务失败 | 行失败、分块失败、提交异常 | 回滚范围符合既定策略 |
| 重复执行 | 同文件、同业务键、并发上传 | 主数据和副作用均不重复 |
| 权限边界 | 跨租户、跨账套、无权限 | 数据不可见且不可写入 |
| 恢复场景 | 中断、重启、补偿和重试 | 从合法检查点继续，结果可对账 |
| 资源边界 | 大文件、慢依赖、超时 | 资源受控，状态和报告仍准确 |

每个测试都要核对数据库最终状态、批次状态和错误报告，而不是只断言接口状态码。如果测试环境无法覆盖真实数据库或异步任务，也要明确替代验证和残余风险。

## AI 的工程能力体现在失败之后

我现在会这样要求 AI 分析导入任务：

```text
请先只读分析【对象】批量导入，不要直接实现读取循环。

1. 定义行粒度、业务键、字段、关联、权限和结果协议；
2. 拆分接收、解析、校验、计划、执行和对账阶段；
3. 比较整批、行级和分块事务，并标出待确认业务语义；
4. 设计批次、业务对象和副作用三层幂等；
5. 说明任务状态、检查点、错误报告和失败恢复；
6. 覆盖正常、错误、重复、并发、越权、中断和大文件测试；
7. 给出最终数据对账方式、风险和最小实现范围。
```

AI 擅长快速展开异常组合、搜索现有事务模式、生成测试数据和检查多表结果。工程师必须决定批次原子性、覆盖规则和可接受的部分成功语义，并对最终数据负责。

批量导入检验的不是 AI 会不会处理 Excel，而是它能否把不完整输入、重复请求、部分失败和资源限制组织成一条可解释、可恢复、可验证的工作流。
