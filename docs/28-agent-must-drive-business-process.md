# 为什么业务 Agent 不能只会回答，还必须能够推动业务流程

很多业务 Agent 的演示都停在一句话：用户提问，模型给出一段回答。真正接进 ERP 后，用户通常还要继续复制订单号、打开菜单、填写参数、提交审批，再回来确认结果。

如果 Agent 只会解释，不会在边界清楚的情况下推动流程，它只是一个更方便的搜索框，没有真正减少业务工作。

## “查库存”与“处理缺货”是两类能力

用户问“这款还有多少库存”，Agent 可以通过受控查询返回数量、门店和账套口径。用户继续说“那就调拨到这家店”，这已经从读操作进入写操作，涉及库存所有权、审批、目标门店、数量和幂等。

两者不能共用一个自由发挥的流程。Agent 应先识别意图发生了变化，补齐必要参数，展示将要执行的动作和影响，确认用户有权限，再调用明确的业务接口。

## 业务动作需要一个明确的闭环

我会把 Agent 的动作拆成四步：理解请求、补齐参数、预览结果、执行并回报状态。预览不是多余的确认页面，它让用户知道 Agent 解释成了什么，也让系统在真正写入前有最后一次校正机会。

```text
自然语言请求
 -> 意图与权限判断
 -> 参数补全
 -> 业务预览/人工确认
 -> 受控工具执行
 -> 结果、流水和后续状态
```

对于查询，预览可能只是数据范围；对于调拨、退款、积分扣减等动作，必须展示对象、数量、金额、业务键和失败处理。

## 不能让模型直接替代业务状态机

Agent 可以理解用户语言，但业务状态仍应由后端工作流或领域服务维护。模型不能自行把“我想处理一下”翻译成已审批、已支付或已完成。每次状态变化都要通过有权限、可幂等、可审计的业务接口。

这也是为什么“给 Agent 一个万能执行工具”很危险：它绕过了原有的校验、状态和审批边界。

## 我会用这些场景验收

```text
查询请求：能否返回正确口径和数据范围？
动作请求：是否补齐参数、校验权限并展示预览？
重复请求：是否使用同一业务键而不重复执行？
失败请求：是否返回真实状态并支持人工或系统补偿？
模糊请求：是否停下来澄清，而不是擅自选择？
```

业务 Agent 的价值不在于替用户多说几句话，而在于把自然语言接到一个安全、可追踪的业务闭环上。回答是入口，流程推进和结果确认才是交付。
