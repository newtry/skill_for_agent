# AI 没有取代工程能力，反而提高了工程能力的门槛

> 系列导航：[完整目录](00-series-titles.md)

AI 让写出一段能运行的代码变得更容易，也让“代码能运行”越来越不能代表一项工程工作已经完成。

以前，错误实现往往受限于人的编码速度；现在，一条错误假设可以迅速变成接口、SQL、缓存、测试和文档，并被多个工具继续复制。实现成本下降了，判断错误的传播成本却上升了。

因此，AI 降低的是局部代码的生产门槛，提高的是系统持续正确的交付门槛。

## 一次库存查询里的两种“高效率”

同样面对“查询当前门店的可售库存”，我看到过两种完全不同的 AI 使用方式。

第一种方式很快。AI 找到相似 Mapper，增加账套参数，补了一条聚合 SQL 和几个单元测试。代码当天完成，测试全部通过。进入双账套数据后，问题才暴露出来：SQL 在入口接收了账套参数，中间汇总表却已经按 SKU 合并；缓存键也没有账套维度。接口运行正常，返回的却是另一个业务集合。

第二种方式开始得更慢。AI 先确认库存口径，写出一行结果的粒度，追踪查询、汇总表、缓存和前端消费链，再构造“同 SKU、不同账套”的碰撞数据。这个过程发现，修复不能停在最终 SQL，而要回到首次丢失账套维度的汇总层，并评估历史数据重算。

两种方式都使用了 AI，也都生成了代码和测试。区别不在提示词长短，而在完成标准：

| 判断对象 | 第一种方式 | 第二种方式 |
| --- | --- | --- |
| 需求 | 增加一个库存查询 | 回答特定账套、门店和时点下的可售库存 |
| 改动范围 | 当前接口和 SQL | 从事实产生到缓存消费的完整数据链 |
| 测试 | 单账套正常样本 | 跨账套碰撞、缓存和历史汇总样本 |
| 完成依据 | 代码生成且测试绿色 | 结果粒度、隔离边界和数据证据共同成立 |
| 后续成本 | 联调返工并重新处理历史数据 | 前期分析更多，交付后的不确定性更低 |

AI 提高工程门槛的含义就藏在这里：代码越容易产生，工程师越要在代码之外证明它回答了正确问题。

## 核心判断：生成门槛降低，系统正确性的门槛提高

AI 擅长生成局部实现，却不会自动获得当前项目的业务语义、组织责任和真实运行条件。模型可以迅速补全缺失部分，但被补全的可能恰好是团队尚未确认的规则。

工程能力的评价因此发生了迁移：

```text
能否写出实现
-> 能否定义正确问题
-> 能否保持系统边界
-> 能否治理执行风险
-> 能否设计交付证据
-> 能否让经验进入持续演进
```

后面的能力不是对编码的替代，而是决定快速生成的代码有没有资格进入真实系统。

## 第一层门槛：把需求定义成正确问题

自然语言需求往往省略对象、范围、状态和时间。“查库存”“算销售额”“任务完成了吗”都不是可以直接实现的业务契约。

工程师需要先回答：谁在什么范围内，基于哪些事实，希望得到什么结果；哪些口径已经确认，哪些仍需业务决定；本次交付明确不解决什么。

AI 可以整理术语、寻找相似实现和列出歧义，却不能从字段名决定库存口径，也不能替负责人选择退款、积分或经营指标规则。问题没有定义清楚时，更快的实现只会更快固化错误假设。

这一层的最低产物不是代码，而是目标、范围、非目标、业务对象、数据粒度、验收条件和开放问题。

## 第二层门槛：让边界贯穿完整系统

复杂系统中的正确性很少停留在一个方法里。租户与账套要贯穿查询、聚合和缓存；协议字段要贯穿生产方、消费者和前端；状态语义要贯穿接口受理、异步任务和最终结果。

AI 可以同时搜索大量文件，因此也更容易一次修改多个层次。但如果没有模块所有权、依赖方向、数据粒度和状态不变量，它会沿最短路径把局部语义复制到其他边界。

边界能力要求工程师能够回答：

```text
这项事实由谁产生和解释
一行数据究竟代表什么
哪些维度在任何层次都不能丢失
哪些状态允许读取、聚合或修改
跨模块和跨版本通过什么契约协作
```

这一层的完成证据，是边界在入口、工具、数据、缓存、输出和迁移过程中始终成立，而不是某个接口已经接收了正确参数。

## 第三层门槛：管理被放大的执行能力

当 AI 只能给建议时，主要风险是答案错误；当它能修改代码、运行测试、访问数据库、调用外部服务和认领任务时，风险变成真实副作用。

工程能力因此还包括权限设计：什么可以自动读取，什么可以在隔离环境写入，什么只能生成计划，什么必须由指定角色确认。确认要绑定环境、对象、参数、有效期和幂等键，不能依赖聊天里一句宽泛的“继续执行”。

同一条命令在不同环境中不是同一种风险：

| 动作 | 隔离资源 | 共享开发环境 | 生产或外部系统 |
| --- | --- | --- | --- |
| 读取结构与日志 | 可自动执行 | 按敏感范围受控 | 需要审计和最小权限 |
| 修改代码与测试 | 在限定工作树执行 | 避免覆盖他人现场 | 不直接影响生产 |
| 数据写入与 DDL | 可重建时受控执行 | 确认使用方和窗口 | 独立变更与回滚授权 |
| 消息、退款、发布 | 使用替身或模拟 | 默认不自动执行 | 明确禁止或高级门禁 |

这一层不是限制 AI 能力，而是让能力拥有清楚的作用范围、失败出口和接管路径。

## 第四层门槛：在实现前设计证据

代码生成速度提高后，验证不能继续作为最后一步补充。否则 AI 会按照最容易通过的测试反向定义完成，而不是按照业务风险提供证据。

工程师需要在实现前确定：每条承诺由什么机制保证，什么样本能够让错误实现失败，验证应发生在哪一层，结果对应哪个代码和环境版本。

```text
业务承诺 -> 系统机制 -> 风险样本 -> 验证命令
-> 实际结果 -> 未验证项 -> 接受或退回
```

单元测试适合局部逻辑，跨账套隔离需要碰撞数据，幂等需要并发和重试，协议迁移需要生产消费回放，发布需要监控、灰度和回退。测试数量不能替代风险覆盖，绿色结果也不能隐藏外部副作用。

这一层的完成标准，是其他人能够从证据包判断目标是否达成、哪些风险仍未关闭，而不是相信原会话的完成声明。

## 第五层门槛：让一次失败改变下一次交付

如果同一种错误在不同会话、工具和成员之间反复出现，说明经验仍然停留在个人记忆里。

成熟团队会把失败放到合适层次：稳定项目事实进入项目规则，当前状态进入任务板和检查点，重复方法进入 Skill，可自动判断的约束进入测试与脚本，高风险动作进入工具权限和人工门禁。

```text
失败发生
-> 还原触发条件与责任层
-> 选择规则、测试、工具或流程防线
-> 用原失败样本回归
-> 发布新版本
-> 观察防线是否真正提前拦截
```

学习能力也包括删除。旧协议、过期命令和无期限兼容会持续污染 AI 上下文；如果团队只会增加规则而不会退出旧链路，知识越多，模型获得的冲突信息也越多。

## 五层门槛是一条递进链，不是五张检查表

这五层存在明确依赖：问题定义决定要守住什么边界；系统边界决定哪些动作风险最高；执行治理决定可以产生什么证据；验证结果决定经验是否值得沉淀；知识演进又成为下一次任务的项目基线。

```text
问题定义
-> 系统边界
-> 执行治理
-> 证据验证
-> 学习演进
-> 更新后的问题定义
```

只加强其中一层会产生局部成熟。例如测试很多但业务问题定义错误，只会更稳定地验证错误口径；权限很严格但没有失败恢复，系统只会更安全地停住；知识库很丰富但没有淘汰机制，则会让不同版本规则同时生效。

## 个人能力与团队基础设施必须同时升级

更高门槛不能只压给某个工程师。个人需要理解业务、系统、数据和运行环境，团队也要提供让正确行为更容易发生的基础设施。

| 个人判断能力 | 团队基础设施 |
| --- | --- |
| 识别业务歧义和数据粒度 | 权威项目规则和任务契约 |
| 判断模块边界和失败策略 | 架构检查、受控工具和状态机 |
| 设计风险样本和验收证据 | 隔离测试环境、回放集和证据包 |
| 接管异常与评估剩余风险 | 评审门禁、审计、灰度和回退机制 |
| 提炼经验并识别过期规则 | 知识生命周期、Skill 和责任人 |

只有个人能力，没有团队系统，经验很难稳定复用；只有流程和工具，没有工程判断，新场景仍会落入错误规则。AI 辅助开发规模化依赖两者共同成熟。

## 更高门槛不等于所有任务使用更重流程

文档修正、局部重构和隔离环境测试，不需要复制支付或生产迁移的完整门禁。成熟度不表现为表单越来越多，而表现为团队能根据可逆性、影响范围、数据敏感度和恢复能力选择恰当强度。

高质量 AI 协作最终应该减少无价值流程：项目基线可复用后不必反复解释，自动检查稳定后不必人工重复，证据包完整后评审可以集中于业务和高风险差异。

门槛提高的是判断质量，不是固定步骤数量。

## 怎样判断工程门槛真的提高了

不能用代码量、AI 使用次数或自动关闭率证明工程能力。更有意义的是观察速度提高以后，系统是否仍然可控：

| 观察维度 | 需要看到的变化 |
| --- | --- |
| 任务定义 | 因目标和验收缺失导致的返工减少 |
| 边界正确性 | 跨模块、跨租户和数据口径缺陷更早暴露 |
| 执行治理 | 未授权动作和环境污染不随自动化增长 |
| 交付证据 | 未验证项透明，评审可以复现关键结果 |
| 学习演进 | 同类错误减少，旧规则和旧链路可以退出 |

如果交付周期缩短，但越权、返工、不可解释状态和缺陷逃逸同步增加，团队只是提高了产出速度，还没有提高工程能力。

```text
请评估【团队或项目】的 AI 工程能力：

1. 用一个真实任务检查问题定义、系统边界、执行治理、证据验证和学习演进；
2. 区分个人判断能力与团队提供的规则、工具、环境和门禁；
3. 检查每层产物能否成为下一层的可靠输入；
4. 比较速度提升前后的返工、越权、副作用、证据缺口和错误重现；
5. 找出当前最薄弱的一层，只增加与实际风险对应的改进。
```

## 阶段复盘之后，问题转向持续演进

前六辑建立了项目认知、真实交付、研发流程、业务 Agent、任务自动化和责任边界。这些方法解决了“一次任务怎样可靠完成”，但第一版系统交付后，新的问题会继续出现。

意图规则和模型怎样避免各自演化？任务停止执行后怎样判断用户目标真的达成？V2 链路上线后，旧协议怎样安全退出？多个 AI、测试资源和共享数据库怎样长期隔离？技术动作完成后，又怎样连接用户反馈和业务结果？

这些问题共同指向下一阶段：工程能力不仅要保证一次修改正确，还要让系统在持续变化中保持统一、可恢复、可退出并能证明价值。

未来优秀的工程师未必是写代码最快的人，而是能把 AI 纳入可靠的交付与演进系统，并持续证明这个系统仍在解决正确问题的人。
