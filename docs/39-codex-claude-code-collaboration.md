# Codex 和 Claude Code 如何协作，而不是互相覆盖

> 系列导航：[完整目录](00-series-titles.md)

同一个项目同时使用多个 AI 工具时，最大的风险不是模型能力不同，而是它们各自以为自己拥有完整上下文。一个工具刚改完文件，另一个工具如果没有读取工作区和任务状态，就可能重复实现、覆盖未提交改动，或者沿着不同的模块边界继续扩散。

我后来把多工具协作设计成角色交接，而不是同时抢同一个任务。

## 核心判断：多工具协作首先是写入所有权问题

不同模型可以同时分析同一个问题，但同一任务、同一文件和同一契约在一个阶段只能有一个明确写入者。协作质量不取决于工具数量，而取决于写入范围能否隔离、交接基线能否核验，以及冲突出现时是否知道谁应该停止。

## 一次重复实现是怎样发生的

一次协议改造中，第一个工具已经修改后端契约并留下未提交测试；第二个工具只读取旧设计文档，判断“后端尚未实现”，准备在相同文件中增加另一套兼容字段。它们的方案各自合理，却基于不同时间点的现场。

真正阻止覆盖的不是提示词，而是第二个工具开始前检查了 `git status` 和 diff。发现未知改动后，它切换为只读复核：先确认已有实现与设计差异，再把前端接线作为独立任务放入另一个工作树。共享契约由一个负责人修改，其他工具只通过提交和交接记录消费变化。

那次重复实现并不是模型能力不足，而是缺少三个事实：后端契约已经由谁负责、当前工作区相对哪个提交发生了变化、未提交测试属于谁。没有所有权和时间点，两个工具都会把自己的局部上下文当成完整现场。

## 先分工，再共享现场

一个工具可以负责探索代码、梳理调用链和提出方案，另一个负责实现、测试或复核。角色不是固定的，关键是一次只让一个工具拥有当前文件的写入责任，其他工具以只读分析或审查身份进入。

所有工具都应共享项目规则、任务说明、当前分支、工作区状态和交接记录。聊天历史不能作为唯一交接媒介。

我会为每个协作任务维护一张责任表：

| 工作项 | 当前角色 | 写入范围 | 输入基线 | 交付物 |
| --- | --- | --- | --- | --- |
| 契约梳理 | 探索工具 | 只读 | 设计文档 + 当前代码 | 差异与开放问题 |
| 后端实现 | 实现工具 | 后端模块 | 已确认契约版本 | diff、测试和提交 |
| 前端接线 | 另一工作树执行器 | 前端模块 | 后端契约提交 | 类型、组件和联调结果 |
| 综合复核 | 评审工具 | 只读 | 合并后的候选版本 | 风险、回归和缺口 |

角色可以变化，但变化必须伴随交接。一个工具从评审切换为修复时，应先获得新的写入范围和基线，不能在只读任务中顺手修改文件。

## 并行前先判断能否真正隔离

目录不同不等于没有冲突。后端和前端可能共同修改协议文件，两个模块可能共享数据库迁移，测试还可能使用同一开发库或对象存储。并行前要识别代码、契约、数据和运行资源四类共享面。

无法隔离的共享契约采用单写者；可以隔离的模块使用独立工作树、分支和测试资源；只能共享的环境则安排顺序执行或只读验证。不要把 Git 不冲突误认为业务上可以并行。

隔离评估至少覆盖四层：

| 层次 | 需要确认 | 常见冲突 |
| --- | --- | --- |
| 代码 | 工作树、分支、生成文件和共享契约 | 同文件覆盖、生成物污染 |
| 数据 | 数据库、缓存、消息和对象存储 | 测试数据互相修改 |
| 任务 | 写入责任、状态与运行标识 | 两个执行器同时宣称完成 |
| 证据 | 测试基线、日志和回写目标 | 旧结果覆盖新版本 |

只有四层都能隔离，任务才适合真正并行；否则应改为分析并行、写入串行，或者明确共享资源的调度顺序。

## 交接要交付证据

探索方不应只说“建议改这里”，而应留下相关文件、已确认事实、开放问题和验证计划。实现方完成后回写 diff、测试和未验证项。复核方以实际工作区为准，检查方案是否被正确实现。

```text
探索：调用链、边界、方案和风险
实现：按方案修改、补测试、执行验证
复核：检查 diff、验收、回归和敏感信息
```

一份可接手的交接包还应包含任务版本、代码基线、已修改文件、明确未修改的范围、已执行命令、未验证项和下一步。结论要区分事实、推断和待确认；大型日志使用引用，不把敏感内容直接复制到会话。

接收方不能只相信交接文字。开始前仍需核对提交、`git status`、diff 和相关测试，因为交接生成后现场可能已经变化。

## 防止两个工具互相覆盖

开始前读取 `git status` 和 diff；执行中保持任务范围；交接时说明当前版本和修改文件；发现工作区有未知改动就暂停确认。不要让第二个工具为了“保持干净”重置或覆盖第一个工具的工作。

发生冲突时，我使用固定处理顺序：停止当前写入，保留双方现场，确认所有权和基线，比较需求与实现证据，再决定合并、重新分工或放弃某一方案。不能让后启动的工具通过重置来“解决”冲突，也不能因为两个版本都能编译就任意选择。

## 怎样证明协作没有相互污染

测试要覆盖两个执行器同时开始、共享文件被修改、契约版本变化、旧交接延迟送达和一个工具异常退出。除代码 diff 外，还要检查数据库、缓存、对象存储和生成文件是否被共用。

AI 工具负责各自限定范围内的分析和交付；编排层负责角色、运行标识与写入租约；工程师负责共享契约和冲突裁决。多工具协作完成的证据，是每项改动都能追溯到唯一写入者和明确基线，任何未知现场都会触发暂停，而不是最后恰好没有 Git 冲突。

```text
请接手【协作任务】，当前先不要写入：

1. 核对任务版本、代码基线、工作区和现有修改所有者；
2. 说明你的角色、允许写入范围、共享契约和运行资源；
3. 读取交接中的事实、推断、未验证项和实际证据；
4. 发现未知改动或责任重叠时停止，保留现场并提出分工方案；
5. 获得写入责任后再执行，交付 diff、测试、风险和下一基线。
```

多工具协作的收益来自不同视角，而不是把更多模型同时放进同一目录。只要责任、上下文和证据清楚，探索与验证可以互相增强；否则只是增加了冲突来源。
