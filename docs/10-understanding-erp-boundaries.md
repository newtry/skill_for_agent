# 复杂 ERP 需求不能只看代码：如何让 AI 理解业务边界

在 ERP 里，很多需求用一句话说起来都很简单：“按门店查库存”“给用户补一个资料字段”“把客户数据导入进来”。真正开始实现后，问题才浮现：这里的“门店”是组织归属、库存地点还是数据权限范围？“客户”属于租户、账套还是销售主体？同一个 SKU 能不能跨账套汇总？

如果 AI 只从当前代码片段理解这些词，它很容易写出能运行、但口径错误的实现。ERP 的难处不只在代码量，更在于同一个名词在不同业务边界中的含义不同。

## 先把业务词翻译成可验证的规则

我现在遇到 ERP 需求时，会先让 AI 写出一个最小术语表，而不是立即打开 Controller。比如：租户是隔离边界，账套是核算或经营边界，门店是组织或经营地点，库存是特定商品在特定维度下的数量。若这些词在当前项目里有不同定义，就以项目实际定义为准。

接着明确一行数据的粒度。库存查询中的一行，到底代表“SKU 总库存”“SKU 在一个门店的库存”，还是“SKU 在一个账套、一个仓库、一个批次下的可用库存”？这一步决定查询条件、聚合维度、权限过滤和缓存键。没有它，AI 写出的 SQL 即使语法正确，也可能把本不该合并的数据合并掉。

## 模块边界和业务边界需要同时成立

真实 ERP 常见 `api` / `biz` 模块拆分、Admin/App 双端入口、跨模块只能走公开 API 等工程约束。它们不是代码洁癖，而是把业务边界落实到依赖关系上。

例如库存模块需要客户信息时，直接引用客户模块的实现类也许最快，但它让两个业务模块在内部细节上绑死。更稳妥的做法是通过对外 API 获取所需事实，或在事件和数据同步中维护自身需要的视图。AI 在提出方案时，应当解释数据所有权和调用边界，而不是只找一条能编译的依赖路径。

## 一个 `ledger_id` 聚合问题的教训

我遇到过一类典型错误：库存或财务数据按 SKU 聚合后，结果总数看起来合理，但实际遗漏了 `ledger_id` 维度。不同账套下的同一 SKU 被合并了，导致查询把不同核算主体的数据混在一起。

这种问题很难靠普通接口测试发现，因为单账套样本完全正常。需要专门准备跨账套、跨门店和无归属记录，验证结果的行数、金额或数量是否仍符合业务口径。AI 可以很快搜索所有 `GROUP BY`、缓存和批量计算入口，帮助发现类似遗漏；但它需要先知道账套是不可跨越的边界，而不是一个可选过滤条件。

## 让 AI 先画边界，再写方案

```text
请分析【ERP 需求】，先不要改代码。

1. 写出涉及的业务术语及当前项目中的定义；
2. 明确每个查询/写入结果的数据粒度、主键和不可跨越的隔离维度；
3. 说明数据由哪个模块拥有，其他模块通过什么方式使用；
4. 还原 Admin/App 入口、权限、租户、账套、门店和逻辑删除的影响；
5. 给出最小实现方案，以及跨维度、无归属、历史数据和权限场景的验证计划。
```

## 先对齐语言，才能让 AI 帮上忙

让 AI 理解 ERP 不是要求它背下所有表名，而是让它在每个需求开始时问对问题：这是谁的数据？在什么边界下有效？由谁维护？什么情况下不能被合并、展示或修改？

当这些业务事实与模块依赖、接口契约和测试样本对齐后，AI 才能真正参与复杂需求。否则它很可能只是高效地产生一段错误的业务逻辑。
