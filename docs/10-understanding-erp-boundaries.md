# 复杂 ERP 需求不能只看代码：如何让 AI 理解业务边界

> 系列导航：[完整目录](00-series-titles.md)

ERP 需求最容易用熟悉的词把复杂性藏起来：“按门店查库存”“按客户汇总”“给用户补一个字段”。工程师和 AI 都认识这些词，却未必对它们指向的业务对象有相同理解。

我在 ERP 项目中越来越少直接从 Controller 开始，而是先问一句：这条数据属于谁，在什么边界内有效，谁拥有它？

## “门店”“账套”“租户”不是三个过滤字段

它们可能都出现在查询条件里，却代表不同的业务边界。租户通常决定数据隔离；账套可能决定核算或经营主体；门店可能是组织、经营地点或库存地点。一个需求说“当前门店”，必须先确认它是用户归属、请求上下文还是查询范围。

同样，“库存”也可能指物理数量、可售数量、预占后数量或某个批次的数量。如果不先定义，AI 会依据字段名和相似 SQL 选择一个看似合理的口径。

## 先写一行数据的粒度

我会让 AI 把结果粒度写成一句话：一行代表“某租户、某账套、某门店、某仓库下的某 SKU 可用库存”，还是代表“某 SKU 的全局库存”。这句话会决定分组字段、权限条件、缓存键、分页和测试样本。

如果单账套的测试数据能通过，跨账套的数据却被合并，说明技术链路是通的，业务粒度是错的。ERP 中很多严重问题就是这样产生的。

## 业务边界要落到模块边界

项目里的 `api` / `biz` 拆分、Admin/App 入口和跨模块调用规则，不只是代码风格。它们是业务责任的工程表达：谁拥有客户数据，谁提供库存事实，谁只能通过公开 API 使用它。

当库存模块需要客户信息时，直接引用客户模块的 Biz Service 虽然快捷，却把两个模块的内部模型绑在一起。AI 应该先说明数据所有权和调用边界，再讨论接口或事件，而不是优先选择最容易编译的路径。

## 字段相似不代表业务语义相同

一次协议升级里，系统同时出现了 `modelCode` 和 `localCode`。它们在类型上都是字符串，旧代码还曾用其中一个字段兜底另一个字段，因此 AI 很容易把迁移理解成重命名。实际上一方表示模型侧标识，另一方表示本地配置编码，来源、唯一性和生命周期都不同。

如果只看 DTO 和序列化代码，新旧字段互相复制似乎最兼容；从业务边界看，这会让两个语义继续混在一起。后来处理这类迁移时，我会先补一张语义表：谁产生字段、谁拥有它、在哪个上下文唯一、哪些调用方消费、旧值何时退出。字段改名只是代码动作，统一语义才是迁移目标。

## 我让 AI 先做业务翻译

```text
请分析【ERP 需求】，先不要修改代码：
1. 定义租户、账套、门店、仓库、客户、商品等术语在当前项目中的含义；
2. 写明查询/写入的一行数据粒度、唯一键和不可跨越的维度；
3. 说明每类数据由哪个模块拥有，其他模块如何使用；
4. 检查 Admin/App、权限、逻辑删除和租户过滤；
5. 给出跨维度、空关联、历史数据和越权场景的验证计划。
```

## 让 AI 理解 ERP，核心是让它先问对问题

AI 不需要在一开始记住所有表名，但必须知道哪些事实会改变答案：数据属于谁，在哪里有效，能否被合并，谁有权修改，跨模块如何获得。业务语言、模块边界和测试样本对齐后，AI 才可能参与复杂 ERP 需求；否则它只是在更快地生成一段口径不明的代码。
