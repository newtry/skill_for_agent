# 为什么业务 Agent 不能只会回答，还必须能够推动业务流程

> 系列导航：[完整目录](00-series-titles.md)

很多业务 Agent 的演示停在一句话：用户提问，模型给出一段回答。真正接进 ERP 后，用户还要继续复制订单号、打开菜单、填写参数、提交审批，再回来确认结果。

如果 Agent 只能解释，不会在边界清楚时推动流程，它只是一个更方便的搜索框；如果它可以直接调用万能执行工具，又会绕过权限、状态、审批和幂等。

业务 Agent 的产品价值在两者之间：理解自然语言，把意图转换为明确业务动作，交给后端工作流执行，并持续报告真实状态。

## 核心判断：Agent 的完成标准是业务状态改变

Agent 不应以“已经调用接口”或“已经回复用户”作为完成标准。它必须把请求推进到一个可确认的业务状态，并如实报告处理中、成功、失败或待补偿。模型负责理解和编排，领域服务负责状态迁移，流程系统负责保证副作用可控。

## 查询和动作必须走不同路径

“这款还有多少库存”是读操作；“那就调拨到这家店”已经变成写操作，涉及目标门店、数量、库存所有权、审批和重复执行。

Agent 必须识别意图发生了变化，补齐必要参数，确认用户权限，展示动作预览，再调用明确的业务接口。不能因为上一轮查询已经通过权限，就默认下一轮写操作也被授权。

## 一次调拨请求怎样从回答变成流程

用户先问“人民路店 A 款还剩多少”，Agent 查询后返回 8 件。用户接着说“那就从总仓调 20 件过去”。第一版实现直接调用调拨接口，并回复“已为你调拨”，但随后出现三个问题：目标账套没有重新确认，接口超时后用户再次提交生成了第二张单，实际单据仍在待审批，页面却展示为已完成。

修复后，这两轮对话被拆成不同业务阶段：

| 阶段 | 系统动作 | 对用户展示的状态 |
| --- | --- | --- |
| 查询 | 读取人民路店库存 | 已确认库存事实 |
| 参数补齐 | 确认来源仓、目标店、SKU、数量和账套 | 待确认参数 |
| 预校验 | 检查权限、可调库存和审批规则 | 可执行或受限原因 |
| 预览 | 生成不可变预览摘要和业务键 | 待确认/待审批 |
| 提交 | 幂等创建调拨单 | 已受理，不等于完成 |
| 跟踪 | 查询审批和出入库状态 | 处理中、成功或失败 |

对话提供连续体验，但每个阶段都要有独立的业务状态和证据。上一轮查询结果只能作为候选上下文，不能替代当前写操作的授权和状态校验。

## 业务动作需要六步闭环

```text
理解请求 -> 补齐参数 -> 权限与状态校验
-> 生成预览 -> 用户确认/审批 -> 受控执行
-> 返回真实状态、流水和后续处理
```

预览不是多余的确认页面。它让用户看到 Agent 实际理解的对象、数量、金额、数据范围和业务键，也给系统在写入前最后一次纠正歧义的机会。

对于高风险动作，确认应绑定预览内容、操作者、有效期和业务键，避免用户确认一项动作后参数又被模型改写。

预览可以生成摘要哈希。确认请求必须携带预览 ID 和哈希，服务端核对数量、对象、账套和操作者没有变化后才执行。库存或权限在确认前发生变化时，旧预览失效并要求重新确认，而不是静默使用新参数。

## 后端状态机不能被模型替代

模型可以理解“帮我处理一下”，但不能自行把订单变成已支付、把调拨变成已审批或把退款标成已完成。每次状态变化都必须通过有权限、可幂等、可审计的领域服务或业务接口。

工具应返回处理中、成功、失败、待确认、待补偿等真实状态，不能把接口受理伪装成业务完成。长流程需要任务 ID、进度、超时和人工接管入口。

```text
DRAFT -> VALIDATED -> WAITING_CONFIRMATION -> SUBMITTED
-> WAITING_APPROVAL -> PROCESSING -> SUCCEEDED
                         |              |
                         v              v
                      REJECTED       FAILED -> COMPENSATING -> CLOSED
```

允许迁移、前置条件和最终状态都由后端定义。模型可以解释当前状态和建议下一步，但不能生成一个系统不存在的“基本完成”，也不能把 `SUBMITTED` 翻译成“调拨成功”。

## 失败和重复是正常路径

业务动作要提前定义：参数校验失败怎么办，外部调用超时怎么办，用户重复确认怎么办，进程中断后如何恢复，部分成功如何补偿，最终谁负责处理差异。

幂等键由业务对象、动作类型和请求意图共同决定，不能只使用会话 ID 或模型生成的随机值。重复请求可以被正常应答，但业务副作用只能产生一次有效效果。

外部调用超时时，系统首先根据业务键查询已有结果，而不是立刻重试；确实未创建时才安全补交。部分成功时记录已完成步骤和待补偿项，由后台任务或人工入口继续处理。Agent 只报告系统确认的状态，不根据“没有收到异常”推断成功。

## 业务 Agent 的价值要落到后续状态

“已为你发起调拨”只是动作受理，不是调拨完成。结果应明确：业务单号、当前状态、数据范围、执行时间、失败原因、下一步和人工处理入口。

Agent 只有让用户少做人工跳转，同时不隐藏真实状态，才真正推动了流程。

## 怎样证明流程已经完成

我会同时检查四类证据：预览与确认内容一致；同一业务键重复提交只产生一个有效单据；状态流水能够解释每次变化；失败、超时和审批拒绝都进入已定义的终态或人工处理状态。

测试至少覆盖权限在确认前变化、库存被并发占用、重复点击、接口超时但实际成功、审批拒绝和补偿失败。只验证一次成功调拨，无法证明这条流程可以进入真实业务。

AI 可以整理状态机、生成边界用例、检查幂等字段和跟踪调用链。领域负责人必须确认哪些状态代表业务完成、谁能确认和审批、哪些失败可以自动补偿。工程师负责把这些规则落实为后端约束，而不是把责任留给对话提示词。

```text
请为【业务动作】设计 Agent 流程：

1. 区分查询、建议、草稿和真实写操作；
2. 定义必填参数、对象范围、权限、业务状态和幂等键；
3. 设计预览、确认/审批、执行、处理中、成功、失败和补偿；
4. 说明重复、超时、中断、部分成功和人工接管；
5. 设计结果卡片、任务 ID、审计流水和最终状态验证；
6. 禁止模型绕过后端状态机、权限和审批。
```
