# 从分析、实现到验证：如何防止 AI 在任务中途宣布完成

> 系列导航：[完整目录](00-series-titles.md)

AI 有时在只读分析后说“建议已完成”，也会在改完一两个文件后说“功能已实现”。这通常不是故意夸大，而是模型把“产生了一个看起来合理的输出”误当成了任务终点。

在真实交付中，分析完成、方案通过、代码实现、测试执行、验收完成和发布就绪是不同状态。每个状态都有独立的退出条件，也可能因为新的证据重新打开。

因此，防止 AI 过早宣布完成，不是再写一句“不要提前结束”，而是把任务变成一个有状态、有产物、有门禁的过程，并规定每个阶段只能声明什么。

## 完成首先是阶段状态，不是自然语言总结

我现在会把任务拆成七个阶段：

```text
分析 -> 方案 -> 测试设计 -> 实现 -> 代码审查
-> 验证 -> 交付
```

| 阶段 | 允许声明的内容 | 不能替代的状态 |
| --- | --- | --- |
| 分析 | 已确认事实、调用链、风险和开放问题 | 代码已实现 |
| 方案 | 设计得到确认，知道怎样实现和回退 | 测试已通过 |
| 测试设计 | 风险有场景、层级和断言计划 | 风险已被覆盖 |
| 实现 | 代码和测试按范围发生变化 | 需求已验收 |
| 代码审查 | 未发现已知阻塞性实现问题 | 运行结果正确 |
| 验证 | 命令、数据和业务证据已经产生 | 发布已授权 |
| 交付 | 结果、风险和接管信息已确认 | 未来问题不存在 |

“实现完成”只能说明代码修改阶段结束，“任务完成”还需要通过验证和责任确认。模型输出应使用准确阶段状态，不能用一个“已完成”覆盖全部含义。

## 每个阶段都必须有进入和退出条件

### 分析阶段

进入时只读检查项目基线、任务契约和实时现场；退出时需要有问题复述、调用链、事实与假设、约束、开放问题、最小范围和验证计划。入口、数据粒度或业务状态仍不明确时，不能进入实现。

### 方案阶段

进入时已有明确目标和风险；退出时方案覆盖模块边界、数据所有权、状态、异常、幂等、迁移、测试、发布和回退。阻塞性业务决策未确认时，只能报告等待确认。

### 测试设计阶段

退出时每个关键验收条件有场景、断言、测试层级、数据和环境要求。测试计划存在不等于测试执行完成。

### 实现阶段

退出时有实际 diff、修改文件、行为变化、新增测试和方案偏差说明。工作区中存在其他任务改动时，还要证明本次范围没有覆盖它们。

### 审查与验证阶段

审查先识别业务回归风险，验证再执行命令和数据检查。退出时要有通过、失败、未执行、环境阻塞和待人工确认的分类，以及残余风险。

### 交付阶段

只有明确授权后，才进入提交、推送、数据库写入、发布或外部业务动作。交付还需要回滚、监控、未决问题和接管记录。

## “当前阻塞”与“长期风险”要分开

一次多端联调中，AI 审查列出了多个长期架构问题，并将它们全部标成高优先级；但当前版本真正的交付阻塞，是一个协议字段尚未在 Java 和前端完成切换。

我后来要求每个发现同时标记两个维度：

| 维度 | 需要回答的问题 |
| --- | --- |
| 风险等级 | 是否可能造成数据、安全、资金或核心业务事故 |
| 阶段关系 | 是否阻塞当前阶段的验收、发布或回滚 |

高风险问题即使暂未阻塞当前版本，也要进入门禁、负责人和后续计划；不影响本次交付的结构优化则单独登记。这样既不会为了赶进度掩盖风险，也不会让长期重构淹没当前验收。

## 新证据可以让任务退回前一阶段

如果测试发现业务规则矛盾，任务应从测试设计退回需求或方案；如果实现发现项目模块边界不支持原方案，应退回方案评审；如果验证发现生产配置缺失，应回到发布准备。

退回不是流程失败，而是保持下游产物诚实。继续沿着已经被证伪的假设实现，才会制造更昂贵的返工。

AI 需要报告“哪个新证据导致阶段退回、哪些产物需要重新生成”，而不是悄悄修改目标和验收条件以保持表面完成。

## 短指令也要恢复阶段状态

“继续”“再验证一下”“按刚才方案实现”都不能脱离当前状态解释。恢复时至少要读取：

```text
当前阶段与授权
已确认事实和开放问题
已完成产物与实际证据
当前 diff、分支和外部环境
失败、阻塞和未验证项
下一步允许执行的最小动作
```

如果上一阶段正在等待业务确认，“继续”不能被解释成直接修改；如果用户最新要求“先只读”，旧计划中的写入步骤必须停止。最新授权改变的是当前可执行范围，不会自动抹掉既有证据和未完成项。

## 用状态记录代替“差不多完成”

```text
任务目标：本次交付要改变什么
当前阶段：分析/方案/测试设计/实现/审查/验证/交付
已确认：事实、规则、决策及依据
已完成：文件、diff、命令和真实结果
未完成：验收缺口、失败、阻塞和开放问题
当前授权：允许分析、修改、测试、提交还是发布
下一步：在现有授权内的最小动作
完成条件：还需要哪些证据才能进入下一状态
```

这份记录既服务于 AI，也服务于人工接管。它让“完成”成为一个可审查状态，而不是一句模型自述。

## 我使用的阶段控制要求

```text
请按任务阶段推进，不要提前宣布整体完成：

1. 先标明当前阶段、目标、授权和退出条件；
2. 分析阶段只读，输出事实、假设、风险、范围和计划；
3. 方案与测试设计未满足门禁前，不进入实现；
4. 实现阶段报告实际 diff、行为变化、测试和方案偏差；
5. 审查与验证阶段逐条对应验收，报告真实命令和结果；
6. 区分已验证、失败、未执行、环境阻塞和待人工确认；
7. 只有得到明确授权，才执行提交、推送、数据库写入、发布或外部动作；
8. 每轮结束更新当前状态、剩余证据和下一步最小动作。
```

第三辑的核心不是让 AI 遵循更多格式，而是让研发过程具备可追溯的状态转换：项目规则提供事实，任务契约定义目标，追溯关系连接承诺，方案和测试建立证据路径，审查和验证决定是否可以推进，人工授权承担最终风险。

到这里，AI 已经不只是一个生成代码的助手，而是一个被纳入阶段、门禁和责任体系的研发参与者。下一辑将把同样的原则移到业务 Agent：当 AI 不再只修改代码，而是直接参与用户业务流程时，路由、工具、权限和评测如何共同保证可靠性。
