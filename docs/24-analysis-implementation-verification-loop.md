# 从分析、实现到验证：如何防止 AI 在任务中途宣布完成

AI 有时会在只读分析后说“建议已完成”，也会在改完一两个文件后说“功能已实现”。这类表述不一定是故意夸大，而是模型把“产生了一个看起来合理的结果”当成了任务终点。

我后来把任务固定成三个阶段，并让每个阶段都有独立交付物：分析说明知道了什么，实现说明改变了什么，验证说明证明了什么。

## 分析阶段不能直接跳到代码

分析阶段应产出问题复述、调用链、相关文件、约束、开放问题、最小方案和验证计划。它的价值是暴露错误假设。如果 AI 还没有确认入口、数据粒度或业务状态，就不应该进入实现。

## 实现阶段必须对照方案

实现时要求 AI 说明修改文件、复用的项目模式、影响的依赖和新增测试。若实际实现偏离方案，要解释原因，而不是默默扩大范围。对于高风险变更，方案确认仍是人工门槛。

## 验证阶段必须交证据

验证报告不能只有“测试通过”。它至少要说明执行了什么命令、测试是否真的运行、哪些验收条件被覆盖、哪些环境项没有验证、工作区是否包含无关改动。

## 当前交付阻塞要和抽象风险等级分开

在一次多端联调中，AI 的审查列出了若干长期架构风险，并把它们标成高优先级；但当时真正阻塞交付的是一个协议字段尚未在 Java 和前端完成切换。若只按抽象严重程度排序，团队会先重构长期问题，当前版本却仍然无法贯通。

我后来要求每个发现同时标两个维度：风险有多大，以及它与当前交付阶段有什么关系。阻塞当前验收的问题先解决；会造成数据或安全事故的问题即使暂未触发，也必须进入门禁；不影响本次交付的结构优化则明确留到后续，而不是混在“未完成”里。

这不是降低风险标准，而是让 AI 理解任务有时间顺序。分析阶段关注决策缺口，实现阶段关注接线和兼容，验证阶段关注证据，发布阶段关注环境与回滚。优先级必须结合当前阶段重新计算。

```text
阶段一：先只读分析，输出依据、假设、风险和计划。
阶段二：按确认方案实施，汇报文件、行为变化和测试补充。
阶段三：执行测试/构建/数据或接口检查，逐条对应验收条件。
阶段四：报告未完成项和人工确认项，不用“已完成”替代未验证结论。
```

这套循环让 AI 不能靠一句总结跳过中间过程。它也让人可以在分析阶段纠正方向，在实现阶段控制范围，在验证阶段判断证据是否足够。
