# 如何让需求、验收条件、测试用例和代码实现相互追溯

> 系列导航：[完整目录](00-series-titles.md)

真实项目中经常出现三种追问：这个测试对应哪条需求？这段特殊逻辑为什么存在？需求变化后，哪些方案、代码和测试需要重新评估？

如果答案只能依靠熟悉项目的人回忆，AI 加快代码生成后，失联会发生得更快。需求写在 PRD，方案写在文档，测试按方法名组织，代码又经历多次重构，最后每一部分都“存在”，却无法证明它们表达的是同一项业务承诺。

我后来把追溯的基本单位从文件改成验收条件。文件会移动，类会重命名，验收条件表达的业务结果则相对稳定。围绕它建立需求、风险、方案、测试、实现和证据关系，才能判断一项承诺是否真正完成。

## 追溯不是给每行代码编号

追溯的目标不是把文档和代码变成庞大索引，而是保护那些一旦遗漏就会造成业务错误的规则。

例如用户资料接口可以拆成：

```text
AC-01 有有效门店归属时，返回当前账套下的正确门店名称
AC-02 没有有效归属时，字段为空且接口不报错
AC-03 不得读取其他租户或账套的门店关系
AC-04 原有路径、状态码和既有字段保持兼容
```

每条条件继续关联风险、方案决策、测试场景、关键实现位置和验证结果。只追踪关键承诺，既能控制维护成本，也能让空白清晰可见。

## 一条完整追溯链包含七个节点

```text
业务目标 -> 验收条件 -> 风险/不变量 -> 方案决策
        -> 测试用例 -> 实现位置 -> 验证证据
```

| 节点 | 需要回答的问题 |
| --- | --- |
| 业务目标 | 为什么要改变，用户要得到什么结果 |
| 验收条件 | 哪个可观察行为代表目标成立 |
| 风险/不变量 | 什么情况最可能破坏该行为 |
| 方案决策 | 通过什么机制守住它，为什么这样选 |
| 测试用例 | 用什么输入和断言验证风险 |
| 实现位置 | 哪些模块和代码兑现该决策 |
| 验证证据 | 实际执行了什么，结果和环境是什么 |

这条链让“已经实现”不再是一个文件存在的判断，而是从业务目标到运行证据的连续关系。

## 追溯矩阵首先用于发现空白

| 验收条件 | 风险 | 方案/实现 | 测试 | 当前证据 | 状态 |
| --- | --- | --- | --- | --- | --- |
| AC-01 正常归属 | 错误关联 | 跨模块 API + 转换 | 正常接口测试 | 响应与数据样本 | 已验证 |
| AC-02 空归属 | 空指针 | 空值语义 | 空关联测试 | 测试未执行 | 已实现未验证 |
| AC-03 数据隔离 | 越权读取 | 租户与账套条件 | 跨边界集成测试 | 无对应用例 | 缺口 |
| AC-04 兼容性 | 旧调用方失败 | 保持契约 | 契约回归 | 构建通过 | 部分证据 |

“有代码”和“有测试”都不是二元完成状态。矩阵应区分待确认、已设计、已实现、已验证、受阻和不适用。这样 AI 不能因为找到一个相似测试就把整条验收条件标成覆盖。

没有测试的验收条件代表证据缺口；没有需求来源的特殊代码可能是历史兼容、技术债或误改；没有实现位置的测试可能验证的是假对象而非真实路径。追溯的价值是让这些关系异常主动暴露。

## 关键词相同不代表语义相同

AI 很适合跨文件搜索，但不能仅凭名称自动建立关系。一个测试断言响应包含 `storeName`，只能证明字段存在，不能证明跨账套隔离；一个名为“重复回调”的测试，如果只断言第二次返回成功，也不能证明资金流水只生成一次。

自动生成矩阵后，仍要检查测试输入、断言和执行层级是否真的对应验收语义。追溯关系需要语义确认，而不是文本相似度。

## 跨代码库时，要按生产者和消费者展开

一次 V2 协议迁移同时涉及 Agent 后端、Java 服务和前端。后端契约已经更新，集成文档也写成新格式，但继续追踪后发现：部分 Java 映射仍读取旧字段，前端类型保留兼容定义，跨端契约测试只覆盖了新生产方。

此时不能只写“新协议已实现”，而要展开每个消费者：

```text
协议条目 -> 后端生产 -> Java 消费 -> 前端展示
        -> 契约测试 -> 发布版本 -> 旧字段退出条件
```

每个仓库单独构建成功，不代表端到端迁移完成。文档也不是天然真相，它可能落后于代码，也可能提前描述尚未完成的目标状态。

## 需求变化时反向使用追溯关系

追溯不只用于验收，还用于影响分析：

- 验收条件变化时，找到受影响方案、测试和实现；
- 技术方案调整时，检查哪些风险和用例需要更新；
- 测试失败时，回到对应业务承诺和最近变更；
- 线上缺陷出现时，补充缺失验收条件与回归证据；
- 旧协议退出时，确认所有消费者和兼容测试都已迁移。

追溯关系应该随真实风险演进，而不是需求评审后冻结。

## 追溯证据必须可维护

小任务可以在 Markdown 表格或任务卡中维护，大型跨仓库迁移可以使用需求系统和自动报告。工具形式不重要，关键是标识稳定、关系可查询、状态有负责人。

代码位置不宜精确到容易变化的行号，可以指向模块、接口、状态迁移或关键测试。验证证据则应保留命令、版本和结果，避免只写“已通过”。

```text
请为【需求】建立轻量追溯矩阵：

1. 将业务目标拆成可观察、可编号的验收条件；
2. 为每项关联风险、不变量和关键方案决策；
3. 映射测试场景、实现模块和实际验证证据；
4. 区分待确认、已设计、已实现、已验证、受阻和不适用；
5. 标出没有测试、没有实现、证据不足或语义不一致的条目；
6. 跨仓库协议按生产者、每个消费者和退出条件展开。

不要把关键词相似自动判断为语义覆盖。
```

追溯关系为第三辑建立了一条纵向主线：后面的方案评审、测试设计、代码审查和验收验证，都可以回到同一组业务承诺。下一篇将先检查技术方案能否真正兑现这些承诺。
