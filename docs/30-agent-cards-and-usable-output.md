# 从 Markdown 到业务卡片：让 Agent 输出真正可用的结果

> 系列导航：[完整目录](00-series-titles.md)

Agent 的第一版通常返回一大段 Markdown。对于问答还可以接受，到了业务场景就会出现问题：用户找不到关键数字，状态和操作混在一起，按钮缺少参数，错误结果与正常结果长得一样。

我在业务 Agent 里逐渐把输出看成一个产品契约，而不是模型随手生成的文字。

## 输出要匹配用户下一步

查库存的结果应突出商品、可用数量、门店、账套和更新时间；订单查询应突出状态、金额、支付和可执行动作；异常结果应突出原因、影响和下一步处理。相同的数据，不同用户需要的重点也不同。

业务卡片的价值在于把答案分成稳定区域：摘要、关键字段、状态、来源、可执行动作和风险提示。前端可以据此渲染按钮、表格和状态标签，而不是解析一段自然语言。

## 结构化输出也要有边界

卡片字段应有明确 schema、类型和必填规则。金额不能用含义不明的字符串，状态不能让模型自由发明枚举，按钮不能只返回“可以退款”而没有订单号、权限和确认信息。

后端或输出适配层需要校验模型结果。字段缺失、类型错误和未知状态应进入兜底展示或人工处理，不能直接把不可信 JSON 当成业务动作。

## 结果必须区分事实、推断和建议

Agent 经常把数据库事实和模型推断混在一起。卡片可以分别标识数据来源、查询时间、计算口径和建议内容，让用户知道哪些是系统记录，哪些只是辅助判断。

对于没有查到数据，也应返回明确的空状态和查询范围，而不是让模型编一个可能的答案。

```text
请为【业务场景】设计结构化输出：
1. 摘要、关键字段、状态、数据来源和更新时间；
2. 正常、空结果、权限不足、工具失败和待确认状态；
3. 可执行动作的参数、权限、幂等键和确认信息；
4. JSON/schema 校验和无法渲染时的兜底；
5. 区分系统事实、计算结果和模型建议。
```

从 Markdown 到业务卡片，不是为了让界面更漂亮，而是为了让 Agent 的结果可读、可渲染、可操作、可审计。输出结构稳定后，模型才真正接上了业务产品。
