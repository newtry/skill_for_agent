# 上下文决定结果：为什么 AI 有时像专家，有时像新人

我遇到过一种很有意思的情况：同一个项目里，AI 在上午能准确说出模块边界和测试命令，下午换个会话后，却把接口放到了错误的目录。模型好像突然退步了。

后来我不再把它简单归因于模型状态。更常见的原因是，上午的 AI 拿到了项目规则、当前 diff 和此前的排查结论，下午的 AI 只拿到了一句新的问题。

## 会话记忆不是项目记忆

在一条长会话里工作很舒服。AI 记得我们刚刚讨论过的模块，知道哪个配置不能改，也知道一个报错排查到哪一步。可一旦切换会话、切换工具，或者让同事接手，这些信息就不一定还在。

我曾经把这种“它应该记得”当成了工作方式。结果是同一条规则反复解释，甚至不同会话给出了互相冲突的实现建议。

于是我开始区分三种上下文：项目长期规则、当前任务事实和阶段交接状态。项目规则回答“这个仓库通常怎样工作”；任务事实回答“这次到底发生了什么”；交接状态回答“已经做到哪里，下一步是什么”。

## 三层上下文，各自放在该放的位置

稳定规则应该离开聊天窗口，放进项目级说明。例如模块职责、API/Biz 依赖、Admin/App 入口、构建方式、租户和敏感操作边界。

当前任务的请求、日志、数据样本和验收条件放在当前对话或任务文档里。它们通常只对这次问题有效，不适合污染所有会话。

阶段状态则用短记录保存：已确认的事实、已经修改的文件、实际跑过的命令、未解决的问题和下一步动作。

如果把所有东西都留在聊天里，换会话就失忆；如果把所有东西都塞进项目规则，规则会变成没人愿意维护的百科全书。

## 上下文不是越多越好

我也尝试过一次性把大量代码、配置和日志交给 AI，结果它复述了很多背景，却没有更准确地做判断。真正需要的不是“更多文件”，而是与当前决策相关、能被验证的事实。

例如要判断一个接口该放在哪，给出项目入口规则和相似 Controller 就够了；要排查数据为空，再补上调用链、关联表和实际响应。每次提供信息时，我会问自己：这条事实会改变实现选择吗？如果不会，就不急着放进上下文。

## 交接记录要让陌生人接得起来

我现在会让 AI 在阶段结束时留下这样的记录：

```text
已确认：现象、根因或当前假设，以及证据
已完成：文件、命令、测试结果和工作区状态
未完成：待验证项、环境阻塞和开放业务问题
下一步：继续时先读什么、执行什么最小动作
```

这比“问题已经基本解决”可靠得多。新的会话可以据此恢复，人类同事也能判断哪些是事实、哪些仍然只是猜测。

## 把项目规则写成“新成员须知”

项目说明不需要解释所有架构历史，应该优先写会导致错误的规则：接口入口不能放错，兄弟模块不能直接引用实现类，测试要在哪个模块执行，哪些生产操作必须确认，敏感配置不能进入输出。

规则还需要随着项目变化更新。一次真实故障或反复出现的纠正，如果以后每个会话都可能再次发生，就值得沉淀；只有当前需求特有的细节，则留在任务记录中。

## 一句恢复上下文的要求

```text
先不要修改代码。请读取项目规则、当前工作区和本任务交接记录，按以下格式恢复：

已确认 / 已完成 / 未完成 / 下一步。

每项结论附文件、diff、日志或命令依据；无法确认的内容标为待验证，不能按历史猜测处理。
```

AI 看起来像专家，并不是因为它永远记得一切，而是因为它在判断前拿到了正确的地图、现场和状态。把上下文从一次性聊天变成项目资产，跨会话协作才会从“重新介绍一遍”变成真正的连续工作。
