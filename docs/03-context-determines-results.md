# 上下文决定结果：为什么 AI 有时像专家，有时像新人

> 系列导航：[完整目录](00-series-titles.md)

我曾在同一个项目里遇到过两次表现差异很大的协作。

上午的会话能够准确识别 API/Biz 模块边界，沿着调用链找到数据问题，并在正确的 Maven 模块中完成验证。下午切换会话后，我只说了一句“继续处理这个问题”。新的会话虽然读到了需求，却不知道工作区已经存在未提交修改，也不知道上一轮测试只完成了一部分。它重新提出了一套实现方案，还准备修改已经被人工调整过的文件。

模型没有突然变差。上午它拥有项目规则、任务目标、当前 diff 和验证结果；下午它只拥有一句指令和部分代码。

这类差异让我重新理解了上下文：上下文不是聊天记录的长度，而是 AI 在当前决策点能够获得的有效事实。项目事实缺失会让它选错路径，任务事实缺失会让它解决错问题，执行状态过期则会让它重复工作甚至覆盖现场。

因此，上下文管理的目标不是“让 AI 记住更多”，而是让每一次判断都建立在相关、可信、最新且可追溯的信息上。

## 会话记忆不能承担工程记忆

在长会话中，AI 看起来像是逐渐理解了项目：它记得模块边界、业务口径、刚修改的文件和失败的测试。但这些信息如果只存在于对话里，就同时存在三个问题。

第一，它不稳定。切换会话、工具或协作者后，隐含信息可能全部丢失。

第二，它不可治理。项目规则、临时假设和过期结论混在同一段历史中，很难判断哪一条仍然有效。

第三，它难以复核。后来接手的人看到“已经处理好了”，却不知道实际改了什么、运行了什么、还有什么没有验证。

会话可以承载讨论，但不能成为项目唯一的记忆系统。真正能支持连续交付的上下文，必须离开单次对话，形成有层次、有来源和可更新的信息结构。

## 三层上下文回答三个不同问题

前两篇已经分别建立了项目认知基线和任务契约。执行开始后，还需要加入实时工作状态。三者共同构成 AI 做出工程判断所需的最小上下文结构。

| 上下文层 | 回答的问题 | 典型内容 | 变化频率 |
| --- | --- | --- | --- |
| 项目基线 | 这个系统通常怎样工作 | 模块职责、依赖方向、数据边界、构建方式 | 较低 |
| 任务契约 | 这一次要完成什么 | 目标、事实、约束、验收、证据和授权 | 中等 |
| 执行状态 | 当前已经做到哪里 | diff、已运行命令、测试结果、阻塞项和下一步 | 很高 |

项目基线不能替代任务契约。知道“系统是多租户的”，并不能确定本次需求在无数据时返回空值还是错误。任务契约也不能替代执行状态。知道最终要做什么，并不能说明某个文件是否已经被修改、某项测试是否真实运行。

三层信息的责任不同，也应该存放在不同位置：稳定规则进入项目文档，任务事实进入任务卡或需求记录，实时状态进入工作区检查和阶段交接。把所有内容塞进一个长期提示词，会让过期细节污染规则；全部留在聊天里，又会让换会话等同于失忆。

## 高质量上下文不以数量衡量

我也尝试过一次性把目录、配置、日志和大量代码全部交给 AI。它确实能够复述更多内容，判断却没有明显变准。原因是信息数量增加了，决策所需的信号没有同步增强。

现在我用四个标准判断一条信息是否应该进入当前上下文：

| 质量标准 | 需要检查的问题 | 反例 |
| --- | --- | --- |
| 相关性 | 它是否会改变当前判断或行动？ | 排查接口权限时加载无关报表模块 |
| 权威性 | 它来自正式规则、实际代码还是个人猜测？ | 把一次聊天中的推测当成业务规范 |
| 时效性 | 它反映的是当前版本和工作区吗？ | 使用旧分支的调用链指导当前修改 |
| 可追溯性 | 能否找到文件、diff、日志或命令依据？ | 只记录“测试应该没问题” |

上下文缺失会导致猜测，过量上下文会稀释重点，过期上下文则更危险，因为它会让 AI 基于错误事实表现得非常确定。

所以，上下文工程不是不断扩大输入，而是围绕当前决策组织最小充分信息：少一项会增加关键歧义，多一项不会实质改善判断。

## 我怎样为一次决策装配上下文

上下文不是开工时准备一次就结束。随着代码、测试和用户指令变化，它需要持续刷新。我现在按照五个步骤装配和维护当前上下文。

### 第一步：先确定当前决策

不同决策需要不同证据。判断接口入口，需要项目路由规则和相似实现；判断数据为什么为空，需要调用链、查询条件和实际样本；判断能否交付，则需要完整 diff、测试结果和未验证风险。

如果连当前要做的判断都没有定义，加载再多文件也只会得到泛化分析。

### 第二步：读取项目基线和任务契约

项目基线提供不能违反的不变量，任务契约提供当前目标、验收和授权。AI 应只提取与本次决策有关的部分，而不是机械复述整份文档。

这一步保证当前行动既没有偏离系统边界，也没有把需求重新解释成另一个问题。

### 第三步：检查实时现场

执行状态不能依赖历史描述，必须重新读取工作区、相关文件、运行进程和测试结果。尤其在跨会话或多人协作时，当前文件内容、`git diff` 和真实命令输出通常比“上一轮应该已经完成”更可信。

检查现场的目的不是否定历史记录，而是确认历史是否仍与当前状态一致。

### 第四步：处理冲突和未知项

上下文之间出现冲突时，不能简单选择最方便的一条。例如任务文档要求修改接口，用户最新指令却是“先不要改”；交接记录说测试通过，当前代码已经再次变化；项目规则要求走公开 API，旧样例却仍在直接调用实现类。

不同信息控制不同维度：最新明确指令决定当前意图和授权，已确认需求决定目标，项目规则约束不变量，实时文件与命令证明现场状态。它们若无法同时成立，AI 应报告冲突并请求确认，而不是静默决定哪一条失效。

### 第五步：行动后更新执行状态

每完成一轮分析、修改或验证，都要更新已经确认的事实、实际变更、命令结果和剩余问题。否则上下文会在执行过程中迅速过期，下一步又重新建立在旧现场上。

这五步构成一个持续循环：

```text
定义当前决策 -> 读取稳定规则与任务 -> 核对实时现场
-> 处理冲突与未知 -> 行动并更新状态
```

## “继续”不是新任务，而是恢复执行状态

短指令本身并不必然模糊。“继续”“再验证一下”“按刚才的方案实现”之所以容易出错，是因为 AI 不知道上一阶段停在哪里，也不知道现场是否发生了变化。

一次可靠的恢复至少要回答：

```text
当前阶段：分析、方案、实现、验证还是交付
已确认：事实、业务规则和证据
已完成：修改文件、实际命令和结果
未完成：验证缺口、阻塞项和开放问题
现场状态：当前分支、未提交改动和外部依赖
下一步：在现有授权内可以执行的最小动作
```

如果当前阶段仍在等待方案确认，“继续”不能被解释成直接改代码；如果用户最新要求改为只读分析，旧计划中的写入步骤就必须停止。恢复上下文的本质，是先恢复任务状态，再决定动作，而不是根据最后一句话猜测工作阶段。

## 交接记录必须让下一位协作者能够复核

我以前使用过“核心功能已完成，只剩少量验证”这样的总结。它看似简洁，实际上几乎不能交接：什么叫核心功能，哪些验证没有做，当前代码能否构建，都需要下一位协作者重新调查。

现在，一份阶段交接至少包含四类可核验信息：

| 交接内容 | 应记录什么 |
| --- | --- |
| 结论与依据 | 已确认事实、仍属假设的判断及对应证据 |
| 改动与现场 | 修改文件、关键 diff、分支和未提交状态 |
| 验证与缺口 | 实际执行的命令、结果、失败项和未覆盖场景 |
| 下一步与权限 | 最小后续动作、阻塞条件和当前授权边界 |

好的交接不是把上一段会话压缩得更短，而是让一个不了解聊天历史的人，能够判断哪些结论可信、从哪里继续，以及哪些动作尚未获准。

我常用的恢复要求如下：

```text
先不要修改代码。请读取项目规则、任务契约、当前工作区和阶段交接记录，恢复当前上下文：

1. 区分已确认事实、推断和待确认项；
2. 核对已修改文件、当前 diff、实际测试结果和未完成工作；
3. 指出文档、历史记录与实时现场之间的冲突；
4. 说明当前阶段、授权边界和下一步最小动作。

所有结论附文件、diff、日志或命令依据。无法由当前现场证明的历史结论，不得直接当作事实。
```

## 上下文的价值，是让判断能够连续

AI 有时像熟悉项目的工程师，有时像刚入职的新人，很多时候不是模型能力发生了变化，而是它所处的信息状态不同。

第 1 篇的项目认知基线提供系统地图，第 2 篇的任务契约定义本次目标，第 3 篇的上下文治理则让这些信息在执行过程中保持相关、可信和最新。三者连接起来，AI 才能从一次回答走向连续协作。

但信息充分仍不等于可以任意行动。AI 知道应该做什么，只解决了判断问题；它是否有权修改文件、写入数据或操作外部系统，还需要另一套清晰的执行边界。
