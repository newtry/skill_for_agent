# 从 Markdown 到业务卡片：让 Agent 输出真正可用的结果

> 系列导航：[完整目录](00-series-titles.md)

Agent 的第一版通常返回一大段 Markdown。问答场景还可以接受，到了业务流程就会出现问题：用户找不到关键数字，状态和操作混在一起，按钮缺少参数，工具失败和正常结果长得一样，前端只能解析自然语言猜下一步。

我在业务 Agent 中逐渐把输出看成产品与系统之间的契约，而不是模型随手生成的文字。稳定输出是为了让事实可读、动作可控、状态可追踪，而不是为了让界面更漂亮。

## 核心判断：输出结构决定结果能否被消费

业务输出不是回答的排版层，而是连接模型、后端状态和前端操作的行为契约。它必须让用户知道系统确认了什么、还缺什么、当前处于什么状态，以及下一步是否允许动作；否则即使文字准确，也无法安全进入业务流程。

## 输出结构要对应用户下一步

查库存的结果应突出商品、可用数量、门店、账套和更新时间；订单查询应突出状态、金额、支付和可执行动作；调拨或退款应突出预览、确认要求、业务单号和当前状态。

我通常把卡片拆成：摘要、关键事实、数据范围、状态、来源、可执行动作和风险提示。不同状态使用不同结构，不能让空结果、权限不足、工具失败和成功推荐共用一张卡片。

## 自由文本为什么无法承载业务状态

早期调拨结果只有一段 Markdown：

```text
已为你处理 A 款调拨，共 20 件，请稍后查看。
```

这句话没有说明是已生成预览、已提交、待审批还是已经出库；前端也不知道是否展示“确认”“查看进度”或“重试”。当工具超时后，模型仍可能生成相似文案，用户无法区分真实受理和回答推测。

改成结构化卡片后，同一场景至少包含：

```json
{
  "type": "transfer_task",
  "status": "waiting_approval",
  "summary": "A 款调拨 20 件到人民路店",
  "scope": {"ledger": "当前账套", "source": "总仓", "target": "人民路店"},
  "businessRef": {"transferNo": "T***", "taskId": "task-***"},
  "actions": [{"type": "VIEW_PROGRESS", "enabled": true}],
  "traceId": "trace-***"
}
```

前端依据 `status` 和 `actions` 渲染，不能从 `summary` 猜测状态。模型可以生成摘要，但业务单号、状态和动作权限必须由后端提供。

## 系统事实和模型建议必须分开

```json
{
  "customer": {"id": "masked", "name": "已脱敏客户"},
  "product": {"code": "A", "availableQty": 18},
  "scope": {"ledger": "当前账套", "updatedAt": "查询时间"},
  "facts": [{"source": "inventory_query", "status": "confirmed"}],
  "recommendation": {"reason": "近期开单与库存匹配", "confidence": "advisory"},
  "action": {"type": "CREATE_DRAFT", "requiresConfirm": true}
}
```

其中商品数量、账套和更新时间应由工具或后端填充，模型只能生成建议性理由。用户需要知道哪些是系统事实，哪些是计算结果，哪些是模型建议。

推荐理由也不能伪装成系统事实。“建议补货”可以来自模型，“当前可售 18 件”必须来自受控查询，“已经创建草稿”必须来自业务接口。三类内容在 Schema 中分区，前端使用不同展示和动作规则，日志也分别记录来源。

## Schema 是行为契约，不是字段清单

卡片字段要有类型、必填规则、枚举、版本和兼容策略。金额不能使用含义不明的字符串，状态不能让模型临时发明枚举，动作不能只返回“可以退款”而缺少订单号、权限、金额和确认信息。

后端或输出适配层必须校验模型结果。字段缺失、类型错误、未知状态或动作参数不完整时，进入安全兜底或人工处理，不能直接当成业务命令。

输出适配层应执行三步：先验证后端事实和工具结果，再让模型补充允许生成的摘要或建议，最后进行 Schema 校验和字段安全过滤。校验失败时返回受控错误卡片，不能退回自由 Markdown 继续展示。

## 结构化输出要区分处理状态

我会为每类结果定义明确状态：

| 状态 | 用户应该看到什么 | 是否允许动作 |
| --- | --- | --- |
| confirmed | 事实、范围、时间和来源 | 按权限和状态允许 |
| empty | 查询范围和明确的无数据结果 | 通常不直接执行 |
| needs_clarification | 缺少什么参数或口径 | 等待补充 |
| forbidden | 权限不足或范围不允许 | 禁止 |
| failed | 工具或系统失败、追踪编号 | 视恢复流程而定 |
| pending | 已受理但尚未完成 | 只能查询状态或取消 |
| advisory | 模型建议和依据 | 必须确认后行动 |

这样前端可以按状态渲染，而不是根据文案猜测业务含义。

## 动作卡片必须能回到业务流程

动作输出应包含稳定业务键、对象、范围、参数摘要、确认要求、幂等信息和有效期。确认后提交的内容必须与预览一致，不能让前端从自然语言重新拼接请求。

卡片是业务流程的最后一层表现，不是绕过后端权限和状态机的快捷接口。

用户点击确认时，前端只提交后端签发的动作 ID、预览版本和确认令牌。服务端重新验证权限、有效期和业务状态。按钮是否可见只是体验控制，真正能否执行仍由后端决定。

## 空结果和错误结果要诚实

没有查到数据时，应返回查询范围、口径和更新时间，说明是确实为空还是工具未执行。工具超时不能伪装成空库存，权限拒绝不能伪装成没有记录，模型无法判断不能编造推荐。

## 输出需要版本和契约测试

卡片结构变化会影响前端、移动端、消息和历史记录。每次新增字段、改变枚举或修改动作参数，都应检查生产方、消费者、兼容窗口和旧版本处理。

契约测试要覆盖正常、空、禁止、失败、处理中、建议和非法结构，并验证未知字段和缺失字段的兼容策略。

我还会做生产者与消费者对照：哪个后端产生字段，哪些前端和消息渠道消费，字段何时必填，新旧版本怎样共存。新增 `pending` 状态却没有旧前端兜底，会让后端正确返回、用户界面却错误显示失败。

AI 可以从接口和前端类型中整理 Schema、生成状态样本并发现生产消费不一致；产品和业务负责人确认用户在每种状态下需要知道什么、允许做什么；后端与前端共同对事实字段和动作契约负责。输出能力完成的证据，是每个业务状态都有稳定结构，所有消费者通过契约测试，未知或非法结构会安全失败。

```text
请为【业务场景】设计结构化输出契约：

1. 定义摘要、事实、范围、状态、来源、更新时间和建议；
2. 区分 confirmed、empty、needs_clarification、forbidden、failed、pending 和 advisory；
3. 为动作定义对象、参数、权限、幂等键、确认内容和有效期；
4. 校验 JSON/schema、版本、未知字段和安全兜底；
5. 设计前端/消费者契约测试和事实、建议、错误的边界。
```

稳定输出让 Agent 接上真实产品和后端流程，但结构正确仍不代表行为可靠。下一篇将把每次请求拆成可回放记录，用评测验证路由、工具、权限、结果和状态是否共同成立。
