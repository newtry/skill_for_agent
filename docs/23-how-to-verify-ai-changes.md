# AI 修改了代码以后，我是如何验证它真的完成了需求的

> 系列导航：[完整目录](00-series-titles.md)

AI 说“已经完成”时，我现在不会先看它写了多少代码，而会追问：完成了哪条验收条件，证据来自哪里，还有什么没有验证？

一次用户资料接口修改中，AI 增加了字段，单元测试也通过了。继续验收后发现，测试只验证字段存在，没有验证门店归属、账套隔离和原有调用方兼容。实现并非完全错误，但“需求已完成”的结论缺少关键证据。

代码实现、测试绿色和需求完成是三个不同状态。验证的任务，是把它们逐一连接起来，并明确连接不上的部分。

## 先确认验证对象和基线

验证前先固定：当前分支、工作区 diff、目标版本、任务契约、方案版本和接手时的基线。否则测试结果可能来自另一份代码，或者把历史失败误判成当前改动造成。

我会先检查 diff：

- 修改是否只落在预期模块和文件；
- 是否混入无关配置、依赖、生成文件或其他任务；
- 接口是否位于正确的 Admin/App 入口；
- 跨模块是否仍通过公开契约；
- 数据库、配置、缓存和消息变化是否已经登记。

范围验证不是功能验证，但越界修改会让后面的功能结果失去可信归因。

## 再逐条回到追溯矩阵

第 18 篇建立的验收条件是验证主键。对每一条条件，我会要求 AI 给出实现位置、测试场景、实际命令和结果，而不是用一段总体总结代替。

| 验收条件 | 实现位置 | 测试/检查 | 实际证据 | 状态 |
| --- | --- | --- | --- | --- |
| 正常关联返回名称 | 查询与转换层 | 正常接口测试 | 响应和数据样本 | 已验证 |
| 无归属返回空 | 空值分支 | 空关联测试 | 测试未执行 | 未验证 |
| 跨账套隔离 | 查询条件与权限链 | 集成测试 | SQL 和结果对照 | 部分验证 |
| 旧调用方兼容 | 接口契约 | 回归测试 | 仅编译通过 | 证据不足 |

这一步能防止“字段已经出现”被误判为全部业务条件已经满足。

## 验证至少包含五个层面

| 验证层面 | 需要证明什么 |
| --- | --- |
| 范围 | 实际修改与任务授权一致 |
| 实现 | 方案和关键不变量在代码中有对应机制 |
| 自动化测试 | 关键场景真实执行，断言覆盖风险 |
| 业务与数据 | 响应、数据库、状态、流水和副作用符合预期 |
| 环境与兼容 | 配置、权限、迁移、外部依赖和旧调用方可工作 |

对于纯算法改动，后两层可以很轻；支付、积分、权限和数据库迁移则不能用单元测试替代数据、环境和对账验证。

## “测试通过”必须有执行证据

报告至少要记录：

```text
实际命令、执行目录和代码版本
使用的模块、Profile 和外部环境
测试发现数，以及通过、失败、跳过数量
关键接口、SQL、日志或数据检查结果
测试替身替代的真实依赖
失败、环境阻塞和未覆盖项
```

Maven Profile 跳过测试、测试类没有被匹配、容器未启动、外部服务不可用，都不能写成“测试通过”。没有执行的检查属于未验证，不属于失败，也不属于成功。

## 数据和状态类功能要验最终结果

过程信号不能代替业务结果：接口 200 不代表数据正确，方法不抛异常不代表事务提交，第二次回调返回“已处理”不代表流水唯一，任务显示成功不代表副作用已完成。

我会根据功能类型增加最终状态检查：

- 查询：行粒度、租户、账套、权限、缓存和时间口径；
- 批量导入：主表、明细、关联、错误报告和批次状态；
- 支付积分：余额、冻结、流水、订单、渠道结果和对账；
- 定时任务：业务键、任务状态、重试、补偿和外部事件；
- 发布变更：数据库版本、配置、日志、监控和回退条件。

## 环境不能验证时要如实分类

有些验证依赖真实数据库、第三方回调、生产配置、网络白名单或人工审批。无法执行时，应写明阻塞原因、替代证据、剩余风险和需要谁确认。

我通常使用五种状态：

```text
已验证：有真实命令、数据或运行证据
失败：实际执行且结果不符合预期
未执行：尚未运行，不能推断结果
环境阻塞：具备条件前无法执行
待人工确认：需要业务、DBA、运维或发布负责人判断
```

这种分类比简单的通过/失败更诚实，也更方便决定下一步。

## 验证需要对照和反例

仅在正确数据上运行测试，很难证明边界成立。验证应尽量包含只改变一个关键条件的对照组：跨账套、无权限、空关联、重复请求、最后合法值、超时和历史版本。

如果删除账套条件后测试仍然绿色，测试没有保护隔离规则；如果把唯一约束去掉后重复回调测试仍然绿色，测试没有保护幂等结果。有效验证应当能够识别错误实现。

## 完成报告要让别人能够复核

```text
请生成【任务】的验证报告：

1. 说明目标、版本、分支、工作区和实际修改范围；
2. 逐条列出验收条件、实现位置、测试/检查和证据；
3. 报告真实执行的命令、通过、失败、跳过和环境依赖；
4. 核对数据、权限、事务、状态、幂等、兼容和配置结果；
5. 区分已验证、失败、未执行、环境阻塞和待人工确认；
6. 列出未完成项、残余风险、回滚条件和下一步动作。

不要用“代码已修改”或“测试通过”替代逐条证据。
```

验证完成后，工程师还需要判断证据是否足以接受风险。AI 可以整理和执行检查，不能自行把证据不足升级为完成声明。
