# 接口正确不等于数据正确：一次账套维度聚合问题的启示

> 系列导航：[完整目录](00-series-titles.md)

最难发现的数据错误，通常不是接口报错，而是接口稳定返回了一个看起来合理的数字。

一次库存聚合中，接口状态码正常，SQL 可以执行，单账套测试结果也完全正确。直到两个账套出现相同 SKU，汇总结果才突然变大。查询按 SKU 分组，却没有把账套放进结果粒度；不同经营边界中的库存被合并成了同一条记录。

代码没有失败，数据库没有异常，测试甚至是绿色的。错误发生在更早的位置：团队没有先定义这个数字究竟代表哪个业务集合。

这次问题让我明确，数据正确性不能由接口成功和公式正确共同推出。它还取决于结果粒度、维度约束、关联基数、时间口径和整条数据血缘是否保持一致。

## 数据契约要先于 SQL

在修改查询之前，我会先写一份数据契约：

```text
业务问题：这个指标要支持什么判断
结果粒度：一行代表哪个业务对象
唯一维度：哪些字段共同区分一行
度量定义：数量、金额或比例怎样计算
过滤口径：租户、权限、状态和逻辑删除怎样生效
时间口径：统计时点、区间、时区和完整性要求
```

以库存为例，“SKU 总库存”“某账套某门店的物理库存”和“指定时点扣除预占后的可售库存”是三个不同指标。只有先选择其中一个，才能判断 `GROUP BY`、关联和过滤是否正确。

SQL 是数据契约的一种实现。契约没有确定时，AI 生成得越快，只会越快得到一条语法正确但口径不明的查询。

## 粒度决定哪些维度不能丢

如果目标结果是“某租户、某账套、某门店下每个 SKU 的可售库存”，那么租户、账套、门店和 SKU 都是结果身份的一部分。

这些维度不仅要出现在入口参数中，还要贯穿：

- 明细查询和关联条件；
- 聚合分组和窗口计算；
- 缓存键与缓存失效范围；
- 分页、排序和去重；
- 离线计算与同步任务；
- 导出、报表和下游接口。

只在 Controller 接收 `ledgerId`，内部聚合时却不使用，等于把数据隔离停留在接口表面。缓存键漏掉账套，则会让 SQL 正确的结果在缓存层再次串用。

因此，检查数据问题不能只搜索一条 SQL，还要沿数据从产生、加工、存储到消费的完整路径追踪维度是否保持。

## 关联基数会悄悄改变总数

遗漏分组维度会把不同对象错误合并，错误关联则会把同一对象重复展开。

例如一个商品关联多个条码、一家门店关联多条有效关系，明细表与关系表直接连接后，库存数量可能被重复多次。SQL 仍然能够执行，结果甚至可能在小样本中看不出问题。

每个连接都需要声明基数：一对一、一对多还是多对多。若业务结果仍需保持原粒度，就要明确使用预聚合、唯一关系、半连接或其他方式防止行数膨胀，而不是在最后盲目 `DISTINCT`。

`DISTINCT` 可以消除完全相同的行，却不能修复被重复累加的金额和数量。

## 时间也是结果身份的一部分

后来分析经营指标时，我又遇到相似问题：环比公式没有错，当前值和对照值也都有数据，但“上一周期”定义错了。

自然月、最近三十天和与当前区间等长的前一周期，会得到不同答案；时区、闭区间与开区间、当天数据是否完整，也会继续改变结果。缺少历史数据时返回空值、零还是“不适用”，同样属于业务语义。

时间口径至少要说明：

| 时间要素 | 需要确定的问题 |
| --- | --- |
| 区间生成 | 自然周期、滚动窗口还是等长前序区间 |
| 边界规则 | 起止时间是否包含，是否存在重叠 |
| 时区 | 按用户、门店还是系统时区解释 |
| 数据完整性 | 当天或当前周期是否已经闭合 |
| 缺失语义 | 无历史数据时返回空、零还是不可比较 |

验证时不能只输出最终百分比，还要同时展示当前区间、对照区间、原始分子和分母。账套遗漏与时间区间错误具有同一根因：计算过程正确，但参与计算的集合错误。

## 测试数据必须主动制造碰撞

单租户、单账套、单门店、唯一 SKU 的“干净数据”只能证明主路径可执行。要验证维度是否完整，测试必须故意让不同业务对象在非关键字段上看起来相同：

| 对照场景 | 要暴露的问题 |
| --- | --- |
| 同 SKU、不同账套 | 账套是否参与过滤、分组和缓存 |
| 同账套、不同门店 | 门店范围是否被错误合并 |
| 一条库存、多条关联 | 连接是否导致数量重复 |
| 相同编码、不同租户 | 租户隔离是否贯穿数据链路 |
| 有效与失效状态并存 | 状态和逻辑删除是否正确 |
| 时间边界前后各一条 | 区间、时区和边界是否准确 |
| 无权限用户拥有同类数据 | 权限是否只影响展示还是源查询 |

这种测试不是为了增加样本数量，而是用最少数据让错误维度发生碰撞。只有错误实现会得到与正确实现不同的结果，测试才真正具备辨识力。

## 数据血缘决定问题要查到哪里

很多指标并不是接口实时查询得到，而是经过离线计算、中间表、缓存、消息同步和再次聚合。最后一层接口即使逻辑正确，也可能读取到上游已经丢失维度的数据。

我会让 AI 画出数据血缘：原始事实从哪里产生，经过哪些过滤、连接、聚合和写回，在哪一层改变粒度，最终由谁消费。每个节点记录输入粒度、输出粒度、关键维度和刷新策略。

如果中间汇总表只按 SKU 保存，后续接口无法重新恢复账套维度。修复就不能停在 Controller 或最终 SQL，而要回到第一次发生不可逆聚合的位置，并评估历史数据重算。

## 正确性需要查询证据和业务对账

```text
请只读分析【指标或查询】的数据正确性：

1. 定义业务问题、结果粒度、唯一维度、度量公式和过滤口径；
2. 声明每个表关联的基数及其对结果行数的影响；
3. 检查租户、账套、门店、状态和时间维度是否贯穿查询、缓存、离线计算与同步；
4. 追踪从原始事实到最终接口的数据血缘，定位首次丢失粒度的位置；
5. 设计跨维度碰撞、重复关联、时间边界、空数据和无权限对照样本；
6. 输出 SQL、样本、分子分母、行数变化和未确认业务口径。
```

AI 擅长沿代码和 SQL 搜索遗漏维度，生成对照数据并比较中间结果。业务负责人必须确认指标含义，数据负责人则需要确认源数据和血缘是否可靠。

## 数据正确性是对业务集合的承诺

接口正确回答“系统是否成功返回”，数据正确回答“返回的究竟是不是用户所问的那个集合”。后者需要粒度、维度、基数、时间和血缘共同成立。

第 9 篇定义 ERP 业务事实受哪些边界约束，第 10 篇把这些边界落实为数据契约。业务含义和数据集合明确之后，下一步才是面对会产生真实价值转移的状态流程。支付将首先展示：当内部订单、外部渠道和异步消息同时存在时，系统怎样保持状态与资金一致。
