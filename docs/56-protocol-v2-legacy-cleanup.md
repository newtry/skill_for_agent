# 协议升级最难的不是切到 V2，而是安全删除旧链路

> 系列导航：[完整目录](00-series-titles.md)

一次 Agent 协议升级中，新版后端已经能够返回 V2 结构，Java 调用方完成联调，前端也展示了新卡片。九个核心场景全部走通，局部和完整回归都有大量用例通过。

如果把“V2 可用”当成完成，这次迁移已经可以结束。但继续跨仓库审计后，仍能找到旧字段、旧事件名、兼容转换和只服务 V1 的测试夹具。部分 Java 请求还在发送旧值，只是后端兜底把它转换成新字段；前端某个旧状态分支也仍能被触发。

新链路确实成功了，系统却没有完成迁移。它只是进入了一个新旧协议都能工作的双轨状态。

## 核心判断：协议迁移完成的标志是旧链路可证明退出

协议升级至少包含两个独立目标：证明新链路在正常、失败和回滚场景下工作；证明旧链路没有真实消费者、没有运行流量，也不再承担兼容和恢复责任。

```text
新链路证据：V2 定义正确、生产消费接通、关键场景通过
旧链路证据：V1 使用归零、历史任务可处理、兼容可以删除
```

只具备第一组证据，说明新版本可以进入迁移；两组证据同时成立，才说明迁移可以关闭。

## 双轨兼容会制造隐性语义债

兼容本身不是问题，没有优先级和退出条件的兼容才是问题。

例如一个字符串字段在 V1 表示本地配置编码，在 V2 表示模型标识。为了让旧调用方继续工作，后端可能同时接收两个字段并互相回填。此时系统里会出现三种行为：新调用方发送新语义，旧调用方发送旧语义，中间层根据字段是否为空进行猜测。

编译器看不出差异，因为类型都还是字符串；正常路径测试也可能通过，因为每条分支都能构造出结果。真正丢失的是唯一语义来源。后来的 AI 搜索到两套实现，还可能继续复制兼容分支。

因此，每个兼容机制都要写清：服务哪个消费者、读取优先级是什么、冲突时怎样处理、记录什么观测、何时删除以及由谁负责。

## 先建立生产者与消费者矩阵

协议不会只存在于一个 DTO。它可能贯穿 HTTP、消息、缓存、数据库 JSON、前端类型、任务快照、测试夹具和文档示例。

迁移前我会建立矩阵：

| 链路 | 生产者 | 消费者 | 当前版本 | 迁移动作 | 回滚责任 |
| --- | --- | --- | --- | --- | --- |
| 请求协议 | Java 服务 | Agent 后端 | V1/V2 | 调用方先切换 | 后端短期双读 |
| 任务事件 | Agent 后端 | 异步执行器 | V2 | 同版本部署或兼容 | 保留在途任务解释器 |
| 结果协议 | Agent 后端 | Web 前端 | V1/V2 | 前端先兼容新字段 | 新后端短期双写 |
| 历史快照 | 任务存储 | 恢复流程 | V1 | 迁移或版本化读取 | 不改写原始事实 |

矩阵的价值是暴露部署顺序。不能只说“前后端一起发”，还要知道灰度期间哪些新旧组合真实存在，以及每种组合是否安全。

## 把迁移拆成引入、切换、观测和清理

### 引入：先固定 V2 语义

定义新字段、状态、错误和版本边界，说明 V1 与 V2 是可转换还是语义变化。语义变化不能用简单字段复制伪装成兼容。

这一阶段要补契约测试和序列化样本，但不立即要求所有调用方切换。回滚通常是关闭 V2 入口或功能开关。

### 切换：按生产消费顺序迁移

根据矩阵逐个切换后端、Java、前端、异步任务和文档。短期双读或双写必须定义唯一优先级；新旧字段同时出现且冲突时，应拒绝或记录明确错误，不能静默选择。

每迁移一个消费者，都记录版本和验证证据。所谓“代码已改”不能替代真实接线，尤其要检查运行配置、依赖版本和部署产物。

### 观测：证明没有遗漏调用方

全局搜索只能找到静态引用，找不到动态序列化、字符串拼接、外部仓库和未部署分支。进入观测期后，需要对 V1 请求、旧事件、兼容分支命中和转换冲突建立指标。

观测窗口要覆盖真实低频周期，并区分旧在途任务与新请求。旧流量不为零时，应定位调用方，而不是直接延长一个没有期限的兼容期。

### 清理：删除全部旧责任

清理对象不仅是字段，还包括路由、转换器、配置键、监控、文档、示例、测试夹具和只为 V1 保留的依赖。删除后重新运行跨端契约、核心业务、失败恢复和回滚组合。

清理提交应保持聚焦，使回归能明确回答：系统不再依赖 V1，而不是恰好没有执行到旧分支。

## 搜索不到旧字段仍然不等于完成

遗留审计至少要结合四类证据：

```text
静态证据：字段、事件、配置、别名和示例引用清零
构建证据：所有生产者和消费者使用目标契约构建
运行证据：观测窗口内旧流量和兼容命中符合退出阈值
场景证据：新链路、失败、在途任务、灰度和回滚组合通过
```

还要检查序列化框架的别名、反射注册、数据库历史 JSON 和消息重放。静态搜索是高效起点，不是最终结论。

## 回滚不能让已经产生的数据失去解释

协议回滚不是把代码切回旧版本那么简单。新版本可能已经创建 V2 任务、写入新状态或向下游发送新事件。旧实例能否读取这些数据，决定了回滚是否真的可用。

常见策略包括：在迁移窗口内保持向后可读；为持久化记录保存协议版本；把不可逆变更推迟到旧版本完全退出之后；或者在回滚时停止接收新任务，只处理已经确认兼容的范围。

如果 V2 数据无法被 V1 解释，方案必须明确前滚修复、人工接管和在途任务处理，不能用一条“回滚部署”掩盖数据语义不可逆。

## “暂时兼容”必须是一项有期限的任务

兼容分支需要责任人、调用方清单、观测指标、退出阈值、最晚时间和删除验证。任何条件缺失，都意味着迁移债务没有进入治理系统。

AI 可以跨仓库搜索旧协议、生成矩阵、比较契约、构造组合测试和追踪兼容命中；工程师确认动态依赖和部署顺序；业务与架构负责人决定语义变化；发布负责人批准观测窗口、清理与回滚。

删除旧链路属于真实变更，不能因为 AI 报告“零引用”就自动执行。先审计证据，再在受控任务和发布窗口中清理。

```text
请审计【V1 -> V2 协议迁移】：

1. 列出请求、事件、存储、结果和历史任务的生产者消费者矩阵；
2. 区分字段兼容与语义变化，明确双读双写优先级和冲突处理；
3. 按引入、切换、观测和清理列出阶段门禁与回滚点；
4. 搜索字段、别名、动态注册、配置、示例、测试和外部消费者；
5. 验证新链路、在途任务、灰度组合、失败恢复和回滚；
6. 为每个兼容分支写明责任人、观测、退出阈值和删除证据。

不把 V2 场景通过当成迁移完成，不在缺少运行观测时自动删除旧链路。
```

协议迁移解决的是系统内部语义怎样持续统一。下一篇把视角继续向外推进：即使技术任务和协议都完成了，怎样证明 Agent 的结果真的到达用户，并与后续业务事实建立可信联系。
