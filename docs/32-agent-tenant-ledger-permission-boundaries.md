# 租户、账套与权限：业务 Agent 必须守住的数据边界

> 系列导航：[完整目录](00-series-titles.md)

普通聊天 Agent 说错一句话，影响可能只是体验；ERP Agent 查错一个账套，影响的可能是库存、销售额和经营判断。因此在业务 Agent 里，租户、账套和权限不能作为提示词中的背景信息，而必须成为每次请求的运行时约束。

## 单账套测试为什么发现不了越权

一次库存场景在开发样本中始终正确，因为测试租户只有一个账套。加入第二个账套后，同一个 SKU 的数量被工具层合并，模型虽然没有展示账套字段，却返回了跨账套总数。最终文本里没有明显敏感信息，数据边界已经被破坏。

修复后，权限测试同时检查五个位置：身份上下文、工具参数、查询过滤、缓存键和输出范围。只要其中一层缺少账套，测试都应失败。这个案例也说明，越权评测不能只看回答中是否出现其他租户名称，还要核对数值来源。

## 自然语言不会自动带来权限

用户说“查一下我的库存”，系统仍然需要知道“我”是谁、属于哪个租户、可访问哪些账套、哪些门店和哪些仓库。模型可以帮助补全用户意图，但不能决定授权范围。

权限应在服务端和工具层校验，查询条件、聚合维度、缓存键和导出范围都要带上隔离上下文。不能只在回答前过滤，因为越权数据可能已经进入模型上下文或日志。

## 账套边界尤其容易被 Agent 隐藏

用户问“这个款还有多少”，模型可能倾向于给出一个总数；但业务系统里的库存也许必须按账套、门店和仓库分别展示。Agent 应先澄清缺失维度，或使用明确的默认上下文，并把查询口径显示给用户。

这也是结构化卡片和受控工具的重要原因：结果中要展示数据范围、账套、门店、时间和更新时间，而不是只返回一个数字。

## 写操作需要更高门槛

查询权限不足时返回受控提示即可；调拨、退款、积分扣减和批量导出则需要更严格的角色、业务状态、审批和幂等校验。模型不能通过改写自然语言参数绕过这些规则。

## 用隔离场景做评测

```text
同一用户跨租户查询
有权限账套与无权限账套
默认门店与显式指定门店冲突
跨账套聚合请求
无账套上下文的模糊查询
拥有查询权但没有写操作权
```

每个场景要检查实际工具参数、数据库过滤、缓存 key、输出字段和审计记录。只测试最终回答是否“看起来没有泄露”远远不够。

业务 Agent 的智能应该建立在权限边界之内。租户、账套和角色不是给模型看的提示，而是系统在每一步都要强制执行的约束。只有这样，Agent 才能进入真实 ERP，而不会把自然语言的便利变成数据隔离的漏洞。
