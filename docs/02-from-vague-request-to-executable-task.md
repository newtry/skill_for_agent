# 从“帮我看一下”到可执行任务：如何向 AI 描述真实需求

> 系列导航：[完整目录](00-series-titles.md)

“帮我把用户资料接口补上门店名称。”

这是一个听起来足够具体的需求：有接口、有字段，也有预期动作。AI 很快在返回对象中增加了 `storeName`，补齐转换代码，项目顺利通过编译。但接口实际返回时，这个字段仍然没有正确值。

继续排查后才发现，需求真正要解决的不是“返回对象少一个字段”，而是“移动端用户看不到自己所属门店”。门店信息来自另一个业务模块，关联关系受租户和账套约束；没有门店归属时应该返回空值，原有调用方还必须保持兼容。

“补一个字段”描述的是我当时设想的动作，“用户能够看到正确的门店名称”才是需要交付的结果。两者之间，隔着数据来源、业务语义、系统边界和验收条件。

这次返工让我明确了一件事：交给 AI 的不能只是一条自然语言指令，而应该是一份可执行的任务契约。它不替代产品需求和技术方案，而是把两者之间最容易被猜测的部分显式化。

## 先区分需求、任务和方案

真实开发中，这三个概念经常混在一句话里：

| 层次 | 核心问题 | 门店名称案例 |
| --- | --- | --- |
| 需求 | 为什么要改变，用户应得到什么结果 | 移动端用户需要看到所属门店名称 |
| 任务 | 本次交付做到哪里，受什么约束，怎样算完成 | 调整资料接口，覆盖无归属、租户隔离和兼容场景 |
| 方案 | 代码具体怎样实现 | 复用跨模块 API、调整服务编排或补充转换逻辑 |

如果把方案直接当成任务，例如“在 Mapper 中增加一条左连接”，AI 只需要证明 SQL 写完了，却不需要证明用户目标已经实现。如果只给出需求，例如“用户要看到门店名称”，AI 又不得不自行决定改动范围、空值语义和验证标准。

任务契约位于二者之间：它固定业务结果、工程边界和完成证据，同时给实现保留合理的选择空间。

## 模糊请求会把关键决策交给 AI

“帮我看一下”“优化一下”“把字段补上”并不只是信息少。更大的问题是，它们把本应由工程师或业务负责人确认的决策隐式交给了模型。

以“帮我看一下这个功能还有什么问题”为例，至少有五件事没有定义：

| 未定义项 | AI 不得不猜测的内容 | 可能造成的偏差 |
| --- | --- | --- |
| 工作目标 | 排查、评审、修复还是发布检查 | 输出很多建议，却没有解决当前问题 |
| 业务口径 | 什么行为才是正确结果 | 代码符合常识，却不符合真实规则 |
| 改动范围 | 可以查看和修改哪些模块 | 为了局部方便扩大依赖或顺带重构 |
| 完成标准 | 编译、测试还是业务验收通过 | 在证据不足时宣布完成 |
| 行动权限 | 只读分析还是可以写入和发布 | 分析请求被理解成直接修改 |

AI 擅长在已有约束中搜索和实现，但它不应该替人决定未定义的业务规则，也不能自行扩大授权。任务描述越模糊，模型看似拥有的“自主性”越大，结果实际上越不可控。

## 一份任务契约需要六类信息

我现在会用六类信息把需求收敛成任务。它们不是固定格式，而是一次工程交接必须回答的六个问题。

### 第一，目标：定义可观察的目标状态

目标应该描述完成后用户或系统能够观察到什么，而不是先规定修改哪个类。

```text
移动端用户资料接口返回当前用户所属门店名称；
没有有效门店归属时返回空值，不改变既有接口路径、字段和状态码语义。
```

这样的目标既能被验证，也没有提前锁死查询方式。相比“给 VO 增加 `storeName`”，它把注意力从代码动作拉回了业务结果。

### 第二，事实：分开已知现象与待验证假设

任务中的“当前情况”必须有证据。接口响应、请求参数、日志、数据样本和版本属于事实；“可能是转换层漏字段”只是根因假设。

```text
已确认：目标接口响应中没有门店名称；用户存在有效门店归属记录。
待验证：字段可能在跨模块查询或对象转换过程中丢失。
```

这一区分可以避免 AI 把提问者的初步判断直接当成结论。事实决定从哪里开始，假设只决定优先查什么。

### 第三，约束：说明不能被破坏的规则

约束既包括第 1 篇建立的项目不变量，也包括本次需求特有的业务边界。例如：

- 只能返回当前租户、当前账套下的门店；
- 跨模块数据通过现有 API 获取，不直接依赖 Biz 实现；
- 不修改原有接口路径、鉴权方式和既有字段语义；
- 不执行数据库写入，不调整无关模块。

目标告诉 AI 要去哪里，约束说明哪些路径不能走。缺少约束的正确结果，可能由一个破坏架构或扩大风险的实现得到。

### 第四，验收：把“完成”展开成场景

验收不能只重复目标，也不能只写“测试通过”。它需要覆盖正常、空值、边界、权限和回归场景。

| 场景 | 输入或前置条件 | 预期结果 |
| --- | --- | --- |
| 正常归属 | 用户在当前账套关联有效门店 | 返回对应门店名称 |
| 无门店归属 | 用户没有有效关联 | 字段为空，不抛异常 |
| 租户隔离 | 其他租户存在同类关联数据 | 不得读取其他租户门店 |
| 账套隔离 | 同一用户在不同账套关系不同 | 仅返回当前账套结果 |
| 兼容回归 | 既有调用方请求原接口 | 路径、状态码和原字段行为不变 |

场景化验收迫使任务在编码前暴露业务分歧。例如“无门店归属时为空还是报错”如果没有确定，就不是实现细节，而是尚未完成的需求决策。

### 第五，证据：规定交付时必须提供什么

验收描述期望行为，证据说明如何证明它发生过。一次完整交付至少应包括：实际修改的文件和原因、执行过的构建或测试命令、各验收场景的结果，以及未能验证的部分。

如果环境不具备集成测试条件，AI 应明确报告验证缺口，而不是用“代码逻辑看起来正确”代替结果。证据要求把完成判定从模型自述变成可复核事实。

### 第六，授权：明确当前允许推进到哪一步

同一项任务可以处于不同授权阶段：只读分析、输出方案、实施修改、运行验证、提交代码或执行发布。前一个阶段获准，不代表后续阶段自动获准。

对于支付、积分、权限、数据库迁移等高风险任务，我通常只先授权分析和方案；业务口径确认后再允许实施。规则明确、影响局部的任务可以直接实施，但提交、推送、数据库写入和发布仍需要单独授权。

授权不是任务末尾的一句安全提醒，而是任务契约的一部分。它定义 AI 此刻能够改变什么状态。

## 完整任务卡不是更长的提示词

把六类信息合在一起，我使用的任务卡大致如下：

```text
【目标】用户或系统最终可观察到的变化
【事实】已确认现象、数据、日志和版本；待验证假设单独列出
【约束】业务规则、项目不变量、改动范围和禁止事项
【验收】正常、异常、边界、权限、幂等与回归场景
【证据】必须执行的命令、测试以及最终交付说明
【授权】当前允许分析、实施、验证或交付到哪一步
```

任务卡的价值不在于格式统一，也不在于让提示词显得专业。它真正建立了三条边界：业务结果由人确认，工程空间允许 AI 探索，完成状态由证据判断。

因此，任务写得清楚并不会把 AI 变成机械执行器。恰恰相反，固定目标、约束和验收后，AI 才能安全地比较多种实现：复用已有查询、调整服务编排，还是补充转换逻辑。被限制的是错误方向，不是合理的技术选择。

## 进入实现前，我会检查四个问题

一份任务只有通过下面四项检查，才称得上可执行：

1. 目标是否描述业务结果，而不是未经验证的实现动作？
2. 事实、假设和待确认业务规则是否已经分开？
3. 约束、验收与授权是否足以阻止 AI 擅自扩大决策？
4. 完成后是否能够用测试、日志、数据或 diff 提供证据？

任何一项回答不清，都应先补充信息，而不是让 AI 用概率最高的答案填空。

第 1 篇建立项目认知基线，回答“这个系统允许怎样改变”；任务契约进一步回答“这一次究竟要改变什么，以及怎样才算完成”。但即使任务定义完整，执行仍可能跨越多个文件、命令和会话。下一步要解决的问题是：怎样让 AI 在整个过程中持续获得相关、可信且最新的上下文。
