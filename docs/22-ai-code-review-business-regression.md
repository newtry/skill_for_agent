# 代码审查不只是找语法错误：如何让 AI 检查业务回归风险

> 系列导航：[完整目录](00-series-titles.md)

让 AI 做代码审查，最容易得到的是一份代码质量清单：命名、空指针、重复逻辑、异常处理和性能建议。它们有价值，却不是 ERP 项目中代价最高的风险。

一次修改可以编译成功、测试通过，也没有明显代码异味，却悄悄改变租户过滤、账套聚合、积分批次顺序、接口兼容或历史数据的时间语义。技术实现仍然合理，系统原来向用户承诺的行为已经发生变化。

业务代码审查的核心不是“这段代码写得好吗”，而是“这次 diff 改变了什么行为，哪些改变有需求依据，哪些不变量可能被破坏”。

## 先把 diff 翻译成行为变化

逐行解释代码会让审查停留在实现细节。我会先要求 AI 总结：

```text
新增、删除或改变了哪些入口
哪些角色、租户和数据范围受到影响
哪些状态迁移、事务和副作用发生变化
读写了哪些表、缓存、消息和外部系统
接口、配置、任务和部署行为是否变化
```

行为摘要应与第 18 篇的验收条件和第 19 篇的方案决策对照。没有需求或方案依据的行为变化，需要解释来源；承诺存在但 diff 中找不到对应机制，则是实现缺口。

## 第一层：检查修改范围和依赖边界

审查先确认改动是否落在预期模块，是否包含无关格式化、配置、生成文件或依赖升级；Admin/App 入口是否正确，跨模块是否仍通过公开契约，是否覆盖了历史工作区中的其他任务。

范围越界不一定立即造成功能错误，却会扩大回归半径、增加评审难度，并让后续问题无法准确归因。

## 第二层：检查业务不变量

我会按四类不变量展开：

| 类别 | 典型风险 |
| --- | --- |
| 范围与权限 | 租户、账套、门店、权限或逻辑删除被漏掉或绕过 |
| 状态与一致性 | 成功、失败、重试、取消和补偿不闭环，多表只更新一部分 |
| 幂等与并发 | 重复回调、并发请求和任务接管产生重复效果 |
| 兼容与语义 | 接口、字段、默认值、错误码或时间含义发生非预期变化 |

每个发现要说明触发场景、影响对象、代码证据和缺失测试，不能只写“可能有问题”。

## 第三层：沿影响面搜索所有消费者

修改一个 DTO 字段可能影响 Java 调用方、前端类型、缓存序列化和历史消息；改变数据库查询可能影响报表、导出和离线任务；调整状态枚举可能破坏定时补偿。

AI 的优势是能够从 diff 中的字段、接口和事件向外搜索所有读写方。但搜索结果仍要区分真实调用、测试、废弃代码和兼容窗口，不能因为出现同名字符串就判定受影响。

审查范围应覆盖代码、测试、配置、迁移、监控和文档，而不只限于当前提交文件。

## “实时查询更准确”也可能是业务回归

一次审查中，AI 看到记录里保存了商品和客户冗余信息，建议删除快照，展示时实时查询主数据。代码更简洁，数据也始终最新，但业务语义已经改变：历史推荐原本需要保留生成当时的商品名称、价格和客户特征。

反过来，如果业务展示的是当前可售库存，继续读取任务创建时的快照同样错误。

快照与实时查询不是单纯性能选择，而是“记录当时事实”与“读取当前状态”的业务选择。审查需要为字段说明时间语义、更新来源和追溯要求，并设计“生成后修改主数据”的对照测试。

很多回归不是数值算错，而是数值代表的时间、范围或所有者变了。

## 第四层：审查失败路径和可观察性

正常流程代码通常最完整，异常路径更容易遗漏。审查要逐项检查超时、部分成功、重试、进程中断、补偿失败和人工处理。

同时确认关键状态变化是否有日志、指标、追踪和审计依据，敏感字段是否脱敏。一个无法观察的恢复流程，即使代码存在，也难以在生产中证明它工作正常。

## 第五层：检查测试是否保护了变化

新增测试不等于新增行为被保护。审查者要确认测试会在实现犯错时失败：漏掉账套是否能被样本发现，重复回调是否检查流水数量，事务失败是否检查最终数据，兼容测试是否真的走旧调用方。

如果测试只复述当前方法调用和返回值，仍然可能与实现共享同一错误假设。

## 审查发现需要严重程度和证据

我会将发现分为：

| 级别 | 含义 |
| --- | --- |
| 阻塞 | 会导致数据、安全、资金、核心业务错误或无法完成当前验收 |
| 需要确认 | 行为变化可能合理，但缺少业务或方案依据 |
| 建议 | 不影响当前正确性，可改善维护性、性能或表达 |

每条发现附文件位置、触发条件、业务影响和建议验证。审查目标不是列出最多问题，而是让决策者知道哪些风险阻止交付。

```text
请基于任务契约、追溯矩阵和技术方案审查当前 diff：

1. 先总结行为变化、受影响入口、角色、模块、数据和外部系统；
2. 检查改动范围、依赖方向和历史工作区边界；
3. 检查权限、租户、账套、状态、事务、幂等、并发和兼容不变量；
4. 搜索接口、字段、缓存、消息、任务和配置的所有消费者；
5. 检查快照/实时、状态和时间语义是否被意外改变；
6. 审查异常、补偿、可观测性和敏感信息；
7. 判断测试能否识别错误实现；
8. 将发现分为阻塞、需要确认和建议，并附触发场景与证据。
```
