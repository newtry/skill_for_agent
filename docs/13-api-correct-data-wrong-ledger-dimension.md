# 接口正确不等于数据正确：一次账套维度聚合问题的启示

接口返回 200，字段齐全，测试也绿了，但财务人员说数字不对。这是数据类需求里最棘手的一种失败：技术链路没有明显异常，错误藏在“这一行数据到底代表什么”的业务口径里。

一次库存聚合中，我们按 SKU 汇总数量，结果与单账套样本完全一致。后来才发现，同一个 SKU 在不同账套下本不应合并；查询缺失了 `ledger_id` 这个隔离维度。接口没有坏，SQL 也没有报错，但数据已经跨了核算边界。

## 先写数据粒度，再让 AI 写 SQL

我现在会让 AI 在方案第一行写清楚：一行结果代表什么对象，唯一标识是什么，哪些维度必须分组，哪些只是筛选条件。例如“某账套、某门店、某仓库、某 SKU 的可用库存”与“某 SKU 的总库存”是两个完全不同的指标。

有了粒度，AI 才能检查 `GROUP BY`、关联条件、缓存键和分页条件是否一致。没有粒度，它通常只会按字段名猜测，最危险的是还能生成一条语法正确的 SQL。

## 三种常被遗漏的数据边界

第一是隔离边界，例如租户、账套、组织和门店。它们不能仅依赖前端传参，服务端查询、聚合和缓存都要带上。

第二是时间边界。库存、余额和价格可能要按日、批次或有效期计算；把不同日期的数据简单相加，常会制造一个“看上去合理”的总数。

第三是状态边界。已删除、已取消、冻结中、未确认的数据是否参与统计，必须由业务规则决定。AI 需要搜索逻辑删除、状态过滤和历史数据处理的位置，而不是只看主查询。

## 验证必须有对照组

数据问题不能只用一组正常样本验证。我会准备至少四类：不同账套同 SKU、同账套不同门店、无关联或历史数据、无权限用户。然后比较行数、聚合值和可见范围。

对离线计算或缓存结果，还要核对它何时同步回在线库、失败时是否可追踪、重新计算是否会覆盖其他维度。数据链路越长，越不能只看接口最后一层。

## 给 AI 的数据口径检查模板

```text
请分析【指标/查询】的数据正确性，先不要改代码。

1. 声明一行结果的数据粒度、唯一键和计算公式；
2. 列出租户、账套、门店、时间、状态等隔离/聚合维度；
3. 检查查询、缓存、离线计算和同步链路是否都保持这些维度；
4. 给出跨维度、历史状态、空关联和权限场景的对照测试；
5. 结论附 SQL、文件路径或样本结果依据。
```

AI 能很快扫描所有查询和聚合入口，但业务人员必须确认“正确数字”的定义。把这个分工守住，才能避免接口无错、数据有错的隐蔽事故。
