# 接口正确不等于数据正确：一次账套维度聚合问题的启示

> 系列导航：[完整目录](00-series-titles.md)

最难排查的数据问题，往往不是接口报错，而是接口正常返回了一个看起来合理的数字。

一次库存或财务聚合中，按 SKU 汇总后的结果与单账套样本完全一致。直到把不同账套的数据放在一起，才发现同一个 SKU 被合并了。API、SQL 和测试都没有明显异常，错误只存在于数据粒度里。

## 先问“一行代表什么”

在让 AI 修改查询之前，我会让它写一句粒度声明：一行结果代表什么对象，唯一键是什么，必须按哪些维度分组。`SKU 总库存`、`某账套某门店的可用库存`和`某批次的库存`不是同一个指标。

这句话会影响 `GROUP BY`、关联条件、缓存 key、分页和权限过滤。没有它，AI 很容易按照字段名生成一条语法正确的错误 SQL。

## 账套不是可选筛选项

如果账套是核算或经营边界，那么它应该贯穿查询、聚合、缓存、离线计算和同步链路。只在 Controller 接收一个 `ledger_id`，却在内部聚合时丢掉它，等于把隔离责任交给了调用方。

我会让 AI 搜索所有同类 `GROUP BY`、缓存构造和汇总逻辑，检查是否有只按 SKU、供应商或门店聚合的绕过点。

## 测试必须故意制造容易混淆的数据

单账套样本不能发现这个问题。测试要至少包含同 SKU 不同账套、同账套不同门店、空关联、历史状态和无权限用户，并比较行数、数量、金额和可见范围。

如果数据先离线计算再写回在线库，还要检查同步失败、重复计算和覆盖范围。最后一个接口通过，不代表整条数据链路正确。

## 时间也是不能省略的业务维度

后来排查经营指标时，又遇到一种相似错误：环比结果有数字，计算也没有异常，但“上一周期”取错了。自然月、最近三十天和与当前区间等长的前一周期，会得到完全不同的答案；时区、当天是否包含完整数据也会继续改变结果。

AI 最初容易把环比理解成两个结果相除，真正需要先确定的是比较区间如何生成、两段时间是否等长、边界是否重叠，以及缺少历史数据时返回空值还是零。验证时不能只看最终百分比，还要把当前区间、对照区间、原始分子和分母一起输出。

账套遗漏和时间口径错误有同一个根源：计算式正确，不代表被计算的业务集合正确。

## 给 AI 的数据正确性任务

```text
请分析【指标/查询】的数据口径，先不要改代码：
1. 写明一行结果的粒度、唯一键和计算公式；
2. 列出租户、账套、门店、时间和状态维度；
3. 检查查询、缓存、离线计算和同步是否保持这些维度；
4. 设计跨维度、空关联、历史数据和无权限对照样本；
5. 所有结论附 SQL、文件或样本依据。
```

AI 能高效找到漏掉维度的代码位置，但业务方必须确认这个数字到底代表什么。数据正确性首先是口径问题，其次才是 SQL 问题。
