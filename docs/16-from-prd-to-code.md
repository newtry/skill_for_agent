# 从 PRD 到代码：我最终固定下来的 AI 研发流程

> 系列导航：[完整目录](00-series-titles.md)

我早期使用 AI 的方式很像把 PRD 当成代码生成器的输入：把需求贴过去，让它直接开始写。第一版通常出来得很快，真正的返工却发生在后面：状态没定义、异常没说清、测试临时补，最后发现 AI 实现的是它理解的需求，而不是业务真正要的结果。

后来我把研发过程固定成一条可追踪的链路：

```text
目标与角色 -> 业务规则与状态 -> 验收条件 -> 测试场景
-> 技术方案 -> 代码实现 -> 验证与交付
```

这不是为了增加文档，而是把错误假设尽量提前暴露。

## 一次积分需求怎样走完这条链

“下单时支持积分抵扣”最初只有一句 PRD。按旧方式，AI 会直接增加扣减接口；按新的流程，第一步先确认用户目标是避免超卖积分且订单失败可恢复。随后把规则展开为冻结、确认、释放三种状态，补上重复请求和余额不足等验收条件，再设计状态转换、流水和幂等测试。

进入实现时，AI 才去确认积分模块的数据所有权和跨模块调用方式。验证阶段不只检查接口成功，还要模拟支付失败、重复回调和超时释放，核对余额、冻结额与流水是否一致。最终交付记录明确哪些场景已自动验证，哪些超时任务需要在集成环境观察。

同一句需求经过这条链后，代码量未必更少，但每一个实现决定都有来源，每一个完成声明都有对应证据。

## PRD 先回答“为什么做”

AI 先要提取用户、场景、业务目标、范围和不做什么。比如“支持积分扣减”还不够，它至少涉及什么时候扣、失败如何恢复、重复请求如何处理、余额不足怎么办、是否跨租户。

如果这些问题没有答案，AI 应该列开放问题，而不是用常见业务规则替我们补全。

## 状态和异常先于类设计

支付、积分、库存、审批和导入需求，我会让 AI 先画状态流和异常路径：谁触发状态变化，哪些事件允许重复，超时后怎么办，失败后谁补偿，哪些状态不能回退。

状态清楚后，验收条件才会具体，测试也不再只是给方法补几个正常输入。

## 实现阶段要回到项目规则

方案确认后，AI 再去找相似代码、确定模块落点、检查数据所有权和事务边界。实现完成后，逐条对照验收条件，补充关键测试，执行受影响模块的构建或接口验证。

人负责确认业务口径、风险接受和发布授权；AI 负责搜索、整理、实现和验证准备。这个分工比让 AI 从头到尾自由发挥更容易审查。

## 每一步都要有产物

```text
分析：术语、目标、调用链、约束、开放问题
设计：状态、模块、数据所有权、异常和验收
测试：正常、边界、失败、幂等、权限和回归
实现：文件、行为变化、依赖和迁移影响
验证：命令、结果、数据证据、未验证项
交付：diff、风险、回滚和后续动作
```

这套流程让我从“让 AI 写更多代码”转向“让 AI 参与完整交付”。真正的效率不是少写几行，而是少在错误方向上走几轮。
