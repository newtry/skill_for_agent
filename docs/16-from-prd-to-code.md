# 从 PRD 到代码：我最终固定下来的 AI 研发流程

> 系列导航：[完整目录](00-series-titles.md)

我早期使用 AI 的方式，是把 PRD 当成代码生成器的输入：复制需求，补一句“请直接实现”，然后等待第一版结果。

代码通常很快出现，返工也随之出现。积分抵扣被实现成直接扣减，却没有冻结与释放；批量导入有正常循环，却没有定义部分失败；接口测试通过，租户与账套数据却被错误合并。AI 完成了它理解的动作，但团队从未把业务承诺、风险和完成证据连接起来。

后来我不再把“PRD 到代码”理解成一次转换，而是把它设计为一条证据逐步累积的交付流水线：每个阶段消除一类不确定性，产生下一阶段可以审查的输入，并设置不能被一句“看起来没问题”绕过的门禁。

## 研发流程不是一条超长提示词

一条提示词即使包含需求、方案、测试和实现，AI 仍可能在同一次推理中用自己的假设相互证明：它先替业务补全规则，再根据这些规则设计方案，最后用贴合自身实现的测试宣布完成。

把过程拆成阶段，不是为了增加等待，而是为了让不同决策可以分别审查：

```text
目标与范围 -> 业务模型与风险 -> 验收与追溯 -> 技术方案
-> 测试设计 -> 受控实现 -> 审查与验证 -> 交付与沉淀
```

前半段定义什么叫正确，中间阶段决定怎样实现，后半段用独立证据判断是否真的正确。代码只是其中一个产物。

## 第一阶段：把 PRD 收敛成任务契约

PRD 通常描述用户需求，却未必包含工程交付所需的全部信息。AI 首先要提取目标用户、业务场景、预期结果、范围、不做什么、已知事实和开放问题。

例如“下单支持积分抵扣”至少还要确认：什么时候冻结，什么时候确认，订单失败怎样释放，余额不足如何表现，重复提交是否再次占用，积分批次按什么顺序使用。

没有答案的问题必须保留为待确认项。AI 可以指出缺口和备选规则，不能用常见产品经验静默补全。

这一阶段的退出条件是：目标、范围、约束、验收方向和当前授权已经明确，团队知道本次任务要改变什么，也知道哪些决定尚未作出。

## 第二阶段：建立业务模型和风险清单

状态型需求要先画状态机，数据型需求要先声明粒度，跨模块需求要先确定所有权，异步任务要先定义幂等键和失败恢复。

模型的作用是把隐藏规则变成可检查的不变量。例如积分需求至少要求：余额不能为负，同一冻结只能确认或释放一次，重复请求不重复产生效果，账户、批次、冻结与流水能够对账。

风险清单则从正常路径继续追问：边界值、异常输入、并发、重试、权限、兼容、迁移和外部依赖会怎样破坏这些不变量。

这一阶段不设计具体类，而是先明确系统必须守住什么。

## 第三阶段：把业务承诺变成验收与追溯

每条关键规则都要形成可观察的验收条件，并拥有稳定标识。验收条件继续关联风险、技术决策、测试场景和最终证据。

```text
需求目标 -> 验收条件 -> 风险 -> 方案决策
        -> 测试用例 -> 实现位置 -> 验证证据
```

追溯关系能在方案阶段发现遗漏，也能在需求变化时反向定位受影响的代码和测试。第 18 篇会专门展开这条证据主线。

## 第四阶段：评审方案，而不是评审文档格式

技术方案需要说明模块责任、数据所有权、接口契约、状态与事务、异常补偿、兼容迁移、测试和发布路径。每项关键选择都应有项目证据、备选方案和取舍理由。

方案门禁回答的是：实现路径是否符合项目和业务边界，失败时能否恢复，新旧版本怎样共存，团队是否知道第一步改什么以及怎样验证。

方案仍有阻塞性业务问题时，不进入实现。第 19 篇会进一步定义什么叫“可以落地”。

## 第五阶段：测试先覆盖风险，再跟随实现细化

测试设计不应等代码完成后才开始。验收条件和风险清单已经能够决定正常、边界、失败、并发、权限和回归场景，以及它们需要单元、集成、接口还是端到端证据。

实现过程中可以补充发现的新风险，但不能只围绕当前代码路径生成容易通过的断言。第 20 篇将讨论如何判断绿色测试是否真的覆盖风险。

## 第六阶段：在受控现场中实现

实现前先检查分支、未提交改动、相关提交和基线测试，区分当前任务、其他工作和未知变更。方案确认不意味着可以覆盖历史现场，也不意味着可以顺手重构所有相似问题。

AI 按已确认范围完成最小改动，持续报告实际方案偏差、修改文件和新增依赖。重大偏差需要回到方案阶段重新评审，而不是在代码里形成既成事实。

## 第七阶段：用审查和验证形成完成证据

代码审查先判断行为和业务不变量是否发生非预期变化，验证再逐条证明验收条件成立。两者不能互相替代：审查能发现遗漏路径和设计风险，测试与运行证据则证明实际结果。

最终报告需要区分已验证、失败、未执行、环境阻塞和待人工确认。只有验收承诺有足够证据，任务才能进入待评审或交付状态。

## 每个阶段都必须有进入条件和退出证据

| 阶段 | 核心产物 | 进入下一阶段的门禁 |
| --- | --- | --- |
| 任务定义 | 目标、范围、事实、约束和开放问题 | 阻塞性业务歧义已确认 |
| 业务分析 | 状态、粒度、所有权、不变量和风险 | 正确性标准可以被验收 |
| 追溯设计 | 验收条件及其风险和证据需求 | 关键承诺没有孤立项 |
| 技术方案 | 边界、数据、异常、迁移和发布设计 | 方案可实施、可验证、可恢复 |
| 测试设计 | 分层用例、数据和环境要求 | 关键风险有对应验证方式 |
| 实现 | 受控 diff、测试和方案偏差说明 | 修改范围完整且可审查 |
| 审查验证 | 发现清单、命令、结果和残余风险 | 验收证据足以支持完成判断 |
| 交付 | 变更、回退、未决项和接管信息 | 责任人接受结果与风险 |

门禁不是要求所有任务都写厚重文档。低风险局部改动可以把多个产物压缩到一张任务卡中；支付、权限、迁移和生产变更则需要更正式的审查。流程深度应随风险增加，但关键决策不能因为任务小就消失。

## 这条流程允许回退，不是瀑布模型

测试可能发现业务规则矛盾，实现可能暴露方案无法复用现有能力，验证也可能证明验收条件定义错误。此时应回到对应阶段更新决策和追溯关系，而不是为了保持计划不变继续打补丁。

流程化的价值恰恰在于知道应该退回哪里，以及哪些下游产物需要重新评估。

## AI 负责加速，人负责给出关键决策

AI 适合搜索项目、整理规则、枚举风险、生成矩阵、实施局部改动并执行验证。工程师和业务负责人必须确认业务口径、架构边界、风险接受和生产授权。

从 PRD 到代码的真正效率，不是缩短生成第一版代码的时间，而是减少错误假设进入实现、测试和发布之后再返工。
