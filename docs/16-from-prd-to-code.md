# 从 PRD 到代码：我最终固定下来的 AI 研发流程

最初我常让 AI 直接根据一段需求写代码。速度很快，返工也很快：业务状态没有定义，异常路径没有讨论，测试只能临时补，最后发现代码回答的是“我以为的需求”。

后来我把 AI 的工作拆成一条明确链路：PRD -> 业务目标与场景 -> 规则与状态 -> 验收条件 -> 测试场景 -> 实现方案 -> 代码 -> 验证与交付。它看起来多了步骤，实际是把返工从代码写完以后提前到最便宜的阶段。

## PRD 先回答“为什么”和“什么算成功”

AI 应先抽取用户角色、触发场景、业务目标、明确不做的范围和成功指标。若需求写着“支持积分扣减”，它需要追问或列出待确认项：什么时候扣？失败是否返还？余额不足怎么办？是否跨租户？这些不是实现细节，而是决定系统行为的规则。

## 把状态和异常写在代码之前

支付、积分、审批、导入和库存这类需求，最有价值的产物往往是一张状态流和异常表。它迫使 AI 与人先确认：哪些事件会改变状态，重复执行会怎样，超时和失败如何补偿，谁有权限操作。

到这一步，验收条件才有可验证的来源。每一条关键规则至少对应一类测试，不让“成功路径跑通”遮住异常和边界。

## 实现是可追溯链路的一环

进入代码阶段时，AI 应给出模块落点、数据所有权、接口兼容性、事务和权限影响，并复用项目已有模式。实现完成后，验证不止是编译：要运行受影响测试、检查关键数据状态、确认接口和配置没有越界。

```text
PRD
 -> 目标、角色、范围
 -> 业务规则、状态、异常
 -> 验收条件
 -> 测试场景和用例
 -> 方案与最小改动
 -> 实现
 -> 测试、数据验证、交付记录
```

## AI 在每一步的正确角色

AI 可以帮助提取歧义、整理状态流、寻找类似实现、生成测试骨架和执行验证。人需要确认业务口径、边界选择、风险接受和发布授权。把这两种责任混在一起，流程再完整也会失控。

这套流程的目的不是把研发文档化，而是让需求、代码和验证之间能互相解释。当用户问“这个规则为什么这样实现”，团队能一路追到 PRD；当测试失败，也能反向知道影响了哪条业务承诺。
