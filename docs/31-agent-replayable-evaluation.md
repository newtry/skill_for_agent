# 模型觉得正确还不够：如何构建可回放、可评测的 Agent

Agent 上线初期，团队常用“我试了一下，回答还不错”判断质量。这个方法无法比较版本，也无法解释某次失败是路由错了、工具错了、权限错了，还是模型把空结果编成了答案。

我后来把一次 Agent 请求当成一条可以回放的执行记录，而不是一段不可复现的聊天。

## 评测对象不只有最终回答

一次请求至少要能看到：输入、意图路由、上下文检索、工具名称和参数、授权判断、工具返回、状态变化、最终输出和错误。最终回答正确但调用了越权工具，仍然是失败；回答措辞漂亮但数据口径错误，也不能算通过。

## 评测集要来自真实失败

通用的“查一个商品”样本很快会被模型学会，真正有价值的评测来自历史问题：行业黑话、相似意图、跨租户请求、缺少参数、重复动作、空数据、工具超时、恶意提示和人工接管。

每条样本都应有预期路由、允许工具、数据范围、关键断言和失败处理，而不是只写一个参考答案。

## 评测要有门槛和版本

每次模型、提示词、工具 schema 或术语库变化，都应运行固定评测集。通过标准可以包括路由准确率、工具参数正确率、越权率、关键字段准确率、重复执行安全性、响应结构有效率和人工接管率。

不同指标不能用一个平均分掩盖高风险失败。一次权限越界，即使其他几十个问题回答得很好，也应阻断上线。

## 回放记录要保护隐私

可回放不等于保存所有原始数据。样本和日志应脱敏，尽量使用合成数据或结构化摘要；记录足够重现决策链，同时不把生产密码、订单详情和个人信息扩散到评测环境。

```text
请为【Agent 能力】设计回放评测：
1. 记录输入、路由、工具、授权、结果和最终输出；
2. 从真实失败中构建正常、边界、越权、注入、重复和工具故障样本；
3. 定义关键断言、阻断级失败和可接受误差；
4. 说明版本变更时的回归门禁与隐私处理。
```

模型自我判断“这次回答正确”没有工程意义。可回放记录让失败能够定位，评测门禁让质量能够比较，二者共同把 Agent 从演示能力变成可运营系统。
