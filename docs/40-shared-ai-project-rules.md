# 如何让多个 AI 工具共享同一套项目规则和研发记忆

> 系列导航：[完整目录](00-series-titles.md)

当 Codex、Claude Code、IDE 助手和任务板机器人同时参与项目时，最容易出现的不是工具不够强，而是每个工具理解的项目不一样：一个知道 App 入口，另一个只看过 Admin 代码；一个遵守 API/Biz 边界，另一个直接引用实现类。

解决办法不是给每个工具分别写一套长提示词，而是把稳定知识放进工具都能读取的项目资产。

## 核心判断：共享规则必须只有一个语义来源

多个工具可以使用不同的适配文件和调用方式，但同一条项目边界只能有一个权威定义。共享不是把相似内容复制到每个工具，而是建立知识分层、来源优先级和同步校验，让工具差异停留在接入层。

## 两份规则都正确，也可能产生冲突

我遇到过一个实际问题：一个工具读取项目根目录规则，知道跨模块必须走公开 API；另一个工具读取了自己维护的工作流说明，其中保留着早期可以直接调用 Biz Service 的示例。两份文档单独看都有来源，执行时却会导向相反实现。

这类冲突不能靠“让模型自己判断最新版本”解决。共享规则需要明确权威入口和覆盖顺序：项目事实由项目规则负责，当前任务由任务卡负责，专业方法由 Skill 负责，工具私有配置只能描述如何接入，不能重新定义业务边界。发现冲突时应停止写入并回报证据，而不是选择最方便的一份。

## 先定义权威层级和覆盖关系

我会明确规则优先级：

```text
安全与组织强约束
-> 当前仓库的权威项目规则
-> 已确认任务契约
-> 适用的专业 Skill
-> 阶段交接记录
-> 工具适配配置
-> 当前会话中的临时说明
```

优先级高不代表可以任意覆盖。例如任务契约可以缩小修改范围，但不能取消项目的租户隔离；Skill 可以规定分析方法，但不能重新定义业务模块所有权；交接记录可以说明当前进度，却不能把未确认推断升级为长期规则。

发生冲突时，要记录冲突内容、来源、版本和影响，交给对应责任人修正权威源。不能在工具私有文件中打补丁后继续，让其他工具仍然读取旧规则。

例如工具配置仍要求从业务模块目录执行 Maven，而项目规则已经改为从聚合根目录构建。正确处理不是任选一个命令试到成功，而是核对父 POM、脚本和 CI，确认项目规则后更新权威说明，删除或重新生成工具适配内容，并对受影响任务重新验证。

## 共享内容要分层

项目规则放在统一入口，例如 `AGENTS.md`，包括模块、构建、测试、接口、权限和禁止动作。任务说明记录本次目标、范围和验收。交接记录保存阶段状态。工具配置只保留各自的适配方式，不重复定义业务规则。

这样，规则只维护一份，工具差异只存在于调用和展示层。

| 内容 | 权威载体 | 更新责任 | 典型消费者 |
| --- | --- | --- | --- |
| 模块、构建和禁止动作 | 项目规则 | 项目维护者 | 所有 AI 与工程师 |
| 当前目标与验收 | 任务卡/需求 | 任务负责人 | 当前执行器与评审人 |
| 当前进度与现场 | 检查点/交接 | 当前运行 | 下一会话或工具 |
| 专业处理方法 | Skill | 能力维护者 | 符合触发条件的任务 |
| 工具启动与格式适配 | 工具配置 | 工具使用者 | 单个工具 |

这张分层表解决“内容放在哪里”，还需要接入适配解决“工具怎样读到”。可以为不同工具生成轻量入口文件，但生成内容只引用或同步权威源，并带版本与校验，不能独立演化。

## 共享规则必须可验证

每条重要规则都应能通过文件、命令或测试找到证据。比如“跨模块走 API”应能在 POM 和调用样例中验证；“生产操作需确认”应能在工作流门禁中看到；“租户不可越界”应有测试或数据检查。

没有证据的记忆很容易变成过期意见，被不同工具各自解释。

规则最好转成可执行检查：模块依赖用构建或架构测试约束，禁止提交敏感配置用扫描工具检查，租户边界用碰撞测试验证，发布确认用任务状态门禁控制。文档说明意图，自动检查阻止规则悄悄失效。

还要验证工具是否真的读取了规则。可以通过初始化报告要求其列出规则版本、相关边界和证据；若工具无法访问权威入口，任务应降级为只读或停止，而不是继续依赖内置常识。

## 规则也会过时

定期合并重复规则，删除已失效的命令，更新模块和部署变化，并把反复纠正 AI 的经验沉淀进去。规则文件越长不代表越好；它应该优先保留那些会导致错误或返工的事实。

规则变更需要影响分析。构建根目录变化会影响自动化脚本，模块边界变化会影响 Skill 和示例，权限规则变化会影响测试和任务模板。更新权威源后，应检查消费者、删除冲突副本并记录最后验证时间。

## 怎样验证多工具真正共享了规则

我会让不同工具针对同一任务分别输出入口、模块、依赖、禁止动作和验证计划，再比较关键决策是否一致；随后用一条故意冲突的工具私有配置验证它们是否按优先级停止。目标不是回答逐字相同，而是实现选择不越过共同边界。

AI 可以发现重复规则、链接证据和生成适配入口；项目维护者负责权威事实；任务与 Skill 负责人分别维护局部约束和专业方法。共享规则完成的标志，是规则只需在权威位置修改一次，所有工具能识别版本变化和冲突，而不是每个工具各有一份“差不多相同”的提示词。

```text
请审计【项目】的多工具规则一致性：

1. 列出项目规则、任务说明、Skill、交接和工具配置的权威来源；
2. 标记重复、冲突、无证据和可能过期的规则；
3. 按优先级说明每个冲突应由哪个责任人和载体修复；
4. 将可执行约束映射到构建、测试、扫描或任务门禁；
5. 验证不同工具读取同一版本后不会做出相反的边界选择。
```

共享记忆的目标不是让所有工具输出完全相同，而是让它们在同一组项目边界内工作。工具可以有不同表达和擅长领域，但不能各自发明业务规则。

```text
项目规则：什么长期成立
任务说明：这次要完成什么
交接记录：当前做到哪里
Skill：一类问题怎样处理
工具配置：如何读取和执行
```
