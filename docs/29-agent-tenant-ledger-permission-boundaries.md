# 租户、账套与权限：业务 Agent 必须守住的数据边界

> 系列导航：[完整目录](00-series-titles.md)

普通聊天 Agent 说错一句话，影响可能只是体验；ERP Agent 查错一个账套，影响的可能是库存、销售额和经营判断。因此租户、账套和权限不能作为提示词里的背景信息，而必须成为每次请求的运行时约束。

一次库存场景在开发样本中始终正确，因为测试租户只有一个账套。加入第二个账套后，同一个 SKU 被工具层合并，模型虽然没有展示账套字段，却返回了跨账套总数。最终文本没有明显敏感信息，数据边界已经被破坏。

修复后，权限测试同时检查身份上下文、工具参数、查询过滤、缓存键和输出范围。只要其中一层缺少账套，测试都应失败。

## 核心判断：权限是运行时约束，不是会话背景

Agent 可以从自然语言中识别用户意图，却不能凭语言推断用户被授予了什么权限。授权范围必须由身份、组织关系、资源边界和当前动作在每次请求中重新计算，并贯穿数据查询、聚合、缓存、输出和写入。

## 自然语言不会自动带来权限

用户说“查一下我的库存”，系统仍需明确：调用者是谁，属于哪个租户，可访问哪些账套、门店和仓库，查询默认范围来自哪里。

模型可以帮助理解“我的”指向哪个业务对象，但不能决定授权范围。授权必须由服务端身份、角色、组织关系、资源状态和当前操作共同计算。

## 先生成授权上下文，再解释业务请求

我会在模型选择工具之前，由服务端生成不可被用户文本覆盖的授权上下文：

```json
{
  "subject": "user-17",
  "tenantId": "tenant-a",
  "allowedLedgerIds": ["ledger-1"],
  "allowedStoreIds": ["store-3", "store-8"],
  "fieldPolicy": "inventory-standard",
  "allowedActions": ["INVENTORY_READ", "TRANSFER_DRAFT"]
}
```

用户可以在允许范围内指定门店和账套，却不能通过“帮我切到账套 2”扩大列表。若请求范围与授权上下文冲突，系统返回明确拒绝；若上下文缺失，系统应重新认证或转人工，而不是用默认账套猜测。

模型看到的最好是经过裁剪的范围标识，而不是所有组织关系。这样既能完成参数补齐，也减少把不可见资源带入上下文的机会。

## 五个运行时边界要同时成立

| 边界 | 需要校验什么 | 常见绕过点 |
| --- | --- | --- |
| 身份 | 用户、服务账号、角色和会话 | 只信模型描述或前端参数 |
| 租户 | 数据所属客户和隔离条件 | 查询或缓存遗漏租户 |
| 账套 | 当前经营/核算范围 | 同 SKU 聚合时丢失账套 |
| 组织资源 | 门店、仓库和授权关系 | 默认门店与显式门店冲突 |
| 字段与动作 | 可见字段、读写权和状态 | 只过滤最终文本，数据已进上下文 |

这些边界必须同时贯穿查询、聚合、缓存、导出、日志和写操作。只在回答前做一次过滤太晚了，越权数据可能已经被模型使用或记录。

## 授权必须沿调用链逐层收窄

一次库存查询的边界传递可以写成：

```text
登录身份
-> 服务端授权上下文
-> 路由允许 INVENTORY_READ
-> 工具参数只能选择授权账套和门店
-> SQL 强制追加租户、账套和组织条件
-> 聚合保持账套与门店粒度
-> 缓存键包含同样的隔离维度
-> 输出再次执行字段策略
```

每层都可以进一步收窄范围，但不能扩大上游授权。工具不能相信模型传入的 `tenantId`，SQL 也不能因为工具已经校验就省略隔离条件。纵深校验不是重复劳动，而是防止任一层配置或实现失误直接穿透系统。

## 账套边界尤其容易被 Agent 隐藏

用户问“这个款还有多少”，模型倾向于给出一个总数；但业务系统中的库存也许必须按账套、门店和仓库分别展示。Agent 应补齐缺失上下文，使用明确默认值，或停下来澄清，并把最终口径显示给用户。

结果卡片应至少展示租户/账套范围、门店/仓库、时间和更新时间。一个没有范围说明的数字，即使来自正确 SQL，也很难被用户审查。

## 缓存和聚合是高风险边界

权限条件加在 SQL 中，不代表结果在缓存中仍然安全。缓存键、失效范围和预计算表必须包含所有决定数据身份的维度。

同样，按 SKU 聚合会丢失账套；按门店聚合会丢失仓库。每一层都要声明输入和输出粒度，不能假设下一层还能恢复已经丢掉的隔离信息。

那次跨账套库存问题最终不是 Controller 少收了参数，而是预计算结果以 `SKU` 作为唯一键。查询层后来补上 `ledgerId` 也无法恢复已经合并的数据。修复必须回到首次丢失维度的位置，将键调整为账套、门店、仓库和 SKU 的业务组合，并重新生成历史数据。

这也是权限问题与普通字段过滤的区别：隔离维度一旦在上游被不可逆地聚合，末端再做过滤已经没有意义。

## 写操作需要更高门槛

查询权限不足时可返回受控拒绝；调拨、退款、积分扣减和批量导出则还需要业务状态、操作范围、审批、预览、确认和幂等。

模型不能通过改写自然语言参数绕过这些规则。业务工具应自行校验资源归属、当前状态和调用者权限，并把拒绝记录到审计中。

查询权、生成草稿、正式提交和审批应是不同动作。一个用户可以看见库存，不代表可以调拨；可以创建调拨草稿，也不代表可以审批。Agent 必须把权限不足表达为 `forbidden` 或 `approval_required`，不能用“我暂时无法完成”模糊真实原因，更不能退化到另一个权限更宽的工具。

## 隔离评测要检查真实数据路径

```text
同一用户跨租户查询
有权限账套与无权限账套
默认门店与显式指定门店冲突
跨账套聚合请求
无账套上下文的模糊查询
拥有查询权但没有写操作权
缓存命中其他范围结果
导出和日志包含不可见字段
```

每个场景都要检查实际工具参数、数据库过滤、缓存键、输出字段和审计记录。只看最终回答是否出现其他租户名称，无法证明数值来源没有越界。

我还会设计“碰撞数据”：不同租户使用相同商品编码，不同账套使用相同 SKU，同一用户只拥有两个门店中的一个。干净样本只能证明正确路径能运行，碰撞样本才能证明缺少任何隔离维度都会被测试发现。

AI 适合搜索授权参数在 Controller、工具、SQL、缓存和输出中的传递，生成碰撞样本并定位首次丢失边界的位置。身份策略、组织授权、字段可见性和动作权限必须由业务与安全负责人确认。权限能力完成的证据，是允许场景得到正确范围、拒绝场景在数据进入模型前被拦截，并且审计能够解释“谁因为什么规则被允许或拒绝”。

```text
请审查【Agent 能力】的数据边界：

1. 从身份、租户、账套、组织、资源和字段动作定义授权上下文；
2. 检查这些维度是否贯穿路由、工具、SQL、聚合、缓存、导出和输出；
3. 区分默认范围、显式范围、缺失上下文和冲突参数；
4. 为读操作、写操作、审批、预览和幂等设置不同门槛；
5. 用隔离、碰撞、缓存、导出和日志场景验证真实数据路径。
```

权限边界确定后，下一篇将处理最容易被越权的能力之一：自然语言查询数据库。重点不是让模型生成更复杂的 SQL，而是让它只能生成和执行受控的查询计划。
