# 技术方案写完以后：如何用 AI 持续审计“还有哪些没有实现”

> 系列导航：[完整目录](00-series-titles.md)

一次 Agent 协议改造进入联调后，项目看起来已经接近完成：后端有了新接口，Java 调用方能够收到新结构，前端也出现了对应卡片。技术方案中的模块名称几乎都能在代码里搜索到。

重新按方案承诺逐项核对时，结果却完全不同：新字段已经定义但没有进入序列化出口；失败状态写进后端枚举，前端仍按旧布尔值展示；文档声明旧事件已停用，运行配置仍允许兼容分支接收流量；测试覆盖了新链路，却没有验证超时后的任务恢复。

这些并不是“完全没开发”，而是处于实现了一部分、接线不完整、验证缺失或旧链路未退出的中间状态。只问一句“方案实现了吗”，很容易把它们全部回答成“基本完成”。

## 核心判断：方案审计管理的是承诺与证据的持续对齐

技术方案不是开工前读一次的静态说明，而是一组有版本的工程承诺。开发过程中的每项承诺，都要经过机制实现、跨层接线、风险验证和旧路径退出，才有资格关闭。

```text
方案承诺
-> 实现机制
-> 生产与消费接线
-> 风险验证
-> 迁移和旧链路退出
-> 可复核的关闭证据
```

AI 的价值不是替项目宣布“完成度 90%”，而是在大量文档、代码、配置和测试之间持续寻找缺口。人仍要判断方案是否有效、差异能否接受以及谁有权关闭承诺。

## 不要直接问“实现了吗”

这个问题缺少对象和证据标准。只要存在同名类、接口或字段，模型就可能给出乐观结论。

更可靠的做法是先把方案拆成原子承诺。每条承诺只表达一个可判断结果，并写明适用范围、责任模块和验收条件。例如“支持 V2”仍然太宽，可以继续拆成：

```text
V2 请求进入唯一受控入口
Java 调用方发送新字段且不再构造旧字段
后端按新语义持久化并输出
前端能区分完成、部分完成和失败
旧协议调用可观测并具备退出条件
回滚后在途任务仍能被解释
```

拆开以后，项目不会因为新接口已经存在，就掩盖消费者、失败路径和迁移仍未完成。

## 每条承诺要检查五层证据

| 证据层 | 核心问题 | 常见假完成 |
| --- | --- | --- |
| 定义 | 语义、边界和版本是否明确 | 字段存在但含义仍有歧义 |
| 实现 | 是否有真正保证承诺的机制 | 只有 DTO，没有业务处理 |
| 接线 | 生产者、消费者和配置是否实际使用 | 代码存在但入口没有注册 |
| 验证 | 风险场景是否能让错误实现失败 | 只有正常路径测试绿色 |
| 退出 | 旧字段、分支、数据和文档是否可删除 | 新链路可用但仍依赖兼容 |

以“失败可恢复”为例，状态枚举只能算定义；重试检查点和幂等逻辑才是实现；任务执行器、队列和前端重试入口需要完成接线；故障注入证明机制有效；如果旧任务状态仍存在，还要说明迁移或兼容何时结束。

只有这五层都达到当前阶段的约定，审计状态才能从“存在实现”变成“有证据关闭”。

## 文档、代码和测试都不是单独的真相

方案可能超前：文档已经描述最终形态，代码仍处于迁移窗口。方案也可能落后：实现根据新发现调整了边界，评审已经批准，但文档没有更新。

同样，代码只能证明某种机制存在，不能证明入口真的使用；测试结果只能证明某个版本和环境下运行过，不能自动适用于当前工作区；运行配置能够说明实际开关，却不能解释这是不是有意决策。

我会给每次审计建立明确基线：

```text
方案版本与批准记录
代码仓库、分支和提交
当前工作区差异
部署配置与功能开关
测试产物对应的代码和环境
迁移阶段与已批准例外
```

如果这些基线不能对齐，结论应降低置信度或标记待确认，不能把旧测试和新代码拼成一份虚假的完成证据。

## 差距需要分类，而不是堆成待办列表

几十条“未实现”如果没有优先级，会同时制造噪声和焦虑。我通常把差异分为：

| 类型 | 处理方式 |
| --- | --- |
| 阻塞交付 | 违反验收、安全、数据或回滚底线，关闭前不能发布 |
| 实现缺口 | 当前迭代承诺缺少机制或接线，需要进入任务 |
| 验证缺口 | 机制可能存在，但缺少足够风险证据 |
| 迁移待办 | 过渡状态符合计划，但必须有退出条件和责任人 |
| 文档漂移 | 已批准实现与文档不一致，需要更新权威说明 |
| 未来规划 | 明确不属于当前版本，不能混入完成率 |
| 待确认决策 | 方案与实现无法判断谁正确，需要责任人裁决 |

分类依据应附文件、配置、测试、运行观测或批准记录。AI 可以提出严重度，但支付、权限、数据迁移和业务口径的风险接受必须由有责任的人确认。

## 把审计放进迭代节点

差距审计不必在每次提交后全量运行，更适合放在状态发生变化的节点：

```text
方案通过后：建立承诺和证据矩阵
实现切片完成后：检查机制与接线
跨模块联调后：核对生产消费关系和失败路径
发布前：关闭阻塞项和验证缺口
迁移窗口结束前：检查旧链路与兼容退出
方案发生变更时：重建受影响承诺和回归范围
```

每次审计只更新发生变化的证据，同时保留历史状态。这样可以看出某条承诺为什么从“已实现”退回“待确认”，也能避免项目结束时重新猜测开发过程中发生了什么。

一个实用的追踪项可以包含：承诺 ID、方案来源、责任模块、当前状态、实现证据、验证证据、旧链路、阻塞原因、责任人和关闭时间。状态变化必须附新证据，不能由文字进度直接覆盖。

## 关闭证据要能被另一个人复核

“代码已完成”“联调没问题”都不是可复核证据。更具体的关闭记录应说明：

```text
实现：哪些代码和配置提供机制
接线：哪些生产者与消费者实际使用
验证：运行了什么场景，结果对应哪个版本
迁移：旧数据和旧调用处于什么状态
例外：哪些环境或场景没有验证，谁接受风险
```

对于运行期才能确认的承诺，可以先进入“待观测”，但要定义指标、观察窗口和关闭责任人。不能为了报表好看，把尚需生产证据的事项提前标成完成。

## AI 负责找证据，人负责判断承诺

AI 擅长拆解方案、跨仓库搜索、建立生产消费矩阵、比较配置和测试、识别孤立实现以及生成待核验场景。工程师要校验搜索是否覆盖动态注册和外部消费者，方案负责人要确认变更是否获批，业务和安全负责人处理口径与风险接受。

审计还应保持只读。发现缺口不等于立即改代码、删兼容或运行生产 DDL；先形成有依据的差异，再按任务和授权进入实施。

```text
请只读审计【技术方案】与当前实现的差距：

1. 固定方案版本、代码基线、工作区、配置、测试产物和迁移阶段；
2. 将方案拆成原子承诺，逐项检查定义、实现、接线、验证和退出；
3. 为每个结论附文件、配置、测试、运行观测或批准记录；
4. 区分阻塞交付、实现缺口、验证缺口、迁移待办、文档漂移和未来规划；
5. 标记冲突、低置信度和需要责任人确认的决策；
6. 给出最小关闭动作、责任人、退出条件和可复核证据。

不修改代码或环境，不把同名结构存在视为实现完成，不用旧测试证明当前版本。
```

差距审计提供了持续演进的控制面。下一篇把它用于最容易出现“新实现已经上线、旧承诺仍未退出”的场景：跨后端、Java 和前端的协议升级。
