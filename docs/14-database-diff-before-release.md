# 用 AI 对比数据库结构：如何辅助发布而不盲目执行 DDL

> 系列导航：[完整目录](00-series-titles.md)

一次发布前检查中，AI 发现目标数据库比开发库多一个状态字段。按照“让两个环境保持一致”的直觉，最直接的建议是删除目标库中的多余字段。

继续检查迁移记录、应用版本和调用代码后，我们才确认：这个字段来自一次线上兼容修复，仍有旧版本任务在读取。若机械执行差异脚本，数据库结构会变得更整齐，正在运行的任务却会立刻失败。

最后的处理既不是马上删除，也不是永久保留，而是把它登记为有来源、有使用方和退出条件的历史差异：本次发布不处理，先迁移读取方，观察旧版本退出，再在后续版本单独清理。

这个案例让我明确了数据库对比的真正目标：结构差异只是一项事实，不能直接推出变更动作。发布需要判断的是，本次应用版本要求什么结构、目标环境当前为什么不同，以及怎样在不破坏现有数据和旧版本的前提下完成迁移。

## 数据库差异不是数据库变更

结构对比工具能够回答“哪里不同”，却不能回答“哪一边正确”。开发、测试和生产数据库都可能包含合理但来源不同的状态：

- 开发库可能提前包含尚未发布的字段；
- 生产库可能有紧急修复留下的结构；
- 测试库可能保留实验索引或不完整迁移；
- 某些租户库可能停留在不同应用版本；
- 已废弃字段可能仍处于兼容窗口内。

因此，环境本身不能作为唯一真相。真正的发布基准应该由本次版本的迁移脚本、应用契约、数据库版本记录和已批准的历史差异共同定义。

AI 可以生成结构差异，但每条差异还必须经过语义判断：它属于本次变更、历史热修复、兼容遗留、环境噪声，还是尚未解释的漂移。未知差异不能自动归入删除清单。

## 先建立版本基线，再比较目标环境

我现在会把数据库检查拆成三个状态：

```text
声明状态：本次应用版本通过迁移脚本和契约要求的结构
实际状态：目标环境当前真实存在的表、字段、索引和约束
历史状态：已执行迁移、热修复、回滚和兼容记录
```

对比的核心是判断“实际状态能否安全演进到声明状态”，而不是选择一个环境完整复制。

如果迁移脚本声明新增字段，而目标库已经存在同名字段，还要继续比较类型、默认值、空值约束和来源；如果目标库缺少某次历史迁移，则需要确认能否直接跨版本执行；如果结构相同但数据回填没有完成，发布仍然不具备条件。

这一步把数据库对比从静态快照比较，提升为版本演进检查。

## 不同结构变化对应不同风险

一份专业差异报告不能把所有 DDL（数据定义语句）放在同一张待执行列表里。至少要按变化性质分类：

| 变化类型 | 典型操作 | 主要风险 |
| --- | --- | --- |
| 扩展型 | 新增可空字段、新表、兼容索引 | 旧应用兼容、默认值、资源占用 |
| 约束型 | 增加非空、唯一键、外键 | 历史脏数据、写入失败、锁表 |
| 转换型 | 修改类型、长度、编码或精度 | 截断、舍入、转换失败和性能影响 |
| 收缩型 | 删除字段、索引、表或旧约束 | 旧版本仍使用、数据不可恢复 |
| 数据型 | 回填、重算、去重或状态修正 | 影响行数、幂等、事务和审计 |

例如，把字段改为 `NOT NULL` 不只是一条 DDL。它需要先统计空值、定义回填来源、处理并发写入，再增加约束。删除字段则必须证明所有读写方都已退出，并确认备份与恢复方式。

AI 很适合批量识别这些风险，但不能根据语法类别自动判断业务是否允许变化。

## 复杂迁移应采用“扩展、迁移、收缩”路径

对存在旧版本并行运行或大量历史数据的系统，我更倾向于把破坏性变更拆成三个阶段：

```text
扩展：先增加向后兼容的新结构
迁移：回填数据，切换读写方，核对新旧结果
收缩：确认旧链路退出后，再删除旧结构
```

例如字段改名不应直接执行 `RENAME` 并要求所有应用同时切换。更稳妥的方式可能是先增加新字段，在兼容期内完成回填和调用方迁移，观察旧字段不再被读写，最后单独删除。

每个阶段都要有进入条件和退出证据。仅仅“新代码已经合并”不能证明旧字段可以删除；需要结合全局代码搜索、运行日志、数据库访问观测和部署版本确认旧链路真正退出。

这种路径会增加迁移步骤，却降低一次发布同时跨越代码、数据和运行版本的风险。

## 候选 DDL 必须升级为数据库变更卡

我要求 AI 输出的不是一段裸 SQL，而是一张可以评审的变更卡：

| 内容 | 必须说明的事实 |
| --- | --- |
| 变更目的 | 对应哪个版本需求或缺陷 |
| 当前与目标状态 | 结构、数据量、历史来源和使用方 |
| 前置条件 | 备份、回填、旧版本退出和资源窗口 |
| 执行计划 | 顺序、批次、事务特性和预计影响 |
| 兼容策略 | 新旧应用并行时怎样读写 |
| 验证方式 | 结构、数据、性能和应用行为怎样核对 |
| 失败处理 | 停止条件、恢复方案和人工决策点 |
| 后续清理 | 临时字段、双写逻辑和兼容代码何时退出 |

“回滚 SQL”也不能被机械理解为安全保证。某些数据库 DDL 会隐式提交，字段删除后的数据无法靠反向建表恢复，大表变更还可能在中断后留下中间状态。恢复方案必须结合具体数据库能力、备份和迁移工具验证。

## 发布前后都需要证据

变更执行前，应确认目标实例、应用版本、备份可用性、历史数据分布、锁和资源风险。执行后则至少核对：

- 数据库版本记录是否正确；
- 表、字段、索引和约束是否达到声明状态；
- 回填行数与预期范围是否一致；
- 新旧应用的关键读写是否正常；
- 慢查询、锁等待和错误率是否异常；
- 临时兼容措施是否已登记后续清理任务。

结构正确只是其中一项。数据没有回填、应用仍读旧字段或索引导致性能下降，都意味着迁移尚未完成。

## AI 的权限应停在待评审产物

```text
请只读审计【版本】的数据库迁移，不执行 DDL 或数据写入：

1. 从迁移脚本、应用契约和版本记录建立声明状态；
2. 比较目标环境的实际结构，并说明差异方向与历史来源；
3. 将差异分类为本次变更、历史兼容、环境漂移或待确认项；
4. 评估扩展、约束、转换、收缩和数据变更风险；
5. 为每项候选变更生成前置条件、执行顺序、验证、失败处理和清理计划；
6. 标出需要 DBA、业务或发布负责人确认的动作。

不输出真实连接信息、凭据和未脱敏业务数据。
```

AI 可以读取元数据、核对迁移文件、搜索字段使用方、生成候选 DDL 和验证 SQL。生产执行、备份确认、窗口选择和失败后的恢复决策，仍应留在受控发布流程中。

## 数据库发布的目标，是保持版本演进可解释

数据库演进不是让两个环境在某个瞬间长得完全一样，而是让应用版本、结构、历史数据和兼容链路进入一个可以解释、验证和继续演进的状态。

前面的文章已经定义了业务、数据和状态在实现过程中怎样保持正确。第 14 篇开始回答另一个问题：当正确实现依赖新的数据库结构时，如何让变更安全穿过历史数据、旧版本和兼容窗口。差异只是输入，迁移路径和退出证据才是交付。
