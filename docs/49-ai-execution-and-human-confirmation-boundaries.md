# 如何划分 AI 的自动执行边界与人工确认边界

> 系列导航：[完整目录](00-series-titles.md)

“哪些事情可以让 AI 自动做”没有一个适用于所有团队的固定答案。真正的边界要看动作是否可逆、影响是否局部、数据是否敏感、业务责任是否明确，以及失败后能否恢复。

## 我用四个问题判断风险

第一，动作能否撤销，回滚是否真实可用？第二，影响是一个文件、一个测试环境，还是多个租户和生产数据？第三，是否涉及金额、权限、隐私或外部承诺？第四，执行后是否能立即观察和校验？

只读扫描、日志整理、测试运行和文档生成通常可以自动化；代码局部修改需要 diff 检查；数据库写入、支付退款、权限变更、发布和删除则需要人工确认。

四个问题最终要落成动作矩阵，而不是一句“高风险需谨慎”：

| 动作 | 默认权限 | 升级条件 |
| --- | --- | --- |
| 搜索代码、读取日志和元数据 | 自动执行 | 触达敏感数据时脱敏 |
| 修改局部代码和测试 | 允许执行，必须复查 diff | 跨模块或改变契约时先确认方案 |
| 生成 DDL、修复 SQL 和发布计划 | 只生成，不执行 | 明确环境、备份、窗口和授权 |
| 支付、退款、权限、生产数据和发布 | 默认禁止 | 指定执行人、范围及回滚后受控执行 |

## 边界要写成状态和动作

不要只写“高风险操作要谨慎”，而要明确：分析可以自动做，脚本可以生成，执行需要谁确认，确认后在哪个环境做，执行后检查什么，失败怎样回滚。

```text
自动分析 -> 生成计划 -> 人工确认 -> 受控执行 -> 结果验证 -> 评审/回滚
```

## 共享开发环境也不是默认沙箱

一次数据约束改造中，AI 可以正确生成唯一索引和历史数据清理脚本，但目标是多人共用的开发数据库。若立即执行，尚未升级的其他分支会因为旧写入方式失败，所谓“开发环境操作”同样会影响团队。

因此环境名称不能代替影响判断。AI 可以在共享库执行只读扫描、生成重复数据报告和幂等修复 SQL；添加强约束、清理数据和回滚仍要确认使用方、执行窗口与恢复路径。只有独立、可重建且没有其他使用者的测试资源，才适合扩大自动执行范围。

同样的边界也适用于测试：如果测试继承真实对象存储或消息配置，即使运行在本机，也已经越过了本地范围。判断权限时要看动作实际触达的资源，而不是命令从哪台机器发出。

## 边界也可以逐步调整

低风险动作积累了稳定证据后，可以扩大自动化；一旦出现越权、数据错误或不可回滚事故，就应缩小权限并补门禁。自动化边界不是一次配置，而是根据失败记录持续校准的工程策略。

最成熟的做法不是让 AI 什么都能做，而是让它在清楚知道不能做什么的情况下，把能做的部分做到足够完整。
