# 测试为什么真的上传了 OSS：AI 开发中的环境污染与副作用隔离

> 系列导航：[完整目录](00-series-titles.md)

一次完整回归结束后，测试报告全部绿色，我却在对象存储里看到了刚生成的测试文件。文件名带着随机前缀，看起来像正常测试产物，但它进入的不是本地模拟服务，而是团队正在使用的真实 OSS 空间。

排查后发现，测试配置只覆盖了存储桶名称，没有覆盖访问端点和凭据来源；一个 Mock 又因为 Spring 上下文装配顺序没有替换到真实客户端。应用启动时沿用本地开发配置，测试于是顺利完成了真实上传。

从业务断言看，上传接口确实返回成功；从测试治理看，这次运行本身就是失败，因为它触达了不允许的外部资源。

## 核心判断：测试成功必须同时证明结果正确和副作用受控

测试退出码只能说明断言和进程状态。可靠验证还要回答：代码连接了什么资源，使用了哪份配置和凭据，产生了哪些写入，是否可重复、可清理，以及失败时有没有影响共享环境。

```text
测试可信度
= 业务断言成立
+ 依赖身份明确
+ 外部访问符合授权
+ 数据与副作用可隔离、可清理
```

AI 可以更高频地运行测试，也会更高频地放大错误配置。环境隔离不能依赖执行者每次记得检查，而要成为测试默认行为。

## 外部副作用往往藏在依赖和配置回退里

测试代码里没有显式上传命令，不代表不会访问 OSS。真实客户端可能通过自动配置、环境变量、用户目录配置、默认凭据链或动态服务发现被创建。

常见入口包括：

| 失控来源 | 典型表现 |
| --- | --- |
| 测试配置缺项 | 缺失值静默回退到开发配置 |
| Mock 注入失败 | 测试以为使用替身，实际 Bean 仍是真实客户端 |
| 默认凭据链 | 从环境或本机配置读取可用账号 |
| 网络无门禁 | 任意第三方地址都能被测试访问 |
| 共享资源名称 | 多个任务写同一桶、主题、缓存或数据库 |
| 清理逻辑脆弱 | 测试失败后资源长期残留 |

邮件、短信、支付、退款、消息队列、Webhook、搜索索引和共享数据库都具有相同风险。有些副作用会计费，有些会触发真实业务动作，还有些只留下难以解释的脏数据。

## 先为测试建立副作用清单

在决定隔离方式前，要列出被测链路可能触达的资源，而不是只看测试方法直接调用了什么。

```text
文件与临时目录
数据库、缓存和搜索引擎
消息队列与任务调度
对象存储和 CDN
邮件、短信与推送
支付、物流和其他第三方接口
回调、监控和审计系统
```

每项资源都应标记读取或写入、是否共享、是否包含敏感数据、能否本地替代、清理责任和允许访问的测试级别。未知依赖默认按不允许处理。

这份清单还要覆盖启动脚本、迁移脚本和测试框架插件，因为副作用可能发生在测试用例执行前。

## 第一层防线：配置必须失败关闭

测试使用独立配置，不能继承开发或生产凭据。关键外部配置缺失时应启动失败，而不是寻找“可用默认值”。

我会在启动阶段输出经过脱敏的资源清单：当前 profile、数据库类型与实例标识、对象存储端点和桶类别、消息命名空间、是否启用真实第三方客户端。检测到生产域名、共享资源或真实凭据来源时立即终止。

配置优先级也要有测试。很多事故不是值写错，而是团队以为测试配置优先，运行时却被环境变量或本机文件覆盖。

## 第二层防线：客户端默认使用替身

单元测试和大部分组件测试应注入 Fake 或本地模拟实现。替身不仅返回成功，还要记录调用参数、模拟失败和验证幂等，避免测试因为“什么都没做”而虚假绿色。

真实客户端的创建需要显式测试标签和授权配置，例如只有 `external-contract-test` 才能启用。应用可以在测试 profile 中注册保护器：一旦真实 OSS、支付或消息客户端被实例化，就直接失败。

Mock 是否生效也需要断言。可以检查实际 Bean 类型、客户端端点和调用记录，不能只相信注解存在。

## 第三层防线：网络和资源侧再次拒绝

即使配置和依赖注入都出错，测试进程也不应拥有任意出网能力。默认网络策略只允许本机、测试容器和明确的 allowlist；访问未知主机直接失败并记录调用栈。

资源侧使用独立账号、最小权限、限额和生命周期策略。测试账号不具备生产写权限，测试桶和消息主题使用任务前缀，数据库账号只能访问专用 Schema。

这三层防线分别应对配置疏漏、代码装配错误和最后一道环境失守，不能互相替代。

## 不同测试级别使用不同资源契约

```text
单元测试：无网络、无共享服务、全部依赖为内存替身
组件测试：本地容器或进程，资源随测试创建和销毁
集成测试：专用测试环境，独立命名空间和可重放数据
外部契约测试：显式授权、独立账号、最小写入、限额和审计
生产验证：独立发布流程，只执行预先批准的只读或探针动作
```

“集成测试需要真实”不等于必须使用团队共享或生产资源。真实协议可以由专用沙箱验证；确实没有沙箱的第三方接口，应限制样本、时间窗口和操作类型，并由人批准。

## 测试资源要有完整生命周期

每次运行使用任务或运行 ID 作为资源前缀，记录创建清单，在正常结束和失败退出时都尝试清理。清理失败不能被吞掉，应生成待处理记录和告警。

删除也不是唯一策略。为了排查失败，资源可以在限定时间内保留，但必须有所有者、过期时间和自动回收。共享开发数据不能因为名字包含 `test` 就由脚本批量删除。

对于不可逆或会触发外部通知的动作，最好根本不执行，而不是寄希望于事后补偿。

## 部署与测试脚本也属于被验证系统

这次问题还涉及 Python 环境、依赖安装、启动参数和 profile 选择。脚本决定应用使用哪个解释器、加载哪份配置、在哪个目录生成文件，也可能把本机值带入容器。

因此脚本要接受静态检查、参数边界测试和临时目录演练。路径应显式，变量缺失要报错，危险环境要拒绝，命令输出要保留配置来源但不泄露凭据。

测试框架、脚本和应用代码共同决定实际副作用，不能只审查业务方法。

## 完成证据要包含“没有发生什么”

可靠测试报告除了用例数量和断言结果，还应记录：

```text
代码提交和工作区状态
测试级别与配置来源
实际创建的客户端和资源标识
网络访问与外联拒绝记录
写入资源、清理结果和残留项
跳过的外部场景及批准人
```

“没有访问真实 OSS”可以通过真实客户端未创建、网络策略零违规和资源侧无新增对象共同证明。单靠操作者说“这次应该用了 Mock”不够。

## AI 与人如何分工

AI 适合扫描外部客户端、追踪配置优先级、生成替身、运行隔离测试和汇总资源清单。环境负责人提供测试账号、网络策略和回收机制；业务与安全负责人决定哪些副作用绝不允许自动化；工程师确认替身和测试级别是否仍能覆盖真实风险。

在未知配置、真实凭据或共享资源出现时，AI 应停止执行并报告，不能为了拿到绿色结果自动尝试可用连接。

```text
请审计【测试或验证命令】的外部副作用：

1. 列出代码、框架、脚本和启动阶段可能访问的全部外部资源；
2. 核对配置优先级、凭据来源、实际客户端类型和目标地址；
3. 按配置失败关闭、客户端替身和网络拒绝建立三层防线；
4. 为不同测试级别定义允许资源、命名空间、限额和授权；
5. 记录资源创建、异常退出、清理失败和自动过期；
6. 将业务断言与环境隔离证据一起作为测试结果。

不使用生产凭据，不静默回退真实客户端，不为追求测试绿色访问未知外部资源。
```

测试隔离解决了单次验证怎样不污染外部环境。下一篇继续讨论最难完全隔离的资源：多人共用的开发数据库，以及正确的强约束为何也必须选择正确的落地阶段。
