# 测试为什么真的上传了 OSS：AI 开发中的环境污染与副作用隔离

> 系列导航：[完整目录](00-series-titles.md)

一次完整测试运行后，我发现对象存储里出现了测试文件。测试本身全部通过，报告也很漂亮，但它连接的不是模拟服务，而是真实可访问的 OSS 配置。

这类问题很能说明“测试通过”为什么不等于验证可靠。代码逻辑可能正确，测试环境却在制造外部副作用。

## 副作用通常来自配置回退

问题不一定写在测试代码里。测试启动时读取了本地环境文件，某个存储配置没有被测试配置覆盖，于是沿用开发凭据；也可能因为 Mock 注入失败，代码静默回退到真实客户端。邮件、短信、支付、消息队列和第三方回调都有相同风险。

AI 执行测试时，如果只关注退出码，很容易把这种绿色结果当成成功。更可靠的验证需要同时回答：测试连接了什么、写到了哪里、是否产生不可逆或计费副作用。

## 测试默认应该拒绝真实外部访问

我后来把防线分成三层。第一层是配置隔离，测试使用独立配置和临时资源，不继承开发或生产凭据。第二层是客户端隔离，默认注入 Fake 或本地模拟实现，只有显式标记的集成测试才能访问外部服务。第三层是网络门禁，测试进程对未允许的主机直接失败，避免静默出网。

```text
单元测试：无网络、无真实存储、无共享数据库
集成测试：容器或专用测试资源，可重复清理
外部契约测试：显式授权、独立账号、限额和审计
```

测试数据也需要唯一前缀、生命周期和清理策略。即使使用专用测试桶，也不能依赖人工记得删除。

## 部署脚本同样需要测试

这次排查还涉及 Python 环境管理、依赖安装、启动参数和环境探测。部署脚本不是附属文本，它会决定应用到底加载哪份配置、使用哪个解释器、是否把开发值带入目标环境。因此脚本要像代码一样接受静态检查、参数测试和临时目录中的演练。

最终完整回归有两千余条用例通过，但真正有价值的改进不是数字增加，而是测试开始证明“没有访问不该访问的资源”。AI 可以高频运行验证，也会放大错误配置的副作用。自动化越快，环境隔离越要成为默认能力。
