# AGENTS.md、工作流文档和 Skill，到底应该怎么分工

> 系列导航：[完整目录](00-series-titles.md)

AI 工具用久以后，项目里会逐渐积累三种文档：项目规则、研发流程和专业 Skill。它们都在约束 AI，但如果都写成“使用 AI 时要注意什么”，很快就会重复、冲突、变长，最后没人维护。

我的分工原则是：项目规则解决“这个仓库是什么样”，工作流解决“一次任务怎样交付”，Skill 解决“某类专业问题怎样处理”。

## 一条跨模块规则应该放在哪里

我曾经把“业务模块之间必须通过公开 API 调用”同时写进项目规则和一个开发 Skill。后来项目边界调整，只更新了项目规则，仍在使用旧 Skill 的会话继续建议直接引用实现层。问题不在规则写错，而在同一事实拥有两个维护入口。

最后我保留项目规则作为唯一事实来源，工作流只要求实现前检查模块边界，Skill 只说明发现跨上下文调用时如何分析和暂停确认。三者可以互相引用，但不再复制完整规则。

| 内容 | 唯一归属 | 其他文档怎样使用 |
| --- | --- | --- |
| 当前模块依赖方向 | `AGENTS.md` | 工作流要求检查，Skill 读取结果 |
| 分析、实现、验证顺序 | 工作流 | 项目规则不重复 |
| DDD 边界分析方法 | Skill | 工作流按需触发 |

## `AGENTS.md` 写稳定事实

它应该像新成员入职须知，放技术栈、模块职责、依赖方向、构建命令、测试入口、接口端口、敏感操作和必须遵守的租户/权限规则。

它不适合放当天的故障、一次性需求、冗长教程和个人偏好。凡是每次进入项目都需要知道、且变化不频繁的内容，才值得写进去。

## 工作流文档写顺序和门禁

工作流回答“先分析还是直接改”“什么时候需要测试设计”“哪些高风险操作必须停下来确认”“验证失败如何报告”。它可以统一分析、实现、验证和交付的顺序，却不必重复每个模块的代码规范。

例如支付、积分、权限、数据库迁移和发布都可以在工作流中设置确认门槛：先给方案、风险和回滚，确认后才能改变状态。

## Skill 写可复用的专业能力

DDD 战略设计、测试用例推导、任务板同步等场景，通常跨项目或需要一套明确流程、参考资料和工具，适合做成 Skill。Skill 要写清适用条件、输入、输出、暂停点和安全边界，而不是成为一个“万能提示词”。

## 一个简单判断法

```text
每次进入仓库都要知道：AGENTS.md
每次完成任务都要遵循：工作流文档
只有特定问题才需要：Skill
只对当前问题有效：任务说明或交接记录
```

文档分层的目的不是增加管理感，而是让稳定事实、交付流程和专业方法各自保持可维护。分工清楚后，新会话更容易恢复，AI 的行为也更容易被团队复用和审查。
