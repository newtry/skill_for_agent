# AGENTS.md、工作流文档和 Skill，到底应该怎么分工

> 系列导航：[完整目录](00-series-titles.md)

AI 工具使用一段时间后，项目里通常会同时出现几类说明：`AGENTS.md` 写项目规则，工作流文档要求先分析再验证，Skill 又保存某类任务的处理步骤，任务卡和交接记录则继续补充当前现场。

如果它们都在重复“使用 AI 时要注意什么”，很快就会出现同一规则的多个版本。一次项目调整后，某份文档已经要求跨模块通过公开 API 调用，旧 Skill 却仍然建议直接依赖实现层。每一份说明单独看都合理，组合起来却无法判断谁是事实来源。

这个问题不是文档写得不够多，而是知识没有明确类型、所有者和依赖方向。我后来建立的原则是：稳定事实、交付流程、专业方法和任务现场必须分层保存，同一个事实只保留一个权威来源，其他载体通过引用使用它。

## 四类载体回答四个不同问题

| 载体 | 核心问题 | 典型内容 | 生命周期 |
| --- | --- | --- | --- |
| `AGENTS.md` 等项目规则 | 这个仓库怎样工作 | 模块、命令、依赖、权限和禁止事项 | 随项目演进 |
| 工作流文档 | 一次任务怎样完成 | 阶段、产物、门禁、验证和交付要求 | 随团队流程演进 |
| Skill | 某类专业问题怎样处理 | 方法、工具、参考资料、输出和暂停点 | 跨任务或跨项目复用 |
| 任务卡/交接记录 | 当前任务发生了什么 | 目标、现场、决策、diff、结果和下一步 | 随任务快速变化 |

项目规则回答“系统事实”，工作流回答“过程控制”，Skill 回答“专业方法”，任务记录回答“当前状态”。四者相互连接，但不能相互替代。

## 项目规则保存稳定且会改变实现选择的事实

项目级说明应该像新成员入职须知，优先保存一旦遗漏就会产生错误的内容：

- 应用和模块职责、依赖方向与公开契约；
- Admin/App 等入口、URL 前缀和鉴权约定；
- 构建、测试、启动命令及执行目录；
- 租户、账套、权限、逻辑删除和事务规则；
- 敏感配置、数据库、发布和删除操作边界；
- 项目特有的兼容性与验证要求。

它不适合保存某次故障、当天需求、个人偏好和长篇通用教程。判断标准仍然是：每次进入这个仓库都需要知道，并且它会约束实现选择。

## 工作流定义顺序、产物和门禁

工作流不描述库存模块有哪些表，而是规定任务怎样从分析进入方案、测试、实现、验证和交付。

例如，高风险任务必须在实施前输出业务不变量、方案、测试和回退；验证失败必须如实分类；提交、推送和发布需要单独授权。它规定“什么时候可以继续”，而不是重复“项目里有哪些规则”。

工作流还应允许风险分级。文档修改可以分析后直接实施，支付和数据库迁移则需要更强门禁。统一的是阶段语义，不是所有任务都使用相同篇幅。

## Skill 封装专业方法，而不是复制项目事实

DDD 业务建模、测试用例推导、数据库迁移审计和任务板同步，通常有稳定步骤、专用工具和参考材料，适合封装成 Skill。

一个可复用 Skill 至少应说明：

```text
适用条件：什么任务应该触发
必要输入：开始前必须获得哪些事实
处理流程：如何分析、调用工具和验证
交付结构：应该输出什么可审查产物
暂停条件：哪些歧义或风险需要人工确认
安全边界：哪些动作默认禁止或需要授权
```

Skill 可以要求读取项目规则，却不应复制当前模块依赖、内部地址和构建命令。否则每个项目变化都需要同步修改多份 Skill。

## 任务记录保存最新现场

当前需求、运行日志、已确认业务口径、未提交改动和测试结果变化很快，不应写进长期项目规则。

任务卡负责目标、约束、验收和授权；阶段交接负责已确认、已完成、未完成、当前工作区和下一步。任务结束后，只有反复出现且足够稳定的经验才回流到项目规则、工作流或 Skill。

这避免长期文档变成历史聊天的堆积，也避免下一次会话把一次性结论误当成永久规则。

## 同一事实只能有一个维护入口

我曾把“业务模块之间必须通过公开 API 调用”同时写进项目规则和开发 Skill。项目边界调整后只更新了一处，使用旧 Skill 的会话继续给出过期方案。

后来我保留项目规则作为唯一事实来源：

| 内容 | 权威来源 | 其他载体如何使用 |
| --- | --- | --- |
| 当前模块依赖方向 | 项目规则 | 工作流要求检查，Skill 读取并应用 |
| 分析、实现、验证顺序 | 工作流 | 项目规则只引用，不复制流程 |
| DDD 边界分析方法 | Skill | 工作流按任务类型触发 |
| 本次已确认调用链 | 任务记录 | 交接时更新，结束后按需沉淀 |

引用关系必须单向清晰。专业方法依赖项目事实，任务执行依赖工作流和 Skill；项目事实不反过来复制每个专业流程。

## 冲突时不能依靠文档名称猜优先级

不同载体可能控制不同维度：用户最新指令决定当前目标和授权，正式需求决定业务结果，项目规则约束仓库不变量，实时工作区证明当前状态，Skill 提供处理方法。

如果它们无法同时成立，AI 应报告冲突及影响，而不是简单认为 `AGENTS.md`、Skill 或较新的文件天然拥有全部优先级。尤其当代码与文档不一致时，需要判断是代码缺陷、文档漂移还是批准过的迁移状态。

## 文档需要所有者和验证机制

规则只有被读取还不够，还要能够被维护和检查：

- 每类载体明确负责人和适用范围；
- 关键命令、路径和链接可以自动校验；
- 规则变化时搜索引用方和重复定义；
- Skill 和工作流使用版本或变更记录；
- 真实故障后判断应更新任务经验还是长期规则；
- 定期删除已经失效且没有使用方的说明。

没有维护机制的“AI 记忆”最终会成为另一种过期依赖。

## 一个稳定的分层判断法

```text
每次进入仓库都必须知道：项目规则
每次完成任务都必须遵循：工作流
只有特定专业问题才需要：Skill
只对当前目标和现场有效：任务卡与交接记录
```
