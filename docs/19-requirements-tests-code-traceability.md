# 如何让需求、验收条件、测试用例和代码实现相互追溯

需求改了，哪些测试要改？一个失败用例对应哪条业务规则？一段关键代码为什么存在？没有追溯关系时，团队通常只能靠记忆和搜索回答这些问题，项目越大，答案越不可靠。

AI 很适合维护这条链路，因为它能在 PRD、方案、测试和代码之间做结构化整理。但前提是每一层都有稳定的标识和清晰的语言。

## 从验收条件开始编号

我会将需求拆成可验证的验收条件，例如 `AC-01`：有门店归属的用户返回正确门店名称；`AC-02`：无归属用户不报错；`AC-03`：不同租户不可互查。每条条件再映射到测试用例和实现落点。

```text
AC-01 -> TC-01 接口正常场景 -> UserProfileService / 转换层
AC-02 -> TC-02 空关联场景   -> 查询与空值处理
AC-03 -> TC-03 跨租户场景   -> 租户过滤与权限测试
```

它不要求把每一行代码都编号，只要关键规则有证据可追即可。

## 追溯矩阵的作用是发现空白

当某个验收条件没有测试，说明交付缺少证据；当测试没有对应需求，可能是历史回归用例，也可能是无效负担；当实现没有对应业务规则，则应评估是否是框架逻辑、技术债或误改。

AI 可以生成初稿，但人需要判断语义是否真的一致。例如“接口返回字段”与“账套隔离正确”不能被同一个浅层测试替代。

## 在变更时反向使用它

需求更新时，从验收条件找到受影响测试和模块；测试失败时，从用例找到业务规则与最近改动；线上缺陷出现时，补一个新的验收条件和回归测试。这会让追溯关系越来越贴近真实风险，而不是一份发布后就过期的表。

```text
请为【需求】建立轻量追溯矩阵：
验收条件 -> 测试场景/用例 -> 关键实现模块 -> 验证证据。
标出没有测试、没有实现依据或存在歧义的条目。
```

可追溯不是文档负担，它是一条把“需求说过什么”和“系统证明了什么”连起来的线。AI 能把线整理得更快，但不能代替人确认线两端表达的是同一件事。
