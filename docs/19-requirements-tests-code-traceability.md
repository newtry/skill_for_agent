# 如何让需求、验收条件、测试用例和代码实现相互追溯

> 系列导航：[完整目录](00-series-titles.md)

项目里经常出现三种追问：这个测试对应哪条需求？这段特殊逻辑为什么存在？需求改了以后，哪些代码和测试需要重新评估？如果只能靠搜索和记忆回答，项目越大越容易失联。

我后来开始给关键验收条件建立轻量的追溯关系，不追踪每一行代码，只追踪那些决定业务正确性的规则。

## 从验收条件开始，而不是从文件开始

例如用户资料需求可以拆成：有门店归属时返回正确名称；无归属时保持空值；不同租户不能互查；旧接口结构保持兼容。每条条件再映射到测试场景、关键实现位置和验证证据。

```text
AC-01 -> 正常关联测试 -> 用户服务/转换层 -> 响应样例
AC-02 -> 空关联测试   -> 查询与空值处理 -> 接口结果
AC-03 -> 跨租户测试   -> 租户过滤       -> 权限断言
```

## 追溯矩阵首先用来发现空白

没有测试的验收条件代表交付证据不足；没有需求来源的测试可能是历史回归，也可能是无效负担；没有业务规则依据的实现则需要判断是否为技术基础设施、技术债或误改。

AI 可以快速生成矩阵初稿、查找测试和代码引用，但不能仅凭关键词判断语义相同。一个断言“字段存在”的测试，不能替代“跨账套数据隔离”的测试。

## 跨代码库时，文档和实现也要进入矩阵

一次 V2 协议迁移同时涉及 Agent 后端、Java 服务和前端。后端契约已经更新，集成文档也写成新格式，但继续追踪后发现，部分 Java 映射仍在读取旧字段，前端类型又保留了兼容定义。每个仓库单独看都能构建，放在一起却存在三套迁移状态。

这时追溯对象不能只写“某接口已经实现”，而要按消费者展开：协议定义、生产方、每个消费方、契约测试、发布顺序和旧链路退出条件。文档也不是天然正确，它可能落后于实现，也可能提前描述了尚未完成的最终状态。

```text
协议条目 -> 后端生产 -> Java 消费 -> 前端展示
        -> 契约测试 -> 当前版本 -> 旧字段清理条件
```

AI 可以跨仓库搜索字段、事件名和示例数据，生成漂移清单；人需要判断差异是遗漏、兼容窗口还是已经批准的新设计。

## 变更时反向使用

需求更新时，从验收条件找到受影响测试和模块；测试失败时，反向定位业务规则和最近改动；线上缺陷出现时，补一条明确的验收条件和回归用例。这样追溯关系会随着真实风险增长，而不是写完一次就失效。

## 让 AI 生成一张轻量矩阵

```text
请为【需求】建立追溯关系：
验收条件 -> 测试场景/用例 -> 关键实现模块 -> 验证证据。
标出没有测试、没有实现依据、存在语义不一致或需要业务确认的条目。
不要把仅有相似关键词的代码自动判定为已覆盖。
```

追溯的目标不是让文档更厚，而是让“需求承诺”和“系统证据”能够互相找到。AI 擅长整理这条线，工程师负责确认线两端表达的是同一件事。
