# 当 AI 进入交付系统之后，我们真正需要管理什么

写完这 60 篇文章再回头看，我最初关心的问题已经发生了变化。

开始时，我想知道 Codex 能不能读懂项目、修复错误、生成接口和补测试。后来问题逐渐变成：它能否在真实业务边界内工作，能否把任务推进到可验证状态，能否跨会话和多工具协作，能否在协议升级和环境变化中继续保持正确，最后又能否连接到用户真正得到的结果。

答案不再取决于某一个模型有多强，而取决于我们是否建立了一套能够管理它的工程系统。

## 第一条线是交付闭环

AI 进入一个任务前，需要项目上下文和现场证据；开始执行前，需要目标、范围、权限和完成条件；执行过程中，只能通过受控工具改变系统；结束时，还要用测试、数据、日志和人工评审证明结果。

```text
理解现场 -> 定义任务 -> 受控执行 -> 验证结果 -> 交付或退回
```

这条闭环解决的是一次任务能否可靠完成。它把“模型说完成了”改造成一组可以检查的事实，也让失败能够停在分析、实现、验证或授权等明确位置。

## 第二条线是学习闭环

一次正确交付不会自动变成长期能力。项目规则可能仍然散落在聊天里，测试可能只存在于某个分支，失败经验也可能随着会话结束而消失。

因此，稳定事实要进入项目规则，专业方法要进入 Skill，关键业务约束要进入测试和脚本，阶段状态要进入任务板和交接记录。协议、配置和兼容代码发生变化时，这些知识还要被重新验证、更新和淘汰。

```text
执行证据 -> 复盘失败 -> 沉淀规则 -> 更新工具与测试 -> 下一轮演进
```

这条闭环决定了团队是在重复使用 AI，还是在积累驾驭 AI 的能力。

## 第三条线是价值闭环

技术动作完成后，还有一个更难的问题：用户目标是否真的达成？Agent 返回了推荐，不代表用户看见；用户点击了，不代表形成成交；订单产生了，还可能退款。代码、接口和模型指标都只是链路中的局部信号。

```text
技术完成 -> 用户触达 -> 业务行为 -> 实际结果 -> 重新校准目标
```

这条闭环要求系统保留可信的业务事实和归因口径，也提醒工程师不能把“任务执行成功”当成最终价值。

## 人最终管理的是判断与责任

当这三条闭环连接起来，AI 辅助开发就不再只是一个提高编码速度的方法。它变成一种新的工程分工：模型扩大搜索、生成和验证的速度，工具限制动作范围，流程保存状态，测试提供证据，人则定义业务意义、接受风险并对结果负责。

人的工作并没有因为代码更容易生成而消失。相反，需要人决定的事情更加集中：什么问题值得解决，什么数据口径成立，哪些边界不能跨越，什么证据足以接受结果，什么时候可以结束兼容，以及技术成果是否真的产生业务价值。

所以，这个系列最后想留下的并不是一套固定提示词，也不是某个工具的最佳实践，而是一个可以继续检验的判断：

> AI 辅助开发的成熟度，不取决于 AI 写了多少代码，而取决于团队能否把工程判断转化为可执行约束，并让每一次交付都可验证、可接管、可演进，最终连接到真实业务结果。

工具还会继续变化，模型也会继续变强。真正值得长期建设的，是围绕它们形成的上下文、边界、证据、记忆和责任系统。
