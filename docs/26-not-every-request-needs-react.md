# 不是所有请求都需要 ReAct：一次 Agent 路由架构的实践

> 系列导航：[完整目录](00-series-titles.md)

一开始做 Agent，很多人会把所有请求都交给一个 ReAct 循环：模型思考、调用工具、观察结果，再继续思考。它灵活，却不一定适合业务系统。简单问题被拉长，执行路径不可预测，失败重试困难，权限和审计也更复杂。

我后来把 ReAct 限制在它真正有价值的局部：需要根据工具结果选择下一步、路径不固定、但工具集合和风险边界已经受控的任务。其他请求优先使用确定性路由和固定流程。

## 从一个万能循环拆成五条路径

第一版路由把报表查询、业务动作和故障诊断都送进同一个 ReAct 循环。上线前回放发现，同一句固定指标查询有时调用一次工具，有时先搜索术语再调用两次；退款请求甚至可能在缺少参数时继续规划。路径灵活，却很难给出稳定的完成条件。

后来我把请求拆成一张路由表：

| 请求类型 | 处理方式 | 结束条件 |
| --- | --- | --- |
| 知识说明 | 检索后回答 | 来源和答案已返回 |
| 固定指标 | 参数校验 + 查询模板 | 指标、范围和数据已返回 |
| 业务动作 | 显式工作流 | 权限、预览、确认和执行状态完整 |
| 开放诊断 | 受控 ReAct | 证据满足诊断目标或达到停止条件 |
| 高风险或歧义 | 人工接管 | 已说明缺失信息和影响 |

拆分后，ReAct 不再承担所有请求的默认控制权，而成为路由系统中的一种执行策略。

## 先按任务类型分流

知识问答可以走检索；固定报表可以走参数校验后的查询；创建订单、冻结积分等业务动作应走明确的工作流；复杂诊断才考虑受控 ReAct；高风险或意图不明的请求转人工。

这种路由让大部分请求拥有稳定的延迟、成本和审计记录。模型不需要为“查一个已知指标”自由规划五步工具调用。

## ReAct 也要有边界

使用 ReAct 时，我会限制最大步骤数、允许的工具、单次查询范围、超时和重试次数。每次工具调用前再次校验权限和参数，禁止模型通过工具结果拼接出未授权操作。工具失败时返回结构化错误，不让模型把失败当成空结果继续编故事。

## 路由正确性需要专门评测

测试不能只问几个典型问题。要加入相似意图、行业别名、跨租户请求、复合请求、缺少参数、恶意诱导和工具不可用。每条用例都应检查路由是否正确、是否调用了不该调用的工具，以及最终是否给出可解释的兜底。

```text
请为【Agent 请求类型】选择处理模式：检索、固定流程、受控查询、局部 ReAct 或人工接管。
说明选择依据、权限和数据边界、超时/重试策略、审计字段及测试场景。
```

Agent 越接近真实业务，越不能把“灵活”误认为“可靠”。让确定的问题走确定的路径，把探索能力放进一个有护栏的局部，系统才容易测试和运营。
