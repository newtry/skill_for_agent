# 从认领、实现到回写：AI 任务自动化的完整闭环

任务板自动化如果只有“认领任务”和“执行脚本”，很快会变成另一套无法追踪的后台操作。真正有价值的闭环，应当让任何人都能回答：谁认领了任务，AI 看到了什么，改了哪些文件，验证了什么，为什么进入下一个状态。

## 一个任务至少经过六步

```text
发现 -> 认领 -> 上下文恢复 -> 分析/实现 -> 验证 -> 回写与评审
```

发现阶段过滤风险和依赖；认领阶段防止并发处理；上下文恢复阶段读取项目规则和工作区；实现阶段保持范围；验证阶段产出真实命令和结果；回写阶段把证据放回任务板，并将任务交给评审。

## 每一步都要有失败出口

任务描述不清，应回写待澄清；项目环境不可用，应回写环境阻塞；测试失败，应保留失败日志和当前 diff；发现高风险动作，应转人工确认；认领状态更新失败，不应继续执行。

没有失败出口的自动化，会把所有异常压缩成一个“执行失败”，既不利于恢复，也不利于统计改进。

## 回写内容比状态名称更重要

至少回写任务摘要、涉及文件、测试命令和结果、未验证项、风险、下一步和会话/版本标识。不要只写“已完成”，也不要把完整敏感日志直接贴到任务板。

## 任务板与代码仓库要互相校验

任务板状态可能过时，代码分支也可能被他人修改。AI 回写前要确认当前版本、分支和工作区，防止把旧会话的结果写到新任务上。评审人还要以实际 diff 和测试结果为准。

任务自动化的最终目标不是让 AI 隐形工作，而是让 AI 的工作可发现、可回放、可接管。完整闭环建立后，自动化才真正成为研发流程的一部分。
