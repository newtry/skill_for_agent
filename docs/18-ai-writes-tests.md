# 让 AI 自己写测试：测试通过不等于风险已经被覆盖

> 系列导航：[完整目录](00-series-titles.md)

AI 写测试很快，甚至可以让一组新代码立即变绿。但绿色只说明当前断言成立，不说明业务风险已经被证明不存在。

我见过只覆盖正常输入的测试，也见过把所有依赖都 mock 掉、只断言返回成功的测试；还有测试因为 profile 或筛选条件没有真正执行，却被报告成“已通过”。

## 测试应从风险开始

我现在不会先说“为这个方法生成单元测试”，而会先让 AI 列出需求中的不变量和风险：编码的最后合法值、积分重复冻结、导入中途失败、跨账套聚合、无权限访问、任务并发和回调乱序。

测试从风险出发，才不会被当前实现牵着走。一个风险如果没有对应断言，就应该明确写为未覆盖。

## 测试层级要和问题匹配

单元测试适合算法、边界和状态判断；集成测试适合事务、Mapper、数据库约束和配置组合；接口测试适合路由、序列化、鉴权和租户；端到端测试适合验证用户最终路径。

如果一个权限问题只在 mock Service 的单元测试里验证，证据是不够的。AI 应说明每条用例为什么选择这一层，以及哪些行为必须用更高层测试确认。

## 我关心测试是否真的执行

测试报告至少要包含命令、匹配到的测试数量、通过/失败/跳过数量和环境依赖。Maven profile 跳过测试、测试类没有被匹配、外部服务不可用，都要报告为未验证或环境阻塞。

```text
请从【需求和风险】设计测试：
1. 列出正常、边界、异常、幂等、并发、权限和回归场景；
2. 为每个场景选择单元、集成、接口或人工验证层；
3. 断言最终数据状态，不只断言成功响应；
4. 给出命令、预期执行范围和环境依赖；
5. 标明当前没有证据覆盖的风险。
```

AI 写测试的最大价值，不是让报告更快出现绿色，而是让“我们还没有证明什么”变得清楚。测试数量是产出，风险覆盖才是结果。
