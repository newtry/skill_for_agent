# 代码审查不只是找语法错误：如何让 AI 检查业务回归风险

让 AI 做代码审查，最容易得到的是一份风格清单：命名是否统一、是否存在空指针、有没有重复代码。它们有价值，但不是真实项目中最贵的风险。

ERP 的一次改动可能编译成功、单元测试通过，却改变了租户过滤、账套聚合、积分扣减顺序或 Admin/App 接口行为。代码审查真正要回答的是：这次修改是否改变了系统原本对业务的承诺。

## 先看改动影响了什么规则

我会让 AI 先总结 diff 的行为变化，而不是逐行解释代码：新增了什么入口，改变了哪些状态，读取或写入了哪些数据，调用了哪些外部模块，哪些异常路径被改变。然后将它与验收条件和项目约束对照。

例如一个查询增加了门店条件，看起来是在收紧数据范围，但如果移动端调用没有门店上下文，可能会让合法用户全部查不到；一个缓存优化改了 key，如果漏掉 `ledger_id`，就可能让不同账套共享结果。

## 四类业务回归风险

第一类是范围回归：权限、租户、账套、门店或逻辑删除条件被漏掉、放错位置或被绕过。

第二类是状态回归：成功、失败、重试、超时、取消和补偿之间的状态转换不再闭环。

第三类是兼容回归：接口字段、路径、默认值、异常码或旧版本调用行为发生非预期变化。

第四类是一致性回归：余额、流水、库存、汇总、缓存和异步任务只更新了一部分。

AI 可以根据 diff 搜索相关调用方、测试和配置，帮助扩展审查范围；但每个风险是否可接受，仍需结合业务确认。

## “改成实时查询”也可能是业务回归

一次审查中，AI 看到表里保存了商品和客户的冗余信息，建议删除快照字段，展示时实时查询主数据。代码更简洁，数据也似乎总是最新，但业务语义已经改变：历史推荐原本要保留生成当时的商品名称、价格和客户特征，实时查询会让过去的结果随着主数据修改而变化。

反过来也一样。如果业务要求展示当前库存，继续读取任务创建时的快照就会误导用户。快照和实时查询不是性能实现的二选一，而是“记录当时事实”与“读取当前状态”的业务选择。

审查这类改动时，我会要求 AI 列出每个字段的时间语义、更新来源和追溯要求，并用“生成后修改主数据”的测试验证旧记录是否应该变化。许多回归不是值算错了，而是值对应的时间变了。

## 一份业务审查提示词

```text
请审查当前 diff，重点检查业务回归，不要只做代码风格检查：

1. 总结行为变化、受影响入口、模块、数据和外部调用；
2. 检查租户、权限、账套、门店、逻辑删除和敏感字段范围；
3. 检查状态流、事务、幂等、并发、重试和补偿；
4. 搜索接口调用方、配置、缓存和任务，判断兼容性影响；
5. 将发现分为阻塞、需要确认、建议优化，并附文件和测试证据。
```

代码审查的目标不是找出最多问题，而是尽早发现那些“技术上能运行、业务上已经变了”的问题。AI 能扩大搜索范围，人需要守住业务不变量。
