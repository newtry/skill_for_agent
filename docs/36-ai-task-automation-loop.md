# 从认领、实现到回写：AI 任务自动化的完整闭环

> 系列导航：[完整目录](00-series-titles.md)

任务板自动化如果只有“认领任务”和“执行脚本”，很快会变成另一套无法追踪的后台操作。真正有价值的闭环，应当让任何人都能回答：谁认领了任务，AI 看到了什么，改了哪些文件，验证了什么，为什么进入下一个状态。

## 核心判断：任务自动化是一台可恢复的状态机

脚本串联只能描述正常路径，真实任务还会遇到需求冲突、认领失败、工作区变化、测试阻塞、评审退回和执行器中断。完整闭环的核心不是步骤更多，而是每个阶段都有进入条件、产物、失败出口和恢复依据。

## 一个任务至少经过六步

```text
发现 -> 认领 -> 上下文恢复 -> 分析/实现 -> 验证 -> 回写与评审
```

发现阶段过滤风险和依赖；认领阶段防止并发处理；上下文恢复阶段读取项目规则和工作区；实现阶段保持范围；验证阶段产出真实命令和结果；回写阶段把证据放回任务板，并将任务交给评审。

一条真实任务在任务板中的记录可以是：

| 阶段 | 状态与证据 |
| --- | --- |
| 发现 | 任务包含目标、验收、项目和风险标签 |
| 认领 | 原子写入执行者、基线版本和运行标识 |
| 恢复 | 读取项目规则、分支、diff 和最近测试 |
| 实现 | 记录修改文件，并保留用户原有改动 |
| 验证 | 回写命令、通过、失败、跳过和环境阻塞 |
| 评审 | 提交差异、未验证项和下一步，不自动关闭 |

如果任务在验证阶段因外部服务不可用而停止，下一轮应从相同基线和当前 diff 恢复，而不是重新认领并从头实现。

## 状态名称必须对应明确契约

我会把任务状态拆成：

```text
READY -> CLAIMED -> CONTEXT_RESTORED -> IMPLEMENTING
-> VERIFYING -> WAITING_REVIEW -> DELIVERABLE -> CLOSED
```

同时保留 `NEEDS_CLARIFICATION`、`ENV_BLOCKED`、`FAILED`、`CANCELLED` 和 `HANDED_OFF` 等出口。每次转换都要校验当前状态、任务版本和运行标识，并写入转换原因和证据引用。

例如进入 `VERIFYING` 前必须存在预期 diff 和验证计划；进入 `WAITING_REVIEW` 前必须有实际测试结果、未验证项和风险；进入 `CLOSED` 前必须有评审接受记录。状态不是进度标签，而是可以被系统检查的阶段契约。

## 每次运行都需要独立记录

任务可以经历多次执行和退回，因此任务 ID 不能代替运行 ID。一条运行记录至少包含：任务版本、执行器、代码基线、工作区或分支、开始和结束时间、状态转换、修改文件、命令摘要、验证结果和退出原因。

```json
{
  "taskId": "TASK-1024",
  "runId": "RUN-03",
  "taskVersion": 7,
  "codeBase": "commit-***",
  "state": "WAITING_REVIEW",
  "changedFiles": ["InventoryCache.java", "InventoryCacheTest.java"],
  "verification": {"status": "passed", "evidenceRef": "artifact-***"},
  "openRisks": ["集成环境缓存未回放"]
}
```

新一轮评审退回后创建新的运行记录，保留上一轮证据，而不是覆盖成最新一句状态。

## 每一步都要有失败出口

任务描述不清，应回写待澄清；项目环境不可用，应回写环境阻塞；测试失败，应保留失败日志和当前 diff；发现高风险动作，应转人工确认；认领状态更新失败，不应继续执行。

没有失败出口的自动化，会把所有异常压缩成一个“执行失败”，既不利于恢复，也不利于统计改进。

失败后是否可以自动重试，要看阶段和副作用。读取代码失败可以重试，原子认领失败应退出，测试环境暂时不可用可以保留现场等待，已经执行外部写入的步骤则必须先核对结果。统一“重试三次”会把技术瞬态故障和业务不确定性混在一起。

## 回写内容比状态名称更重要

至少回写任务摘要、涉及文件、测试命令和结果、未验证项、风险、下一步和会话/版本标识。不要只写“已完成”，也不要把完整敏感日志直接贴到任务板。

回写要幂等。相同运行和相同阶段重复提交不应生成多份互相冲突的报告；旧运行也不能覆盖新运行的结果。大型日志保存到受控产物中，任务板只记录脱敏摘要和引用。

## 任务板与代码仓库要互相校验

任务板状态可能过时，代码分支也可能被他人修改。AI 回写前要确认当前版本、分支和工作区，防止把旧会话的结果写到新任务上。评审人还要以实际 diff 和测试结果为准。

如果任务版本变化、基线提交前移或相关文件出现未知修改，当前运行应停止并重新恢复上下文。自动化不能为了完成任务而重置工作区，也不能把用户改动当成噪声删除。

## 一次中断怎样从检查点恢复

假设运行在 `VERIFYING` 阶段因测试数据库不可用而中断。恢复时不应重新执行认领和实现，而是先校验任务版本与代码基线，确认 diff 未变化，再读取上次失败命令和环境证据。数据库恢复后只重跑受影响验证，并把新结果绑定到当前代码版本。

若中断期间相关文件被其他人修改，原验证计划已经失效，任务应退回 `CONTEXT_RESTORED` 重新分析影响；若任务验收发生变化，则创建新运行。恢复点由事实决定，不能只看上次状态名称。

## 闭环需要运行指标

除了任务是否完成，还应观察认领冲突率、各阶段停留时间、环境阻塞率、评审退回率、自动重试次数、人工接管率和证据缺失率。这些指标可以定位流程瓶颈：任务总在上下文恢复阶段失败，说明任务输入不足；总在评审阶段补测试，说明验证契约不完整。

AI 负责在限定状态中执行分析、实现、验证和结构化回写；任务板服务负责并发、版本与状态约束；工程师负责评审、风险接受和接管。闭环完成的标准，是任务能够从任何中断点解释现场并继续，而不是所有任务都被自动标成成功。

```text
请恢复并继续【任务运行】：

1. 核对任务版本、运行标识、代码基线、分支和工作区；
2. 读取最近检查点、状态转换、验证结果和退出原因；
3. 判断历史证据是否仍适用于当前代码，不重复已完成步骤；
4. 若存在未知改动、外部副作用或验收变化，停止并说明接管条件；
5. 只执行当前状态允许的最小下一步，并幂等回写结果。
```

任务自动化的最终目标不是让 AI 隐形工作，而是让 AI 的工作可发现、可回放、可接管。完整闭环建立后，自动化才真正成为研发流程的一部分。
