# 不是所有请求都需要 ReAct：一次 Agent 路由架构的实践

> 系列导航：[完整目录](00-series-titles.md)

第一版业务 Agent 把所有请求都交给一个 ReAct 循环：模型规划、调用工具、观察结果，再继续规划。它很灵活，却让一个固定指标查询和一次退款请求拥有了相似的控制权。

上线前回放发现，同一句“本月销售额”有时直接调用查询，有时先检索术语再调用两次；退款请求在缺少订单号时仍然继续规划。路径不可预测，完成条件不稳定，权限和审计也难以解释。

我后来把 ReAct 限制在真正需要探索的局部，把大多数问题放进确定性路由和固定工作流。路由不是为了削弱模型，而是先决定模型在什么问题上可以发挥灵活性。

## 核心判断：路由应按风险和不确定性分流

ReAct 不是 Agent 的默认工作模式。固定问题需要可预测、可审计的路径；业务动作需要显式工作流；只有目标和路径都不确定的诊断任务，才适合进入受控探索。路由层的职责，就是在灵活性和可控性之间先做一次系统判断。

## 先识别意图、风险和完成条件

路由判断不能只输出一个意图名称，还要同时确定：

```text
请求类型：问答、固定查询、开放诊断还是业务动作
业务对象：客户、订单、库存、积分或其他对象
必需上下文：租户、账套、门店、时间和身份
风险等级：只读、建议、创建草稿还是改变业务状态
允许工具：本次请求可以调用哪些能力
结束条件：什么证据出现后可以停止
```

术语消歧未完成、关键参数缺失、权限不明或高风险动作需要确认时，路由应澄清或转人工，不应让 ReAct 自行补齐。

## 从万能循环拆成六种路径

| 请求类型 | 处理方式 | 典型结束条件 |
| --- | --- | --- |
| 知识说明 | 检索与引用 | 来源和回答已返回 |
| 固定指标 | 参数校验 + 查询模板 | 口径、范围和数据已返回 |
| 业务查询 | 受控工具或查询计划 | 权限通过，结果可审计 |
| 业务动作 | 显式工作流 | 参数、预览、确认和状态完整 |
| 开放诊断 | 受控 ReAct | 证据满足目标或达到停止条件 |
| 高风险/歧义 | 澄清或人工接管 | 缺口、影响和下一步已说明 |

这里的分类不是按模型能力，而是按任务不确定性和风险。固定问题走固定路径，开放问题才使用受控探索。

## 同一个业务主题为什么要走不同路径

“库存”相关请求至少可能进入三条完全不同的执行链：

```text
本月库存周转率是多少
-> 固定指标 -> 参数校验 -> 查询模板 -> 返回口径与结果

把 A 款调 20 件到人民路店
-> 业务动作 -> 补齐参数 -> 权限与库存校验
-> 预览 -> 确认/审批 -> 调拨工作流

为什么 A 款连续三天显示库存不同步
-> 开放诊断 -> 受控 ReAct -> 查询日志、任务和同步状态
-> 达到证据条件后停止或转人工
```

如果三者都进入 ReAct，固定指标会产生不必要的路径波动，调拨动作可能绕过确认，诊断任务又可能因为结束条件不清无限调用工具。路由真正控制的是执行权和停止权，而不仅是选一个提示词。

## 复合请求要拆成有依赖的子任务

用户经常把查询和动作放在一句话里：“如果库存超过 50，就给人民路店调 20 件。”系统不能把它当成一个自由推理任务一次完成。

更稳妥的执行方式是：先按固定查询路径得到带口径的库存事实，再根据条件生成调拨预览，最后等待确认。前一步失败、结果过期或权限变化时，后一步不得继续。子任务之间传递结构化事实和业务键，不传递模型自由改写后的自然语言结论。

这种拆分也让完成状态可解释：查询完成不等于调拨完成，生成预览不等于已经写入，接口受理不等于业务状态收敛。

## ReAct 的边界必须由系统强制

允许使用 ReAct 时，我会限制最大步骤数、工具集合、单次查询范围、并发、超时、重试和成本。每次调用前重新校验身份、权限和参数，禁止模型根据工具结果拼接出新的未授权操作。

工具错误必须与空结果区分，模型不能把“查询失败”总结成“没有数据”。达到步骤或预算上限时，返回未完成状态或转人工，而不是继续循环或编造结论。

## 路由表本身也是业务契约

每条路由都要有示例、反例、所需上下文、允许工具、失败处理和版本。新增一个意图不只是添加提示词，还要更新路由、权限、评测、监控和人工接管规则。

路由冲突时，安全和授权约束优先于模型偏好。无法区分“查库存”和“调拨库存”时，应停在澄清，而不是选择更有副作用的动作。

一条可审查的路由记录至少包含：识别出的意图、业务对象、风险等级、缺失参数、候选路径、最终路径、允许工具、结束条件、路由版本和选择依据。这样发生错误时，团队才能判断是术语识别错、路由规则错，还是后续工具越过了边界。

## 路由失败也要有确定结果

路由器不必强行命中一个业务能力。无法识别、上下文冲突、工具不可用、风险过高和超出支持范围，都应是正式结果：澄清、拒绝、降级或人工接管。

降级路径也要受控。固定查询工具不可用时，可以返回稍后重试或转人工，不能自动退化成模型编写自由 SQL；业务动作缺少审批能力时，可以创建草稿，不能把草稿描述成已执行。

## 路由正确性需要专门评测

评测样本应包含行业别名、相似意图、复合请求、缺少参数、跨账套、空数据、恶意诱导、工具不可用和重复动作。每条用例检查的不只是最终文本，还包括路由、工具、参数、权限、停止原因和输出状态。

AI 可以帮助整理历史请求、生成相似意图和识别路由冲突；工程师负责定义允许路径、预算和技术降级；业务与安全负责人确认高风险动作和人工接管条件。路由上线的完成证据应包括版本化路由表、冲突样本、阻断规则以及每条路径的成功和停止回放。

```text
请为【Agent 请求类型】选择处理模式：

1. 识别意图、业务对象、必需上下文和风险等级；
2. 在检索、固定查询、受控工具、业务工作流、局部 ReAct 和人工接管中选择路径；
3. 说明允许工具、参数、权限、超时、重试、预算和结束条件；
4. 列出相似意图、缺参、越权、工具失败和恶意输入测试；
5. 输出路由版本、审计字段和未确认项。
```

路由的价值，是让系统大部分时候可预测，在不确定时知道停下，在需要探索时把探索限制在安全空间。下一篇将处理这条路由链上的纵深安全：即使模型被诱导，工具和输出仍然不能泄露或越权。
