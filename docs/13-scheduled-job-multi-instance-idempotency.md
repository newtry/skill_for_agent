# 从单机定时任务到多实例运行：让 AI 帮助设计幂等机制

> 系列导航：[完整目录](00-series-titles.md)

一个月度积分发放任务在本地运行了很久，从未出现问题。服务扩容到两个实例后，两个调度器在同一时刻扫描到相同用户，各自完成了一次发放。日志显示两个任务都“成功”，用户账户里却多了一笔积分。

最直接的修复是增加分布式锁，保证同一时刻只有一个实例执行。但如果实例在写入积分后、释放锁前崩溃，任务重试仍可能再次发放；人工补偿、消息重投和下一次扫描也可能绕过原来的锁入口。

锁解决的是某一时刻谁能进入，幂等解决的是同一个业务动作被请求多次后，最终只能产生一次有效结果。两者不是同一个问题。

## 先定义什么叫“同一个业务动作”

幂等设计的起点不是选择 Redis 还是数据库锁，而是定义业务幂等键。

对于月度积分，稳定业务键可能是：

```text
租户 + 用户 + 积分类型 + 业务月份 + 发放规则版本
```

JVM 实例、线程、任务执行时间和随机批次号都不能识别同一个业务动作。它们只描述某次执行，不描述这次执行想完成的业务效果。

业务键还必须覆盖规则变化。如果同一月份允许按新规则补差额，就需要明确这是原动作的修正，还是一个新的发放动作；不能简单修改幂等键绕过历史记录。

## 幂等的目标是重复执行后结果收敛

可以用一个非数学化表达理解幂等：对同一个业务键执行一次或多次，系统最终可观察到的业务结果相同。

这不代表每次请求都返回完全一样，也不代表代码只运行一次。重复请求可以被识别、记录和正常应答，但积分余额、业务流水、消息通知等有效副作用不能重复产生。

因此，验证幂等需要检查最终业务状态，而不是只看第二次调用是否报错或某个实例是否拿到锁。

## 重复来源远不止多实例调度

我会先让 AI 列出同一动作可能从哪些路径再次进入：

- 多个服务实例同时触发定时任务；
- 调度平台因超时自动重试；
- 进程中断后恢复或补偿；
- 消息至少投递一次造成重复消费；
- 运维或业务人员人工重跑；
- 历史失败记录被下一周期再次扫描；
- 状态更新失败后，上游认为任务尚未完成。

如果幂等只加在定时任务入口，其他入口仍能重复产生业务效果。真正的保护应该靠近业务副作用发生的位置，并由所有触发路径共同使用。

## 四层机制承担不同责任

可靠方案通常由四层共同组成：

| 层次 | 作用 | 不能单独解决的问题 |
| --- | --- | --- |
| 调度协调 | 减少多个实例同时扫描和争抢 | 锁失效、人工重跑和历史补偿 |
| 任务认领 | 用租约或条件更新确定当前处理者 | 写入成功后状态更新失败 |
| 业务幂等 | 根据业务键判断效果是否已发生 | 并发检查同时通过 |
| 数据约束 | 唯一键、条件更新和事务保证最终结果 | 外部消息等非数据库副作用 |

分布式锁可以降低竞争和资源浪费，但数据库唯一约束或原子条件写入才负责守住“只能有一条有效发放记录”。业务流水与余额更新应处于明确事务中，使冲突失败不会留下半完成状态。

对于外部通知、消息或文件生成，还需要稳定事件标识和消费端幂等。主表没有重复，不代表邮件发送、积分到账通知或下游事件没有重复。

## 任务状态必须允许中断后接管

重要任务不能只靠一条开始和失败日志。它需要持久化业务键、批次、处理实例、开始时间、租约、重试次数、错误摘要和最终状态。

```text
待执行 -> 处理中 -> 成功
                   | 可重试失败 -> 待执行
                   | 不可重试失败 -> 人工处理
```

“处理中”不能永久属于某个已经崩溃的实例。租约到期后，其他实例可以接管，但接管前必须先核对业务效果是否已经发生。否则在“数据写入成功、任务状态更新失败”的崩溃点，接管会再次执行。

这也是为什么状态记录与业务结果必须能够对账。任务状态是流程事实，业务表和流水是结果事实，两者不一致时需要恢复规则，而不是盲目相信其中一个。

## 要逐个分析崩溃点

顺序执行的代码中，每两个关键步骤之间都可能中断：

```text
认领任务
-> 写入业务数据
-> 记录业务流水
-> 发送下游事件
-> 更新任务成功状态
```

AI 应逐段回答：如果进程在这里崩溃，哪些状态已经提交，下一次执行如何识别，是否需要补偿。尤其要关注以下情况：

- 业务数据成功，流水失败；
- 数据和流水成功，事件未发送；
- 所有效果成功，任务状态未更新；
- 事件发送成功，发送记录未保存；
- 自动重试与人工补偿同时发生。

把整个方法放进一个大事务，只能覆盖同一数据库内的操作，无法原子包含消息、第三方接口和进程状态。跨系统副作用仍需可重试、可识别和可对账的设计。

## 并发测试要验证最终效果

我会让 AI 至少覆盖下面的测试：

| 场景 | 关键断言 |
| --- | --- |
| 两个实例同时触发 | 同一业务键只有一个有效结果 |
| 锁或租约执行中到期 | 接管不产生重复效果 |
| 写入后进程中断 | 重试能够识别既有业务结果 |
| 状态更新失败 | 任务记录与业务结果可以重新对账 |
| 自动重试与人工补偿并发 | 条件更新和唯一约束阻止双重处理 |
| 下游消息重复投递 | 消费方最终效果仍然唯一 |
| 跨周期扫描历史失败 | 不把旧成功记录当成新任务执行 |

测试需要并发启动真实处理路径，并检查业务表、流水、任务状态和外部事件数量。只验证“第二个实例没有拿到锁”会遗漏锁过期和补偿入口。

## 观察重复被正确拦截同样重要

幂等机制生效后，重复请求不会都表现为错误。系统应记录业务键、触发来源、首次结果、重复次数和最终处理方式，以便区分正常重试、异常风暴和人为重复操作。

唯一键冲突如果只被吞掉，团队无法判断是保护机制正常工作，还是上游持续错误重放。监控应同时关注任务积压、长期处理中、重试次数、幂等命中和人工处理量。

## 我让 AI 先画“重复安全性”

```text
请只读分析【定时或异步任务】的重复执行安全性：

1. 定义业务效果和稳定幂等键，不使用实例或执行 ID 代替；
2. 列出调度、重试、补偿、消息和人工重跑等全部触发源；
3. 说明调度锁、任务认领、业务幂等和数据约束各自责任；
4. 画出任务状态、租约、接管和失败恢复路径；
5. 逐个分析关键步骤之间的进程崩溃结果；
6. 验证业务数据、流水、状态和外部副作用最终只生效一次；
7. 给出监控、对账和人工处理方案。
```

AI 能快速搜索所有触发入口、生成崩溃点矩阵和并发测试。工程师必须确认什么构成同一个业务动作，以及重复情况下允许返回什么结果。

## 幂等不是阻止重复，而是让重复变得安全

分布式系统无法假设请求只来一次。可靠设计接受重试、重复投递和进程中断是常态，再通过业务键、状态、约束和对账让结果收敛。

支付和积分说明了单个业务流程怎样在异步、失败和补偿中保持状态正确；第 13 篇进一步把问题扩展到多实例、重试和重复投递，让相同业务动作无论执行多少次都只产生一次有效结果。
