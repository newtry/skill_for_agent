# 不要只看 AI 写了多少代码，要看它完成了多少验证

> 系列导航：[完整目录](00-series-titles.md)

AI 让代码产生速度明显变快，也让“写了多少”变成一个很容易被误用的指标。新增几百行代码不代表完成了需求，删掉几百行也不代表风险已经消失。

我现在更关注另一组问题：它查清了哪些事实，覆盖了哪些风险，执行了哪些验证，还有哪些结果只是推测。

## 代码只是交付链的一段

一个积分功能的质量，不在于写了多少 Service，而在于冻结、确认、释放、幂等、并发和流水是否闭环。一个发布任务的质量，不在于脚本有多长，而在于配置、迁移、监控和回滚是否经过检查。

因此 AI 的交付报告应该包含需求、改动、测试、数据证据、环境限制和未验证项，而不是只贴 diff 统计。

## 验证要和风险对齐

正常路径用单元测试可能够用；跨租户需要权限或接口验证；事务和批量导入需要数据库最终状态；支付和发布需要受控环境与人工确认。测试层级不是目标，但必须与风险匹配，最终证据要足以回答业务问题。

如果测试被跳过、外部服务不可用或只 mock 了关键依赖，应该明确说明覆盖边界。诚实的“未验证”比虚假的绿色更有价值。

## AI 可以把验证做得更系统

让 AI 根据验收条件生成测试矩阵，搜索所有入口，执行聚焦命令，整理失败日志，比较前后数据和生成发布检查表。工程师则检查断言是否真的代表业务规则。

衡量 AI 的指标可以从“生成代码行数”换成：有效发现的问题数、风险覆盖率、返工次数、验证证据完整度和高风险误操作次数。

## 测试数量也不能单独成为绩效

在一个持续扩展的 Agent 项目里，完整回归从近两千条增长到两千余条。这个数字说明覆盖面在增加，却没有阻止一次测试连接真实对象存储。所有断言都通过了，环境隔离仍然失败。

因此团队度量至少要分三层：

```text
产出：代码、测试、文档和完成任务数量
质量：验收覆盖、回归失败、返工和缺陷逃逸
治理：未授权动作、环境污染、证据完整度和可回滚性
```

进入业务 Agent 后还要增加结果层：任务完成率、人工接管率、用户采纳和净业务结果。产出指标回答做了多少，质量与治理指标回答是否可信，结果指标回答这些工作是否真的有价值。

代码是手段，验证才是交付的证明。
