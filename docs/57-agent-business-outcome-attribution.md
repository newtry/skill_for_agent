# Agent 如何从任务完成走向业务结果：曝光、反馈与净成交归因

> 系列导航：[完整目录](00-series-titles.md)

一个推荐 Agent 可以顺利生成客户和商品组合，接口返回成功，前端也展示了卡片。按照技术指标，这次任务已经完成。但业务方真正关心的问题是：用户看到了吗，采纳了吗，最后成交了吗？

如果系统回答不了这些问题，Agent 的优化就只能依赖“模型觉得推荐合理”或少量主观反馈。

## 先把一条结果链连接起来

我在后续实践中把推荐结果看成一条可追踪链路：

```text
推荐生成 -> 前端曝光 -> 用户反馈/操作 -> 业务单据 -> 成交或退款
```

每个环节都需要稳定的关联标识。推荐生成时记录批次和条目，前端曝光时回传用户实际看到的内容，反馈事件标记采纳、忽略或不相关，后续订单事实再通过明确规则与推荐关联。

这里不能简单地把“推荐后发生的订单”都算成 Agent 成果。客户可能本来就要购买，订单也可能只包含部分推荐商品，还可能随后退款。归因必须定义时间窗口、客户和商品匹配规则、重复推荐去重方式，以及成交金额是毛额还是扣除退款后的净额。

## 技术事件与业务事实要分开

曝光和点击属于交互事件，订单和退款属于业务事实。它们的数据所有权、可靠性和到达顺序不同。实践中，我让推荐上下文记录自身事件，通过 Outbox 保证关键反馈可投递，再由适配层读取销售事实，而不是让推荐模块直接修改订单模型。

这样既保留了业务边界，也允许订单延迟、重复消息和退款反转。归因结果可以重算，原始事实不能被推荐系统随意改写。

## 指标必须能指导下一步

我最终更关注一组分层指标：生成成功率衡量系统可用性，曝光率衡量结果是否到达用户，反馈率衡量交互，采纳率和净成交衡量业务价值。某个指标下降时，才能判断问题在路由、内容、展示还是后续流程。

这也改变了 Agent 评测。离线测试可以判断工具和答案是否正确，线上反馈用来观察真实效果，但不能直接把成交当成单一模型分数。业务季节、库存、价格和销售人员都会影响结果，需要保留实验分组和归因口径。

Agent 从“能完成任务”走向“能创造结果”，中间差的不是更强的提示词，而是一套可信的反馈和业务事实链。只有技术执行与业务结果被连接起来，优化才有方向，投入也才有证据。
