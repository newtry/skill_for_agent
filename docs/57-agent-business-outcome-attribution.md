# Agent 如何从任务完成走向业务结果：曝光、反馈与净成交归因

> 系列导航：[完整目录](00-series-titles.md)

一个推荐 Agent 成功生成了客户与商品组合，接口返回 `completed`，前端也渲染出业务卡片。按照技术指标，这次任务已经完成。

几周后复盘时，团队却回答不了几个更重要的问题：推荐卡片是否真的出现在用户可见区域；销售人员有没有查看、采纳或修改；后续订单包含了哪些推荐商品；成交以后是否发生退款；没有使用 Agent 的相似客户表现怎样。

如果这些事实没有被连接起来，“生成成功率很高”只能证明系统在运行，不能证明它创造了业务价值。反过来，把推荐后发生的所有订单都算成 Agent 成果，又会把自然成交误认为模型贡献。

## 核心判断：从技术完成到业务价值需要一条可重算的事实链

Agent 的一次运行应该沿稳定标识连接到曝光、反馈、业务动作、订单和退款，但这些事实要保持各自的数据所有权，不能为了归因被推荐系统改写。

```text
推荐生成
-> 用户实际曝光
-> 反馈或业务动作
-> 订单明细
-> 履约、取消与退款
-> 按版本化规则计算净结果
```

这条链的目标不是制造一个更漂亮的总成交额，而是让团队能够区分：系统是否可用、结果是否到达、用户是否采用、业务事实是否发生，以及其中多少变化可以合理归因于 Agent。

## 先区分技术事件、交互事件和业务事实

| 层次 | 示例 | 数据所有者 | 能证明什么 |
| --- | --- | --- | --- |
| 技术执行 | 任务完成、工具成功、卡片生成 | Agent 平台 | 系统产出了结果 |
| 结果曝光 | 卡片进入可视区域、用户打开详情 | 前端与行为平台 | 用户有机会看到结果 |
| 用户反馈 | 采纳、忽略、不相关、修改建议 | 业务应用 | 用户对结果作出反应 |
| 业务动作 | 创建报价、加入跟进、生成补货单 | 对应业务模块 | 建议进入工作流程 |
| 业务事实 | 订单、发货、取消、退款 | 交易与财务系统 | 实际经营结果 |

生成卡片不等于曝光，曝光不等于采纳，采纳不等于成交，成交也不等于净收益。漏掉任一层，指标变化时就无法判断问题发生在哪里。

## 每个结果条目都需要稳定关联标识

只给整次任务一个 ID 不够。一次推荐可能包含多个客户和商品，同一客户还可能在短期内收到重复推荐。

我会至少保留运行 ID、推荐批次 ID、条目 ID、客户、商品、规则或模型版本、数据快照时间和生成范围。前端曝光和反馈必须回传条目 ID；后续业务动作保存来源关系；订单适配层再根据明确规则关联到推荐条目。

```text
run_id：一次 Agent 执行
batch_id：面向一个业务范围的结果集合
item_id：一个客户与商品建议
source_version：意图、规则、模型和数据口径版本
occurred_at：事实实际发生时间
recorded_at：系统收到事实的时间
```

实际发生时间与记录时间要分开，因为订单、退款和离线同步可能延迟到达。没有这一区分，回算窗口和实时看板会得到不同结论却无法解释。

## 事件可靠性不能依赖一次接口调用

业务操作成功后再单独发送事件，可能出现业务已提交而事件丢失；先发事件再写业务，又可能记录一个最终失败的动作。

对关键反馈和业务动作，我更倾向于使用 Outbox：业务数据与待发送事件在同一事务保存，投递端按至少一次语义重试，消费端根据事件 ID 和业务键幂等。原始事件只追加，不由归因任务覆盖；迟到事件和退款通过重新计算修正结果。

这套机制还要处理：

```text
重复曝光和重复反馈
消息乱序与延迟到达
同一推荐产生多个订单
一个订单只包含部分推荐商品
订单取消、部分退款和跨期退款
推荐条目或客户随后被删除
```

归因结果应是可以重算的派生数据，订单和退款仍由交易系统解释。推荐模块不能为了让指标闭合去修改业务事实。

## 先定义归因规则，再讨论成交贡献

“推荐后七天内同一客户下单”只是相关性规则，不天然代表因果贡献。至少要明确：

| 规则维度 | 需要作出的决定 |
| --- | --- |
| 时间窗口 | 从生成、曝光还是采纳开始，持续多久 |
| 匹配粒度 | 客户、商品、规格、门店和账套怎样一致 |
| 重复推荐 | 多次推荐命中同一订单时如何分配 |
| 部分成交 | 只计算命中明细还是整单金额 |
| 反向事实 | 取消、退款、拒收何时冲减 |
| 自然成交 | 如何用对照组或基线排除原本会发生的订单 |
| 规则版本 | 口径改变后历史结果是否重算 |

如果没有实验或可靠对照，只能诚实地叫“关联成交”或“推荐后净成交”，不能包装成 Agent 带来的增量成交。

更强的归因需要随机对照、分阶段灰度或相似群体基线，并控制价格、库存、季节、活动和销售人员差异。模型版本之间的比较也要使用相同口径和足够观察窗口。

## 用漏斗指标定位问题，而不是只看一个结果数

我会把指标分成几层：

```text
系统层：任务成功率、延迟、工具错误和成本
到达层：结果生成率、可展示率和真实曝光率
交互层：查看、反馈、采纳、修改和忽略
流程层：报价、跟进、补货或其他业务动作
结果层：订单明细、履约、退款和净成交
增量层：与对照或基线相比的变化
```

生成成功但曝光下降，问题可能在前端或协议；曝光稳定但采纳下降，可能是内容和业务时机；采纳正常但成交下降，还要看库存、价格和销售流程。只有分层指标才能指导下一步改进。

反馈本身也有偏差。主动点击“不相关”的用户不是全部用户，未反馈不能直接视为认可。团队需要同时保留显式反馈、实际动作和业务事实，避免优化成“更容易被点击”而不是“更有业务价值”。

## 隐私、权限和保留周期仍然适用

关联链可能跨客户、员工、行为日志和交易数据，不能因为要评估 Agent 就绕开原有边界。事件只记录归因需要的最小字段，查询继续受租户、账套和角色权限约束；敏感明细与聚合指标分层存储，并设置保留和删除策略。

离线评测数据和线上业务事实也要分开。真实订单不能直接进入任意提示词或调试日志，匿名化样本不能反向识别客户。

## AI 与人如何分工

AI 可以梳理事件链、发现断点、生成数据质量检查、比较不同版本漏斗并提出待验证假设。前端和业务系统负责产生可信事实，数据与工程团队维护关联、幂等和重算，业务负责人定义指标口径，实验负责人决定是否足以声称增量价值。

模型不能自行选择一个最有利的归因窗口，也不能把相关成交改名为贡献。指标名称、规则版本和限制条件必须与数字一起展示。

## 业务闭环完成需要什么证据

一条可用的业务结果链至少应证明：核心结果可以从生成追踪到曝光和动作；关键事件在失败与重试下不丢不重；订单和退款可以按相同口径重算；关联规则有版本和责任人；指标能按租户、时间和版本解释；无法证明因果的部分被明确标成相关性。

```text
请为【Agent 业务场景】设计结果与归因链：

1. 区分技术执行、真实曝光、用户反馈、业务动作和业务事实；
2. 设计运行、批次、条目和业务单据之间的稳定关联标识；
3. 处理 Outbox、至少一次投递、消费幂等、乱序和可重算；
4. 明确窗口、匹配粒度、重复推荐、部分成交、取消和退款规则；
5. 区分关联结果与增量贡献，说明对照或基线限制；
6. 给出分层指标、权限边界、数据质量检查和完成证据。

不把生成成功当成用户曝光，不把推荐后订单直接声明为 Agent 贡献。
```
