# 共享开发库里的强约束：为什么上线门禁不能提前成为团队阻塞

> 系列导航：[完整目录](00-series-titles.md)

为了保证数据正确，我们很容易在设计中加入唯一索引、非空约束或严格外键。若目标是一个独立环境，这些约束通常是好事；但在多人共用的开发数据库里，提前执行强约束可能让其他尚未升级代码的分支立刻无法写入。

一次数据治理任务中，新逻辑要求某组业务字段唯一。直接加唯一索引最省事，却会同时遇到历史重复数据、旧版本仍在写入、多个开发分支共用表结构三个问题。约束本来是上线门禁，过早落地却变成了团队阻塞。

## 正确性约束也有部署阶段

我把这类变更拆成“先兼容、再观测、后收紧”：

```text
代码先支持新规则，并保持对旧数据可读
扫描历史数据，生成只读报告和修复 SQL
所有写入方升级后开启告警或软校验
确认无违规写入，再添加数据库强约束
保留可重复执行的回滚或降级方案
```

这里的关键是把最终正确状态与当前协作条件分开。暂时不加唯一索引，不代表放弃唯一性，而是先用应用幂等键、冲突检测和观测保证过渡期可控。

## AI 可以准备变更，但不能替团队决定窗口

AI 很适合扫描重复数据、分析受影响写入点、生成幂等清理 SQL 和检查回滚脚本。对于生产或共享库，我通常只允许它执行只读查询，写操作脚本由人评审后在约定窗口运行。

生成的 SQL 也要考虑重复执行：清理第二次运行不能继续破坏数据，回滚不能假设现场完全没变，DDL 前还要再次检查冲突记录。所谓“可回滚”不是附上一条 `DROP INDEX`，而是说明数据转换后还能否恢复原语义。

## 门禁应该跟着发布成熟度逐步收紧

早期可以使用日志和监控发现违规，中期在新接口执行硬校验，最后才把约束下沉到数据库。等所有调用方、历史数据和回滚方案都准备好，数据库门禁才真正保护系统，而不是阻止协作。

AI 辅助开发经常追求一次把设计做到最终态，但真实系统必须经过迁移。一个约束是否正确，不只取决于规则本身，还取决于它在什么环境、什么阶段、由谁授权执行。把时间维度加入边界设计，才是系统演进中的工程正确性。
