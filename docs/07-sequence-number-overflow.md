# 一个流水号溢出问题，暴露了 AI 处理边界条件的能力

> 系列导航：[完整目录](00-series-titles.md)

商品编码和供应商编码采用四位流水号时，所有人都很容易理解这条规则：编号从 `0001` 开始，最大到 `9999`。

问题真正发生在已有最大编号为 `9999` 的那一刻。程序解析出数字、加一，再按四位格式化。很多人会直觉地认为结果会被限制在四位，实际上常见格式化函数不会自动截断，`10000` 仍然是五位。后续代码要么在长度校验处失败，要么在字符串截取、数据库字段或外部接口中暴露问题。

如果只围绕这次异常加一个长度判断，系统仍然没有回答最重要的问题：四位空间耗尽后，下一次创建应该发生什么？

这个问题让我认识到，流水号不是一段字符串，而是一个有命名空间、有限容量、并发分配和耗尽策略的资源系统。AI 能否修好它，取决于它是否从异常代码继续追问到完整规则。

## 先把编号从字符串还原成模型

一条业务编号通常由多个部分组成：

```text
业务编号 = 业务前缀 + 范围标识 + 固定宽度流水号
```

例如，同样的四位流水号可能按租户、账套、门店、日期或业务类型分别计数。若每个命名空间独立使用 `0001` 到 `9999`，理论容量是每个空间 9999 个；如果所有业务共享同一序列，容量和冲突风险则完全不同。

因此，排查编号问题至少要建立六个维度：

| 模型维度 | 必须回答的问题 |
| --- | --- |
| 命名空间 | 哪些租户、账套、业务类型或日期共享一组序列 |
| 数值范围 | 起始值、最大合法值以及是否允许零 |
| 格式规则 | 前缀、补零、总长度和字符集怎样组成 |
| 分配方式 | 当前最大值从哪里读取，并发时怎样保证唯一 |
| 历史兼容 | 旧格式、缺失前缀和异常数据怎样解析 |
| 耗尽策略 | 到达最大值后拒绝、扩容、换段还是人工处理 |

只看 `String.format` 或补零函数，最多能解释格式化行为，无法解释整套编号承诺。

## 容量问题有两条边界

流水号溢出通常同时涉及逻辑容量和物理容量。

逻辑容量由业务规则决定。四位十进制流水号从 `0001` 到 `9999`，在一个命名空间内只有 9999 个合法值。到达上限后继续取模或截断，会重新生成历史编号，直接破坏唯一性。

物理容量由存储和接口决定。即使业务决定把流水号扩成五位，还要确认数据库列长度、唯一索引、DTO 校验、前端展示、导入模板、外部接口和历史解析是否都能接受新格式。只扩大数据库字段，不能完成编号协议升级。

这两条边界必须分开评估：业务是否允许扩大编号空间，以及现有系统是否承载得住新格式。前者是产品与业务决策，后者是工程影响分析。

## 局部修复为什么会制造更隐蔽的问题

面对 `10000`，几种看起来直接的处理都可能出错：

| 局部处理 | 表面效果 | 隐藏风险 |
| --- | --- | --- |
| 截取最后四位 | 重新得到四位字符串 | `0000` 或历史编号重复 |
| 对 10000 取模 | 序列可以继续生成 | 静默回绕，唯一性失效 |
| 只扩大字段长度 | 五位编号可以入库 | 调用方、解析器和外部协议仍按四位工作 |
| 遇到冲突后重试 | 当前请求可能成功 | 容量耗尽时形成无效循环和数据库压力 |
| 重置当前最大值 | 暂时恢复生成 | 与历史数据和并发节点发生冲突 |

这些做法都在消除眼前异常，却没有维护编号系统的不变量。边界问题最危险的地方，正是一个“能继续运行”的补丁可能把显式失败变成静默数据错误。

## 修复前先定义编号不变量

我不会再把验收标准写成“流水号不再溢出”，而是先明确无论采用哪种方案都必须成立的条件：

```text
同一命名空间内，成功分配的编号始终唯一
生成结果符合当前有效的格式和长度协议
最后一个合法值可以被正常分配且不会提前拒绝
容量耗尽后行为明确，不截断、不回绕、不静默复用
并发请求不能拿到同一个编号
历史合法编号仍可读取、查询和展示
失败请求不会留下半完成业务数据
```

这些不变量会反向决定实现位置。唯一性不能只依赖应用层先查后写，还需要数据库约束或具备原子性的分配机制；耗尽检查必须位于所有生成入口都会经过的位置；格式升级需要兼容读取旧编号，而不是只修改新建逻辑。

## 边界测试要围绕状态跃迁设计

普通值只能证明普通路径成立，无法证明系统怎样跨越边界。我会把测试集中在编号状态发生变化的时刻：

| 场景 | 当前状态 | 需要验证的结果 |
| --- | --- | --- |
| 首次分配 | 没有历史编号 | 生成合法起始值 |
| 普通递增 | 最大值为 `0099` | 生成 `0100`，格式和范围正确 |
| 最后合法值 | 最大值为 `9998` | `9999` 能正常分配 |
| 首次超限 | 最大值为 `9999` | 按已确认策略明确失败或切换号段 |
| 异常历史值 | 存在无法解析或越界编号 | 不把异常值静默当成零继续生成 |
| 命名空间切换 | 不同租户、账套或前缀 | 序列隔离规则符合业务定义 |
| 并发分配 | 多个请求同时申请下一号 | 编号唯一，无重复成功记录 |
| 格式迁移 | 新旧编号同时存在 | 读取兼容，新增遵循新协议 |

其中“最后一个合法值”和“首次超限”必须分成两个测试。前者证明边界没有提前一位，后者证明容量耗尽策略真实生效。

并发测试也不能只断言接口都返回成功，需要收集全部结果并验证唯一性、连续性要求和数据库最终状态。若业务允许序列存在空洞，测试就不应错误地要求绝对连续；但重复编号通常不能接受。

## 容量耗尽是业务决策，不是 AI 自行选择的实现细节

达到上限后，系统可能有多种策略：停止创建并提示人工处理，扩大流水号位数，增加新的业务前缀，按年份或账套切换命名空间，或者迁移到另一种编号机制。

每种方案都影响用户认知、历史兼容、外部系统和数据库约束。AI 可以比较容量、改动范围、迁移成本与风险，却不能因为“扩成五位最简单”就替业务选择长期编号规则。

在业务决定前，安全行为通常是显式拒绝并告警，而不是猜测一个可以继续生成的规则。编号接近容量阈值时还应提前监控，避免等到最后一个号码使用后才通过用户报错发现资源耗尽。

## 我要求 AI 交付完整的边界分析

```text
请只读分析【编号规则】，不要先修改异常行。

1. 还原命名空间、起始值、最大值、格式、存储和全部生成入口；
2. 统计历史数据格式、当前容量使用和异常编号；
3. 明确唯一性、并发、兼容性和耗尽行为的不变量；
4. 区分技术事实、可选方案和需要业务确认的策略；
5. 覆盖首次、普通、最后合法值、首次超限、异常历史值、并发和迁移场景；
6. 给出影响范围、候选修复、监控和验证计划。
```

AI 在这里真正擅长的是横向搜索：找出所有编号入口、格式校验、数据库字段、唯一索引、导入导出和外部契约，再生成边界矩阵。工程师负责确认编号在业务中的长期含义，并判断哪种耗尽策略可以被接受。

## 边界条件检验的是系统承诺

流水号溢出看似只是一个五位数字放不进四位规则的问题，实际上暴露了系统对容量、唯一性、并发和兼容性的完整承诺。修复的目标不是让 `10000` 不再报错，而是让每一个状态跃迁都有明确行为，并由数据约束和测试共同证明。

第 6 篇处理的是一次失败请求怎样形成因果链；第 7 篇进一步说明，即使没有复杂调用链，一个边界值也可能牵动完整系统规则。下一篇进入批量导入：当异常数据、重复请求和部分失败同时出现时，工程能力将从单点边界扩展为一整套可恢复流程。
