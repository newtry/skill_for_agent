# 从自由 SQL 到受控查询：如何平衡 Agent 能力与数据安全

> 系列导航：[完整目录](00-series-titles.md)

让 Agent 查询数据库，是业务智能体最有吸引力的能力之一。用户可以直接问“上个月哪个门店销售额最高”，不用记报表入口和筛选条件。

但“让模型自己写 SQL 并执行”几乎把所有风险叠加在了一起：越权、跨租户、误聚合、慢查询、敏感字段泄露和不可审计。真正可用的方案不是禁止自然语言查询，而是把自然语言转换成受控查询计划。

## 模型可以理解问题，不能拥有数据库权限

Agent 可以识别指标、时间范围和业务对象，但最终查询应经过服务端的 schema、字段、租户、账套和角色校验。工具只暴露允许的指标和维度，不把数据库连接、任意表名和任意 SQL 执行能力交给模型。

例如销售额查询可以允许销售额、订单数、门店和月份这些已定义字段；不应允许模型顺手读取用户手机号、支付密钥或任意系统表。

## 查询计划比裸 SQL 更容易审查

我会让模型先输出结构化计划：指标、维度、过滤条件、时间范围、数据范围和排序限制。服务端校验计划后，再由固定查询模板或查询构建器生成 SQL。

```text
用户问题
 -> 指标/维度识别
 -> 术语和权限校验
 -> 结构化查询计划
 -> 固定模板生成 SQL
 -> 超时/行数/字段限制
 -> 脱敏结果与审计记录
```

这样既保留了自然语言入口，也把风险集中在可以测试的规则里。

## 三层验证不可省略

第一层验证查询是否只使用允许的表、字段、聚合和范围。第二层验证当前用户是否能访问这些租户、账套、门店和指标。第三层验证运行时资源，例如最大行数、超时、分页和成本限制。

即使查询只读，也要记录调用人、查询计划、数据范围、耗时和结果状态。只读不等于没有数据风险。

## 我会这样设计 Agent 查询任务

```text
请为【业务查询】设计受控查询方案：
1. 定义指标、维度、数据粒度和业务口径；
2. 将自然语言转换成结构化查询计划，不直接执行自由 SQL；
3. 列出允许字段、租户/账套/权限过滤和敏感字段；
4. 设计行数、超时、分页、审计和脱敏限制；
5. 给出错误口径、越权、慢查询和空结果测试。
```

Agent 的灵活性应体现在理解问题，而不是拥有无限数据库权限。查询计划、固定模板和运行时限制，才是自然语言和数据安全之间可维护的平衡。
