# 什么时候应该把提示词升级为 Skill

> 系列导航：[完整目录](00-series-titles.md)

我曾经把一段有效提示词复制到不同会话里使用。开始时它很方便，后来版本越来越多：不同项目各有一份，改了规则却忘记同步，真正需要的参考文件和验证步骤也只能临时补上。

这通常意味着它已经不再是一句话，而是一套需要复用和维护的方法。

## 核心判断：Skill 是有触发条件和验收标准的能力包

提示词主要影响一次回答，Skill 则要稳定处理一类任务。它不仅包含说明文字，还应明确适用场景、输入、步骤、参考材料、工具、暂停点、输出和验证方式。升级的目的不是让提示词更长，而是把重复判断变成可组合、可测试、可维护的执行协议。

## 第一版 Skill 往往只是“更长的提示词”

我最初把需求分析流程做成 Skill 时，几乎把所有经验都塞了进去：术语、方案、测试、实现和发布检查一口气执行。它看起来完整，实际触发范围太宽，小改动也被迫生成大量文档；遇到业务边界和上下文映射等高影响决定时，又没有明确暂停点。

后来我把专业能力拆开：领域边界设计负责统一语言、事件和上下文，并在关键边界停下来确认；测试设计负责把需求追溯到可执行用例；研发工作流只负责判断当前处于分析、实现、验证还是交付阶段，再按需调用前两者。拆分之后，Skill 才从文本模板变成可以组合的能力。

这次拆分还暴露出一个原则：Skill 应围绕一种稳定责任，而不是围绕“把整个项目做完”。领域建模、测试设计和研发编排有不同输入、完成标准和人工确认点，把它们塞进一个 Skill 会让触发范围和责任都失去边界。

## 不是所有提示词都值得做成 Skill

一次性的需求背景、临时日志和个人偏好留在当前任务里就够了。只有当一套流程会重复出现，有明确输入和输出，涉及固定的检查顺序、参考资料或工具，并且错误成本较高时，才值得升级。

例如从 PRD 推导测试、做 DDD 战略拆解、生成任务板交付记录，这些都不仅是措辞，而是完整方法。

我会用一张升级判断表：

| 判断项 | 适合保留提示词 | 适合升级 Skill |
| --- | --- | --- |
| 使用频率 | 偶发、一次性 | 跨任务重复出现 |
| 输入输出 | 每次完全不同 | 可以定义稳定契约 |
| 处理步骤 | 主要依赖临场判断 | 有可复用顺序和门禁 |
| 参考资料 | 当前会话即可 | 需要固定资料或脚本 |
| 错误成本 | 低、容易人工纠正 | 高、遗漏会造成返工或风险 |
| 维护需求 | 无版本依赖 | 会随工具、规则和项目演进 |

满足一两项并不必然升级。只有重复收益大于维护成本，并且能力边界能够说清，Skill 才比一段任务提示更合适。

## 一个 Skill 至少要写清楚五件事

适用场景、输入材料、处理步骤、输出格式和暂停/安全边界。若需要读取参考文件或执行脚本，还要说明来源、失败处理和验证方式。

Skill 不能只告诉 AI“请认真分析”，而要规定什么时候先问问题、什么时候必须停下确认，哪些动作禁止自动执行。

一个成熟 Skill 的结构通常包括：

```text
触发条件：什么请求应该使用，什么请求不应该使用
输入契约：必需材料、可选材料和缺失处理
执行步骤：顺序、分支、工具和参考资料
人工门禁：哪些决定必须暂停确认
输出契约：文档、代码、测试或任务回写的格式
验证标准：怎样证明能力完成，而不是只生成结果
版本与维护：依赖、变更记录、负责人和失效条件
```

若 Skill 会调用写工具，还要限制目录、环境和副作用；若会调用其他 Skill，则说明组合顺序和责任边界，避免多个能力重复产出或互相覆盖。

## Skill 也需要测试和回归

我会选取典型成功、输入缺失、边界冲突、高风险暂停和不应触发的反例任务。测试不只看最终文档是否完整，还要看是否正确触发、是否读取了必要材料、是否在人工门禁前停下，以及输出是否可以被下一流程消费。

工具、项目规则和参考资料变化时，要重新运行这些任务。一个过去有效的 Skill，如果仍引用旧命令或过期 Schema，会比临时提示词更稳定地制造错误。

Skill 的版本变化也需要说明兼容影响。修改触发条件可能让原本不使用该能力的任务自动进入；修改输出格式会影响下游任务板或文档；增加写工具会改变安全等级。这些都不是普通文案调整，应触发回归和评审。

## 从候选到正式 Skill 的生命周期

```text
重复提示词/纠正
-> 候选能力与边界分析
-> 最小 Skill 实现
-> 典型任务、反例和门禁测试
-> 小范围使用并收集失败
-> 正式发布与版本管理
-> 定期回归、拆分、合并或退役
```

候选阶段不要急着支持所有项目。先选择一类稳定输入和一个清晰输出，证明它能减少重复判断，再逐步加入变体。长期无人使用或与其他 Skill 重叠时，应合并或退役，避免能力目录本身成为选择负担。

## 用复盘而不是感觉决定升级

当同一类纠正反复出现、多个项目都复制同一套流程、输出质量依赖某些固定文件，或者新人无法稳定复现结果，就可以评估做成 Skill。

升级后也要用真实任务验证，定期删掉过期规则。Skill 越长不代表越专业，能稳定减少重复判断才有价值。

AI 可以从重复会话中发现候选步骤、生成样本和检查引用；能力维护者负责触发范围、人工门禁和版本；实际使用者提供失败反馈。Skill 成熟的证据，是同类任务在不同会话和工具中得到稳定过程与可审查结果，同时错误场景会正确拒绝或暂停。

```text
请评估【重复方法】是否应升级为 Skill：

1. 统计复用频率、输入输出稳定性、固定步骤和错误成本；
2. 划定触发与不触发场景，识别与现有 Skill 的重叠；
3. 定义输入、步骤、参考资料、工具、人工门禁和输出契约；
4. 设计成功、缺参、冲突、高风险暂停和反例任务；
5. 说明版本依赖、维护人、回归方式和退役条件。
```

提示词适合一次对话，Skill 适合一类可维护的工作。边界清楚后，个人经验才不会停在自己的聊天记录里。

判断一个 Skill 是否成熟，我现在看三件事：它是否在正确场景触发，是否在高影响决定前停下，是否能用真实任务证明输出比原流程稳定。
