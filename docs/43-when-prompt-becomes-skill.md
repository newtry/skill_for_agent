# 什么时候应该把提示词升级为 Skill

> 系列导航：[完整目录](00-series-titles.md)

我曾经把一段有效提示词复制到不同会话里使用。开始时它很方便，后来版本越来越多：不同项目各有一份，改了规则却忘记同步，真正需要的参考文件和验证步骤也只能临时补上。

这通常意味着它已经不再是一句话，而是一套需要复用和维护的方法。

## 第一版 Skill 往往只是“更长的提示词”

我最初把需求分析流程做成 Skill 时，几乎把所有经验都塞了进去：术语、方案、测试、实现和发布检查一口气执行。它看起来完整，实际触发范围太宽，小改动也被迫生成大量文档；遇到业务边界和上下文映射等高影响决定时，又没有明确暂停点。

后来我把专业能力拆开：领域边界设计负责统一语言、事件和上下文，并在关键边界停下来确认；测试设计负责把需求追溯到可执行用例；研发工作流只负责判断当前处于分析、实现、验证还是交付阶段，再按需调用前两者。拆分之后，Skill 才从文本模板变成可以组合的能力。

## 不是所有提示词都值得做成 Skill

一次性的需求背景、临时日志和个人偏好留在当前任务里就够了。只有当一套流程会重复出现，有明确输入和输出，涉及固定的检查顺序、参考资料或工具，并且错误成本较高时，才值得升级。

例如从 PRD 推导测试、做 DDD 战略拆解、生成任务板交付记录，这些都不仅是措辞，而是完整方法。

## 一个 Skill 至少要写清楚五件事

适用场景、输入材料、处理步骤、输出格式和暂停/安全边界。若需要读取参考文件或执行脚本，还要说明来源、失败处理和验证方式。

Skill 不能只告诉 AI“请认真分析”，而要规定什么时候先问问题、什么时候必须停下确认，哪些动作禁止自动执行。

## 用复盘而不是感觉决定升级

当同一类纠正反复出现、多个项目都复制同一套流程、输出质量依赖某些固定文件，或者新人无法稳定复现结果，就可以评估做成 Skill。

升级后也要用真实任务验证，定期删掉过期规则。Skill 越长不代表越专业，能稳定减少重复判断才有价值。

提示词适合一次对话，Skill 适合一类可维护的工作。边界清楚后，个人经验才不会停在自己的聊天记录里。

判断一个 Skill 是否成熟，我现在看三件事：它是否在正确场景触发，是否在高影响决定前停下，是否能用真实任务证明输出比原流程稳定。
