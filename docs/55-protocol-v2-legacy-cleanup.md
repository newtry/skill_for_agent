# 协议升级最难的不是切到 V2，而是安全删除旧链路

> 系列导航：[完整目录](00-series-titles.md)

一次 Agent 协议升级中，新版后端、Java 调用方和前端展示都已经跑通，测试也全部通过。表面上看，V2 已经上线条件具备，但继续审计代码后，仍能找到旧字段、旧事件名、兼容分支和只在文档里存在的过渡说明。

这让我意识到，协议迁移的完成标准不能是“新链路可用”，而必须包括“旧链路可以被证明不再需要”。

## 双轨兼容会制造隐性语义债

迁移期间同时接受新旧字段很常见。例如一个字段原来表达本地配置编码，后来改成模型标识。如果只是增加新字段并保留旧字段兜底，短期联调会更顺利，长期却可能出现三种语义：新调用方传新值，旧调用方传旧值，某些中间层又把两者互相复制。

编译器发现不了这种问题，因为类型可能都是字符串。常规接口测试也未必发现，因为任意一条路径都能返回成功。真正的风险是系统没有唯一语义来源。

## 我把迁移拆成四个阶段

```text
引入：定义 V2 契约、版本边界和新语义
切换：逐个迁移后端、Java、前端和文档
观测：记录旧协议调用，确认没有遗漏消费者
清理：删除旧字段、兼容分支、配置和测试夹具
```

每个阶段都有不同的回滚点。引入阶段可以关闭功能开关；切换阶段允许短期双读，但要明确优先级；观测阶段不能无限延长；清理阶段则需要重新跑跨端契约和关键业务场景。

## 搜索遗留只是起点

AI 很适合对多个代码库做全局审计：搜索旧字段、协议版本、事件名、配置键、示例 JSON 和文档。但搜索不到不等于迁移完成，还要验证运行时是否有动态拼接、序列化别名或外部消费者。

在这次迁移里，我把 Java、前端和 Agent 后端作为一个整体检查，并用九个受治理场景做跨链路验证。完整测试最终达到两千余条通过。测试结果证明新链路工作，而遗留搜索和调用观测证明旧链路可以退出，两类证据缺一不可。

## “暂时兼容”必须有退出条件

每个兼容分支都应写清责任人、观测指标、最晚删除时间和删除前验证。否则“先兼容着”会成为永久架构，后来的 AI 又会根据旧代码继续生成新实现，让语义债不断扩散。

协议演进真正考验的不是生成 V2 的速度，而是管理完整生命周期的能力。新链路上线只是中点，旧链路被安全删除，迁移才算结束。
