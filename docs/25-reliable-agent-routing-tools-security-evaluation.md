# AI Agent 不能只靠提示词：路由、工具、安全和评测

> 系列导航：[完整目录](00-series-titles.md)

做业务 Agent 时，最容易先写一段很长的系统提示词：告诉模型它是谁、知道什么、应该如何回答。演示阶段可能有效，能力一多就开始失控：固定指标查询被拉进复杂推理，写操作缺少确认，工具参数越界，敏感字段进入日志，出了问题也无法解释是模型、路由还是权限哪一层失效。

我后来把 Agent 看成一套受治理的业务系统，而不是一个会话框。自然语言只是入口，真正的产品能力由多个层次共同完成：理解业务语言，选择正确路径，在受控工具中执行，经过运行时安全约束，生成稳定输出，并用可回放评测证明系统满足底线。

第四辑的核心链路可以写成：

```text
业务语言 -> 意图路由 -> 安全与权限 -> 受控工具
-> 业务流程 -> 结构化输出 -> 回放评测 -> 上线门禁
```

提示词可以影响模型倾向，却不能替代任何一个系统边界。

## 核心判断：Agent 的可靠性来自责任分层

一个可交付的 Agent，不能把理解、授权、执行、状态和结果都压缩成一次模型调用。模型适合处理不确定的语言，服务端和业务系统则必须掌握确定的边界。只有先把责任拆开，后续的路由、工具、安全和评测才有明确归属。

## Agent 的责任不能集中在模型里

我会把一条业务请求拆成六类责任：

| 层次 | 主要问题 | 不能交给模型自行决定的内容 |
| --- | --- | --- |
| 语言理解 | 用户说的术语和目标是什么 | 业务词的最终口径和授权范围 |
| 路由 | 应该走哪种处理路径 | 高风险动作是否可以直接执行 |
| 工具 | 允许读取或改变什么 | 任意 SQL、任意接口和无限范围 |
| 安全 | 谁能看到、调用和操作什么 | 跨租户、敏感字段和真实资金动作 |
| 业务流程 | 状态怎样变化、失败如何恢复 | 已审批、已支付和已完成等事实状态 |
| 结果与评测 | 用户看到什么，系统是否可靠 | 用漂亮回答掩盖证据和安全失败 |

模型可以参与理解、分类和建议，但权限、数据范围、状态迁移和关键副作用必须由服务端、工具和工作流强制执行。

## 一次请求怎样穿过这套架构

以“帮我把 A 款从总仓调 20 件到人民路店”为例，完整链路不应由模型从头包办：

```text
用户表达
-> 术语层确认 A 款、总仓和人民路店对应的业务对象
-> 路由层识别为库存调拨动作，而不是库存查询
-> 权限层计算当前用户可操作的账套、仓库和门店
-> 工具层查询可调数量并生成调拨预览
-> 工作流等待用户确认或审批
-> 领域服务幂等创建调拨单
-> 输出层返回业务单号和真实处理状态
-> 评测与审计记录整条决策链
```

模型主要参与术语理解、参数提取和结果说明。仓库归属、可调数量、审批条件、幂等键和调拨状态都由确定性系统提供。这样即使模型误判了数量或漏掉了门店，后续校验仍能阻止错误写入。

早期版本的问题恰恰相反：一个通用工具同时接收查询和写入参数，模型根据对话自行决定是否执行。它在演示中路径很短，却无法回答“谁批准了这次调拨”“重复确认会不会生成两张单”“工具超时后到底有没有成功”。责任分层首先解决的不是扩展性，而是这些交付问题能否被明确回答。

## 路由决定系统的可预测性

用户问知识、查指标、查订单、执行调拨或诊断故障，风险、延迟、成本和完成条件都不同。让所有请求进入一个通用推理循环，等于放弃了这些差异。

路由层至少需要识别：意图、必需上下文、风险等级、所需工具和结束条件。模型可以提供候选分类，但高风险写操作、权限不明和关键歧义不能只依据模型置信度放行。

## 工具决定模型实际能做什么

工具不应是“执行任意 SQL”或“调用任意接口”的大门，而应是带有明确输入、数据范围、权限、幂等和审计字段的窄接口。查询工具限制指标和维度，业务动作工具限制状态、对象和操作类型，写操作工具要求业务键和确认。

工具失败必须返回结构化错误，不让模型把错误当空结果继续编造；工具结果也应尽量只包含完成下一步所需的最小数据。

## 安全必须覆盖完整数据流

安全边界贯穿输入、检索、路由、工具参数、数据库、模型上下文、输出和日志：

```text
用户输入 -> 意图与身份 -> 工具授权 -> 数据查询
-> 模型处理 -> 输出适配 -> 审计与遥测
```

任一环节泄露内部字段或绕过租户条件，最终页面没有显示敏感内容也不能算安全。提示词中的“不要泄露”不能替代字段过滤、权限校验、工具限制和日志脱敏。

## 评测要验证执行链，而不只是文案

Agent 的评测至少要能回答：路由对不对，工具是否越权，参数是否完整，数据口径是否正确，重复动作是否安全，输出结构是否可消费，失败是否转人工。

一次看起来正确的回答，如果调用了不允许的工具，或者把空结果推断成有数据，仍然是失败。每次请求都应该留下可回放的输入、路由、工具、授权、结果和输出摘要。

## 分层之后，每层都要有契约

只有架构图还不够，每一层都要定义输入、输出、失败状态和责任人：

| 层次 | 最低契约 | 关键证据 |
| --- | --- | --- |
| 语言 | 标准术语、歧义和业务对象 | 术语版本、消歧结果 |
| 路由 | 意图、风险、允许路径和结束条件 | 路由记录、停止原因 |
| 工具 | Schema、范围、权限和错误状态 | 参数摘要、授权与调用结果 |
| 工作流 | 状态机、确认、幂等和补偿 | 业务键、状态流水 |
| 输出 | 事实、建议、状态和动作契约 | Schema 校验、来源 |
| 评测 | 样本、断言和阻断条件 | 回放报告、版本基线 |

当某一层没有契约时，问题就会向模型提示词回流：靠提示词提醒它别越权、别重复、别泄露、别误报成功。这样的规则无法稳定执行，也无法在失败时定位责任。

## AI 和工程师分别负责什么

AI 适合扫描已有接口、整理意图清单、生成候选工具 Schema、寻找权限遗漏并构造失败样本。工程师和业务负责人必须确认术语口径、模块所有权、允许动作、风险等级、状态迁移和上线底线。

判断标准很简单：凡是会改变真实业务状态、扩大数据可见范围或影响责任归属的决定，都不能因为模型“看起来有把握”而自动生效。

## 一套 Agent 架构的上线门槛

在进入真实业务前，我至少要求系统能够证明：

1. 支持的意图和明确不支持的意图有清单；
2. 每类意图有确定、受控的处理路径；
3. 工具输入、数据范围、写入和幂等受到服务端限制；
4. 租户、账套、角色和敏感字段在运行时校验；
5. 业务动作经过预览、确认、执行和结果回报；
6. 输出符合结构契约并区分事实、推断和建议；
7. 失败、越权、注入、重复和人工接管有评测样本；
8. 版本、配置、工具和评测集可以回退和审计。

这些门槛决定 Agent 是否是一项可运营的业务能力，而不是一次模型效果演示。

这里的完成证据也不是一份架构文档，而是每层契约、至少一条完整回放、阻断级失败样本和明确的人工接管路径。第 25 篇先建立整张系统地图，后续文章再逐层说明这些证据怎样产生。

```text
请为【业务 Agent】建立整体架构和治理清单：

1. 列出支持、不支持和必须人工接管的意图；
2. 为每类意图选择检索、固定流程、受控查询、业务动作或局部推理；
3. 定义工具的参数、数据范围、权限、幂等、确认和审计字段；
4. 检查输入、上下文、输出、日志和遥测中的敏感数据边界；
5. 设计结构化输出、失败处理和人工接管；
6. 从真实失败构建可回放评测和上线阻断条件。
```

后续文章会按这张架构地图逐层展开：先处理业务语言，再设计路由和安全边界，接着讨论查询工具、业务动作、结构化输出、评测和上线。
