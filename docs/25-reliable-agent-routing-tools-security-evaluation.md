# AI Agent 不能只靠提示词：路由、工具、安全和评测

> 系列导航：[完整目录](00-series-titles.md)

做业务 Agent 时，最容易先写一段很长的系统提示词：告诉模型它是谁、能做什么、如何回答。短期看起来能工作，功能一多就会变得脆弱：意图判断不稳定，工具参数容易错，越权查询难以发现，出了问题也无法回放。

我在 Agent 实践中逐渐把能力拆成四层：路由决定请求交给谁，工具决定允许做什么，安全决定边界，评测决定是否真的可靠。

## 路由不是“让模型自由发挥”

用户问业务指标、查订单、执行动作或闲聊，风险和处理方式不同。路由层应先识别意图、权限和所需上下文，再选择固定流程、检索能力、受控工具或人工处理。模型可以参与分类，但高风险意图不能只靠一句自然语言判断。

## 工具必须有窄接口

不要给 Agent 一个“执行任意 SQL”或“调用任意接口”的大工具。工具应限制参数、数据范围、字段集合和操作类型，返回结构化结果，并记录调用人、租户、参数摘要和结果状态。

这样即使模型判断错，也只能在受控范围内失败。真正改变业务状态的工具还应要求幂等键、二次确认或人工审批。

## 安全要贯穿模型到日志

安全不只是提示词里写“不能泄露密码”。需要同时处理输入注入、数据权限、租户隔离、敏感字段脱敏、工具授权、输出过滤和日志/Telemetry（遥测与链路数据）脱敏。不要把内部思考过程、原始 SQL 或系统提示词直接展示给用户；应输出可审计的结果和必要的解释。

## 评测关注失败，不只关注回答像不像

评测集要覆盖意图混淆、权限越界、空数据、异常工具、重复请求、敏感信息诱导和业务术语。每次结果都应能回放：输入、路由、工具、关键参数、授权判断和最终输出。

```text
请为【业务 Agent】检查：
1. 意图路由和兜底策略；
2. 每个工具的参数、权限、数据范围和幂等约束；
3. 租户、敏感字段、日志和输出安全；
4. 工具失败、模型幻觉、重复调用和人工接管；
5. 可回放评测集、通过标准和上线门禁。
```

Agent 的工程质量不是“回答更像人”，而是动作边界清楚、结果可追踪、失败可恢复。提示词只是其中一层，不能替代路由、工具和评测设计。
