# 我不是从写代码开始的，而是从让 AI 认识项目开始的

刚开始使用 AI 编程工具时，我也习惯直接下指令："帮我加个接口"、"这个报错怎么改"、"把这段代码重构一下"。

它往往能很快给出一段看起来不错的代码，但一放进真实项目，问题就来了：模块放错了、接口路径不对、绕开了既有的跨模块调用方式，甚至本地可以编译，却不符合部署环境。代码不是没有写出来，而是没有写在这个项目真正允许的位置。

后来我接手一个 ERP 项目时，先改变了一件事：不让 AI 立刻改代码，先让它认识项目。

## 一个“加接口”需求，为什么不能直接开始写

这个 ERP 后端是一个 Maven 多模块项目。业务按领域拆分，模块对外暴露 API，具体实现放在各自的 Biz 模块；后台管理端与移动端又分别有不同的 Controller 包和 URL 前缀。框架、业务、部署脚本和配置文件也不在同一个位置。

假如只说“新增一个库存查询接口”，AI 有很多机会走错：

- 把移动端接口写到后台管理端的 Controller 目录；
- 让一个业务模块直接依赖另一个模块的实现类；
- 在错误的 Maven 根目录执行构建；
- 忽略租户、账套、数据权限或逻辑删除等项目约束；
- 复制一个看似相近的接口，却漏掉已有的鉴权、返回体和转换层约定。

这些都不是模型会不会写 Java 的问题，而是它是否拿到了足够的项目事实。真实项目的难处，恰恰藏在这些事实里。

## 我先让 AI 回答四个问题

在任何修改之前，我会让 AI 做一次只读扫描，并把结果写成可核验的报告。目标不是让它复述目录，而是先回答下面四个问题：

1. 项目由哪些模块组成，各自负责什么？
2. 请求从哪里进入，核心调用链经过哪些层？
3. 本地如何构建、启动和验证？
4. 哪些规则是这个项目不能碰的边界？

在这次 ERP 项目里，扫描的结果很快把关键约束暴露出来：项目存在框架和业务两个代码库，业务模块采用 `api` / `biz` 拆分；Controller 需要按 Admin 和 App 入口放置；跨模块访问要走公开 API，而不是直接导入对方的 Service；本地构建还依赖固定的 JDK、Maven 模块顺序以及数据库、缓存等外围服务。

有了这些信息，后面的需求才有了准确的落点。AI 不再只会给“一个通用实现”，而是能先说清楚：该改哪个模块、为什么放这里、涉及哪些依赖、应该执行什么验证。

## “了解项目”不是让它读完所有文件

代码库大、时间有限，最容易走向另一个极端：把整个仓库都塞进上下文，期待 AI 自动理解一切。实际效果通常并不好。信息越多，重点反而越模糊，而且每次会话都要重复付出阅读成本。

我现在会分三层提供上下文。

第一层是稳定规则，放到项目根目录的 `AGENTS.md` 或类似项目说明中。这里写技术栈、模块边界、编码约定、构建命令、敏感操作限制，以及哪些事情必须人工确认。它的作用是让每次进入项目的 AI 都有同一份基本地图。

第二层是本次任务的事实，例如相关需求、报错日志、接口契约、涉及的表和模块。这些不能只说“看一下”，而要明确问题的表现、预期结果、允许修改的范围和验收标准。

第三层是现场证据。需要 AI 查看的文件、实际执行的构建结果、测试输出和数据查询结果，都应当在对话中可回溯。对生产配置、账号、内部地址和真实业务数据，则先脱敏再提供。

这样做的结果是，稳定知识不会随着会话结束消失，任务事实也不会被项目背景淹没。

## 一次有效的项目初始化，不该只输出“目录结构”

我会要求 AI 输出下面这类内容，并附上对应文件路径或命令依据：

```text
项目入口：服务启动类、前端入口、关键配置位置
模块边界：每个模块的职责、允许的依赖方向
运行方式：构建命令、启动命令、必要的外部依赖
请求链路：Controller -> Service -> Mapper/Repository -> 外部调用
高风险规则：权限、租户、账套、金额、状态流转、数据迁移
本次任务落点：预计修改的模块、文件类别和验证方式
```

这里有一个很实际的判断标准：报告必须能被工程师拿来行动。只有“项目使用 Spring Boot 和 MyBatis”没有价值；指出“移动端接口必须在指定包下，路径使用既有前缀，跨模块通过 API 接口调用”才是能防止错误的上下文。

## 我现在会这样开始一个改动

下面这段提示词是我常用的起点。它不是为了让 AI 显得更聪明，而是把目标、边界和交付物一次说清：

```text
先不要修改代码。请只读扫描当前项目，完成以下内容：

1. 说明与【需求/问题】相关的模块、入口和完整调用链；
2. 找出项目已有的相似实现，说明可复用点和不能照搬的差异；
3. 列出必须遵守的项目约束，包括接口入口、跨模块依赖、权限/租户、事务和数据规则；
4. 给出最小修改方案：预计涉及的文件类别、风险及验证命令；
5. 所有结论附文件路径或命令输出作为依据。

不要执行写操作、数据库变更、发布或删除操作。敏感配置只描述字段用途，不输出真实值。
```

等这一步完成，我会先审查它是否找对了模块和规则，再让它进入实现。对于高风险改动，例如支付、积分、权限、批量导入或生产数据库变更，我会再加一层：先输出方案和测试场景，确认后才允许写代码。

## 真正节省时间的地方

有人会觉得这一步增加了流程，反而变慢。但在复杂项目中，最贵的从来不是写出第一版代码，而是发现代码改错位置后的返工：接口做完才发现入口错了，联调时才发现忽略了账套维度，发布前才知道配置没有补齐。

让 AI 先认识项目，并不等于把判断交给 AI。相反，它让工程师更早看到假设，能在改动发生前纠正方向。AI 负责快速扫描、整理证据、追踪调用链；人负责确认业务口径、划定风险边界，并对最终交付负责。

这也是我之后所有实践的起点：先建立共同上下文，再讨论实现；先说清验证方式，再开始修改。把这一步做扎实，AI 才会从一个随时生成代码的工具，变成真正能参与项目的协作者。
