# 我不是从写代码开始的，而是从让 AI 认识项目开始的

我第一次使用 AI 进行真实项目开发时，给它的任务是：新增一个接口。

现在回头看，这个任务要求其实缺了最重要的一句话：在什么项目规则下新增？

在示例项目里，接口通常只需要考虑参数、返回值和业务逻辑；然而在实际项目中，同一个“新增接口”还要回答入口属于 Admin 还是 App，代码属于哪个业务模块，跨模块数据通过什么 API 获取，租户和账套如何隔离，最后要在哪个 Maven 根目录构建。AI 如果不知道这些，写得越快，带来的后果越严重,返工的成本也越高。

## 我曾经把“能编译”当成“理解了项目”

那时 AI 很快找到一个相似的 Controller，复制了 DTO 和 Service 调用，代码也顺利编译。问题出在联调阶段：需求实际面向移动端，接口却落在后台管理端；为了取一个关联数据，又直接引用了兄弟模块的实现类；本地环境里能查到数据，换到带租户隔离的环境后结果不一致。

这些错误并不说明 AI 不会写 Java。它只是按照当前文件和最短路径完成了任务，而项目真正的规则分散在目录结构、父 POM、配置文件、相邻实现和历史约定里。没有先建立项目地图，AI 只能用通用经验填空。

## 新项目交给 AI，我先让它做“入职”

现在进入一个陌生代码库，我会把第一轮工作定义为:对当前项目进行扫描分析，不要修改代码。目标不是得到一份目录树，而是得到一份可以指导下一步行动的说明,如:

- 服务和前端从哪里启动，构建命令在哪个目录执行；
- 每个模块负责什么，模块之间允许怎样依赖；
- 请求从哪个入口进入，经过哪些 Controller、Service 和数据访问层；
- 租户、权限、账套、逻辑删除和事务规则在哪里体现；
- 哪些配置、数据库或发布动作属于高风险操作。

在我的实际ERP项目里，这一轮确认了几个关键事实：业务模块分成 API 与 Biz 两部分；后台管理和移动端有不同入口；兄弟模块不能直接引用对方的实现类；框架代码库和业务代码库存在构建依赖；启动还依赖数据库、缓存和具体环境配置。

这些事实一旦明确，后续的讨论就不再是“你觉得应该放哪”，而是“根据项目规则，这个需求应落在哪个入口和模块”。

## 项目理解应该形成一份可审查的地图

我会要求 AI 的扫描结论都带证据。比如“这是 App 接口”，后面应该有 Controller 路径和 URL 前缀；“这个模块不能直接依赖另一个模块”，后面应该有 POM 和现有跨模块调用样例；“这样启动项目”，后面应该有脚本或配置依据。

一个有用的初始化报告大致只有五块：

```text
项目入口：启动类、前端入口、构建和启动命令
模块边界：职责、依赖方向、API/Biz 分工
请求链路：入口、业务服务、数据访问、外部调用
项目规则：权限、租户、事务、数据和兼容性约束
任务落点：相关文件、最小改动、验证方式和风险
```

如果报告只有“项目使用 Spring Boot、MyBatis 和 Redis”，它更像技术栈摘要，不像项目理解。真正有用的是那些会改变实现选择的事实。

## 不是读得越多，理解就越深

我也走过另一个极端：让 AI 一次性扫描整个仓库，把所有配置、日志和代码都塞进上下文。结果是它记住了很多名词，却没有抓住当前任务真正受影响的链路。

后来我把信息分成三层。稳定规则放在项目说明里，任务事实放在当前需求里，现场证据通过文件、命令和测试结果提供。这样既不用每次重讲项目，也不会让无关背景压过眼前的问题。

敏感配置也只保留结构，不保留真实值。AI 需要知道“这里有数据库、缓存和第三方回调配置”，不需要知道密码、内部地址和生产账号。

## 我现在的第一句提示词

```text
先不要修改代码。请把当前项目当作一个需要接手的真实系统，完成只读扫描：

1. 说明与当前任务相关的模块、入口和调用链；
2. 找出相似实现，并说明哪些地方不能直接照搬；
3. 列出构建、启动、测试和外部依赖；
4. 说明权限、租户、事务、数据粒度和模块依赖约束；
5. 给出最小修改范围、风险和验证计划。

所有结论附文件路径或命令依据。不执行写操作、数据库变更、发布和删除。
```

这一步并没有让 AI 变得更聪明，却让它少了很多猜测。人也能在代码修改前发现它是否走错了入口、误解了边界，或者漏掉了必要的运行条件。

## 真正的起点是共同上下文

让 AI 先认识项目，并不是增加一道形式流程。复杂项目里，最昂贵的返工往往不是把一行代码改对，而是发现整个改动落在了错误的模块、错误的数据口径或错误的部署假设上。

AI 负责快速扫描、整理和串联证据；工程师负责确认业务意义、选择边界并承担交付结果。两者建立共同上下文之后，AI 才不只是一个会生成代码的工具，而是开始像一个能进入项目工作的协作者。
