# 用 AI 对比数据库结构：如何辅助发布而不盲目执行 DDL

开发库跑得好好的，到了发布前才发现线上少一个字段、索引不同，或者某个列的空值约束不一致。这类问题很常见，也很适合让 AI 帮忙：它可以快速读取表结构、归类差异、生成候选脚本和发布清单。

但有一个边界必须守住：AI 能生成 DDL，不等于 AI 应该执行 DDL，更不等于“让线上和开发完全一致”就是正确目标。

## 结构差异不是一份简单的 diff

两张表看起来不同，背后的含义可能完全不同。新增一个可空字段通常风险较低；把字段改成 `NOT NULL`，则可能要求先回填历史数据；删除列、缩短字段长度或修改索引，可能影响旧版本程序、锁表时间和回滚能力。

因此我要求 AI 的输出不只是 SQL，而是按风险分组的差异报告：新增、删除、类型变化、默认值变化、空值约束、索引、主键和注释分别列出，并标明每项的方向和可能影响。开发到线上并不总是唯一方向，线上也可能有尚未回合的热修复或兼容字段。

## 先确认“谁是基准”，再讨论脚本

发布时最危险的提示词之一是：“把生产库改成和开发库一样。”它把开发环境误当成唯一事实来源，忽略了版本、迁移状态和生产数据。

更好的问题是：本次发布版本应当包含哪些结构变化？这些变化分别是否已在目标环境落地？每个环境的 schema 版本和应用版本是什么？AI 可以据此从迁移脚本、提交记录和元数据中核对，而不是机械地消除所有差异。

对于历史遗留差异，应该单独登记、评审和安排清理，不能混在本次发布里顺手处理。

## 每条变更都要有发布路径

我会让 AI 为每一条候选变更补齐四个问题：

- 是否向后兼容，旧版本应用运行时会不会出错？
- 是否需要先做数据回填、双写或灰度？
- 是否可能长时间锁表、占用大量资源或影响索引？
- 如果失败，回滚操作是什么，是否会造成数据不可逆？

这让 SQL 从一条命令变成可评审的发布单元。特别是金额、库存、权限、租户和账套相关表，哪怕只是新增列，也要确认默认值和历史数据不会改变业务含义。

## AI 最适合承担发布前的“繁琐核对”

在这个场景里，我会把权限划分得很清楚。AI 可以：只读获取元数据、比较差异、生成报告、草拟脚本、检查脚本依赖、列出备份和验证步骤。AI 不可以：直接连生产执行 DDL、删除“多余”字段、覆盖未知差异。

人工确认并不意味着人工手工做完一切。反而可以让 AI 把差异缩小到少数需要判断的条目，让 DBA 或工程师把注意力集中在真正有风险的决定上。

## 一个发布前检查模板

```text
请以只读方式比较【源环境】和【目标环境】中与本次版本相关的表结构。

输出要求：
1. 分别列出字段、类型、默认值、空值约束、主键和索引差异；
2. 标明每项是否属于本次版本，未知项单列为待确认；
3. 为候选变更给出兼容性、数据回填、锁表和回滚风险；
4. 生成“待评审 DDL”，不要执行；
5. 给出执行前备份、执行后结构验证和应用验证清单。
```

数据库发布不是一个“把差异抹平”的动作，而是一次受控的版本演进。AI 可以极大压缩比较和整理的时间，但批准变更、承担数据风险和确认业务兼容性，仍应由人完成。
