# 用 AI 对比数据库结构：如何辅助发布而不盲目执行 DDL

发布前做数据库差异检查，最容易产生一个错误目标：“把线上改成和开发一样。”这句话看似明确，实际上跳过了版本、历史迁移、热修复和生产数据等关键事实。

AI 很适合比较表结构，却不应该成为一个自动抹平差异的工具。

## 差异报告首先要说明方向

同样是字段不同，新增可空字段、收紧 `NOT NULL`、缩短长度、删除列和修改索引的风险完全不同。因此我会让 AI 将差异分成字段、类型、默认值、空值约束、索引、主键和注释，并写明是源环境多了什么，还是目标环境多了什么。

目标环境多出的字段不一定是垃圾，可能是生产热修复或兼容旧版本所需。差异本身不是问题，未经判断地消除差异才是问题。

## 先确定本次发布的基准

正确的问题不是“哪个环境看起来更完整”，而是“本次版本声明了哪些结构变化，目标环境是否已经具备”。AI 应同时检查迁移脚本、应用版本、schema 版本和发布记录，把属于历史遗留的差异单列出来。

如果一个字段改为非空，还要先回答历史数据如何回填；如果删除列，还要确认旧版本应用是否仍在运行；如果新增索引，还要评估锁表和资源影响。

## 候选 DDL 必须带发布路径

我希望 AI 输出的不是一段裸 SQL，而是一份变更卡片：变更目的、影响表、前置数据处理、兼容窗口、执行顺序、验证 SQL、失败处理和回滚条件。这样 DBA 或工程师评审的是一个可执行计划，而不是一条无法解释的命令。

AI 可以只读读取元数据、生成差异、草拟 DDL 和验证语句；生产执行、备份确认和回滚选择仍然需要明确授权。

## 我会这样做发布前检查

```text
请只读比较【源环境】和【目标环境】与本版本相关的结构：
1. 输出字段、类型、默认值、空值约束、索引和主键差异；
2. 区分本次版本变更、历史遗留和未知差异；
3. 为候选 DDL 标记兼容、回填、锁表、数据风险和回滚方式；
4. 生成待评审脚本和执行后验证清单；
5. 不执行 DDL，不输出真实连接信息。
```

## 发布不是“让两个库长得一样”

数据库演进的目标是让应用版本、数据结构和生产数据在一个可解释的状态上协同工作。AI 能把人工逐表比较的时间压缩下来，也能提醒人关注遗漏；但它不能替团队承担一次错误 DDL 的后果。

只要把差异、方向、风险和回滚都保留下来，AI 就能成为发布前非常高效的审查助手，而不是一个危险的自动执行器。
