# AI 修改了代码以后，我是如何验证它真的完成了需求的

AI 最容易给人的错觉是：它写完一段代码、说“已完成”，任务就结束了。实际项目中，这最多说明它完成了一个假设中的实现。需求是否完成，还取决于改动范围、业务结果、测试执行和环境条件。

我现在要求 AI 在每次实现后交付一份证据，而不是一句总结。

## 第一层：改了什么

先看 diff。修改是否只触及预期模块？有没有顺手调整无关配置、依赖或生成文件？新增接口是否放在正确的 Admin/App 入口？跨模块调用是否仍遵守 API 边界？这一层防止“功能似乎有了，架构已经歪了”。

## 第二层：规则是否实现

将改动逐条对照验收条件。余额不足、空关联、重复调用、跨租户、失败补偿这些规则是否有对应实现？AI 不能只说明“加入了判断”，要指出判断在哪个路径生效，是否有其他入口能够绕过。

## 第三层：验证是否真的执行

运行聚焦测试，再运行受影响模块构建；有接口、数据库或配置改动时补充集成检查。报告要写实际命令、通过/失败/跳过数和环境限制。某项因环境问题无法跑，结论应是“未验证”，而不是“已通过”。

## 第四层：结果是否可观察

对数据类功能检查最终数据状态，对接口检查响应和权限，对异步任务检查幂等记录和日志，对发布变更检查配置、监控和回滚条件。验证对象是用户和系统实际看见的结果，不是代码本身。

```text
请对本次改动提交验证报告：
1. 改动文件和范围，以及与方案不一致之处；
2. 每条验收条件对应的实现位置和验证证据；
3. 实际执行的测试/构建命令及通过、失败、跳过结果；
4. 数据、权限、事务、兼容性和配置检查；
5. 未验证项、环境阻塞和需要人工确认的风险。
```

只有当证据覆盖了需求，AI 的“完成”才可以被接受。把这套检查固定下来，AI 的交付会从一段代码变成一个可审查的工程结果。
