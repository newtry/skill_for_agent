# AI 修改了代码以后，我是如何验证它真的完成了需求的

> 系列导航：[完整目录](00-series-titles.md)

AI 说“已经完成”时，我现在不会先看它写了多少代码，而会问：完成了哪条验收条件，有什么证据，哪些部分仍然没有验证？

## 先看 diff 的边界

修改是否只落在预期模块？有没有顺手改变无关配置、依赖或生成文件？接口是否放在正确的 Admin/App 入口？跨模块是否仍通过公开 API？

这一步检查的是范围，而不是功能。功能可能看起来正常，但越界的依赖和无关改动会在后续维护中制造更大的问题。

## 再逐条对照验收条件

对于积分，要确认冻结、确认和释放的失败路径；对于批量导入，要确认事务和重复提交；对于查询，要确认租户、账套和权限；对于编码，要确认最后合法值和超限行为。

我会要求 AI 指出每条规则在哪个代码路径生效，并搜索是否存在其他入口绕过它。只说“增加了判断”是不够的。

## 测试和环境结果要如实分类

受影响模块先跑聚焦测试，再做构建；涉及接口、数据库或配置时增加对应检查。报告分成已验证、失败、跳过、环境阻塞和待人工确认，不把不能运行写成通过。

```text
请生成本次改动的验证报告：
1. 文件和行为变化、实际修改范围；
2. 每条验收条件的实现位置和证据；
3. 实际测试/构建命令及通过、失败、跳过结果；
4. 数据、权限、事务、兼容性和配置检查；
5. 未验证项、环境阻塞和人工确认项。
```

## 最终结果要回到用户和数据

代码 diff 是中间证据。数据类功能要检查最终数据，接口要检查响应和权限，异步任务要检查幂等记录和日志，发布改动要检查配置、监控和回滚条件。

AI 写完代码只是“实现阶段完成”。只有证据覆盖需求，工程师才有理由接受它的“完成”声明。
