# AI 并行开发为什么需要 Git Worktree 和写入隔离

> 系列导航：[完整目录](00-series-titles.md)

一次跨端改造中，我同时安排三个 AI 会话：一个修改 Agent 路由，一个迁移前端协议，另一个补回归测试。任务看起来边界清楚，开始后却共享同一个工作目录。

路由会话格式化了公共类型文件，前端会话读到了尚未完成的后端字段，测试会话运行时又把两组未提交修改一起编译。最后三边都声称测试通过，却没人能说明结果对应哪一个代码状态，也无法把某组改动独立提交。

并行没有缩短交付时间，只是把原本按顺序暴露的冲突提前混在了一起。

## 核心判断：并行必须隔离写入、资源和证据

Git Worktree 能为每个任务提供独立目录和分支，是多 AI 并行的基础边界。但目录隔离只解决代码文件互相覆盖的问题，端口、缓存、数据库、对象存储、契约决策和测试证据仍可能共享。

```text
并行任务
-> 独立分支与工作树
-> 明确文件和契约所有权
-> 独立进程与资源命名空间
-> 每条分支独立验证
-> 集成后重新验证完整系统
```

Worktree 不是并行正确性的全部答案，而是让责任边界变得可执行的第一层机制。

## 不是所有任务都适合并行

拆分前先检查任务之间是否具有稳定接口。若两项工作同时决定同一字段语义、状态机或数据库迁移，强行并行只会让两个会话分别发明契约。

适合并行的任务通常满足：输入基线一致，修改区域相对独立，共享契约已经确认，验证可以局部执行，合并顺序明确。以下情况更适合先串行：

```text
业务口径和核心协议尚未确定
多个任务必须修改同一高冲突文件
第二项工作依赖第一项产生的数据迁移
只有一套不可隔离的外部测试资源
无法说明各分支的独立完成证据
```

并行资格是工程判断，不应由“有三个会话可用”决定。

## 分支不能隔离同一目录中的未提交修改

Git 分支只是提交历史指针。多个执行者共用一个工作区时，未提交文件仍属于同一个现场。任何批量格式化、生成代码、切换分支、恢复文件或清理临时产物，都可能影响其他任务。

Worktree 为每条任务分支创建独立目录，共享 Git 对象但不共享工作区。每个任务开始时应固定：

| 项目 | 需要记录的内容 |
| --- | --- |
| 任务与基线 | 任务 ID、起始提交、依赖版本 |
| 工作位置 | 工作树绝对路径和分支 |
| 写入范围 | 允许修改的模块、生成目录和禁止区域 |
| 共享契约 | 契约版本、责任人和变更方式 |
| 验证 | 局部命令、环境和预期产物 |
| 交接 | 提交、差异、测试结果和未决风险 |

主工作树更适合作为集成和最终验证现场，不应同时承载某条尚未稳定的实现任务。

## 共享契约需要单一决策入口

即使目录分开，两个 Agent 仍可能分别修改同一协议文件，或者在不同模块中实现不一致的字段含义。

对路由注册表、API Schema、数据库迁移和公共状态枚举，我会指定单一责任分支或责任人。其他工作树只消费已确认版本；确需变更时，通过任务或提交回到契约分支，再由各消费者同步。

```text
契约提议 -> 责任人确认 -> 发布版本或提交
-> 各工作树更新基线 -> 消费方实现 -> 契约回放
```

聊天里互相转述字段变化不能替代版本化契约。并行中的共同事实必须可以被所有工作树读取和追踪。

## 目录隔离后还要隔离运行资源

多个工作树默认仍会争用相同端口、缓存键、临时目录、消息主题、测试账号和数据库。两个测试进程写同一个 SQLite 文件，即使代码完全隔离，结果也会互相污染。

每个任务最好拥有资源命名空间：

```text
端口：按工作树分配固定区间
临时目录：绑定任务 ID，不使用共享输出目录
缓存和消息：增加工作树前缀或使用独立实例
数据库：独立容器、Schema 或可识别的数据前缀
对象存储：专用测试桶和唯一对象前缀
进程：记录 PID、配置来源和启动版本
```

无法隔离的资源要显式标成串行锁。例如共享开发数据库只有一份时，不允许多个迁移任务同时写入；生产或外部服务默认不应成为并行测试资源。

## 每条分支的证据也必须独立

测试记录至少绑定起始提交、当前提交或 diff、命令、环境、结果和跳过项。不能让测试工作树验证混合代码后，把“绿色”分别贴给三个任务。

局部完成时，交接包应说明：修改了什么，依赖哪个契约，运行了哪些验证，产生了什么外部资源，仍有哪些假设。提交要保持任务内聚，避免主工作树只能接收一个包含多项责任的巨大补丁。

## 合并是新的代码状态，必须重新验证

三个分支各自通过，不代表合并后仍然正确。合并可能改变依赖解析、生成代码、路由优先级、数据库迁移顺序和前端类型。

```text
检查各分支基线是否过期
-> 按依赖顺序合并
-> 解决契约和语义冲突
-> 重新生成受影响产物
-> 运行跨模块与端到端回归
-> 更新最终证据包
```

冲突解决不是选择能编译的一边，而是回到共享契约判断最终语义。集成验证通过后，才可以删除工作树或释放资源；清理动作还要确认没有未提交改动和仍需保留的测试证据。

## AI 与人如何分工

AI 可以评估文件重叠、创建任务清单、在指定工作树实施、记录验证和发现过期基线。集成负责人决定任务是否适合并行、共享契约由谁拥有、合并顺序和冲突语义；环境负责人提供可隔离资源并控制外部副作用。

任何会话都不应自行重置主工作树、删除未知修改或清理其他任务资源。看到不属于自己的现场时，应保持原状并报告。

```text
请为【并行开发任务组】设计隔离方案：

1. 判断任务依赖、文件重叠、共享契约和不可并行资源；
2. 为每项任务指定基线、分支、Worktree 路径和允许写入范围；
3. 指定公共协议、迁移和高冲突文件的单一责任入口；
4. 隔离端口、临时目录、缓存、消息、数据库和外部资源；
5. 要求每条分支绑定代码状态、环境、测试结果和未决风险；
6. 定义合并顺序、集成回归、资源清理和异常接管。

不在共享工作区混合未提交改动，不把分支各自绿色当成集成完成。
```

Worktree 解决了代码和任务现场的第一层隔离。下一篇继续检查更容易被测试绿色掩盖的问题：即使工作树彼此独立，测试进程仍可能连接真实 OSS、消息、支付或共享数据库并产生外部副作用。
