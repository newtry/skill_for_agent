# AI 并行开发为什么需要 Git Worktree 和写入隔离

> 系列导航：[完整目录](00-series-titles.md)

当一个 AI 会话在修改 Agent 路由，另一个会话在补前端协议，第三个会话同时跑回归测试时，效率看起来提高了。但如果它们共享同一个工作目录，风险也会迅速放大：一个会话看到另一个会话尚未完成的文件，格式化命令改写无关代码，测试结果对应的工作区状态也无法复现。

人的并行开发需要分支，AI 的并行开发更需要物理写入隔离。Git Worktree（独立工作树）正好提供了这种目录级边界。

## 分支不能隔离同一个目录里的写操作

Git 分支只是提交历史指针。多个执行者共用一个工作区时，未提交修改仍混在一起，任何会话切换分支、恢复文件或批量格式化，都可能影响其他任务。尤其是 AI 会主动搜索和修改文件，如果边界只写在提示词里，误操作很难完全避免。

Git Worktree 为每条任务分支提供独立目录，同一仓库对象仍可复用。实际使用时，我会为每个并行任务明确四件事：工作树路径、分支、允许写入的模块、验证命令。

```text
主工作树：只负责集成与最终验证
工作树 A：意图路由与注册表
工作树 B：协议迁移与前端接线
工作树 C：评测和文档
```

这不意味着任务可以随意拆开。共享契约仍要先确定，容易冲突的核心文件应指定单一负责人，跨工作树只通过提交或明确补丁交接。

## 隔离还要覆盖进程和环境

目录分开后，端口、缓存、临时文件和数据库仍可能共享。两个测试进程写同一个 SQLite 文件或开发库，仍会互相污染。因此每个工作树最好拥有独立的环境文件、临时目录和测试数据命名空间；无法隔离的外部服务则标记为串行资源。

## 合并前要恢复一条完整证据链

每个任务在自己的工作树通过测试，只能证明局部状态。合并到集成分支后，还要检查契约冲突、迁移顺序和跨模块回归。提交说明应记录基线、改动范围和测试结果，使主工作树能够重放，而不是依赖某个会话口头说“已经验证”。

Worktree 的价值不是让 AI 同时写更多代码，而是让并行任务的输入、输出和责任边界可见。并行带来的速度只有在写入互不覆盖、证据能够合并时，才是真正的工程效率。
