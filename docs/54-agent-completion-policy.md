# 停止执行不等于任务完成：Agent 如何判断用户目标真的达成

> 系列导航：[完整目录](00-series-titles.md)

在一次客户推荐任务中，用户要求“找出最近需要跟进的客户，并给出适合推荐的商品和理由”。Agent 先查询客户列表，工具返回了十几条数据。由于上下文已经很长，模型直接总结客户信息并结束执行。

从运行记录看，工具调用成功、没有报错、模型也输出了答案；但推荐商品和理由根本没有生成。执行器停止了，用户目标只完成了一半。

类似情况也会反向发生：补货方案已经生成，Agent 仍继续查询相似数据，既增加成本，又可能触发重复写入。可靠执行不仅要知道怎样开始，还要知道何时应该结束、结束时究竟交付了什么。

## 核心判断：完成策略是用户目标的可执行契约

模型没有继续调用工具，只能说明当前推理停止；工具返回成功，只能说明一个技术步骤结束；计划项全部执行，也不一定说明结果满足用户目标。

真正的完成判定必须把用户目标拆成可以由系统检查的证据，并明确空结果、部分完成、失败和人工接管分别如何表达。

```text
用户目标
-> 必要结果与业务约束
-> 计划步骤产生证据
-> 完成策略核对证据
-> 输出完成、部分完成、失败或接管状态
```

完成策略不是附在提示词里的提醒，而应成为任务状态机、输出协议和评测共同使用的契约。

## 先区分四种经常混在一起的“结束”

| 层次 | 表示什么 | 不能证明什么 |
| --- | --- | --- |
| 推理停止 | 模型没有生成下一步动作 | 计划已经执行完 |
| 步骤成功 | 某次工具调用返回成功 | 后续步骤不再需要 |
| 技术任务完成 | 系统产出了约定结果 | 用户已经看到或采用 |
| 业务结果达成 | 后续业务事实满足目标 | 完全由本次 Agent 导致 |

这里先关注前三层之间的边界。业务结果还需要曝光、反馈、订单和归因链路，后面会单独展开。

这一区分能避免两个常见错误：把 `tool_success=true` 当成整个任务成功，或者把成交等长期结果塞进当前执行，让 Agent 永远无法结束。

## 任务计划描述过程，完成策略约束结果

对“生成客户商品推荐”，计划可以写成：

```text
1. 确定客户范围
2. 获取客户偏好和历史事实
3. 获取可售候选商品
4. 生成推荐条目
5. 输出可操作结果
```

但计划被逐项勾选仍可能产生空洞结果。完成策略还要声明：

```text
客户集合及租户、账套、时间范围已经确定
每个推荐条目都包含客户、商品、数量或范围和理由
理由能够追溯到允许使用的事实
不可售、越权和重复商品已经排除
没有推荐时返回原因，而不是编造结果
部分客户失败时保留已完成项并说明缺口
```

计划允许因工具和实现变化而调整，完成策略则应稳定对应用户承诺。新增一个缓存查询不应改变什么叫“推荐完成”；业务要求增加库存可售约束，才需要修改完成契约并同步评测。

## 完成状态必须表达真实差异

只返回 `finished=true/false` 会把多个业务状态压成一个布尔值。更实用的状态至少包括：

| 状态 | 含义 | 系统动作 |
| --- | --- | --- |
| `completed` | 必要证据齐全 | 交付结果并记录证据 |
| `empty` | 执行成功但业务集合为空 | 说明范围和空结果原因 |
| `partial` | 部分对象完成，仍有明确缺口 | 保留结果并提供继续入口 |
| `retryable_failed` | 临时失败且重试仍安全 | 记录重试点、次数和幂等键 |
| `blocked` | 缺参数、权限或外部条件 | 指明解除阻塞需要什么 |
| `handoff` | 风险或歧义需要人工处理 | 冻结自动动作并移交现场 |

“没有数据”和“查询失败”必须分开；“完成两个客户”和“全部完成”也必须分开。否则前端无法正确展示，重试器无法选择动作，评测还会把半成品统计为成功。

## 停止条件与完成条件不能互相替代

Agent 还需要预算和安全停止条件，例如最大步骤数、最大成本、连续重复调用、工具超时、权限拒绝和高风险动作待确认。这些条件用于防止失控，不代表目标已经完成。

```text
达到完成条件：completed 或 empty
触发预算上限：partial 或 blocked
遇到可恢复故障：retryable_failed
遇到高风险或业务歧义：handoff
检测到循环或非法动作：立即停止并保留审计
```

把两类条件分开后，系统不会为了结束循环而谎报成功，也不会因尚未观察到业务成交而无限执行。

## 证据要绑定对象、版本和当前状态

完成策略不能只检查“某个字段非空”。推荐理由可能存在，却引用了错误账套；卡片已经生成，却对应旧一次运行。每条证据应绑定任务、业务对象、数据范围、协议版本和产生时间。

对于可恢复任务，还要记录哪些步骤已经产生外部副作用、哪些结果可以复用、从哪里继续以及重复执行如何去重。这样 `partial` 才是可恢复状态，而不是一段无法继续的说明文字。

前端也应读取同一完成契约：展示已完成项和未完成项，区分重试、补参数和人工接管，不能把后端所有终态都渲染成“任务完成”。

## 评测要检查是否过早结束和过度执行

完成策略显式化后，评测不再只比较最终文本。回放可以断言：

```text
必要步骤缺失时不能返回 completed
空集合不能被包装成查询失败或虚构结果
部分对象失败时已完成结果不会丢失
完成以后不会继续调用无关或有副作用的工具
重试从正确检查点开始且不会重复写入
达到停止条件时保留原因、现场和接管动作
```

还要加入对抗样本，例如工具返回大量无关内容、模型声称“任务已完成”、某一步状态乱序或历史结果混入当前任务。完成判定应相信结构化证据，而不是模型自我描述。

## AI 可以检查证据，人定义什么值得交付

AI 适合把目标拆成候选步骤、从工具结果提取证据、识别缺口和生成回放场景。业务负责人确认什么结果对用户有用，工程师定义状态、幂等和恢复机制，安全与运营负责人决定哪些情况必须停止或转人工。

如果完成条件包含尚未确认的业务口径，系统应标成待确认，不能让模型根据“通常做法”补全。完成策略的权威性来自责任人和版本，而不是写得像一份完整答案。

```text
请为【Agent 任务】设计完成策略：

1. 区分推理停止、步骤成功、技术任务完成和后续业务结果；
2. 将用户目标拆成可核验的必要结果、约束和证据来源；
3. 定义 completed、empty、partial、retryable_failed、blocked 和 handoff；
4. 将预算、循环、超时和安全停止条件与完成条件分开；
5. 说明证据对应的任务、对象、数据范围、版本和时间；
6. 设计提前结束、过度执行、重试、乱序和人工接管回放。

不把工具成功、计划走完或模型自述直接判定为用户目标完成。
```

完成策略明确了“交付承诺何时成立”。下一篇把视角扩展到整个技术方案：在持续迭代中，怎样知道这些承诺究竟已经实现、接线、验证，还是只存在于文档里。
