# 停止执行不等于任务完成：Agent 如何判断用户目标真的达成

> 系列导航：[完整目录](00-series-titles.md)

在 Agent 的执行记录里，“没有下一步工具调用”很容易被当成完成。真实业务中，这两个状态经常不是一回事。

用户问“哪些客户需要跟进，并给出建议”，Agent 可能已经查到客户列表，于是停止执行；但建议还没有生成。用户要求“分析库存并形成补货方案”，系统可能完成了数据查询，却没有产出可操作的补货项。流程停了，只说明执行器没有继续，并不能说明用户拿到了想要的结果。

## 完成条件不能藏在模型感觉里

最初的 Agent 往往依赖模型自己判断“信息已经足够”。这种判断对简单问答尚可，对多步骤任务就会变得不稳定。模型可能因为工具返回内容很长而提前总结，也可能在目标已经达成后继续调用无关工具。

后来我把任务计划和完成策略拆开。任务计划描述要做哪些步骤，完成策略描述满足什么证据才能结束。

```text
目标：为目标客户生成可执行的商品推荐

计划：
1. 获取目标客户
2. 获取客户偏好和历史事实
3. 获取候选商品
4. 生成推荐结果

完成策略：
- 客户集合已确定
- 每个结果都有推荐对象和理由
- 数据范围与账套已确认
- 无结果时给出明确原因
```

这样，工具执行完毕只是产生证据；完成判定要逐项检查这些证据是否满足目标。

## 失败、空结果和部分完成必须分开

“查询成功但没有数据”不等于工具失败，“三个客户中只完成两个”也不应被包装成全部成功。完成策略至少要区分成功、空结果、部分完成、可重试失败和需要人工介入。

这对前端同样重要。若后端只返回一个 `finished=true`，界面无法告诉用户任务究竟完成了什么。更合理的结果应包含阶段状态、已完成项、缺失项、失败原因和下一步动作。

## 完成策略也是评测契约

有了显式完成条件，评测就不必只看最终文本像不像标准答案。可以回放同一请求，检查 Agent 是否遗漏必要步骤、是否在证据不足时提前结束、是否在完成后继续执行，以及异常时是否保留了可恢复状态。

我在后续项目里逐步把典型业务场景做成受治理的任务链，并让它们共享同一套完成策略。测试数量增长到两千条以上不是最重要的，重要的是“完成”终于从模型的一句自我声明，变成了系统可以检查的事实。

Agent 的可靠性，很大一部分取决于它何时停下来。过早停止会交付半成品，过晚停止会增加成本和副作用。只有先定义用户目标，再定义完成证据，系统才知道一次执行究竟是结束了，还是完成了。
