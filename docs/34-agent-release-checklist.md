# 智能体上线前要验证什么：一次真实项目的发布检查实践

> 系列导航：[完整目录](00-series-titles.md)

Agent 的上线检查不能只问“模型能不能回答”。一个业务智能体真正上线时，模型、路由、工具、术语库、权限、输出组件、日志和评测数据都会一起变化。

因此我会把上线看成一次能力组合发布，而不是替换一个模型版本。

## 一次发布为什么停在了联调之后

一次 Agent 协议升级已经完成后端联调，局部接口也能返回新结构。上线检查把九个核心场景串起来回放时，其中一个场景仍由 Java 调用方发送旧字段，前端又保留旧状态类型。单个仓库的测试都是绿色，组合链路却依赖兼容分支才能工作。

这次发布没有因为“基本可用”继续推进，而是退回到协议迁移：逐个核对生产方和消费方，删除无依据的字段兜底，再运行跨端场景和完整回归。最终两千余条测试通过，跳过项也被单独说明；发布、灰度和旧链路清理仍保留明确授权。

真实上线门禁的价值就在这里：它不只是列检查项，还必须能够在证据不足时阻止发布。

## 先确认能力边界

上线清单的第一项不是模型名称，而是 Agent 现在支持哪些意图、哪些工具、哪些写操作，哪些请求必须转人工。超出范围时，系统应稳定地拒绝、澄清或转交，而不是临时发挥。

## 再验证关键路径

每个核心意图都要至少跑一次完整链路：路由、上下文、工具授权、查询或业务动作、结构化输出、日志和审计。查询类要验证数据口径；写操作要验证预览、确认、幂等和失败恢复。

## 用失败样本做上线门禁

我会固定检查意图混淆、行业术语、参数缺失、空数据、工具超时、重复请求、跨租户、敏感信息诱导、自由 SQL、模型返回非法结构和人工接管。

这些用例不要求模型每次都给出完美答案，但必须满足安全和业务底线。权限越界、错误写入和敏感数据泄露应属于阻断级失败。

## 发布后还要能观察和回退

上线前确认请求量、延迟、工具错误率、转人工率、越权拦截、结构化输出失败和成本指标可见。模型或工具版本要可回退，评测样本和配置要能恢复到上一版。

```text
请生成【Agent】上线检查表：
能力边界、路由、工具、权限、租户、术语库、输出 schema（结构契约）、日志、评测、监控和回滚。
按上线前、灰度中、上线后三阶段列出验证命令、样本和阻断条件。
```

Agent 上线不是“对话框打开了”，而是系统可以在真实输入、真实权限和真实失败下保持可控。把门禁写清楚，才能知道它是否真的准备好了。
