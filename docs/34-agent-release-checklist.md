# 智能体上线前要验证什么：一次真实项目的发布检查实践

> 系列导航：[完整目录](00-series-titles.md)

Agent 的上线检查不能只问“模型能不能回答”。一次业务智能体发布，模型、术语库、路由、工具 Schema、权限、查询模板、输出组件、日志和评测数据都会一起变化。

一次协议升级已经完成后端联调，局部接口也能返回新结构。上线前把九个核心场景串起来回放时，仍发现 Java 调用方发送旧字段，前端保留旧状态类型，部分链路只能依赖兼容分支工作。每个仓库单独构建绿色，组合系统却没有完成迁移。

这次发布被阻断，直到逐个核对生产方和消费者、删除无依据的字段兜底、完成跨端回放并说明跳过项。上线门禁的价值，不是把检查表写得更长，而是在证据不足时有权阻止发布。

## 核心判断：上线依据是证据，不是局部成功

Agent 发布的是一条由模型、数据、工具、权限、状态和前端共同组成的业务链路。单个仓库能构建、单个接口能返回，最多证明局部组件可用；只有关键路径完成回放、失败样本满足底线、兼容和回退方案都有证据，版本才具备上线资格。

## 那次发布为什么在最后阶段被阻断

待发布版本把 Agent 输出从旧的 Markdown 响应升级为带状态和动作的 V2 卡片。后端单元测试通过，Java 服务联调可以返回 V2，前端也完成了新卡片组件。按组件看，三个仓库都处于绿色状态。

真正串联场景时，证据却显示迁移没有闭合：

| 链路 | 局部结果 | 端到端问题 | 门禁结论 |
| --- | --- | --- | --- |
| Agent -> Java | 新接口可用 | 一个调用方仍发送旧字段 | 阻塞 |
| Java -> 前端 | V2 可返回 | 旧状态枚举把 `pending` 显示为失败 | 阻塞 |
| 查询工具 -> Agent | 正常结果通过 | 超时仍被兼容层转换为空数组 | 阻塞 |
| 动作卡 -> 工作流 | 可创建草稿 | 重复确认场景没有幂等证据 | 阻塞 |
| 回滚组合 | 应用可以回滚 | 新版已创建任务旧版无法展示 | 需要补充方案 |

最初的“可以上线”来自局部构建和正常场景联调；最终的“暂不上线”来自跨组件回放和失败样本。这次差异让我把发布检查从经验清单改成证据门禁。

## 第一道门：能力边界已经声明

上线清单首先要说明 Agent 支持哪些意图、工具和写操作，哪些请求必须澄清、拒绝或转人工。超出能力范围时，系统要稳定地停下，而不是临时发挥。

还要确认每项能力的责任版本：术语定义、路由、工具、权限、输出结构、评测样本和配置是否来自同一发布基线。

那次发布中，我们把能力基线收窄为库存查询、商品推荐和调拨草稿。正式提交调拨、退款和自由 SQL 明确不在范围内。这样回放失败时，团队能判断是支持能力失效，还是请求本来就应被拒绝，而不是让模型临时决定能力边界。

## 第二道门：关键路径完整回放

每个核心意图至少执行一次端到端场景：输入、术语消歧、路由、上下文、工具授权、查询或动作、状态变化、结构化输出、日志和审计。

查询类验证数据粒度、范围、时间和空结果；写操作验证预览、确认、幂等、失败和补偿；开放诊断验证停止条件和人工接管。

单个接口通过不能替代整条链路回放。

九个核心场景不是九次随意提问，而是覆盖三类能力：正常查询、带确认的动作和需要停止的异常路径。每次回放都保存路由、授权、工具参数、状态、卡片和审计编号。只看到页面结果而没有中间证据，不能标记为通过。

## 第三道门：失败样本必须满足安全底线

上线前固定检查：

```text
术语和相似意图混淆
缺少租户、账套、时间或业务参数
跨租户、越权和敏感信息诱导
固定查询误走开放推理或自由 SQL
工具超时、空结果、慢查询和非法返回结构
重复请求、确认后重试、状态乱序和补偿
权限拒绝、错误输出和人工接管
```

这些用例不要求模型每次给出完美答案，但必须满足业务和安全底线。权限越界、敏感泄露、未确认写入、错误资金动作和不可解释的跨端协议失败属于阻断级问题。

门禁必须预先定义，不能在看到失败后临时降低等级。那次工具超时被转换为空数组，页面文案只是“暂无库存”，表面影响不大，却会让业务员停止补货，因此被归为数据语义阻断，而不是普通体验问题。

## 第四道门：跨版本与跨组件兼容

上线前要核对模型、Agent 后端、Java 服务、前端、查询工具、数据库、缓存和消息的生产消费关系：

- 新输出被旧消费者读取时是否安全；
- 新工具参数与旧版本调用方是否兼容；
- 旧字段和兼容分支是否仍有真实使用；
- 路由、权限和术语版本是否一致；
- 灰度期间新旧实例能否共存；
- 回滚后已产生的任务、卡片和状态能否继续处理。

协议升级不能只验证新链路能走通，还要证明旧链路可以退出，或者明确兼容窗口和清理责任。

修复过程中，我们建立生产者与消费者矩阵，为每个字段和状态记录生产方、消费方、最低版本、兼容方式和退出证据。旧字段只有在调用观测归零、消费者完成升级、回滚窗口结束后才允许删除；无期限的双写和字段兜底不能算迁移完成。

## 第五道门：观察、回退和人工接管可用

上线前确认以下指标可见：请求量、延迟、模型和工具错误率、路由分布、越权拦截、结构化输出失败、转人工率、成本、重复动作和业务结果。

每个版本需要可回退的模型、提示词、路由、工具 Schema、术语库和配置；异常时要知道由谁暂停能力、恢复上一版、处理未完成任务和核对外部副作用。

健康检查只证明进程活着，不能证明业务 Agent 在正确范围内工作。

## 修复后怎样决定可以灰度

阻断项修复后，并不是立刻全量发布。我们重新执行同一批回放，确认旧字段调用归零、`pending` 在新旧前端都有安全展示、工具超时返回明确失败、重复确认只生成一个草稿；随后才进入小范围灰度。

灰度前预先约定停止条件：越权或未确认写入出现一次立即停止；结构化输出失败率、工具错误率和人工接管率超过阈值暂停放量；业务结果与基线明显偏离时由业务负责人确认。停止权限落实到具体值班角色，而不是笼统写“必要时回滚”。

回退也分层处理：模型或路由异常可回退配置，工具 Schema 不兼容需要应用版本回退，已经创建的业务任务不能删除，必须由兼容读取或人工队列继续处理。回退目标是停止新增风险并保存已发生事实，不是把系统假装恢复到从未发布过。

## 上线检查要保留实际证据

```text
【能力基线】支持、不支持、人工接管和版本
【链路回放】样本、路由、工具、权限、状态、输出和审计
【安全结果】越权、敏感泄露、注入和未授权动作
【兼容检查】生产者、消费者、旧链路和回滚组合
【运行观察】延迟、错误、成本、质量和业务指标
【上线动作】灰度、停止条件、负责人和人工确认
【回退方案】版本、配置、任务、数据和外部副作用处理
【未决风险】跳过项、环境阻塞和接受人
```

证据包中的每一项都要指向实际产物：版本号、回放报告、测试记录、监控面板、变更单或责任确认。写着“已检查权限”但没有样本和结果，只能算待办描述。

跳过项也不能隐藏。因环境不可用而未验证的消息重试，需要记录影响、临时控制、补测时间和风险接受人；没有接受人和截止时间的跳过项，应继续阻塞上线。

## 分阶段发布，而不是一次切换

风险较高时，我会分成：

```text
上线前：离线回放、契约、权限、工具和安全门禁
灰度中：小范围流量、指标、人工抽查和快速停止
上线后：业务结果、失败样本、成本、版本回归和旧链路清理
```

灰度不是把验证责任推迟，而是让真实流量在可控范围内提供额外证据。必须先定义何时停止、谁有权停止以及停止后怎样处理已经受理的动作。

AI 在发布阶段适合比对生产者和消费者、搜索旧字段、整理回放证据、检查版本差异并生成候选风险。是否接受未验证项、是否继续放量、如何处理真实业务副作用，必须由研发、业务、安全和运维负责人共同决定。上线门禁的完成标准不是所有清单都打勾，而是每个放行判断都有证据、责任人和可执行的停止方案。

```text
请生成【Agent 版本】上线检查和证据包：

1. 声明能力边界、路由、术语、工具、权限和输出版本；
2. 用核心正常、边界、越权、注入、重复、失败和人工接管样本回放；
3. 检查跨端协议、生产者消费者、旧链路退出和回滚组合；
4. 验证日志、审计、指标、告警、成本和业务结果可观察；
5. 设计上线前、灰度中、上线后的停止条件和人工确认；
6. 列出实际证据、跳过项、环境阻塞和风险接受人。

不执行真实生产写操作，不输出凭据，不把未验证项标记为通过。
```

第四辑由架构地图开始，经过业务语言、路由、安全、权限、受控查询和业务流程，最终落到结构化输出、回放评测和上线门禁。它说明业务 Agent 的可靠性不是模型单点能力，而是整条执行链在真实数据、权限和失败条件下仍然可控。
