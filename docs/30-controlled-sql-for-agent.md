# 从自由 SQL 到受控查询：如何平衡 Agent 能力与数据安全

> 系列导航：[完整目录](00-series-titles.md)

让 Agent 查询数据库，是业务智能体最有吸引力的能力之一。用户可以直接问“上个月哪个门店销售额最高”，不用记报表入口和筛选条件。

但让模型自己写 SQL 并执行，会把越权、误聚合、敏感字段泄露、慢查询和不可审计同时引入。真正可用的方案不是禁止自然语言查询，而是让模型理解问题，生成结构化查询计划，再由服务端校验并使用固定模板执行。

## 核心判断：让模型表达查询意图，不让它拥有数据库权限

自然语言查询的安全边界在“计划”和“执行”之间。模型可以选择经过登记的指标、维度和过滤条件，但不能决定任意表、列、连接和表达式。服务端只有在业务口径、授权范围和运行成本都通过校验后，才生成并执行受控 SQL。

## 自然语言首先要变成数据契约

用户问“上个月哪家门店销售额最高”，系统不能直接把“销售额”和“上个月”拼成 SQL。至少要明确：

```text
指标：含税还是未税，是否扣除退款和取消订单
粒度：门店、仓库、客户还是其他组织对象
时间：上个自然月、滚动三十天还是等长前一周期
范围：当前租户、账套、门店和用户权限
状态：哪些订单状态和支付状态参与统计
结果：排序、并列、限制数量和空数据语义
```

指标和时间口径未定义时，应该澄清或拒绝执行，而不是选择最常见的解释。

## 查询计划比裸 SQL 更容易审查

模型应先输出结构化计划，例如：

```json
{
  "metric": "net_sales_amount",
  "dimensions": ["store"],
  "period": "previous_calendar_month",
  "scope": {"tenant": "current", "ledger": "current"},
  "filters": {"orderStatus": ["completed"], "excludeRefund": true},
  "orderBy": [{"field": "net_sales_amount", "direction": "desc"}],
  "limit": 1
}
```

服务端再验证指标、维度、时间、范围、字段和权限，最终由固定模板或查询构建器生成 SQL。模型不能直接指定任意表名、列名、连接和表达式。

计划是可审计的业务意图，SQL 是受控执行产物。两者分离后，查询规则可以测试、版本化和回滚。

## 从查询计划到 SQL，中间还要经过编译

服务端不会直接信任模型生成的 JSON，而是把它当作待校验输入。以刚才的计划为例，执行过程可以拆成：

```text
校验 metric 是否在指标注册表
-> 校验 store 是否是该指标允许的维度
-> 将 previous_calendar_month 转换为明确起止时间
-> 从授权上下文注入 tenant_id、ledger_id 和门店范围
-> 选择 net_sales_by_store 模板
-> 使用参数绑定生成 SQL
-> 执行成本预检、超时和行数限制
-> 返回带口径和状态的结构化结果
```

最终 SQL 可以由模板或查询构建器生成，例如：

```sql
SELECT store_id, SUM(paid_amount - refunded_amount) AS net_sales_amount
FROM sales_order_daily
WHERE tenant_id = :tenantId
  AND ledger_id = :ledgerId
  AND store_id IN (:allowedStoreIds)
  AND biz_date >= :startDate
  AND biz_date < :endDate
  AND order_status = 'COMPLETED'
GROUP BY store_id
ORDER BY net_sales_amount DESC
LIMIT :limit
```

表名、金额公式、租户条件和状态口径来自注册表与模板，不来自模型。模型即使在计划中插入未知字段或表达式，也会在编译前失败。

## 受控查询工具的边界

工具应限制：

- 可用指标、维度、过滤项和排序项；
- 当前用户可访问的租户、账套、门店和仓库；
- 可返回字段及其脱敏规则；
- 最大时间范围、行数、分页和查询时长；
- 聚合粒度、并列处理和空结果状态；
- 调用人、计划摘要、耗时和结果状态等审计字段。

只读不等于无风险。大范围查询可能造成资源消耗，结果也可能泄露经营数据，因此需要成本限制和数据最小化。

## 三层验证不可省略

```text
计划验证：指标、维度、时间、字段和业务口径是否合法
授权验证：用户能否访问本次租户、账套、组织和数据范围
运行验证：行数、超时、成本、分页和资源使用是否受控
```

三层验证都通过后才能执行。工具执行过程中还要处理超时、部分结果、数据库错误和取消，不让模型把失败包装成空结果或编造答案。

验证失败需要返回结构化原因。例如指标未登记返回 `unsupported_metric`，账套不在授权范围返回 `forbidden_scope`，时间跨度过大返回 `query_too_broad`，执行超时返回 `tool_failed`。这些状态决定下一步是澄清、拒绝、缩小范围还是稍后重试，不能统一返回空数组。

## 查询结果也要带口径和来源

返回结果不能只有一个数字。至少应携带指标定义、数据范围、时间区间、更新时间、是否完整、是否存在并列和查询状态，方便后续输出卡片和用户复核。

原始数据库错误不应直接暴露给用户；内部需要保留追踪编号和审计信息，外部返回可理解的失败状态。

```json
{
  "status": "confirmed",
  "metric": "net_sales_amount",
  "period": {"type": "previous_calendar_month"},
  "scope": {"ledger": "当前账套", "stores": "授权门店"},
  "rows": [{"storeId": "store-3", "value": 182340.50}],
  "dataUpdatedAt": "2026-08-23T23:00:00+08:00",
  "traceId": "query-***"
}
```

前端和模型都基于这个结构解释结果。模型可以把数字转成自然语言，却不能改写指标、范围和状态；数据不完整时，结果必须显式标记，而不是只在文案末尾加一句模糊提醒。

## 受控查询需要反例测试

我会主动测试：指标未定义退款口径、缺少账套、跨租户请求、请求敏感字段、时间范围过大、连接多对多导致重复、查询超时、空结果和并列第一。

测试同时检查查询计划、最终 SQL 的允许范围、参数绑定、数据库过滤、返回字段和审计记录。

其中最重要的是让错误实现发生碰撞：同名 SKU 分布在两个账套、一条订单关联多个标签、退款跨越时间边界、用户请求未授权门店。测试不仅比较最终数字，还比较计划、模板选择、SQL 参数、扫描行数和结果范围。

AI 可以生成候选查询计划、搜索指标定义和构造反例，但指标口径、允许维度、成本预算和数据库权限必须由数据与业务负责人确认。受控查询完成的标志不是“模型能生成 SQL”，而是它无法越过注册表和授权边界，并且每个结果都能回到确定的指标定义、参数和查询证据。

```text
请为【业务查询】设计受控查询方案：

1. 定义指标、维度、粒度、时间、状态和空结果口径；
2. 将自然语言转换成结构化查询计划，不直接执行自由 SQL；
3. 列出允许字段、租户/账套/权限过滤和敏感字段；
4. 设计模板、参数绑定、行数、超时、分页、成本和审计限制；
5. 覆盖错误口径、越权、重复关联、慢查询、空结果和工具失败。
```

Agent 的灵活性应体现在理解问题，而不是拥有数据库权限。查询计划和固定工具把自然语言能力接到数据安全边界之内。下一篇将讨论比查询更高风险的场景：Agent 如何在确认和幂等约束下推动真实业务流程。
