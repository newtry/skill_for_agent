# 从会话记录自动生成工作日报：把 AI 使用过程变成知识资产

> 系列导航：[完整目录](00-series-titles.md)

使用 AI 后，一天的工作常常分散在多个会话里：一个会话排查接口，一个修改测试，一个核对发布配置，还有一个讨论技术方案。只看最终提交，很难知道为什么这样改、哪些问题被排除、哪些风险仍未验证。

我开始把会话记录当作研发过程数据，而不只是聊天历史。

## 核心判断：过程记录只有经过事实对账才是资产

会话中同时存在用户目标、模型建议、待执行计划、真实命令、失败结果和最终判断。自动总结如果不区分这些事件，就会把讨论过的事情写成完成过的事情。工作资产的第一步不是压缩文字，而是按证据重建当天实际发生了什么。

## 一份自动日报最容易把“计划”写成“完成”

有一天的会话同时涉及数据口径诊断、协议迁移、部署脚本和测试环境问题。自动摘要最初写成“完成生产数据修复并发布新协议”，但真实记录是：生产只做了只读查询，修复 SQL 尚待评审；协议完成了代码和测试，没有执行发布。

错误来自摘要只抓住了讨论中的动作词，没有区分计划、实际执行和授权状态。后来生成日报时，我要求每条结果都能回到命令、diff、测试输出或任务状态；找不到证据的内容只能标成建议、待确认或未执行。

那天的记录最后被纠正为：完成协议代码与测试，发布未执行；完成生产问题只读诊断，修复 SQL 待评审；部署脚本仅形成修改建议。文字看起来没有原摘要“成果丰富”，却能够真实支持交接、复盘和责任追踪。

## 先把会话转换成事件

我会先提取结构化事件，再生成日报：

```text
任务事件：开始、切换、阻塞、恢复、结束
决策事件：选择、拒绝、待确认及其依据
修改事件：文件、diff、提交和影响范围
验证事件：命令、代码版本、通过、失败和跳过
外部动作：数据库、发布、消息、对象存储和第三方调用
交接事件：当前状态、未完成项和下一步
```

每个事件包含来源会话、时间、任务或运行标识、状态和证据引用。模型说“接下来运行测试”属于计划；工具返回退出码和测试报告才属于已执行验证。两者不能使用同一种完成状态。

## 日报不应只是活动流水

“今天和 AI 聊了很多，修改了几个文件”没有太大价值。更有用的日报应回答：解决了什么问题，做了哪些关键判断，留下了哪些证据，哪些决定被推迟，下一步是什么。

```text
任务：
问题/目标：
关键发现：
实际改动：
验证结果：
未完成和风险：
沉淀出的规则或工具：
下一步：
```

日报按任务组织，而不是按会话或时间顺序堆叠。一个任务可能跨四个会话，一个会话也可能切换多个任务；只有绑定任务和运行标识，才能把同一目标的分析、修改和验证重新合并。

对关键结论，我会保留证据引用而不是复制完整输出。例如记录测试命令、结果摘要和产物地址，保留失败追踪编号，不把几千行日志贴进日报。这样既可复核，也避免日报变成另一个噪声源。

## 自动总结必须保留不确定性

AI 可以从会话中提取任务、文件、命令和测试结果，但不能把“推测根因”总结成“已解决”，也不能把计划中的测试写成已执行。日报应区分事实、判断、未验证和阻塞。

敏感信息要先脱敏，内部地址、账号、订单和用户数据不应被原样复制到日报或知识库。

我通常使用四种结论状态：`confirmed` 表示有执行或项目证据，`inferred` 表示基于证据的判断，`planned` 表示尚未执行，`blocked` 表示受外部条件限制。摘要生成后再做一致性检查：完成项是否都有证据，失败是否被遗漏，未验证项是否被改写成无风险。

## 从日报到知识候选，而不是直接入库

日报中的“沉淀项”只是候选。一次临时命令、一次项目特例和未经复核的根因不应自动进入长期规则。重复出现且经过验证的问题，可以进入规则、模板、测试或 Skill 的候选队列，再由责任人确认适用范围。

例如连续三次日报都记录“在错误 Maven 根目录执行测试”，说明项目入口文档或自动脚本需要改进；连续出现“测试访问真实 OSS”，则应升级为环境隔离规则和自动门禁，而不是只在周报中提醒。

## 日报也要经过质量检查

我会抽查三类内容：完成项是否有实际证据，重要失败和未验证项是否被保留，敏感信息是否被脱敏。自动生成的任务归并也需要校验，避免把两个同名模块的工作合并，或把上一天未完成的计划算进当天结果。

| 检查项 | 错误示例 | 正确处理 |
| --- | --- | --- |
| 状态 | “计划发布”写成“已发布” | 标为 planned |
| 归属 | 他人提交算作当前会话改动 | 保留作者与来源 |
| 版本 | 测试结果绑定到修改前代码 | 标记证据失效 |
| 风险 | 环境不可用被摘要省略 | 保留 blocked 与影响 |
| 隐私 | 原样复制账号和订单 | 脱敏或只存引用 |

## 从日报反推长期改进

一周后回看日报，可以发现哪些问题重复出现：模块规则总被解释，某类测试总被漏掉，某个发布配置经常遗忘。重复问题就值得升级为项目规则、检查脚本、Skill 或任务模板。

会话记录的价值不在于保存每句话，而在于帮助团队把一次解决方案提炼成下一次可以复用的工作方式。

日报因此不只是汇报工具，也是一种轻量审计：它迫使一天中的分析、执行、验证和未完成事项重新对账。

AI 可以做事件提取、任务归并、证据链接和候选模式发现；工程师负责确认关键判断、风险和知识升级。日报生成完成的证据，是每个“已完成”都能回到实际动作，每个未执行和阻塞都被保留，而不是文案读起来流畅。

```text
请从【会话与工具记录】生成工作资产：

1. 先按任务和运行标识提取决策、修改、验证、外部动作和交接事件；
2. 将结论标记为 confirmed、inferred、planned 或 blocked；
3. 每个完成项附命令、diff、任务状态或产物引用；
4. 保留失败、跳过、未验证和未授权动作，不补写不存在的结果；
5. 脱敏后输出日报，并将重复问题列为待评审的知识候选。
```
