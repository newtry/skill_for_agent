# 真实项目中，AI 最容易犯的十类错误

> 系列导航：[完整目录](00-series-titles.md)

把几个月的使用经验放在一起看，AI 犯错并不是完全随机的。很多错误有固定模式，也有固定的预防办法。

## 核心判断：错误模式应被转化为系统防线

复盘错误的目的不是提醒模型“下次小心”，而是找到它在什么条件下会稳定失效，并把防线放进项目规则、任务输入、工具权限、测试样本和评审门禁。只有错误不再依赖某个人记得，它才真正进入团队学习闭环。

## 十类高频错误

| 错误 | 真实项目中的表现 | 应有防线 |
| --- | --- | --- |
| 没读项目规则就改代码 | App 接口被放进 Admin 入口 | 项目入职扫描和文件证据 |
| 把相似实现当模板 | 复制查询时漏掉账套过滤 | 对比相同点与不能照搬的差异 |
| 把日志最后一行当根因 | 看到事务回滚，却漏掉更早的业务校验 | 按请求 ID 还原时间线和调用链 |
| 只覆盖正常路径 | 流水号到达最后合法值后才溢出 | 围绕不变量设计边界、失败和重试 |
| 把接口成功当数据正确 | API 返回正常，同一 SKU 却跨账套合并 | 声明结果粒度并构造对照数据 |
| 漏掉权限和业务维度 | Agent 给出一个跨门店总数 | 权限上下文进入查询、缓存和输出 |
| 用锁代替完整幂等 | 多实例不并发了，失败重试仍重复写入 | 业务键、状态、唯一约束和补偿 |
| 直接执行生成脚本 | 候选唯一索引阻塞共享开发库 | 只读分析、人工窗口和回滚检查 |
| 把绿色当成验证完成 | 测试通过，却真实上传了对象存储 | 检查执行范围、依赖和外部副作用 |
| 把历史改动当噪声 | 为了“干净”覆盖用户未提交文件 | 先做变更地图，未知改动保持不动 |

这些错误背后的共同原因是：模型在缺少事实时会补全，在缺少边界时会选择最短路径，在缺少验证时会把局部结果当成完成。

## 十类错误其实来自四个失效阶段

| 失效阶段 | 对应错误 | 根本问题 |
| --- | --- | --- |
| 理解现场 | 未读规则、误用相似实现、覆盖历史改动 | 把局部上下文当成完整项目 |
| 推理业务 | 误判根因、漏边界、丢数据维度 | 没有声明因果、不变量和粒度 |
| 执行动作 | 用锁代替幂等、直接执行脚本 | 权限、状态和失败恢复未强制 |
| 验证交付 | 只测正常路径、把绿色当完成 | 证据范围小于风险范围 |

这个分类比记住十条更重要。它说明防线必须覆盖任务开始、方案与实现、工具执行和交付接受四个阶段，不能只靠代码审查在最后兜底。

## 一次错误怎样进入学习闭环

以“测试通过却真实上传对象存储”为例，最初看起来是测试配置疏忽。继续追踪后发现：测试继承默认环境、上传工具没有测试替身、执行报告只记录断言通过、流程也没有检查外部副作用。

修复因此分成四层：测试配置默认指向隔离存储；上传能力在测试环境使用替身；验证报告增加副作用检查；历史事故样本进入回归。若只在项目文档增加一句“不要访问真实 OSS”，错误仍可能重现。

## 错误清单要进入流程，而不是停在文章里

这十类错误分别对应项目规则、任务模板、测试矩阵和人工门禁。比如“测试是否真的执行”可以由脚本检查，“是否跨模块直接引用实现”可以由依赖规则检查，“是否允许执行生产 SQL”则必须由权限和人工授权控制。

不是每一类都要靠提醒解决。能够静态检查的就写成检查器，能够通过测试证明的就进入回归集，只有业务口径和风险接受等无法自动判断的部分才保留给人。

我会按控制强度选择载体：

```text
知识提醒：说明为什么容易错
任务模板：要求开始前提供必要事实
静态检查：阻止结构性违规进入代码
测试回归：用碰撞和失败样本暴露行为错误
工具约束：从执行能力上禁止越权
人工门禁：处理业务决定与风险接受
```

越靠后的防线成本通常越高。能在任务输入阶段发现入口错误，就不应等到集成测试；能由工具禁止生产写入，就不应只依赖评审人看见一条危险命令。

## 预防办法也可以工程化

项目规则减少第一类和第二类错误；调用链和证据要求减少第三类；风险驱动测试减少第四类和第五类；数据粒度检查减少第六类；业务键和状态机减少第七类；人工确认门禁减少第八类；真实命令和结果报告减少第九类；接手前读取工作区减少第十类。

AI 不会因为知道这十类错误就永远不犯，但团队可以让错误更早暴露、更容易回滚、更不容易进入生产。

## 错误清单也需要版本和优先级

不是所有项目都同样关注十类错误。ERP 优先租户、账套和状态，Agent 系统还要关注路由、工具与敏感输出，任务自动化则增加并发认领、工作区和环境副作用。团队应按历史事故和当前架构维护自己的高风险清单。

每个错误项至少记录触发条件、影响、检测方法、防线、责任人和回归样本。重复发生说明防线位置或强度不够；长期不再适用的条目可以降级，但事故样本仍应保留在历史记录中。

AI 可以从会话、评审和事故中聚类错误、寻找遗漏防线并生成反例；工程师负责根因和修复层级；业务与安全负责人确认影响和阻断等级。错误治理完成的证据，是原失败样本能够稳定被提前拦截，并且团队知道拦截发生在哪一层。

```text
请将【AI 工程错误】转化为系统防线：

1. 还原最小触发条件、影响范围和首次失效阶段；
2. 区分理解、业务推理、动作执行和交付验证问题；
3. 在规则、模板、检查器、测试、工具权限和人工门禁中选择防线；
4. 构造能区分错误与正确实现的回归样本；
5. 记录责任人、阻断等级和防线失效后的升级路径。
```

错误模式已经明确后，下一篇将把这些风险落实为动作权限：哪些步骤可以自动执行，哪些只能准备材料，哪些必须等待人工确认。
