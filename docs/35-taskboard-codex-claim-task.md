# 任务板接入 Codex：让 AI 从等待提问走向主动领取任务

> 系列导航：[完整目录](00-series-titles.md)

当 AI 只存在于聊天窗口里，它只能处理有人主动描述的事情。接入任务板之后，AI 可以读取待处理任务、判断自己是否适合、认领一个任务，再进入分析、实现和验证流程。

这一步看似只是增加一个 API，实际改变了任务的责任边界：AI 不再只响应问题，而开始参与团队的工作队列。

## 核心判断：认领是带条件的处理租约，不是无限授权

任务板允许 AI 主动发现工作，但不能因此把任务描述、执行权限和完成责任全部交给模型。一次有效认领只能证明：当前任务满足自动处理条件，并在限定时间内交给某个执行器。它不代表需求已经理解，也不代表执行器可以发布、修改生产数据或最终关闭任务。

## 两个轮询器曾经同时看见同一条任务

最初的认领逻辑是先查询“待处理”任务，再单独更新为“处理中”。两个执行器在相近时间轮询时，都可能读到同一条记录，并分别开始恢复项目上下文。即使最后只有一个成功回写状态，两个工作区也已经产生重复修改。

后来认领变成带前置状态的原子更新：只有任务仍为待处理且没有认领人时才能写入执行者和版本；更新影响行数不为 1 时，当前执行器立即退出。认领成功后还要生成运行标识，后续回写必须携带同一标识，防止旧会话覆盖新一轮结果。

```text
读取候选任务 -> 条件认领
条件不成立 -> 不执行
认领成功 -> 记录执行者、版本和运行标识 -> 恢复项目
```

这实际上是一份最小认领协议：

```text
claim(taskId, expectedStatus, workerId, runId, leaseUntil, taskVersion)
```

服务端通过条件更新校验状态和版本，并返回新的任务版本。后续续租、回写和释放都必须携带 `runId` 与版本；旧执行器即使稍后恢复，也不能继续更新已被重新分配的任务。

## 为什么认领还需要租约和恢复

执行器可能崩溃、网络中断或长时间卡在外部依赖上。如果认领只有“处理中”状态而没有租约，任务会永久悬挂；如果租约到期后直接交给新执行器，旧执行器又可能在恢复后继续写代码和回写结果。

因此需要区分租约到期与任务取消：租约到期后先标记为待恢复，检查运行记录、工作区和外部副作用，再决定续租、转人工或创建新运行。发生过数据库写入、发布或第三方调用的任务，不能仅凭超时自动重跑。

## 自动领取之前先定义“能领取什么”

不是所有任务都适合自动认领。描述清楚、范围有限、风险可控的代码和文档任务可以进入自动队列；生产变更、支付退款、模糊需求和需要业务拍板的任务应停在待分析或人工分配。

任务板需要提供足够上下文：目标、验收条件、相关项目、优先级、依赖、风险和当前状态。只有一句标题的任务，不应该被 AI 误判为可直接执行。

我会把任务分成四类：

| 类型 | 示例 | 自动处理策略 |
| --- | --- | --- |
| 可直接执行 | 明确范围的文档、测试、小型代码修复 | 可以自动认领 |
| 先分析 | 需求明确但方案和影响范围未知 | 只认领分析阶段 |
| 需要确认 | 数据迁移、权限、支付或业务口径 | 生成方案后等待人工 |
| 禁止自动化 | 生产发布、真实退款、不可逆删除 | 不进入自动队列 |

资格判断不能只依赖标题关键词。任务的风险标签、环境、所需动作和验收完整度要由任务板规则与服务端共同判断，模型只能提供候选分类。无法判断时宁可进入待分配，也不能默认放行。

## 任务本身也要满足输入契约

一条可认领任务至少应包含：目标、范围、不做什么、验收条件、项目或模块、依赖、风险等级和人工确认点。任务还要绑定版本，认领后若需求或验收被修改，执行器必须重新读取并决定是否暂停。

```json
{
  "taskId": "TASK-1024",
  "goal": "修复账套维度缺失的库存缓存",
  "scope": ["inventory-query", "cache-key"],
  "acceptance": ["跨账套碰撞用例通过", "缓存键包含 ledgerId"],
  "risk": "medium",
  "forbiddenActions": ["production-write", "release"]
}
```

任务板是工作入口，但这份结构仍要与代码、项目规则和当前现场核对。任务描述过时或与代码冲突时，应回写差异并暂停，而不是让 AI 自行选择哪一边正确。

## 认领动作必须可追踪

AI 认领前要确认任务仍处于可认领状态，认领后记录执行者、时间、会话或运行标识。并发轮询时不能让两个 AI 同时处理同一任务；认领失败也不能继续修改代码。

认领只是获得处理权，不代表获得发布权。任务状态可以继续拆成待分析、处理中、待验证、待评审和已完成，保留人工节点。

审计记录至少包括候选发现时间、资格判断、认领条件、执行器与模型版本、运行标识、租约变化和退出原因。这样出现重复修改时，才能判断是任务板并发控制失效、租约恢复错误，还是执行器无视认领失败继续工作。

## 任务板是上下文入口，不是事实来源的替代品

AI 仍然需要读取项目规则、当前工作区和实际代码。任务板描述可能过时，标题也可能省略关键约束。因此认领后第一步应是恢复项目上下文，并把任务板事实与代码事实对照。

```text
待处理 -> 可执行性检查 -> 认领
       -> 项目恢复 -> 分析/实现/验证
       -> 回写证据 -> 待评审或人工接管
```

任务板接入的价值，不是让 AI 自动多做几件事，而是把任务发现、执行、验证和责任记录连接起来。自动领取越成熟，越需要清晰的风险分级和人工接管条件。

## 怎样验证认领机制真的可靠

我会主动制造并发认领、任务版本变化、租约超时、执行器崩溃、旧运行延迟回写和高风险任务误入队列。验证目标不是“最终只有一个状态”，而是任何时刻只有一个有效处理权，失败执行器不会产生未登记写入，所有退出和接管都能从运行记录解释。

AI 可以帮助筛选候选任务、恢复项目上下文和生成资格判断依据；任务板服务负责原子认领、租约、版本和审计；工程师负责风险分类与接管。认领完成的证据，是任务获得唯一运行标识并进入可恢复状态，而不是执行器已经开始修改文件。

认领只解决任务怎样进入自动化队列。下一篇将继续连接上下文恢复、实现、验证、失败出口和回写，把一次认领扩展成可恢复的完整任务状态机。
