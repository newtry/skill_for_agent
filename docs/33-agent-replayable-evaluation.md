# 模型觉得正确还不够：如何构建可回放、可评测的 Agent

> 系列导航：[完整目录](00-series-titles.md)

Agent 上线初期，团队常用“我试了一下，回答还不错”判断质量。这个方法无法比较版本，也无法解释一次失败究竟来自术语消歧、路由、权限、工具参数、数据口径、输出结构还是模型建议。

我后来把一次 Agent 请求看成一条可回放的执行记录，而不是一段不可复现的聊天。评测对象也从“最终回答像不像参考答案”扩展为整条业务执行链是否满足契约。

## 核心判断：评测对象是执行链，不是最终文案

最终回答只是链路的最后一个产物。路由错误、权限越界、数据口径错误或确认前写入，即使被一段流畅的文字掩盖，也仍然是失败。可回放记录的价值，是把一次结果拆成可定位、可比较、可阻断的证据。

## 一条请求需要记录哪些事实

至少要能看到：

```text
输入与会话范围
术语/意图识别与路由版本
身份、租户、账套和授权判断
检索内容摘要、工具名称和结构化参数
工具返回状态、数据范围和关键结果摘要
状态变化、确认、幂等和人工接管
最终结构化输出与错误处理
模型、提示词、工具 schema 和配置版本
```

涉及敏感数据时，记录应使用脱敏值、哈希、摘要或合成数据，但仍要保留足以定位决策链的事实。

## 一条回放记录长什么样

以“够三手就生成调拨草稿”为例，回放记录不保存完整对话和原始库存明细，而保存可验证摘要：

```json
{
  "caseId": "transfer-conditional-01",
  "versions": {
    "model": "model-version",
    "termSet": "fashion-terms-v4",
    "router": "router-v7",
    "toolSchema": "inventory-v3",
    "outputSchema": "card-v2"
  },
  "recognized": {"term": "一手配码", "intent": "conditional_transfer_draft"},
  "scope": {"tenant": "hash-a", "ledger": "hash-1"},
  "calls": [
    {"tool": "inventory_sets", "status": "confirmed", "result": {"sets": 5}},
    {"tool": "transfer_preview", "status": "waiting_confirmation"}
  ],
  "finalStatus": "waiting_confirmation"
}
```

这条记录能够证明术语、路由、权限、工具顺序和最终状态，却没有复制手机号、完整订单或数据库结果。回放时可以替换底层模型，再比较每个断言是否仍然成立。

## 评测对象不只有最终回答

一次最终回答正确，但调用了越权工具，仍然是失败；答案措辞漂亮，但把空结果编成有数据，也不能通过；动作卡结构有效，但确认前已经发生写入，更是阻断级问题。

我会将每条评测拆成多个断言：

```text
输入 -> 预期术语/意图 -> 允许路由
-> 必需上下文 -> 允许工具 -> 参数和权限
-> 数据口径 -> 状态与副作用 -> 输出契约
-> 失败、停止或人工接管
```

这样失败能够定位到控制层，而不是只能说“模型回答错了”。

刚才的样本至少需要这些断言：识别为“一手配码”而不是货源；先查询再生成草稿；库存不足三手时不得调用写工具；授权范围不包含目标门店时返回拒绝；满足条件也只能停在待确认，不能直接提交；最终卡片必须携带预览 ID 和范围。

任何一条失败，都能定位到术语、路由、授权、工具或输出层。只比较最终文案，很可能看不见已经发生的非法工具调用。

## 评测集必须来自真实失败

通用的“查一个商品”样本很快会被模型适应，真正有价值的样本来自历史纠正、线上失败和人工接管：

- 行业术语和相似意图混淆；
- 缺少账套、时间或商品参数；
- 跨租户、越权和敏感信息诱导；
- 固定查询与开放诊断路由冲突；
- 工具超时、空结果、慢查询和非法结构；
- 重复动作、确认后重试和状态乱序；
- 输出需要澄清、拒绝、待处理或人工接管。

每条样本都要有预期路由、允许工具、数据范围、关键断言、阻断条件和可接受误差，而不是只保存一段参考文案。

我会把线上纠正进入评测集的过程固定下来：先脱敏并还原最小触发条件，再判断失败属于哪一层，补充预期断言，确认修复后加入长期回归。这样评测集记录的是系统曾经付出过代价的问题，而不是为了让分数好看而挑选的标准问法。

## 质量指标要分层，不能用平均分掩盖越权

我会分别统计：

| 指标 | 说明 |
| --- | --- |
| 语言层 | 术语消歧和意图路由准确率 |
| 工具层 | 参数正确率、非法调用率、工具失败处理 |
| 数据层 | 口径、粒度、租户账套和字段准确率 |
| 状态层 | 重复动作安全、状态收敛和补偿正确 |
| 产品层 | 输出结构有效率、澄清率、人工接管率 |
| 治理层 | 越权率、敏感泄露率、审计完整度和成本 |

权限越界、未确认写入、真实敏感数据泄露和重复资金动作属于阻断级失败，不能被其他大量普通问答的高分抵消。

平均指标还要结合业务分布。高频查询准确率高，不能掩盖低频退款动作存在未确认写入；整体转人工率下降，也可能是路由错误地放行了高风险请求。上线门槛需要同时设置分层指标和关键样本零容忍规则。

## 版本变化必须触发回归评测

模型、系统提示词、术语库、路由表、工具 Schema、权限规则、查询模板和输出组件任何一项变化，都可能改变整条执行链。

评测记录应绑定版本，比较新增失败、恢复失败和指标变化；不能只看新版本平均分是否上升。历史失败样本要长期保留，修复一个问题不能让旧问题重新出现。

模型输出存在波动时，同一用例可以重复执行，区分确定性契约与允许波动的文案。路由、权限、工具调用和业务状态应稳定满足断言；摘要措辞可以设置语义或结构容差。不能因为模型天然不确定，就放宽安全和副作用要求。

## 回放环境要避免真实副作用

回放查询优先使用脱敏快照、合成数据和只读工具；写操作使用模拟执行、事务回滚、沙箱或专用环境。评测记录不能包含生产密码、订单明细和完整个人信息。

同时要确认工具返回和日志不会把敏感字段扩散到评测样本。可回放和数据最小化必须同时成立。

AI 可以帮助从执行记录生成候选用例、聚类失败并比较版本差异；工程师负责定义链路断言和可复现环境；业务、安全与产品负责人共同确定阻断级失败和可接受误差。评测完成的证据不是一个总分，而是一份绑定版本、可以定位失败、不会产生真实副作用的回放报告。

```text
请为【Agent 能力】设计回放评测：

1. 记录输入、术语、路由、身份、授权、工具、参数、结果、状态和输出版本；
2. 从真实失败构建正常、边界、歧义、越权、注入、重复和工具故障样本；
3. 为每条样本定义关键断言、阻断级失败和可接受误差；
4. 分别统计路由、工具、数据、状态、输出和治理指标；
5. 说明模型、提示词、术语、工具或权限变化时的回归门禁；
6. 使用脱敏、合成、沙箱或只读环境，禁止产生真实业务副作用。
```

评测把“这次看起来正确”变成可重复比较的执行证据。下一篇将把这些证据接入上线流程：能力、路由、工具、权限、输出和评测全部满足门禁后，Agent 才能进入真实环境。
