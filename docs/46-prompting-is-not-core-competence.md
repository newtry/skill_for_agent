# 为什么提示词技巧不是 AI 编程的核心竞争力

> 系列导航：[完整目录](00-series-titles.md)

提示词当然重要，但它很容易被误解成一套神秘的措辞技巧：加几个角色、换一种格式、要求模型“深度思考”，就能稳定得到好结果。

我的经验是，真正决定效果的通常不是句子写得多漂亮，而是工程师是否知道要提供什么事实、划定什么边界、要求什么证据。

## 核心判断：提示词是接口，工程系统才是能力底座

提示词负责表达当前目标和协作方式，却不能凭空产生项目事实、业务规则、执行权限和验证环境。稳定结果来自一套可被读取和执行的工程系统：项目规则、任务契约、代码现场、工具边界、测试证据与人工门禁。措辞优化可以减少歧义，但无法替代这些基础设施。

## 同一句“继续”，结果为什么完全不同

在一次跨仓库迁移中，我分别让两个会话“继续处理”。一个会话只有需求标题，于是重新分析架构并提出一套新方案；另一个会话先读取提交记录、工作区 diff、交接文档和最近的测试结果，准确定位到尚未切换的调用方。

提示词完全相同，差异来自第二个会话拥有可验证的任务状态。它知道哪些结论已经确认、哪些改动属于用户、哪些测试对应当前代码版本，也知道“继续”不包含提交和发布授权。

这个例子也说明，上下文不是越长越好。完整聊天记录可能包含过期方案和重复讨论，而任务版本、代码基线、diff 与测试结果虽然更短，却直接决定下一步。高质量上下文的关键是权威性和相关性，不是 token 数量。

## 同一句话在不同项目里结果不同

“帮我加一个接口”在示例项目里可能足够，在 ERP 里却需要说明入口、模块、租户、账套、兼容性和验收。模型结果的差异，来自问题空间不同，不是某个神奇关键词。

即使在同一项目，任务阶段也会改变含义。“帮我看一下”在分析阶段意味着只读调查，在评审阶段意味着检查交付证据，在生产故障中则可能需要受控日志和数据访问。提示词没有携带阶段和权限时，模型只能用常见经验补全。

## 一份可靠输入由四层组成

```text
项目基线：模块、依赖、构建、数据和禁止动作
任务契约：目标、范围、验收、开放问题和授权
当前现场：版本、diff、运行状态、测试与阻塞
当前指令：这一步要分析、实现、验证还是交付
```

项目基线跨任务复用，任务契约约束本次目标，当前现场随执行更新，提示词只表达当前动作。把四层都塞进每次对话会重复且容易漂移，更好的方式是让 AI 从权威载体读取，并在开始前报告证据和冲突。

## 更高阶的提问是工程准备

好的任务说明包含目标、事实、范围、约束、开放问题、验收条件和授权。好的工作区包含项目规则、相似实现、测试入口和交接记录。好的反馈包含实际 diff、命令、数据结果和失败证据。

这些东西比“请你像专家一样回答”更能改变结果。

工程准备还包括让错误能够暴露。任务卡写验收条件，项目规则写依赖边界，测试记录真实命令，交接文档写未完成项。它们共同减少模型需要猜测的空间，也让错误结论更容易被人发现。

我会比较两种任务输入：

| 只优化措辞 | 完成工程准备 |
| --- | --- |
| “你是资深 Java 专家，请完整实现” | 给出模块、调用链、边界和相似实现证据 |
| “请深度思考所有边界条件” | 明确数据粒度、不变量和风险样本 |
| “确保代码质量并充分测试” | 列出验收、测试层级、命令和环境限制 |
| “完成后告诉我结果” | 要求 diff、实际输出、未验证项和副作用 |

左侧可以改善回答风格，右侧才真正约束实现选择和完成判定。

## 提示词模板也有适用边界

模板适合提醒固定输入与输出，但不能让使用者跳过判断。复杂任务若机械套模板，可能出现大量形式完整但无事实依据的章节；简单任务若套用过重流程，又会增加不必要成本。

因此模板和 Skill 应包含触发条件、缺参处理和暂停点。遇到业务口径、权限或生产动作时，最专业的输出可能不是更完整的方案，而是明确说明还缺谁的决定。

## 核心能力仍然是判断和验证

工程师要能识别业务不变量，知道数据粒度，理解事务、权限、依赖和部署，判断测试是否真的覆盖风险。AI 可以放大这些能力，也会放大缺少这些能力时的错误速度。

所以 AI 编程的竞争力不是谁会背更多提示词，而是谁能把模糊问题变成可验证任务，再把结果纳入真实工程流程。

这种能力至少包括：识别哪些事实会改变方案，发现模型正在用假设填空，把业务语义翻译成数据和状态不变量，设计有辨识力的反例，以及判断验证结果是否对应当前代码与环境。

AI 可以帮助整理输入、发现信息缺口和生成任务模板；工程师负责事实选择、规则确认与证据接受。提示词优化完成的标准，不是回答更像专家，而是不同会话在同一事实和边界下能够稳定做出相近的工程选择。

```text
请不要只优化【提示词】，先检查任务的工程准备：

1. 列出项目基线、任务契约、当前现场和当前指令；
2. 标出已确认事实、推断、开放问题和授权缺口；
3. 说明哪些信息会改变模块、数据、状态或验证选择；
4. 将稳定内容放入权威载体，只在提示词中保留当前动作；
5. 用实际 diff、测试和未验证项评价结果，不评价措辞是否漂亮。
```

提示词负责表达当前意图，上下文和工程系统负责让这个意图可以被正确执行。两者都重要，但后者才是难以通过复制一段文字获得的能力。
