# 规则优先，LLM 兜底：意图识别为什么需要统一注册表

> 系列导航：[完整目录](00-series-titles.md)

业务 Agent 上线第一版后，新增意图往往很快：在路由器里加几个关键词，在提示词里补一段说明，再注册一个工具。问题通常不会立刻出现，因为 LLM 能用语义理解填补一些配置差异。

当意图增长到几十个以后，这种宽容开始变成风险。同一个“查销售趋势”，路由规则叫 `sales_trend`，计划模板使用 `sales_analysis`，工具注册处只支持“销售汇总”，评测样本又把它归入“经营分析”。修改时间参数时，有人只改了工具 Schema，结果规则命中的请求走旧计划，模型兜底的请求却走新参数。

表面上是分类偶尔不准，实际问题是系统里没有一份统一答案说明：这个业务能力究竟是什么。

## 核心判断：意图注册表是业务能力的单一语义来源

意图识别不只是把一句话分类成标签。分类结果还会决定需要补充哪些参数、允许调用什么工具、执行什么计划、何时算完成以及用哪些样本回归。

因此，规则和 LLM 都不应该各自定义业务能力。它们只负责把用户表达映射到已经注册、具备边界和执行契约的意图。

```text
用户表达
-> 确定性规则匹配
-> 无唯一结果时交给 LLM 消歧
-> 映射到已注册意图
-> 参数校验与权限检查
-> 计划、工具和完成策略
-> 评测与运行观测
```

注册表不是关键词表，而是业务语义进入执行系统的控制面。

## 为什么把所有路由交给 LLM 不够可靠

LLM 适合处理别名、省略、口语和跨句信息，却不适合独自承担稳定业务分流。

第一，同一句明确请求可能因上下文和模型版本变化走向不同路径。第二，模型可以生成一个听起来合理、系统却没有工具和权限支持的新意图。第三，分类答案通常无法解释参数、计划与完成条件为什么随之变化。第四，稳定请求每次重新推理会增加延迟、成本和回归面。

反过来，只使用关键词也不够。服装业务里的“看下这批货走得怎么样”可能指销售趋势、库存周转或客户反馈；“客户库存”与“库存不足客户”包含相同词，却对应完全不同的数据对象。

更合理的分工是：规则处理高置信、可解释的稳定表达，LLM 处理规则无法唯一判断的开放语言，但 LLM 的输出仍必须回到受控注册表。

## 一条意图定义要贯穿路由、执行和评测

我会为每个意图至少维护以下内容：

| 定义项 | 回答的问题 | 主要消费者 |
| --- | --- | --- |
| 业务含义与边界 | 这个意图解决什么、不解决什么 | 产品、路由、评审 |
| 别名与正向样本 | 哪些表达可以高置信命中 | 规则、LLM、评测 |
| 排除条件与冲突意图 | 哪些相似表达不能命中 | 路由、回归测试 |
| 参数契约 | 必填维度、默认值和澄清条件是什么 | 参数提取、前端 |
| 工具与权限 | 能读什么、能写什么、谁能执行 | Agent、授权层 |
| 计划模板 | 稳定步骤和允许的分支是什么 | 计划器、状态机 |
| 完成策略 | 什么证据足以交付结果 | 执行器、评测 |
| 版本与责任人 | 谁批准变更、何时生效或退役 | 发布、审计 |

例如“销售趋势”不能只写成几个触发词。它还要声明统计对象、时间粒度、账套和门店范围，明确它与“销售明细”“商品排行”的差异，并绑定受控聚合工具和空结果处理。

当这些定义来自同一注册表时，增加参数不再只是修改 Schema，而会显式暴露路由样本、计划模板、前端输入和评测数据的同步影响。

## 规则优先的前提是冲突可以被解释

规则并非命中越多越好。每条规则都需要置信级别、优先级、排除条件和冲突处理。

```text
唯一高置信命中：直接进入已注册意图
多个候选命中：比较排除条件和上下文
仍不能唯一判断：交给 LLM 在候选集合中消歧
缺少关键参数：先澄清，不进入执行
没有受控意图：拒绝、转人工或进入开放问答
```

LLM 消歧时只应看到候选意图的业务定义和边界，不应获得任意发明执行路径的权限。返回结果还要经过注册状态、参数和权限校验。模型说“这是库存预测”不能让系统临时拼一条自由 SQL 去完成尚未注册的能力。

这条约束把不确定性留在语言理解层，而不让它直接扩散到工具执行层。

## 注册表还要管理版本和退出

统一入口不能只解决新增，也要解决变更和删除。否则旧名称、旧参数和旧评测会永久留在系统里。

一次意图变更至少要回答：这是兼容扩展还是语义变化；哪些调用方和历史任务受影响；规则、提示词、工具、卡片和评测是否使用同一版本；旧意图何时停止接收新请求；运行中任务由哪个版本继续解释。

对准备退役的意图，我会先停止新增依赖，观测实际调用，再删除规则、模板、工具授权和样本。只从提示词里删掉名称，不代表能力已经退出。

## 测试不能停在分类标签

如果测试只断言 `intent == sales_trend`，注册表后半段仍可能断裂。完整回归至少要覆盖：

```text
表达 -> 候选意图与命中依据
意图 -> 参数提取与澄清
参数 -> 权限与工具选择
工具结果 -> 计划推进与完成判定
最终状态 -> 输出结构、日志和评测结果
```

我还会固定检查冲突表达、旧别名、缺失参数、越权范围、停用意图和 LLM 返回未知标签。对每次注册表变更，根据依赖关系选择受影响样本，而不是只跑新增的几个正例。

完成证据不只是“近两千条用例通过”，还包括每个核心意图能够说明：为什么命中、使用哪个版本、允许做什么、怎样完成，以及改动后哪些消费者已经同步。

## AI 与人分别负责什么

AI 适合从日志和会话中聚类别名、发现重复定义、生成冲突样本、扫描注册表消费者并执行回放。业务负责人决定意图边界和口径，架构与安全负责人确认工具和权限，工程师保证定义能够从路由贯穿到执行与评测。

模型不能根据历史频率自行合并两个业务意图，也不能因为某个工具“能查到”就扩大能力范围。统一注册表的价值，正是让这些决定拥有明确责任和版本。

```text
请审计【业务 Agent】的意图体系：

1. 汇总规则、提示词、工具、计划、完成策略和评测中的意图定义；
2. 找出同名异义、同义异名、参数不一致和无执行契约的意图；
3. 为每个意图补充业务边界、排除条件、参数、权限、工具和版本；
4. 设计规则优先、LLM 候选消歧、未知意图拒绝或转人工的路径；
5. 生成冲突、边界、旧别名和端到端回放样本；
6. 列出变更影响、退役条件、责任人和实际证据。

不让 LLM 发明未注册的可执行意图，不把关键词命中直接等同于业务目标成立。
```

统一注册表回答了“系统提供的能力是什么”。下一篇继续回答另一个容易漂移的问题：能力开始执行以后，什么状态才代表用户目标真的完成。
