# 规则优先，LLM 兜底：意图识别为什么需要统一注册表

业务 Agent 做到一定规模后，我遇到的一个问题是：意图识别规则散落在太多地方。

同一个“查销售趋势”，路由器里有一组关键词，提示词里有一段说明，工具注册处又维护了一份参数定义，评测数据还使用另一套名称。修改一个意图时，经常只改了其中两处。模型偶尔能靠语义补上差异，因此问题不会立即暴露，却会在边界表达、别名或新场景中反复出现。

## LLM 不应该承担所有路由工作

模型适合处理开放表达，但大量业务请求其实有稳定结构。例如用户明确说“查某时间段的销售额”，系统已经知道对应场景、必填参数、可用工具和完成条件。此时每次都让模型从头推理，不仅增加成本和延迟，也让同一句话可能走向不同链路。

后来的改造采用了“规则优先，LLM 兜底”：高置信度、可解释的规则先匹配；规则无法唯一决定时，再交给模型判断。关键不只是增加一个规则层，而是建立统一的意图定义注册表。

```text
意图定义
 -> 名称与业务含义
 -> 触发表达与排除条件
 -> 参数契约
 -> 可调用工具
 -> 任务计划模板
 -> 完成策略
 -> 评测场景
```

路由、执行和评测都读取同一份定义，才能避免一个意图在不同阶段拥有不同名字和语义。

## 注册表解决的是治理问题

统一注册表让每次变更都有明确影响范围。新增参数时，可以检查任务计划和工具契约是否同步；调整触发词时，可以回放冲突意图；停用场景时，也能找到所有依赖方，而不是只删掉一段提示词。

这次改造还引出了两个容易忽略的设计。第一，规则命中必须有优先级和冲突处理，否则“库存不足客户”和“客户库存”之类的表达可能同时命中。第二，规则失败不代表请求失败，它只是把决定权交给 LLM；但 LLM 的结果仍要映射回注册表中的受控意图，不能临时发明一个没有工具和完成条件的新场景。

## 测试要覆盖整条意图链

我没有只验证“分类结果等于某个标签”，而是把测试延伸到参数提取、计划生成、工具选择和完成判定。一次完整回归通过了近两千条用例，但更重要的是新增场景能够说明：它为什么命中、使用了哪个定义、执行到什么程度才算完成。

意图识别从来不只是模型分类问题。它是业务语义进入执行系统的第一道契约。规则提供稳定性和可解释性，LLM 提供对开放语言的适应能力，统一注册表则让两者不会各自演化成另一套系统。
