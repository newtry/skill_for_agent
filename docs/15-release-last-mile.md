# 发布前的最后一公里：让 AI 检查配置、日志、JVM 和运行环境

许多问题不是代码写错，而是发布时遗漏了一个配置、依赖服务不可达、JVM 参数不合适，或回调地址仍指向测试环境。开发环境能运行，只能说明开发环境具备了条件，不代表生产环境也具备。

发布前，AI 最适合承担一项枯燥但重要的工作：把代码变更、配置、基础设施和验证动作串成一张检查清单。它不能替代发布审批，却能显著减少人靠记忆漏项的概率。

## 先做变更影响清单

我会让 AI 从本次 diff、依赖和配置中反推影响面：新增接口需要哪些网关或权限规则，新增表字段需要哪些迁移，新增异步任务需要哪些开关，新增第三方调用需要哪些密钥、网络和回调配置。

这比直接问“生产还要配什么”更可靠，因为清单与具体改动绑定。每一项应注明来源、目标环境、负责人和验证方式；不确定项必须保留为待确认，而不能用“应该没问题”带过。

## 四类最容易被忽略的差异

配置差异包括环境变量、Profile、对象存储、缓存、消息队列和第三方地址。日志差异包括脱敏规则、错误码、追踪 ID 和告警阈值。运行时差异包括 JDK、容器内存、JVM 参数、时区和文件权限。网络差异包括 DNS、HTTPS 证书、安全组、回调白名单和跨网段访问。

AI 可以逐项比对配置样例和部署脚本，但不能输出真实密码、私钥、内部地址或完整生产配置。报告字段名、用途和是否缺失已经足够。

## 验证要分层，而不是只看健康检查

服务 `health` 为 UP 只代表进程存活。发布后还应分别验证：版本和配置是否生效，数据库迁移是否正确，核心接口是否具备权限，缓存或消息是否连通，定时任务是否未重复启动，关键日志和监控是否可见。涉及支付或权益的变更，再增加沙箱或受控业务验证。

如果某项需要真实业务数据或外部授权，应明确标记为人工验证，而不是让 AI 假装已经完成。

## 发布前提示词

```text
请基于本次改动生成只读发布检查清单：

1. 代码、数据库、配置、权限、外部依赖、网络和运行时影响；
2. 每项的来源、环境差异、验证方法和回滚条件；
3. 需要人工确认或外部授权的项目；
4. 发布后从进程、接口、数据、日志、监控五层验证的顺序。

不要读取或输出真实凭据，不执行发布、迁移或生产操作。
```

发布的最后一公里并不神秘，它只是要求把“代码完成”后那些仍可能失败的条件显性化。AI 擅长做这份系统性核对，人负责批准、执行和对风险负责。
