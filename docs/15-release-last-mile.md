# 发布前的最后一公里：让 AI 检查配置、日志、JVM 和运行环境

> 系列导航：[完整目录](00-series-titles.md)

一次服务发布前，业务测试和代码构建都已经通过，部署脚本却在目标机器连续失败。

目标环境使用新的 Python 环境管理方式，脚本仍假设系统解释器和旧的依赖安装命令；修复这一处后，脚本又因为工作目录不同找不到配置；进程最终启动，健康检查返回正常，但真正请求第三方服务时才发现生产网络和回调白名单尚未配置。

每个问题单独看都不是业务代码缺陷，它们共同说明：代码通过测试，只能证明代码在测试条件下成立，不能证明目标环境已经具备运行这次变更的全部条件。

发布不是把构建产物复制到服务器，而是让代码、配置、数据结构、运行时、外部依赖和可观测性从旧状态共同迁移到新状态。AI 在发布阶段最有价值的工作，是把这些分散条件变成一份有来源、有验证、有负责人和有回退条件的发布证据包。

## 从变更反推运行条件

发布检查不应从一张通用清单开始，而应先读取本次需求、代码 diff、配置变化和数据库迁移，逐项反推运行影响。

| 代码变化 | 可能引出的发布条件 |
| --- | --- |
| 新增接口 | 网关路由、鉴权、限流、文档和客户端兼容 |
| 新增字段 | 数据库迁移、历史回填、序列化和旧版本兼容 |
| 新定时任务 | 调度配置、开关、多实例幂等和监控 |
| 新第三方调用 | 密钥、地址、证书、网络、回调和超时策略 |
| 新缓存或消息 | 资源创建、权限、容量、序列化和消费组 |
| 新日志与指标 | 脱敏、采集、看板和告警阈值 |

每个条件都要指向变更来源。无法说明“为什么需要检查”的通用条目容易流于形式；从 diff 推导出的影响则可以追溯到具体代码和验收场景。

## 发布需要一张兼容矩阵

在滚动发布中，新旧实例可能同时运行，数据库和配置也不会在同一时刻全部切换。因此，我会让 AI 检查多个版本组合是否能够短暂共存：

| 组合 | 需要回答的问题 |
| --- | --- |
| 旧应用 + 新数据库 | 扩展字段和约束是否向后兼容 |
| 新应用 + 旧数据库 | 迁移未完成时是否会立即失败 |
| 新旧应用并行 | 消息、缓存和接口协议是否一致 |
| 新应用 + 旧配置 | 缺少配置时能否快速失败而非错误运行 |
| 回滚应用 + 已迁移数据 | 回滚版本是否还能读取新结构和新状态 |

如果任何组合不成立，发布顺序、停机窗口或回滚方式就必须据此调整。第 14 篇的“扩展、迁移、收缩”同样适用于配置和协议：先引入兼容能力，再切换使用方，最后清理旧项。

## 环境差异要按六类检查

我会把运行条件分成六个层面：

```text
配置：Profile（环境配置组合）、环境变量、功能开关和配置中心
数据：数据库版本、回填、缓存预热和基础数据
运行时：JDK、JVM、解释器、依赖、时区和文件权限
基础设施：数据库、缓存、消息、对象存储和调度平台
网络与外部系统：DNS、证书、安全组、白名单和回调地址
可观测性：日志、追踪、指标、看板、告警和审计
```

AI 可以比较配置键、模板、部署脚本和基础设施声明，但敏感值不应进入分析结果。需要验证的是字段是否存在、来源是否正确、权限是否满足，而不是把真实密码、私钥和内部地址复制到报告里。

环境差异还包括默认值。开发环境因本地配置自动启用某项能力，生产缺少配置时却使用了另一种默认行为，这类问题仅比较“有没有配置文件”无法发现。

## 部署脚本本身就是可执行产品

部署脚本决定经过验证的代码如何进入运行环境，必须像应用代码一样具备输入、输出、错误处理和测试。

一份可靠脚本至少要明确：

- 构建产物和版本来自哪里；
- 使用哪个用户、工作目录和运行时；
- 配置与凭据通过什么受控方式注入；
- 依赖、磁盘、端口和权限怎样预检；
- 旧进程怎样停止，新进程怎样确认启动；
- 重复执行是否安全；
- 失败后退出码、日志和恢复动作是什么。

我会要求在隔离环境中演练：首次部署、重复部署、依赖缺失、端口占用、启动超时、健康检查失败和版本回退。脚本如果遇到错误仍返回成功，自动化平台就会把失败发布标记为完成。

## 测试通过也可能污染目标环境

发布前执行完整测试时，我遇到过测试向真实对象存储上传文件的情况。原因不是业务代码主动访问生产，而是测试配置没有替换本地环境中的真实存储客户端。

因此，发布验证不仅要问“测试是否通过”，还要问测试连接了什么：数据库、缓存、消息、对象存储、邮件、支付和第三方 API 是否使用隔离资源或 Fake（可控测试替身）。

必须访问真实外部系统的契约测试，应使用专用账号、显式开关、最小权限、限额和清理记录。测试成功但留下真实消息、文件或资金副作用，不能算安全验证。

## 健康检查只能证明进程活着

发布后的验证需要从低到高分层进行：

| 验证层次 | 需要证明的事情 |
| --- | --- |
| 进程层 | 正确版本已启动，资源和端口正常 |
| 依赖层 | 数据库、缓存、消息和外部服务可访问 |
| 契约层 | 网关、鉴权、接口和序列化符合预期 |
| 数据层 | 迁移、回填、缓存和关键查询结果正确 |
| 业务层 | 核心用户路径和状态迁移完成 |
| 观察层 | 日志、指标、追踪和告警能够发现异常 |

支付、库存、积分和批量任务还需要业务对账。接口返回 200、容器存活或首页可打开，都不能替代最终业务状态验证。

某项验证依赖真实资金、人工审批或尚未开放的第三方环境时，应明确标记为未验证和发布风险，而不是用较低层的检查代替。

## 回滚计划必须考虑不可逆变化

“发布失败就回滚代码”只对纯应用变更成立。数据库回填、新格式数据、消息协议和外部回调一旦生效，旧版本可能已经无法正确处理。

发布前需要区分：

- 可以直接回滚的应用与配置；
- 需要保持向后兼容的数据结构；
- 只能停止继续影响、不能自动逆转的数据变化；
- 已发送到外部系统、必须补偿或对账的副作用。

回滚条件也应可观察，例如错误率、核心交易失败、数据差异或资源指标达到什么阈值。没有触发条件和负责人，“出现问题及时回滚”就只是愿望。

## 发布证据包决定能否进入生产

我会让 AI 生成一份发布证据包，而不是只输出检查清单：

```text
【变更范围】需求、提交、构建产物和数据库迁移版本
【兼容矩阵】新旧应用、数据库、配置和协议组合
【环境差异】配置、数据、运行时、基础设施、网络和观察能力
【执行计划】顺序、负责人、授权点、停止条件和预计影响
【验证结果】实际命令、接口、数据、业务路径和监控证据
【回退方案】可逆项、不可逆项、恢复步骤和补偿方式
【未决风险】尚未验证的外部条件及接受人
```

AI 可以只读核对 diff、配置模板、迁移脚本、部署声明和监控规则，生成预检命令与验证步骤。生产发布、凭据使用、数据库写入和真实业务动作仍需要明确授权。

## 发布完成的标准，是系统进入可运行的新状态

```text
请基于【版本或变更】生成发布证据包，不执行生产变更：

1. 从需求、diff、配置和迁移反推全部运行条件；
2. 检查新旧应用、数据库、配置和协议的兼容组合；
3. 比对配置、数据、运行时、基础设施、网络与可观测性差异；
4. 验证部署脚本的首次、重复、失败和回退场景；
5. 说明测试访问的外部资源及其隔离、限额和清理方式；
6. 设计进程、依赖、契约、数据、业务和观察六层验证；
7. 标出授权点、停止条件、不可逆变化和未决风险。

不读取或输出真实凭据，不执行发布、数据库写入或真实外部业务动作。
```

第二辑从一条错误日志开始，先由故障、边界值和批量任务展开工程问题，再定义 ERP 业务边界与数据语义，随后处理支付、积分和多实例任务中的状态收敛，最后通过数据库迁移与环境检查完成发布。它们共同说明：真实交付不是代码完成，而是系统在数据、状态、并发和环境变化之后仍然满足业务承诺，并且有证据证明这一点。
