# 发布前的最后一公里：让 AI 检查配置、日志、JVM 和运行环境

> 系列导航：[完整目录](00-series-titles.md)

很多线上故障发生在代码已经合并之后：回调地址仍指向测试环境，生产缺少一个配置，数据库迁移没有执行，JVM 内存参数不适合容器，HTTPS 或安全组阻断了外部请求。

开发环境能启动，只能证明开发环境具备条件。发布前需要把代码变更与运行环境重新对照一遍。

## 从 diff 反推发布影响

我会让 AI 根据本次代码和配置 diff 生成影响清单：新增接口是否需要网关和权限；新字段是否需要迁移和回填；新任务是否需要开关；第三方调用是否需要密钥、网络和回调白名单；日志是否新增敏感字段。

清单中的每一项都要有来源、目标环境、验证方法和负责人。未知项单列待确认，不能用“应该已经配了”带过。

## 四类环境差异最容易漏

配置差异包括 Profile、环境变量、数据库、缓存、对象存储、消息和第三方地址。运行时差异包括 JDK、JVM 参数、内存、时区和文件权限。网络差异包括 DNS、HTTPS、证书、安全组和回调白名单。观察能力差异包括日志格式、追踪 ID、监控指标和告警阈值。

AI 可以比对配置模板和部署脚本，但不能读取或输出真实密码、私钥、内部地址和生产账号。

## 部署脚本本身也要当作产品测试

一次服务部署中，业务测试已经通过，真正阻塞启动的却是脚本：目标机器使用 `uv` 管理 Python 环境，脚本仍假设系统解释器和传统依赖安装方式；环境探测选错配置，缺失依赖直到进程启动后才暴露。单独修复某条命令后，下一次又在工作目录和进程检测上失败。

后来我不再把部署脚本当成一段运维说明，而是要求它具备可测试的输入和结果：明确解释器、工作目录、配置来源、依赖检查、端口占用、进程退出和日志位置。脚本要在临时目录和缺失依赖等场景中演练，重复执行也不能破坏已有环境。

```text
首次部署：环境不存在时能否完整初始化
重复部署：已有环境和进程时是否幂等
失败启动：能否返回非零状态并指出真实日志
环境差异：解释器、包管理器和配置文件是否明确
回退：新版本启动失败后旧版本是否仍可恢复
```

部署脚本决定了经过验证的代码以什么方式进入运行环境，它本身就是交付物。

## 验证过程也可能污染环境

同一轮检查中，完整测试意外向对象存储上传了测试文件。原因不是业务代码主动访问生产，而是测试配置没有覆盖本地环境中的真实存储客户端。测试全部通过，却留下了外部副作用。

因此发布前不仅要问“测试是否通过”，还要检查测试连接了哪些数据库、存储、消息和第三方服务。默认测试应使用隔离资源或 Fake 客户端；必须访问外部系统的契约测试，则需要独立账号、显式开关、限额和清理记录。

## 健康检查不是发布验证

健康检查只能证明进程活着。发布后还要分层验证：版本和配置生效，数据库结构和数据正确，核心接口权限正常，缓存和消息可用，任务没有重复启动，日志和监控能看到关键路径。支付、库存和积分类改动还需要受控的业务验证或对账。

某项必须依赖人工授权或真实外部系统时，应标记为未验证，而不是让 AI 用一次进程检查代替它。

## 我会让 AI 生成发布清单

```text
请基于本次改动生成只读发布检查清单：
1. 代码、数据库、配置、权限、外部依赖、网络和运行时影响；
2. 每项的来源、环境差异和验证方法；
3. 需要备份、审批、外部授权或人工确认的项目；
4. 发布后按进程、接口、数据、日志、监控验证的顺序；
5. 不读取或输出真实凭据，不执行发布或生产变更。
```

发布的最后一公里，本质是把“代码已完成”与“系统可运行、可观察、可回退”之间的差距显性化。AI 适合做系统核对，人负责审批和承担发布风险。
