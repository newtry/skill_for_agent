# 让 AI 听懂行业黑话：服装批发业务术语库的建设实践

> 系列导航：[完整目录](00-series-titles.md)

业务人员说“拿一手货”“看波段”“这个款走份”“查一下老客”，技术人员和通用模型可能都认识这些词，却未必知道它们在当前公司的具体含义。

一次用户问“这个款还能拿几手”，Agent 检索到了“一手货源”相关内容，把尺码配货数量理解成了供应链层级。回答语言流畅，商品和库存也都是真实数据，业务含义却完全错了。

这让我意识到，行业术语库不是一张同义词表，而是自然语言到业务对象、数据口径、权限范围和可执行动作之间的翻译层。术语没有完成语义落地，后面的路由、工具和权限都会建立在错误对象上。

## 核心判断：术语是业务契约，不是词汇装饰

术语库的完成标准不是“模型能说出这个词”，而是它能把用户表达稳定地映射到一个经过确认的业务对象、数据口径和允许动作。只要这个映射仍然含糊，Agent 就应该澄清或停止，而不是用最相近的词替用户做决定。

## 术语条目必须描述边界

一个可用于 Agent 的术语条目，至少要包含：

| 信息 | 作用 |
| --- | --- |
| 标准名称与定义 | 说明当前公司认可的业务含义 |
| 同义词与常见问法 | 覆盖真实用户表达 |
| 反例与近义混淆 | 防止误路由和错误检索 |
| 对应业务对象 | 连接商品、库存、客户或订单等系统事实 |
| 关键维度 | 租户、账套、门店、仓库、时间和状态 |
| 适用角色 | 业务员、采购、仓管或管理者等 |
| 允许动作 | 只读查询、建议、创建草稿或正式执行 |
| 来源与版本 | 说明定义依据和生效时间 |

例如“一手”可以定义为同款同色下各尺码各一件，需要出现尺码、颜色、库存、件数等上下文；“一手货源”则强调工厂、源头、供应商或价格。两个条目共享词面，却必须进入不同对象和路由。

## 从一句黑话到可执行对象

用户说“这个款还能拿几手”时，我会要求系统保留中间翻译结果，而不是直接生成回答：

| 翻译阶段 | 结果 | 证据或处理 |
| --- | --- | --- |
| 原始表达 | 这个款还能拿几手 | 保留原句和会话对象 |
| 候选术语 | 一手配码、一手货源 | 词库返回候选与版本 |
| 上下文消歧 | 当前会话包含颜色、尺码和缺码 | 选择“一手配码” |
| 业务对象 | 当前款号 + 当前颜色 + 尺码组 | 映射到商品主数据 |
| 数据口径 | 各尺码可售库存可组成的完整套数 | 库存模块正式定义 |
| 权限范围 | 当前租户、账套和授权仓库 | 服务端授权上下文 |
| 后续路径 | 固定库存查询 | 不允许直接生成调拨动作 |

假设 S、M、L、XL 的可售库存分别是 8、6、7、5，“还能拿几手”应返回 5 手，并说明限制尺码是 XL。若系统只对库存求和再除以四，会得到错误答案；若忽略账套和仓库，又可能把不同经营范围的库存拼成一手。

这说明术语映射不仅决定一个标签，还会决定计算公式、结果粒度和查询范围。术语一旦翻译错，后面的 SQL 即使完全正确，也只是在精确回答另一个问题。

## 术语消歧要依赖上下文，不要只堆同义词

同一个词的含义通常由上下文决定：

```text
用户表达 -> 候选术语 -> 上下文消歧 -> 业务对象
-> 数据口径 -> 可用工具与权限
```

“老客”可能由交易次数、最近购买时间、累计金额或人工标签定义；“库存”可能是物理、可售、预占后或指定仓库库存。没有上下文时，Agent 应澄清或返回候选解释，不能选择概率最高的定义直接行动。

消歧条件要进入评测：包含“尺码、缺码、还能拿几手”时进入配货语义，包含“工厂直供、源头”时进入货源语义。正例只能证明会识别，反例才能证明不会混淆。

复合表达还需要拆解。例如“看一下这个款还能拿几手，够的话调到人民路店”同时包含库存查询和调拨意图。术语层只负责确定“几手”和业务对象，不能因为句子里出现“调”就直接授权写入；后续路由必须把查询和动作拆成两个阶段。

## 术语必须连接到系统事实

如果术语只保存自然语言解释，Agent 仍然不知道如何安全执行。每个重要概念都要连接到数据对象、唯一范围、查询入口、结果粒度和权限边界。

例如“可售库存”需要说明门店、账套、仓库、预占和冻结规则；“销售额”需要说明时间区间、订单状态、退款和含税口径；“老客推荐”需要说明客户标签来源和隐私范围。

这个连接会影响路由：有些术语直接进入固定查询，有些需要补齐账套和时间，有些只能生成建议，不能直接产生写操作。

## 术语库需要版本和责任人

业务语言会变化。新商品线、新渠道和新规则可能改变同一个词的含义，旧定义不能悄悄覆盖。

我会为术语保留来源、确认人、生效时间、适用组织和变更记录；定义不一致时保留多个候选，并让路由转人工确认。历史会话可以产生候选词，但不能自动成为正式定义。

术语变更也要评估消费者。例如“老客”从“历史成交过”改为“最近一年成交两次以上”，会影响客户查询、推荐策略、业务卡片和历史评测。正式发布时应绑定术语版本，不能让同一批请求在不同实例上使用不同口径。

## 怎样验证术语真的可用

我会为每个高频术语准备四类样本：明确正例、近义反例、上下文不足和复合请求。验证结果不只看模型解释，还要检查映射到的业务对象、口径、权限和路由。

```text
正例：这个款 S 到 XL 还能配几手
反例：这家供应商是不是一手货源
缺参：这个还能拿几手
复合：够三手就帮我生成调拨草稿
```

前两项验证消歧，第三项必须触发澄清，第四项必须先查询再进入需要确认的业务动作。模型偶然答对一句话，不代表术语契约已经成立。

AI 可以从历史会话中聚类表达、生成候选反例并发现未覆盖词形；业务人员负责确认定义和适用范围，工程师负责把定义连接到系统对象、路由和测试。词库只有经过这三方闭环，才有资格进入正式版本。

## 从真实错误中维护术语库

术语库最有效的输入包括：历史会话、客服问法、报表名称、搜索失败、错误路由和人工纠正。每次错误都要判断是缺少术语、消歧条件不足、数据口径不清还是工具参数错误，不能只添加一个同义词就结束。

```text
请整理【业务领域】术语，不直接写入正式词库：

1. 输出标准定义、同义词、常见问法和反例；
2. 说明对应业务对象、唯一范围、数据粒度和关键维度；
3. 标出适用角色、允许动作、权限和敏感信息；
4. 给出消歧上下文、正例、反例和需要澄清的问题；
5. 记录来源、版本、确认人和待确认项。
```

术语库的目标不是让 Agent 说得更像业内人士，而是让它在正确的业务口径下选择对象、查询和动作。下一篇会在语义已经明确的前提下，讨论一个请求应该进入哪条处理路径。
