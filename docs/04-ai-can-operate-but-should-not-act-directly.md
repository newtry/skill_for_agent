# AI 可以操作电脑，但不代表应该直接操作

> 系列导航：[完整目录](00-series-titles.md)

有一次开发机磁盘空间不足，我给 AI 的指令是：“帮我清理一下。”

这句话看起来只是一个运维小任务，但“清理”可能意味着删除构建产物、清空依赖缓存、移除 Docker 数据、截断日志，甚至处理用户目录里的文件。它们都能释放空间，影响和可恢复性却完全不同。

如果 AI 只能回答问题，最坏的结果通常是一条错误建议；当它能够执行终端命令，错误建议就可能立刻变成真实删除。能力从“生成答案”升级为“改变系统”以后，协作规则也必须随之升级。

我后来把这条规则概括为一句话：AI 的可执行能力可以很强，但默认权限必须受限。能力决定它技术上能做什么，授权决定它在当前任务中被允许做什么，两者不能混为一谈。

## 能力与授权是两个不同维度

AI 能够调用终端、浏览器、数据库和外部系统，只说明工具已经连通，不代表每次任务都获得了完整使用权。

例如：

- 能读取 Git 状态，不等于可以丢弃未提交修改；
- 能生成 DDL（数据定义语言）脚本，不等于可以修改数据库结构；
- 能打开管理后台，不等于可以代表用户点击发布；
- 能识别退款接口，不等于可以操作真实资金；
- 能读取配置结构，不等于可以在回答中输出密码和令牌。

在传统软件中，权限通常授予一个用户或服务；在 AI 协作中，还需要进一步限制本次任务的动作、对象、环境和有效阶段。一次“允许修改代码”的授权，不能自动扩展成提交、推送和发布；一次“允许查询生产数据”的授权，也不能被解释为允许更新数据。

因此，任务授权不是一句笼统的“你可以处理”，而是一项作用于具体动作的临时能力。

## 风险不能只按命令名称判断

同一个动作在不同环境中的风险可能完全不同。删除临时测试目录与删除用户目录都使用文件删除命令；更新本地模拟数据与更新生产账务也可能使用相同的 SQL 语法。

我现在从五个维度判断一个动作需要什么级别的控制：

| 风险维度 | 需要回答的问题 | 风险升高的信号 |
| --- | --- | --- |
| 可恢复性 | 失败后能否完整恢复，恢复成本多大 | 无备份、覆盖写、真实资金或外部通知 |
| 影响范围 | 会改变一个文件、一套服务还是共享系统 | 目标含糊、递归操作、批量更新 |
| 环境属性 | 本地、测试、共享开发还是生产环境 | 多人共享、线上流量、真实业务数据 |
| 外部效应 | 是否会影响仓库、用户或第三方系统 | 推送、发布、发消息、支付和退款 |
| 数据敏感性 | 是否涉及凭证、权限、隐私或账务数据 | 密钥、跨租户数据、订单和资金流水 |

风险评估的对象不是“这条命令看起来危险吗”，而是“它会在什么环境中，对哪些对象产生什么后果”。如果目标和影响范围尚未确定，就不能进入执行阶段。

## 我把动作划分为四个执行等级

风险维度用于判断，执行等级用于决定默认行为。我通常把 AI 的动作分成四级：

| 等级 | 典型动作 | 默认处理方式 |
| --- | --- | --- |
| A：只读调查 | 搜索代码、读取日志、查看 Git 状态、统计磁盘 | 可在任务范围内直接执行并报告证据 |
| B：局部可逆修改 | 编辑工作区文件、生成测试、启动本地服务 | 需要任务级授权，执行后展示 diff 和验证结果 |
| C：共享状态写入 | 推送分支、修改共享数据库、更新任务状态 | 执行前确认精确对象、影响和回退方案 |
| D：不可逆或外部业务动作 | 删除重要数据、发布生产、发送消息、支付退款 | 默认禁止自动执行，必须逐次明确确认 |

这个分级不是静态白名单。只读动作也可能泄露敏感配置，局部修改也可能覆盖用户未提交的代码。因此，任何等级都必须受到任务范围约束；等级越高，确认越具体，自动化程度越低。

核心原则不是“AI 只能读，不能写”，而是让默认权限与风险相匹配：低风险动作自动化，高风险动作设置可审计的确认点。

## 从“直接执行”改成受控执行协议

磁盘清理事件之后，我不再让 AI 根据目标直接选择命令，而是把状态改变拆成六个阶段。

### 第一步：只读确认现场

先解析精确对象和当前状态。磁盘清理要统计目录大小、用途和所有者；Git 同步要检查分支、工作区、提交和远端差异；数据库变更要确认目标环境、结构版本和受影响数据。

如果只读阶段仍不能确定操作对象，后续步骤必须暂停。

### 第二步：提出候选动作

AI 应列出能够达到目标的不同方案，而不是直接选择影响最大的一个。例如磁盘清理可以优先删除可重新生成的构建产物，再考虑依赖缓存，最后才评估共享 Docker 数据。

候选动作要说明预计收益、影响范围和必要前提，方便人比较，而不是只展示一条命令。

### 第三步：说明失败与恢复路径

每个状态改变都要回答：执行失败会停在哪里，是否存在部分完成，怎样验证恢复，备份是否真实可用。

“可以回滚”不是充分说明。需要明确回滚对象、命令、数据来源和恢复验证；无法可靠恢复的动作，应直接提高风险等级。

### 第四步：获得精确授权

有效授权至少包含：操作对象、动作类型、目标环境、影响范围和附加限制。

```text
允许删除 /project/module-a/target 下的构建产物；
不处理依赖缓存、Docker 数据和其他目录；
执行后重新统计磁盘空间并报告删除结果。
```

这种授权只对当前对象和动作有效，不能扩展到“顺便清理”其他目录。环境、对象或命令发生实质变化时，需要重新确认。

### 第五步：执行最小必要动作

获准之后，AI 仍应选择能够满足目标的最小改变，避免扩大范围和顺带重构。支持预览、试运行、事务或分批处理时，应优先使用这些机制降低一次性影响。

执行过程中如果实际状态与确认前不同，例如目标文件新增、数据库影响行数超出预估，应停止并重新评估，不能沿用过期授权继续推进。

### 第六步：验证并回写结果

执行完成不等于目标达成。需要重新检查磁盘空间、Git 状态、数据库数据或服务健康度，并报告实际执行的动作、改变的对象、验证结果和残余风险。

六个阶段形成一条完整控制链：

```text
确认现场 -> 提出方案 -> 评估影响与恢复 -> 获得授权
-> 最小执行 -> 验证并回写
```

前四步建立决策依据，后两步产生并证明真实改变。任何高风险动作都不应绕过中间的授权门。

## 权限控制还要落实到工具层

只在提示词里写“谨慎操作”并不可靠。条件允许时，执行边界应该由工具和环境共同保证：生产账号默认只读，数据库写权限按需临时授予，文件操作限制在明确工作区，外部发送和发布接口设置人工确认，日志输出自动脱敏。

提示词负责表达任务意图，工具权限负责限制最坏后果，审计记录负责追踪实际发生了什么。三者缺一不可：仅靠模型自律无法替代最小权限，仅靠权限系统也无法解释一项动作为什么被执行。

## 我使用的操作任务模板

```text
请先对【目标】执行只读调查，不改变代码、数据、环境或外部系统。

1. 确认精确操作对象、当前状态和目标环境；
2. 按只读、局部可逆、共享写入、不可逆或外部动作进行分级；
3. 给出候选动作、预计影响、失败方式、备份和恢复路径；
4. 标出需要人工确认的步骤，未获授权前停在方案阶段；
5. 获准后只执行确认范围内的最小动作；
6. 执行后报告实际命令、状态变化、验证结果和残余风险。

删除、覆盖、数据库写入、提交推送、发布和外部发送不得由模糊指令推定授权。
```

模板不是安全机制本身，它只是把受控执行协议带入当前任务。真正的安全来自明确边界、最小权限、逐步确认和结果审计共同作用。

## 成熟的自动化，首先表现为知道何时停下

AI 辅助开发追求的不是“所有事情都自动完成”，而是在风险可控的前提下减少不必要的人力操作。AI 可以承担大规模搜索、状态检查、方案比较和验证准备；工程师负责确认业务口径、接受高风险后果并授予改变状态的权限。

前三篇分别解决了项目认知、任务定义和上下文连续性。第 4 篇再加上一条执行原则：信息充分只意味着 AI 有条件做出判断，并不意味着它已经获得行动权。

建立这条边界以后，最适合扩大 AI 使用范围的起点，恰恰是输入明确、结果容易核对、默认可以只读完成的任务。Excel、SQL 和日志就是三类典型场景。
