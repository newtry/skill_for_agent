# 跨会话继续开发：如何解决 AI 换会话就失忆的问题

> 系列导航：[完整目录](00-series-titles.md)

长任务不可能永远停留在一个会话里。上下文达到限制、模型切换、工具切换或工作日结束后，下一次都需要继续。真正的问题不是 AI 没有记忆，而是我们没有把“当前做到哪里”保存成可恢复状态。

## 核心判断：连续性来自检查点，不来自聊天记忆

会话内容只能说明上一次讨论过什么，不能证明代码现在是什么状态。可恢复检查点必须同时绑定任务版本、代码基线、工作区差异和验证结果。新会话先重建事实，再决定下一步，而不是把旧摘要当成当前指令继续执行。

## 一句“继续”曾经差点让任务重新开始

一次跨后端、Java 和前端的协议迁移持续了多个会话。上一轮已经完成几组独立提交，完整回归也有两千余条用例通过，但工作区还保留着用户自己的部署脚本和文档改动。新会话只收到一句“继续”。

如果它只读需求文档，很可能重新规划已经完成的工作；如果它把未提交文件当成残留清理，又会破坏别人的现场。恢复过程最终依赖三类证据：提交记录说明什么已经完成，工作区 diff 说明什么仍在进行，最近测试结果说明哪个代码状态被验证过。三者对齐后，下一步才被缩小为迁移剩余调用方，而不是“继续整个需求”。

恢复时使用的证据各自回答不同问题：

| 证据 | 回答什么 | 不能单独证明什么 |
| --- | --- | --- |
| 任务与设计 | 原目标、范围和验收 | 当前实现进度 |
| 提交记录 | 已稳定保存的改动 | 未提交现场和运行结果 |
| 工作区 diff | 正在进行或用户已有的修改 | 改动是否正确 |
| 测试记录 | 某个代码版本验证过什么 | 当前代码仍与该版本一致 |
| 交接记录 | 上一会话的判断和下一步 | 判断尚未过时 |

任何一项缺失都不一定阻塞恢复，但必须降低结论置信度。尤其不能把“上次测试通过”直接套到已经继续修改过的工作区上。

## 交接记录不需要复述全部聊天

我会保存四类信息：已确认的事实和证据，已经完成的改动和命令，未完成的问题与阻塞，下一步最小动作。不要复制整个对话，也不要只写一句“继续开发”。

```text
任务目标：
当前版本/分支：
已确认：
已修改：
已验证：
未完成/阻塞：
下一步：
```

这份记录要与项目规则和代码 diff 配合使用。记录是导航，不是事实来源；新会话仍需检查工作区和实际文件。

我还会为交接增加来源和新鲜度：记录由哪个运行生成、对应哪个任务版本和提交、最后验证时间是什么。开放问题要写明谁能确认，下一步要小到可以直接核验，例如“检查剩余三个 V1 调用方”，而不是“继续完成迁移”。

## 检查点应在稳定边界产生

不是每条消息后都保存摘要。更有价值的检查点出现在分析结论确认、独立实现切片完成、验证结束、外部阻塞和会话主动交接时。每个检查点都说明当前阶段是否稳定，哪些改动可以复用，哪些只是未验证现场。

```text
分析检查点：调用链、边界、方案、待确认项
实现检查点：基线、diff、已完成切片、剩余改动
验证检查点：命令、结果、代码版本、跳过项
阻塞检查点：失败证据、现场、副作用、接管条件
```

## 重新开始时先恢复，不要直接执行

新的 AI 会话第一步应读取交接记录、项目规则、`git status`、相关 diff 和最近测试结果，再判断历史结论是否仍然成立。如果记录和代码不一致，要以当前工作区为准并标记冲突。

恢复流程可以固定为：识别任务和运行标识，读取权威规则与交接，检查提交和工作区，对齐测试结果，重新确认风险与权限，最后只提出一个最小下一步。发现未知改动时保持只读，不能为了匹配交接记录而回退现场。

如果目标或验收已经变化，旧检查点只能作为历史参考，新会话要显式标记哪些结论失效。继续工作不是机械接上最后一句话，而是在新时间点重新建立共同上下文。

一份恢复报告应明确区分：仍然成立的事实、已经完成且有证据的工作、当前未提交现场、已经失效的历史结论、尚未确认的问题和推荐下一步。例如：

```text
仍然成立：V2 契约及九个核心验收场景
已完成：后端生产方切换，提交与测试证据已确认
当前现场：前端类型存在用户未提交改动，保持不动
已失效：旧交接中的“Java 调用方尚未迁移”已被后续提交解决
未完成：三个 V1 消费方和旧流量观测
下一步：只读搜索 V1 消费方，更新迁移追踪表
```

这样的报告可以让用户在恢复阶段先纠正事实，再授权执行，减少一句“继续”带来的范围误判。

## 将交接记录当作阶段产物

分析结束记录一次，实施结束记录一次，验证结束再记录一次。这样即使任务被中断，下一次也可以从最近稳定点继续，而不是从模糊的聊天记忆重新开始。

跨会话协作的核心不是让 AI 永远记住过去，而是让过去变成结构化、可核验、可更新的项目事实。

## 怎样验证恢复机制

我会模拟无交接摘要、交接与 diff 冲突、测试结果对应旧提交、任务版本变化和工作区混入用户改动。恢复成功的标准不是新会话能复述历史，而是它不会重复已完成工作、不会覆盖未知修改，并能指出当前最小未完成项及其证据。

AI 可以生成检查点和执行恢复扫描；代码仓库、任务板和测试产物提供事实；工程师负责处理冲突和确认开放业务问题。跨会话记忆完成的证据，是任意新会话能够从相同检查点得出相近的当前状态，而不是依赖某个模型记得过去。

```text
请只读恢复【任务】现场：

1. 读取任务、权威规则、最近检查点和交接记录；
2. 核对提交、分支、git status、diff 与测试产物的对应版本；
3. 区分仍成立、已完成、进行中、已失效、待确认和阻塞；
4. 保护未知改动，不执行重置、清理、发布或数据写入；
5. 给出一个有证据的最小下一步，等待确认后再继续。
```

跨会话检查点先解决同一个任务沿时间继续的问题。下一篇再把执行者从一个扩展为多个工具，讨论不同 AI 接力或并行时怎样划分写入责任、隔离现场并交付证据。
